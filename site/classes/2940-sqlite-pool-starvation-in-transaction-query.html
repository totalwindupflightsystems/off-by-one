Fix: sqlite pool starvation when an open transaction queries through the pool

Problem class: sqlite-pool-starvation-in-transaction-query Symptom: 4 concurrent idempotent POSTs hang forever. CI only surfaces panic: test timed out after 10m0s; the DB layer and every HTTP/context layer stay silent. Fix principle: Any code path that already holds a transaction must read through that transaction, never through the pool. One in-flight request must not need two connections while holding a write lock.

1. Root cause

handleIdempotentSessionMessage does:

tx, err := s.db.BeginTx(ctx)      // pins ONE pooled connection for the whole request
...
if memory.SkipDuplicateUserMessage(ctx, s.db, id, req.Content) { // borrows a SECOND pool conn
...
tx.Commit()

memory.SkipDuplicateUserMessage calls s.db.Query → database/sql.(*DB).QueryContext → the connection pool. With the SQLite default cap (the driver falls back to MaxOpenConns = 4 when Config.MaxOpenConns <= 0) the sequence under 4 concurrent retries is:

  1. All 4 requests call BeginTx and pin all 4 connections.
  2. Each then calls the dedupe probe through s.db, which needs a 5th connection.
  3. database/sql queues all four waiters. No goroutine ever reaches Commit, so no connection is ever released.
  4. On file:...?mode=memory&cache=shared (no WAL) the readers additionally queue behind the writer's table lock.
  5. Permanent deadlock. database/sql's Tx.awaitDone goroutines stay pending; nothing times out because every layer is merely waiting.

Goroutine-dump classes (the diagnosis key)

Three distinct classes on the same test mean bounded-pool exhaustion, not lock corruption or a driver bug:

Class Frame
sync.Mutex.Lock modernc.org/sqlite.(*conn).retry ← (*conn).step ← (*Tx).QueryContext
database/sql.(*DB).conn select database/sql.(*DB).QueryContext waiting for a pool connection
chan receive database/sql.(*Tx).awaitDone

Don't read the top frame — read the class of block.

Why MaxOpenConns is not the fix

Raising it (4 → 8) made the flake disappear in a probe (80/80 in ~0.37s), which proves starvation, but it only moves the threshold. The structural defect — one request holding a connection + write lock while asking for a second connection — still costs latency and throughput and reappears under enough concurrency. Revert the probe.

3. The fix

3.1 internal/memory/dedupe.go — one implementation, satisfied by pool and Tx

Introduce a minimal read interface that both db.DB and db.Tx satisfy, add Tx-capable variants, and make the existing pool-shaped entry points delegate to the same body so the two paths cannot drift.

// querier is the read surface the dedupe probe needs. Both db.DB (the pool)
// and db.Tx (an open transaction) satisfy it.
type querier interface {
    Query(ctx context.Context, query string, args ...any) ([]db.Row, error)
}

// Pool-shaped entry point (unchanged signature).
func IsDuplicateUserMessage(ctx context.Context, database db.DB, sessionID, content string, now time.Time) (bool, error) {
    return isDuplicateUserMessage(ctx, database, sessionID, content, now)
}

// Tx-capable variant. Use inside an open transaction so the probe never
// borrows a second pooled connection.
func IsDuplicateUserMessageTx(ctx context.Context, tx db.Tx, sessionID, content string, now time.Time) (bool, error) {
    return isDuplicateUserMessage(ctx, tx, sessionID, content, now)
}

// Single implementation both exported probes delegate to.
func isDuplicateUserMessage(ctx context.Context, q querier, sessionID, content string, now time.Time) (bool, error) {
    rows, err := q.Query(ctx,
        `SELECT created_at FROM memory_events
         WHERE type = 'user_message' AND session_id = $1 AND content = $2
         ORDER BY id DESC LIMIT 20`, sessionID, content)
    if err != nil {
        return false, fmt.Errorf("dedupe probe: %w", err)
    }
    windowStart := now.Add(-UserMessageDuplicateWindow)
    for _, row := range rows {
        stored, ok := row["created_at"].(string)
        if !ok {
            continue
        }
        ts, err := time.Parse(time.RFC3339, stored)
        if err != nil {
            continue
        }
        if !ts.Before(windowStart) && !ts.After(now) {
            return true, nil
        }
    }
    return false, nil
}

func SkipDuplicateUserMessage(ctx context.Context, database db.DB, sessionID, content string) bool {
    if database == nil {
        return false
    }
    return skipDuplicateUserMessage(ctx, database, sessionID, content)
}

func SkipDuplicateUserMessageTx(ctx context.Context, tx db.Tx, sessionID, content string) bool {
    if tx == nil {
        return false
    }
    return skipDuplicateUserMessage(ctx, tx, sessionID, content)
}

// Shared skip-or-deliver decision: same query, same window, same
// parse-failure-is-not-a-duplicate rule, same warn-and-deliver policy.
func skipDuplicateUserMessage(ctx context.Context, q querier, sessionID, content string) bool {
    if q == nil || strings.TrimSpace(sessionID) == "" {
        return false
    }
    duplicate, err := isDuplicateUserMessage(ctx, q, sessionID, content, time.Now().UTC())
    if err != nil {
        slog.Warn("memory: user_message dedupe probe failed; delivering anyway",
            "session_id", sessionID, "error", err)
        return false
    }
    if duplicate {
        slog.Info("memory: dropped duplicate user_message within dedupe window",
            "session_id", sessionID, "window", UserMessageDuplicateWindow.String())
    }
    return duplicate
}

The pool-shaped functions are kept (other call sites use them) and now delegate to the same isDuplicateUserMessage / skipDuplicateUserMessage body, so the pool and Tx paths are byte-identical in behavior.

3.2 internal/api/sessions.go — probe on the transaction

// Before (deadlock):
if memory.SkipDuplicateUserMessage(ctx, s.db, id, req.Content) {

// After:
if memory.SkipDuplicateUserMessageTx(ctx, tx, id, req.Content) {

tx is the transaction opened a few lines above; the probe now reads its own connection and the request needs only the one it already holds.

3.4 internal/memory/dedupe_test.go — pin the Tx probe

TestIsDuplicateUserMessageTx_ReadsThroughTheTransaction opens a tx against a cache=shared in-memory DB and asserts the Tx probe sees (a) an already-committed in-window row, (b) a row written earlier in the same tx, (c) negative for different content, (d) SkipDuplicateUserMessageTx uses the same policy, (e) nil tx / blank session id → not duplicate.

3.5 Convention

Add the rule to the package/handler docs:

No pooled-connection call (s.db.*) may appear between BeginTx and Commit/Rollback. Pass the Tx down to any helper.

5. Checklist to prevent recurrence

  1. Any helper invoked between BeginTx and Commit/Rollback must accept a querier interface (Query(ctx, q, args...) ([]Row, error) is enough) or a db.Tx.
  2. Keep the pool-shaped exported functions delegating to one shared implementation — never fork the SQL.
  3. Verify with the boundary-aware grep above. Do not silence the symptom by raising MaxOpenConns.
  4. Bound every concurrent integration test with an explicit watchdog naming the deadlock class, and fail fast instead of consuming the CI job timeout.
  5. Keep assertions intact — a retry-until-green loop hides the exact bug this test exists to catch.
