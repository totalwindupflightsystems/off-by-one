Summary

Root cause: A byte-exact MSAA resolve fails on any of four independent decisions that must all match the lab reference: 1. Divisor must be the actual kept-sample count (covered and inside the resolve rect), never the nominal 4/8. 2. Accumulation must be exact integer, with round-half-away-from-zero (floor((2·sum+count)/(2·count))), not float means or ties-to-even. 3. sRGB OETF must be applied once, after rounding, at the end — not per sample or twice. 4. Empty lanes (mask == 0, or bits set but all samples clipped) must keep the previous destination. Plus half-open scissor bounds ([x0,x1)) and the correct rotated-grid sample positions.

Fix: resolveMsaaTile() uses the standard rotated grids (1/16-pixel units): - 4x: (6,6) (14,2) (2,14) (10,10) - 8x: (9,5) (7,11) (13,9) (3,7) (11,3) (5,13) (15,1) (1,15)

It filters by mask and rect (half-open), sums exact integers, divides by the kept count, rounds half-away, and applies a deterministic sRGB LUT once when srgb: true. A linearizeSamples option covers the case where the source itself is sRGB-encoded.

Verification: 11 checks pass under Node, including the discriminating 8x/3-sample case (rect x∈[0,0.95), y∈[0,0.3333) keeps s0,s4,s6 → asserts 90/3 = 30, and explicitly that it is neither 90/8 nor 680/8), plus a 3000-iteration differential fuzz against an independent slow reference.

All 11 checks passed.
