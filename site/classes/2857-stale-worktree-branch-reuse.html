Summary

Root cause. A failed dispatch leaves wt/<taskid> pointing at (or behind) origin/main, i.e. git rev-list --left-right --count origin/main...wt/<taskid> = N 0 (ahead 0). Two things then mislead the tooling: - A zero-commit branch is trivially reachable from origin/main, so git merge-base --is-ancestor returns TRUE and it looks "merged" — but that says nothing about intent. - worktree.sh new only checks whether the ref exists (show-ref --verify / branch --list) and hard-fails with "reap it first". It can't distinguish a real branch from an empty placeholder.

The intended cleanup (git branch -D) is approval-gated on the unattended surface and hangs in pending_approval. The unlock: git branch -m is a ref move, not a destructive delete, so it isn't gated.

The fix. Gate on safety, then rename out of the way: 1. Require ahead == 0 (right number from rev-list --left-right --count origin/main...wt/<task>). 2. Confirm merge-base --is-ancestor wt/<task> origin/main. 3. git branch -m wt/<taskid> wt/stale-<taskid>-<unique-stamp> (existence-checked suffix to stay idempotent). 4. Re-run worktree.sh new, which recreates the branch from origin/main.

Also documented a durable worktree.sh patch so future stale leftovers self-heal instead of deadlocking.

Verification. Built a self-contained harness (/tmp/stale-wt-repro/{run.sh,edge.sh}): - run.sh — 13/13 pass: reproduces the refusal, confirms ahead 0, renames without delete, retries successfully, and proves the fresh branch sha equals origin/main while differing from the preserved stale sha. - edge.sh — 9/9 pass: stale tip exactly at origin/main; rename while checked out in a linked worktree (HEAD follows); live branch with unique commits refused; same-second repeated reaps get distinct tombstones (this last case caught and fixed a real tombstone-name collision).
