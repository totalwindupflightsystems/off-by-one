Answer

Done. I diagnosed the bug, implemented and verified the fix, and wrote the solution.

Root cause

sweep-status classified "fixable" rows from the status column only, but --apply rewrites each row through NormalizeTask, which validates all vocab columns (status, guard_result, ci_result). A clean status alias (e.g. todo) sitting next to a legacy off-vocab ci_result:"pending" was advertised as fixable, then NormalizeTask refused it and sweep.go:119 returned a fatal mid-file error — after earlier rows were already written. The dry-run never inspected guard_result/ci_result, so the abort was unpredictable.

Fix (in /workspace/sweep-fix.patch)

Two coordinated changes in internal/board/sweep.go:

  1. Classify all three columns up front. Off-vocab guard_result/ci_result values become Explicit (human-decision) rows and an alias status on the same row is never advertised as fixable.
  2. Apply skips-and-reports instead of aborting. A per-row NormalizeTask failure is recorded and the sweep continues; OffAfter is measured from the file and now counts blocked alias/result rows too, so nothing looks repaired that isn't.

Verification

Built the original (9b276f7) and fixed binaries against the same board:

  • Before: dry-run showed 3 fixable, 0 explicit; --apply exited 1 with the exact reported abort, leaving CLEAN-001 written and both DEPS-* rows dirty (partial write).
  • After: dry-run names the blocked rows (... blocked by ci_result "pending"); --apply exits 0, fixes the decidable row, keeps blocked rows byte-identical, and prints before: 3 ... after: 2.
  • After explicit boardctl update <id> --ci GREEN/RED, a re-run reaches before: 2 ... after: 0, and an independent jq scan reports 0 rows outside the vocabularies.
  • New regression tests in internal/board/sweep_result_block_test.go; go test ./... and go vet are green.
