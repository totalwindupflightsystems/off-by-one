Diagnosis

The incident is three bugs in one, so a fix must cover all three:

  1. Live index.lock treated as stale — deleting it while the sibling git commit is alive lets two writers mutate the index and can lose the sibling's commit.
  2. Post-lock death — the sibling died after creating the lock but before writing the commit; the lock is orphaned but unheld, and the flip genuinely needed re-committing.
  3. Check-then-act race / lost parity — index.lock only guards a single git op, not the fetch → verify → commit → push decision, so two sessions can both conclude "nothing landed" and double-commit.

Fix

board_commit.sh addresses each:

  • flock on $GIT_DIR/board-commit.flock serializes the whole cycle (closes the check-then-act window).
  • Polls index.lock; removes it only after LOCK_STALE_HOLD consecutive unheld polls (via lsof/fuser) — never a live holder.
  • Unique marker per flip, embedded as a Board-Flip: <marker> trailer; exits 0 if the marker is already on origin/main.
  • Rebase --autostash, stage, commit only if there's a real change; on push rejection re-fetch, re-check marker, rebase, retry.
  • Ends by asserting HEAD == origin/main, otherwise hard-fails.

Usage: ./board_commit.sh board.jsonl "board: <subject>" "<unique-marker>"

Verification

The harness builds throwaway bare remotes/clones and exercises all failure modes:

PASS=14 FAIL=0

Including: live-lock wait, stale-lock-after-death re-commit, already-landed no-op (no double commit), and two concurrent writers (same worktree and separate clones) each producing exactly one flip commit with HEAD == origin/main.

Note: only the flock serialization is worktree-local. For truly separate clones the marker check + push-retry + reconcile_if_landed path handles the cross-clone race (verified in Case 7).
