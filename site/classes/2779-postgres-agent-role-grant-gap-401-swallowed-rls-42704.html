Answer

Solution written to /workspace/solution.md and verified against a live PostgreSQL cluster.

What I found

The problem is three independent defects layered on top of each other:

  1. Grant gap — agent_role has no SELECT on api_keys (auth) or external_events (event sink). Postgres returns 42501.
  2. Swallowed error — authMiddleware (server.go:373) maps every lookup error, including the permission failure, to 401, hiding the root cause.
  3. 42704 from RLS — policies use current_setting('consensus.session_id') (strict form). The GUC is written with set_config(..., is_local=true) and the later task-claim/approval query runs as a separate non-tx pooled statement (possibly a different connection), so the transaction-local value is gone and current_setting raises instead of denying.

The fix (all in the doc)

  • Migration: GRANT SELECT ON api_keys, DML on external_events, USAGE on schema + enum type, USAGE, SELECT on sequences, ALTER DEFAULT PRIVILEGES to stop drift, and rewrite policies to current_setting('consensus.session_id', true) so a missing GUC fails closed (NULL comparison) instead of 42704.
  • Go: distinguish pgx.ErrNoRows (401) from operational errors (500 + log), and run set_config(..., true) inside the same pgx.Tx as every RLS query via a withSession helper.

Verification

I reproduced all three exact errors (permission denied for table api_keys, permission denied for table external_events, unrecognized configuration parameter "consensus.session_id") on a disposable cluster, then re-ran after applying the fix:

  • api_keys select works
  • external_events insert works (confirms sequence grant was needed)
  • tasks with unset GUC → 0 rows, no 42704; unset-GUC insert is rejected by WITH CHECK
  • tx-scoped GUC → correct row visibility

The doc includes copy-pasteable SQL, Go snippets, and a regression-test checklist. Note: the target is PG16, but this environment only had PG18 installed — the semantics used are unchanged across those versions and the doc says so explicitly.
