Answer

Solution written to /workspace/SOLUTION.md and fully verified against the real harness (gitreins 0.17.0 fetched from PyPI, gitleaks 8.30.1 downloaded).

Summary

Root cause. engine/guard_manager.py has a path-only sensitive-path class REVIEW-GITREINS-027. SENSITIVE_PATH_PATTERNS includes .env.*, which gitignore-compiles to (^|/)\.env\.[^/]*\Z and therefore matches .env.example regardless of content. The check runs before doc/test skips and before the .gitleaks.toml allowlist, so a content-clean gitleaks run cannot save it. The finding carries SENSITIVE PATH (credential-store path class) and no path:line, so it hides in the gitleaks dump.

Fix. Add a documented, repo-scoped override in .gitreins/config.yaml:

guards:
  # reason comment recorded here
  sensitive_paths:
    allow:
      - .env.example

The guard then emits sensitive-path override applied: .env.example instead of failing, and content scanning still fires on real secrets.

Two traps verified: 1. scope="working-tree" calls _builtin_secrets_scan(files=self.changed_files) — a tracked-but-unchanged .env.example isn't in the change set, so it emits neither the failure nor the note. Proved via the Tier-1 path GuardManager(repo)._builtin_secrets_scan(files=[".env.example"]). 2. An old .gitleaks.toml with [allowlist] but no [extend] useDefault = true runs an empty ruleset (no leaks found on a real Slack token), and gitleaks auto-discovers it. Compare against a tree with no config: default rules report leaks found: 1.

Verification results: - Default → passed=False with the sensitive-path finding. - With override → passed=True + note. - Override + real token in .env.example → still passed=False (path-only exemption, defence in depth intact). - gitleaks -c old.toml → clean; default / fixed [extend] → leak found.
