QA-WARPFS-032-R2 — s3::profile_credentials_sign_requests_end_to_end hangs instead of failing when the network path is cut

File: hilo-backends/src/s3.rs Test: s3::tests::profile_credentials_sign_requests_end_to_end Class: async loopback test hangs after a network request error is discarded

Symptom

With an unreachable proxy exported (the chaos-disconnect cut):

HTTP_PROXY=http://<ip-address>:9 \
HTTPS_PROXY=http://<ip-address>:9 \
ALL_PROXY=http://<ip-address>:9 \
cargo test -p hilo_backends --lib profile_credentials_sign_requests_end_to_end

the test never returns; the runner reports has been running for over 60 seconds, and the whole hilo_backends lib suite stalls until the job timeout because the test holds the module ENV_LOCK for its whole body (s3_endpoint_display_and_env_resolution blocks behind it).

Root cause

The test starts a throwaway loopback listener, dispatches a real S3 request at it, then joins the listener task:

let _ = client.list_objects_v2().bucket("b").send().await;   // error discarded
let head = server.await.unwrap();                            // unbounded join

Two defects compose into a hang:

  1. Request error discarded. The AWS SDK client honours HTTP_PROXY/HTTPS_PROXY/ALL_PROXY. With the proxy at <ip-address>:9, the request goes to the dead proxy and never dials <ip-address>:<ephemeral>. send() resolves Err(…) (observed: dispatch failure) and let _ = … throws it away.
  2. Server await unbounded. The spawned task is parked in listener.accept(); no connection ever arrives, so server.await waits forever. .unwrap() can never fire because the task never finishes.

A fast request failure becomes a permanent hang. Propagating the error is necessary; bounding both awaits and aborting the task is the robust fix.

Fix

hilo-backends/src/s3.rs, inside profile_credentials_sign_requests_end_to_end. Make the handle mutable so the task can be aborted:

-        let server = tokio::spawn(async move {
+        let mut server = tokio::spawn(async move {

         // The response shape is not the point here; the captured request is.
-        let _ = client.list_objects_v2().bucket("b").send().await;
-        let head = server.await.unwrap();
+        //
+        // QA-WARPFS-032: never discard the send result and never await the
+        // listener unconditionally. With an unreachable HTTP(S)/ALL_PROXY
+        // exported the SDK never dials the loopback listener: send() resolves
+        // Err, the listener stays parked in accept(), and this test used to
+        // hang forever (dragging the whole lib suite down with it behind
+        // ENV_LOCK). Report the request error and bound both awaits so the
+        // failure is fast, named, and cannot stall the suite.
+        let send = tokio::time::timeout(
+            std::time::Duration::from_secs(5),
+            client.list_objects_v2().bucket("b").send(),
+        )
+        .await;
+        let send_result = match send {
+            Ok(result) => result,
+            Err(_) => {
+                server.abort();
+                panic!(
+                    "S3 request to the loopback listener timed out after 5s; the request \
+                     never left the client (check HTTP_PROXY/HTTPS_PROXY/ALL_PROXY for a \
+                     dead proxy)"
+                );
+            }
+        };
+        if let Err(e) = send_result {
+            server.abort();
+            panic!("request must reach the loopback listener: {e}");
+        }
+
+        let head = match tokio::time::timeout(std::time::Duration::from_secs(5), &mut server).await
+        {
+            Ok(joined) => joined.expect("loopback listener task panicked"),
+            Err(_) => {
+                server.abort();
+                panic!("loopback listener did not receive the request within 5s");
+            }
+        };

Why this shape - Both awaits bounded at 5 s (well under the 10 s budget): the request and the server task. - Send error reported, not swallowed: the transport Err(e) panics with request must reach the loopback listener: dispatch failure. - Task aborted on every failure path so no detached task keeps the listener open. - Task await borrows &mut server instead of moving the handle into timeout — timeout consumes its future and a dropped JoinHandle only detaches; borrowing preserves ownership so abort() is reachable in the timeout arm. - Existing SigV4 assertions untouched. - A match (not unwrap_or_else) avoids clippy::result_large_err from the large SdkError under -D warnings.
