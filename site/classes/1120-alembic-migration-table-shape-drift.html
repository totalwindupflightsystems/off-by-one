Summary

Important: The dexdat-core repository is not present in this environment (only the problem spec and pi's own files exist on disk), so I could not run the raw A/B verification here. However, the problem spec itself carries the verification evidence, and the required fix is fully prescribed.

Root cause

Migration 001 executed a raw consensus/init.sql full of CREATE TABLE IF NOT EXISTS statements, which built routing_rules with the legacy HITL shape (name/pattern/target_session/target_workflow/priority/enabled/tenant_id) instead of the SQLAlchemy model shape (user_id/rule_name/rule_priority/is_active/conditions/actions). Because create_all only creates tables that don't already exist, it silently skipped the wrongly-shaped table, so the bad shape persisted on fresh DBs and POST /v1/routing-rules 500'd with column user_id does not exist.

The fix (in the doc)

  1. New migration 004 (down_revision = "003") that does DROP TABLE IF EXISTS routing_rules then recreates it with the exact model columns:
  2. id UUID PK DEFAULT gen_random_uuid()
  3. user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE
  4. rule_name VARCHAR(255) NOT NULL
  5. rule_priority INTEGER NOT NULL DEFAULT 100
  6. is_active BOOLEAN NOT NULL DEFAULT true
  7. conditions / actions JSONB NOT NULL DEFAULT '{}'
  8. created_at / updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
  9. ix_routing_rules_user_id index
  10. DDL_STATEMENTS kept at module scope so tests exec the exact same DDL.
  11. Idempotent-ish by construction (DROP IF EXISTS + CREATE IF NOT EXISTS).
  12. Integration test — runs the DDL twice (idempotency) plus an ORM round-trip with cascade delete.
  13. Verification section — A/B scratch-DB commands reproducing the HITL shape at 003 (5 FAIL) vs. model shape at head (5 PASS), plus the recorded evidence (foreman 7 passed, unit 487, gitreins tier2 PASS 494f5b49).

The document is at /workspace/solution.md. To actually run/verify it you'll need to restore the dexdat-core repo (commit around head 003), drop in the migration file + test, and run the A/B steps against a scratch Postgres.
