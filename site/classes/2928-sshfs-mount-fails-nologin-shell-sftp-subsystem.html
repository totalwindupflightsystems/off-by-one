Fix: sshfs / SFTP fails for an account whose shell is /usr/sbin/nologin

Symptoms

On the client:

read: Connection reset by peer                   # sshfs
Received message too long 1416128883             # sftp / ssh subsystem

On direct SSH to the account:

This account is currently not available.

The number 1416128883 is decimal for 0x54686973, the first four bytes of This account is currently not available. (This). The SFTP client expects a 4-byte packet length there, not text from the login shell.

Root cause

For a normal SFTP subsystem, sshd executes the user's login shell to run the subsystem command, effectively:

<login-shell> -c /usr/lib/openssh/sftp-server

If the account's login shell is /usr/sbin/nologin (or /bin/false), that "shell" prints its message to standard output and exits before the SFTP server starts:

This account is currently not available.

The client therefore sees the nologin banner instead of the first SFTP protocol packet. sftp reports Received message too long 1416128883; sshfs's SSH transport gets EOF/reset and reports read: Connection reset by peer.

The account does not need password login or an interactive shell. It only needs a shell that can execute a non-interactive command (/bin/sh is sufficient). The password may and should remain locked; authentication can remain key-only.

Diagnosis

On the SSH server, run as root:

TARGET_USER=sftpuser

# What shell does sshd see?  nologin/false here is the root cause.
getent passwd "$TARGET_USER"

# Confirm the SFTP subsystem sshd is configured to use.
sshd -T | grep -i '^subsystem'

# Check whether the account password is locked (L / LK in the second field).
passwd -S "$TARGET_USER"

On the client, the diagnostic trio is:

# 1. Direct SSH prints the nologin banner; do not trust the exit status alone.
ssh "$<email>" true

# 2. SFTP receives the banner as a malformed protocol packet.
sftp "$<email>"

# 3. sshfs sees the connection die before SFTP initialises.
mkdir -p /mnt/data
sshfs "$<email>:/srv/data" /mnt/data

Fix

On the SSH server, as root, give the account a real non-interactive shell:

TARGET_USER=sftpuser

# Any shell that can run a command works: /bin/sh, /bin/bash, /bin/dash, ...
usermod -s /bin/sh "$TARGET_USER"

# Keep the password locked; use SSH keys only.
passwd -l "$TARGET_USER"        # or: usermod -L "$TARGET_USER"

# Verify the account data.
getent passwd "$TARGET_USER"
# Example expected last field:
#   /bin/sh
passwd -S "$TARGET_USER"
# Example expected status: L (locked)

No sshd restart is required just to pick up the shell change; new login sessions read the updated account information.

If password authentication is not already disabled, make it key-only and reload sshd:

cat >/etc/ssh/sshd_config.d/99-key-only.conf <<'CONF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
CONF

sshd -t
systemctl reload ssh        # on some distributions: systemctl reload sshd

The user's ~/.ssh/authorized_keys, home directory ownership, and permissions must still be correct:

install -d -m 700 -o "$TARGET_USER" -g "$TARGET_USER" "/home/$TARGET_USER/.ssh"
touch "/home/$TARGET_USER/.ssh/authorized_keys"
chown "$TARGET_USER:$TARGET_USER" "/home/$TARGET_USER/.ssh/authorized_keys"
chmod 600 "/home/$TARGET_USER/.ssh/authorized_keys"
# Then append the client public key to authorized_keys.

Alternative: keep the nologin shell and use internal-sftp

If policy requires the account to keep /usr/sbin/nologin but the account must serve SFTP/sshfs, configure sshd to run the built-in SFTP server as a forced command. OpenSSH handles internal-sftp internally and does not invoke the nologin shell:

cat >>/etc/ssh/sshd_config <<'CONF'
Match User sftpuser
    ForceCommand internal-sftp
    PermitTTY no
    AllowTcpForwarding no
    X11Forwarding no
CONF

sshd -t
systemctl reload ssh

This keeps interactive shell access disabled while allowing SFTP. The simpler usermod -s /bin/sh fix is usually preferable unless the nologin shell must be preserved for policy reasons.

Verification

From the client:

TARGET_USER=sftpuser
SERVER=server.example.com

# 1. Direct command execution should return only the command output.
ssh "$TARGET_USER@$SERVER" 'echo SSH_OK; id -un'
# Expected: SSH_OK followed by the username; no nologin banner.

# 2. A non-interactive SFTP session should succeed with rc=0.
printf 'pwd\nls -l /\n' | sftp -b - "$TARGET_USER@$SERVER"
echo "sftp rc=$?"
# Expected: Remote working directory and a directory listing, rc=0.

# 3. Mount with sshfs, verify, then unmount.
mkdir -p /mnt/data
sshfs "$TARGET_USER@$SERVER:/srv/data" /mnt/data
mountpoint /mnt/data
ls -la /mnt/data
fusermount3 -u /mnt/data     # or: fusermount -u /mnt/data

On the server, the key check is:

getent passwd "$TARGET_USER" | awk -F: '{print "shell=" $7}'

It must no longer print /usr/sbin/nologin or /bin/false. After the change, the SFTP subsystem starts normally, so neither Received message too long nor read: Connection reset by peer should recur.

Representative result from an isolated OpenSSH 10.2 test instance:

Before:  ssh <email> 'echo hello'
         This account is currently not available.

         sftp <email>
         Received message too long 1416128883

After:   ssh <email> 'echo hello; id -un'
         hello
         user

         sftp <email>
         Remote working directory: ~
         sftp rc=0

sshfs uses the same SFTP subsystem, so it succeeds once the SFTP handshake succeeds. The actual mount step additionally requires a working /dev/fuse and fusermount on the client.
