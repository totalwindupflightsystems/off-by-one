Solution written to ~/bunker-qa-chaos-resource-sqlite3-cli-missing-env-class.md.

Diagnosis

The five failures are a single env-class root cause, not a product regression and not the memory cap:

  • tests/hrs010_session_store.rs spawns the system sqlite3 CLI. The JIT Rust-cell image doesn't contain it, so execvp returns ENOENT → Rust Os { code: 2, kind: NotFound }.
  • OOM/rlimit would be SIGKILL/exit 137, and the suite finishes in 3.4s; the failure count exactly equals the sqlite3-dependent tests. Same HEAD is green on the control host because sqlite3 is on its PATH.

Fix (two layers, both in the doc)

A. Primary/durable — provision in the JIT bootstrap. I verified the live bunker CLI's image-spec schema and that this is accepted:

{ "base": "docker.io/library/ubuntu:24.04",
  "packages": [ { "manager": "apt", "packages": ["sqlite3"] } ] }

pass it via bunker spawn --image-spec rust-cell.imagespec.json, plus a command -v sqlite3 preflight that maps a missing CLI to an env-skip (exit 200) instead of 5 panics.

B. Secondary — skip-with-reason in tests. A system_sqlite3_available() probe + require_system_sqlite3!() macro that emits a greppable SKIP ... marker and returns, so an un-provisioned image can never masquerade as a product bug. Optional Fix C: switch tests to in-process bundled rusqlite/libsqlite3-sys to drop the CLI entirely.

Verification

What I could actually run here is captured in §3, with raw output: - image-spec apt/sqlite3 add parsed and validated by the real bunker spawn --image-spec (only the deliberately bogus server errors); - reproduced exec: "sqlite3": executable file not found in $PATH under a pruned PATH (the exact condition behind Os { code: 2 }); - reproduced the guard returning 0/1 with/without the CLI.

cargo test couldn't be re-run locally (no Rust toolchain or hermes-rs checkout here), so §3.2 gives the exact before/after commands to run on bunker-mvp (spawn → command -v sqlite3 → cargo test, expect 17/5 ENOENT before, 29/29 after, and the SKIP path with the CLI hidden).
