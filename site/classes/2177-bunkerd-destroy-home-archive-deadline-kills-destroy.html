Answer

I diagnosed the failure against the actual deployBunker/bunker source (cloned from GitHub) and produced a verified write-up at /workspace/solution.md.

Root cause (confirmed in code)

  • internal/agent/manager_destroy.go (DF-BUNKER-33) archives + verifies the agent home with exec.CommandContext(ctx, "tar", "czf", ...) before userdel -rf, and fails closed (status: home_retained) if the archive errors.
  • The ctx is the inbound RPC request context, so the caller's deadline propagates in.
  • internal/cli/destroy.go hard-codes context.WithTimeout(..., 30*time.Second) (daemon request_timeout is 300 s, but the earliest deadline wins).
  • A 1.4 GB node_modules home needs >30 s to gzip → the deadline SIGKILLs tar → signal: killed → archive error → home retained, userdel skipped, API maps to CodeInternal (500), registry row stays running, retries repeat.
  • --force does not help (the archive gate runs before userdel and ignores force).
  • Bonus defect: tar wrote straight to the final timestamped path, so killed runs leave truncated .tar.gz files.

Deliverable contents

  1. Immediate runbook (the verified remedy): manual tar -czf + tar -tzf verify → rm -rf node_modules .local .cache → re-run bunker destroy → verify home/user/registry gone. Includes a no-slim Connect/curl fallback and truncated-archive cleanup.
  2. Durable patch: detach the archive onto its own context.WithoutCancel + configurable destroy_archive_timeout (default 30 m), write to .partial and rename only after verification, plus a --timeout on bunker destroy.
  3. Verification: a before-fix reproduction (signal: killed, home retained, 157 MB truncated artifact, then success after slimming) and after-fix go test/go build results.

I applied and tested the durable patch in /tmp/bunkersrc (build + focused tests pass, including a new test proving an already-cancelled request context no longer aborts the archive). The write-up is self-contained and directly usable.
