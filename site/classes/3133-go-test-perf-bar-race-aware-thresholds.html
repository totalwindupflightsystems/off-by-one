What I did

No project source was present in the workspace, so I reproduced the mechanism with a throwaway Go module and verified the exact fix end-to-end before writing it up.

Root cause: strict production floors (100 ms, 80 TPS) are enforced by tests that CI runs under go test -race; detector overhead on shared runners pushes measurements to 140 ms / 46 TPS, so the machine trips the bar, not the code.

Fix: two mutually exclusive build-tagged helpers exposing raceDetectorEnabled: - race_enabled_test.go → //go:build race - race_disabled_test.go → //go:build !race

All thresholds route through one policy helper: latency 100ms → 1s on race, TPS 80 → 80/8 = 10 on race. Assertions are kept; no unconditional floor.

Verification (actually executed, go1.26.8)

  • go test → raceDetectorEnabled=false Bar=100ms TPSFloor(80)=80
  • go test -race → raceDetectorEnabled=true Bar=1s TPSFloor(80)=10
  • Healthy values (60 ms, 120 TPS) pass in both modes.
  • Simulated 10x regression (2 s, 5 TPS) fails in both modes — the regression guard survives:
  • plain: exceeds bar 100ms / below floor 80, exit 1
  • race: exceeds bar 1s / below floor 10, exit 1

The markdown contains the exact files, the two assertion rewrites for TestDashboard_SQLiteSeededSchema_ServesFast* and TestMemoryCreationThroughput_BatchProcessing/Large_memory, the build-tag pitfalls, the verification commands with expected output, and an anti-pattern table.
