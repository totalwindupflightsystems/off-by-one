Solution: PYSEC-2026-4298 on python-jose==3.5.0 is upstream-blocked — retain the pending row, do not re-pin

Repository: &lt;project&gt;-core · Environment: Python 3.11 venv, audited 2026-10-26 Advisory: PYSEC-2026-4298 (GHSA-3qf3-8w2g-rqmx, CVE-2026-85394) Affected: python-jose through 3.5.0 · Fix versions: (none published) Disposition: upstream-blocked → keep the row pending, record evidence, do not change the pin.

1. Root-cause analysis

pip-audit reports the direct dependency python-jose==3.5.0 as PYSEC-2026-4298 with an empty fix-version list. This is not a misconfiguration or stale lock: it is an advisory with no upstream remediation path.

Exact advisory metadata (from pip-audit -f json):

{
  "id": "PYSEC-2026-4298",
  "fix_versions": [],
  "aliases": ["GHSA-3qf3-8w2g-rqmx", "CVE-2026-85394"],
  "description": "python-jose through 3.5.0 fails to properly validate asymmetric keys in HMAC initialization, accepting DER-encoded public keys that lack PEM armor or SSH prefixes. Attackers holding the service's public key can forge HS256 tokens that pass verification when algorithms are not explicitly restricted. This is an incomplete fix for CVE-2024-33663."
}

The failure chain:

  1. Installed == latest. pip index versions python-jose shows LATEST: 3.5.0 = INSTALLED: 3.5.0. No newer release exists to move to.
  2. No fix version exists. fix_versions: [] means the advisory database declares no patched artifact.
  3. Downgrading is strictly worse. PYSEC-2026-4298 is an incomplete fix for CVE-2024-33663; reverting below 3.4.0 reinstates CVE-2024-33663 plus CVE-2024-33664.
  4. Pinning an unpublished version is unsupported. A fabricated pin (e.g. 3.5.1) is not installable and breaks reproducible builds.
  5. The vulnerable path is conditional. The key-confusion / HS256-forgery path requires jwt.decode() to be called without an explicit algorithms=[...] allow-list. In &lt;project&gt;-core the only JOSE usage is src/security.py, which already passes an explicit allow-list (see §2.5).

Conclusion: for a direct, unfixable, latest-version advisory the correct action is to retain the pending row with upstream-blocked evidence and enforce the call-site mitigation. Changing requirements.txt is unsupported and must not be done.

Note: the same audit run also surfaces transitive ecdsa==0.19.2 PYSEC-2026-1325 (CVE-2024-23342), also fix_versions: [] with "no planned fix" upstream. Record it as a second upstream-blocked row rather than silently ignoring it.

2. Exact fix

No application dependency change. The fix is an evidence-and-tracking change plus a documented, scoped CI ignore.

2.1 Do not modify requirements.txt

Leave the direct pin exactly as-is:

python-jose==3.5.0

2.2 Capture immutable evidence

Run from the repository root so .venv/bin/pip-audit resolves:

EVID="security/evidence/PYSEC-2026-4298"
mkdir -p "$EVID"

# 1) Human-readable audit output (the exact pip-audit report)
.venv/bin/pip-audit -r requirements.txt 2>&1 | tee "$EVID/audit.txt"

# 2) Machine-readable audit output (fix_versions proof)
.venv/bin/pip-audit -r requirements.txt -f json -o "$EVID/audit.json"

# 3) Upstream availability proof: latest PyPI version
.venv/bin/pip index versions python-jose 2>&1 | tee "$EVID/pypi-versions.txt"

# 4) Import-usage proof: every place python-jose is imported
grep -RIn --include='*.py' -E '\b(from|import)\s+jose\b|python[-_]jose' src/ \
  | tee "$EVID/import-usage.txt"

# 5) Integrity hashes so evidence can't drift silently
sha256sum "$EVID"/audit.txt "$EVID"/audit.json \
          "$EVID"/pypi-versions.txt "$EVID"/import-usage.txt \
          requirements.txt | tee "$EVID/SHA256SUMS"

2.4 Keep CI green with a documented, scoped ignore

Never glob-ignore. Ignore only the recorded upstream-blocked IDs while their rows exist:

.venv/bin/pip-audit -r requirements.txt \
  --ignore-vuln PYSEC-2026-4298 \
  --ignore-vuln PYSEC-2026-1325

The ignore is justified by the recorded row — deleting the row must delete the ignore.

2.5 Preserve the call-site mitigation

The advisory scopes the exploit to "when algorithms are not explicitly restricted." Keep the explicit allow-list in src/security.py:

ALLOWED_ALGORITHMS = ("HS256", "RS256")


def decode_token(token: str, key: str, issuer: str, audience: str) -> dict[str, Any]:
    return jwt.decode(
        token,
        key,
        algorithms=list(ALLOWED_ALGORITHMS),  # never trust the token header
        issuer=issuer,
        audience=audience,
    )
