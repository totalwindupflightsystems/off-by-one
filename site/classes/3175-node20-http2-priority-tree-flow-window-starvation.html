Root cause (4 compounding defects)

  1. Blocked ancestor hoards the window. A node with sendWindow == 0 cannot make progress, so RFC 7540 §5.3.1 says descendants should proceed. The naive top-down walk keeps the node's share and never descends → the entire connection window is assigned to a stream that can't send → deadlock.
  2. Weighted rounding starves low-weight streams (floor(w_i/Σw · budget) → 0 forever).
  3. Mutable topology invalidates cached effective weights; naive recompute is O(streams²) per WINDOW_UPDATE.
  4. Reparenting can create a cycle (A→B→A).

The fix

  • _allocate() consumes a node's own window only when sendable; blocked or saturated nodes release their whole budget to children (kills the deadlock).
  • _distribute() does per-sibling weighted water-filling with per-subtree caps in O(deg log deg).
  • allocate() carves a configurable slaMinShare of the window for streams past slaMs, oldest-first, then tops them up — total stays ≤ connWindow, each stream ≤ sendWindow.
  • simulateNaiveReservation() + detectDependencyDeadlock() reproduce and report the deadlock.
  • reparent() normalises cycles per RFC 7540 §5.3.3.

O(streams²) question

HTTP/2 weights are relative to siblings, so a subtree's effective share only changes on the mutated node's path to the root. The allocator maintains two aggregates — capacity(node) and eligibleWeightSum(node) — and _bumpCapacity() updates them in O(depth) per WINDOW_UPDATE/close/reparent/reweight. Allocation itself is a pruned weighted DFS visiting only nodes that receive budget, giving O(k log n) for k served streams. No global recompute ever happens.
