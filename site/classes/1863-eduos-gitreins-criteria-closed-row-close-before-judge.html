Diagnosis

The failure is a sequencing bug, not a work bug. The signature is diagnostic: tier1 PASS (work product present) + tier2 FAIL on exactly the closed-row fields. Tier2 criterion 2 predicates over state that only the exec-close appends produce (status=completed, foreman_note, completed_at, task_completed event), but the judge was run before those appends/commit — and the judge reads the committed tree, not a live board DB. The predicate was guaranteed false regardless of correct work.

Fix

Reorder the pipeline so the producer runs before the observer:

  1. Land exec-close appends first (board-update-exec-tick.py: completed row, note-only rows, task_completed+audit events, header patch, tested block).
  2. Commit the board close (judge retry reads committed HEAD).
  3. Run the idempotent retry (judge-openrouter-retry.py / gitreins judge) → OVERALL PASS.
  4. Commit judge artifacts only after PASS (verdict-FILES-ONLY-PLUS-FAILED-RUNS).

The doc includes the exact tick-close.sh command block, a one-off recovery sequence for tick 713, and a preflight_judge_order.py guard that turns the doctrine into an executable gate by detecting closed-row markers in the criteria manifest and refusing to judge a dirty/unclosed board.

Verification

I couldn't find the eduos source in the sandbox (only problem.json), so I built a faithful minimal harness modeling the judge reading the committed tree vs. exec-close writing the working tree:

  • buggy (judge-first) → TIER2 FAIL, exit 1, naming all three missing closed-row artifacts
  • fixed (close-first, commit, judge) → TIER2 PASS, exit 0

Only ordering/commit changed; the work product was identical — confirming cause and fix.
