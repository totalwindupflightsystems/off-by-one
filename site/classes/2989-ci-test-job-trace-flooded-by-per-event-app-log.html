# Fix: CI test leg dies from a per-event WebSocket broadcast log flood

**Problem class:** `ci-test-job-trace-flooded-by-per-event-app-log`
**Observed on:** GitLab pipeline 3669 (`gitlab.readydedis.com`, `node:22-alpine` runner)
**Failing leg:** `test` → `script_failure` (exit 1), with **no failing assertion** in the trace.

---

## 1. Symptom

- One CI leg (`test`) exits `1` and GitLab marks it `script_failure`.
- Its trace is ~489 KB, dominated by repeated lines such as:
  ```
  [ws] broadcast topic=... type=... sent=N
  ```
- There is **no** `Tests N failed` / assertion summary for that package, and no thrown stack trace.
- All sibling legs (`lint`, `spec-drift`, `e2e-harness-syntax`) are green, and every other package still prints its own test total. Only the one leg dies. This is the tell: it is a **logging/volume** failure, not a logic/assertion failure.

## 2. Root cause analysis

1. **Unconditional operational log on a hot path.** The WebSocket delivery path logs once per delivered event, e.g.:
   ```ts
   // packages/ws/src/broadcast.ts
   export function broadcast(topic: string, type: string, subscribers: Subscriber[]) {
     const sent = subscribers.length;
     console.log(`[ws] broadcast topic=${topic} type=${type} sent=${sent}`); // <-- always on
     for (const s of subscribers) s.send({ topic, type });
     return { sent };
   }
   ```
2. **Test volume scales the line count multiplicatively.** The suite drives *real* servers with *live* subscribers, so emitted lines ≈ `tests × topics × subscribers`. A few hundred tests over many topics and several subscribers trivially produce tens of thousands of lines.
3. **CI treats an oversized trace as failure.** The runner captures the flooded output, the job hits its log/execution budget, and the process is killed/aborted before the test reporter can print its summary. Hence `script_failure` + missing `Tests N failed` line. The application log is the *only* thing wrong; delivery itself works.
4. **GitLab roughly doubles the volume.** When GitLab reports the job it echoes console output a second time, so effective trace size ≈ 2× what the test emitted. That pushes an otherwise-borderline leg over the limit.
5. **Why other packages stay green.** Their suites do not open live subscriber sockets on the same code path, so they emit normal, bounded output and print their totals. The failure is isolated to the package that exercises `broadcast()`.

**Conclusion:** the broadcast log line must be silent by default and only emitted on explicit operator opt-in. Delivery must not change.

## 3. Exact fix

Gate the operational line behind an opt-in environment variable that is **read at call time** (never cached at module load, so no import-order or test-runner inheritance surprises). Leave the send loop untouched.

### 3.1 Code change — `packages/ws/src/broadcast.ts`

```diff
+const BROADCAST_LOG_ENABLED = (): boolean =>
+  process.env.HEADING_WS_BROADCAST_LOG === '1';
+
 export function broadcast(topic: string, type: string, subscribers: Subscriber[]) {
   const sent = subscribers.length;
-  console.log(`[ws] broadcast topic=${topic} type=${type} sent=${sent}`);
+  if (BROADCAST_LOG_ENABLED()) {
+    console.log(`[ws] broadcast topic=${topic} type=${type} sent=${sent}`);
+  }
   for (const s of subscribers) s.send({ topic, type });
   return { sent };
 }
```

If the log lives in many call sites, centralize it once and reuse:

```ts
// packages/ws/src/log.ts
export const wsBroadcastLog = (topic: string, type: string, sent: number): void => {
  if (process.env.HEADING_WS_BROADCAST_LOG === '1') {
    console.log(`[ws] broadcast topic=${topic} type=${type} sent=${sent}`);
  }
};
```

Dos and don'ts:

- **Do** evaluate `process.env.HEADING_WS_BROADCAST_LOG` inside the function/at call time.
- **Do** keep the value strictly opt-in (`=== '1'`); anything else is silent.
- **Don't** hoist it to a module-level `const enabled = process.env...` — that freezes the decision at import time and defeats per-invocation control.
- **Don't** touch the `for (const s of subscribers) s.send(...)` delivery path.
- **Don't** use a log level that CI enables globally; the default must be silent.

### 3.2 Operator env table update

Add the knob to the operator/runbook environment table (e.g. `docs/operations/env.md`):

| Variable | Default | Purpose |
| --- | --- | --- |
| `HEADING_WS_BROADCAST_LOG` | unset (off) | Set to `1` to emit one `[ws] broadcast topic=... type=... sent=N` line per delivered event. Off by default; leave off in CI. Intended for short-lived manual debugging only — it scales with tests × topics × subscribers. |

### 3.3 Why not just raise the CI log limit

Raising the limit hides the real problem (unbounded hot-path logging) and keeps doubling effective trace cost via GitLab's echo. The gate is the minimal, correct fix.

## 4. Secondary contributor (do not confuse it with the flood)

A host Docker daemon with an exhausted default address pool can independently kill compose-preflight cells with:

```
all predefined address pools have been fully subnetted
```

Distinguish it from the broadcast flood by inspecting the failing leg's failure text:

- **Broadcast flood:** failure is trace-size/`script_failure`, trace is full of `[ws] broadcast ...` lines, no assertion summary.
- **Docker pool exhaustion:** the failure explicitly mentions Docker network creation / `all predefined address pools have been fully subnetted`.

If the docker message is present, fix the daemon pool (e.g. prune networks, or widen `default-address-pools` in `/etc/docker/daemon.json`, then restart Docker) — the log gate will not help that leg.

## 5. Verification

### 5.1 Mutation proof (runnable, no repo required)

The harness below reproduces the exact failure mode: a `cell` drives real broadcast volume and fails when captured stdout exceeds a byte limit (proxy for the CI log budget).

```bash
mkdir -p /tmp/wsflood && cd /tmp/wsflood

# --- fixed implementation: opt-in gate, env read at call time ---
cat > ws.fix.js <<'EOF'
'use strict';
function broadcast(topic, type, subscribers) {
  const sent = subscribers.length;
  if (process.env.HEADING_WS_BROADCAST_LOG === '1') {
    console.log(`[ws] broadcast topic=${topic} type=${type} sent=${sent}`);
  }
  for (const s of subscribers) s.recv({ topic, type });   // delivery untouched
  return { sent };
}
module.exports = { broadcast };
EOF

# --- mutated implementation: unconditional log (the bug) ---
cat > ws.bug.js <<'EOF'
'use strict';
function broadcast(topic, type, subscribers) {
  const sent = subscribers.length;
  console.log(`[ws] broadcast topic=${topic} type=${type} sent=${sent}`); // BUG
  for (const s of subscribers) s.recv({ topic, type });
  return { sent };
}
module.exports = { broadcast };
EOF

# --- one CI "cell": 200 topics x 20 messages x 3 subscribers = 12,000 deliveries ---
cat > cell.js <<'EOF'
'use strict';
const { broadcast } = require(process.argv[2]);
let captured = 0, bytes = 0;
const orig = console.log;
console.log = (...a) => { captured++; bytes += a.join(' ').length + 1; };
let delivered = 0;
const subs = Array.from({ length: 3 }, () => ({ recv() { delivered++; } }));
for (let t = 0; t < 200; t++)
  for (let m = 0; m < 20; m++)
    broadcast(`topic.${t}`, 'message', subs);
console.log = orig;
const LIMIT = 2000; // CI runner/script trace budget proxy
const pass = delivered === 12000 && bytes <= LIMIT;
orig(`delivered=${delivered} log_lines=${captured} log_bytes=${bytes} cell=${pass ? 'PASS' : 'FAIL(script_failure: trace flooded)'}`);
process.exit(pass ? 0 : 1);
EOF

echo "=== FIX, default (gate present, env unset) ==="; node cell.js ./ws.fix.js; echo "exit=$?"
echo "=== MUTATION, gate removed (ws.bug.js) ===";         node cell.js ./ws.bug.js; echo "exit=$?"
```

Observed output:

```
=== FIX, default (gate present, env unset) ===
delivered=12000 log_lines=0 log_bytes=0 cell=PASS
exit=0
=== MUTATION, gate removed (ws.bug.js) ===
delivered=12000 log_lines=4000 log_bytes=201800 cell=FAIL(script_failure: trace flooded)
exit=1
```

This proves the required property: **with the gate the default-silent cell passes; removing the gate makes the same cell fail with the captured flood line.** Delivery is identical in both runs (`delivered=12000`).

### 5.2 Prove the knob is opt-in and read at call time

```bash
cd /tmp/wsflood
cat > optin.js <<'EOF'
'use strict';
const { broadcast } = require('./ws.fix.js');
let lines = 0;
const orig = console.log;
console.log = (...a) => { lines++; orig(...a); };
process.env.HEADING_WS_BROADCAST_LOG = '1';       // set AFTER import
broadcast('t', 'message', [{ recv() {} }]);
orig(`opt-in emitted lines=${lines} (read-at-call-time proven)`);
EOF
node optin.js
```

Observed:

```
[ws] broadcast topic=t type=message sent=1
opt-in emitted lines=1 (read-at-call-time proven)
```

Setting the variable after the module is imported still enables the line → the gate is evaluated per call. The real default run (5.1) emitted 0 lines → strictly opt-in.

From the repo root (pnpm/npm monorepo):


Expected: steps 1–2 green, step 3 prints `0`, step 4 prints one broadcast line.

### 5.4 Pipeline acceptance

- Commit the gate + env-table doc as one corrective commit.
- The follow-up pipeline must go **all-green**, including the previously dying `test` leg, with a normal-sized trace and a `Tests N passed` summary for that package.
- Guardrail: add the `grep -c '\[ws\] broadcast' == 0` check (5.3 step 3) to the CI cell so a regression that removes the gate fails fast with a clear message instead of a silent trace flood.

### 5.5 Ruling out the docker secondary contributor

```bash
# On the runner host, after a failed leg:
journalctl -u docker --since '30 min ago' | grep -i 'address pools\|fully subnetted' || echo 'no docker pool exhaustion'
# and in the failing job trace:
#   grep -i 'all predefined address pools' <trace> && echo 'DOCKER issue, not flood'
```

If the docker message is present and the broadcast lines are absent, the fix is the daemon address pool, not this code change.
