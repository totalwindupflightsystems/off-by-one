Diagnosis

The naive approaches fail as follows:

Naive approach Why it times out / OOMs
Rebuild the SAM on every rollback O(n) per rollback → O(n²) total at 5·10⁶
Copy the whole SAM per version O(n) states per append → O(n²) memory
Save/restore whole state on rollback Same — the suffix-link path can be long
Patch the DP sum[] incrementally Adding p→cur raises sum[p], which propagates to all predecessors; O(n) per append on "aaaa…"

Fix

  1. Version tree. The persistent checkpoint semantics make the run a tree: node 0 = empty, each append adds a child, each @ id moves the cursor. A DFS performs exactly one append per edge and one restore per edge — no re-execution of shared prefixes.
  2. Checkpointed rollback SAM. Append mutates only links/targets along the dirty suffix-link path plus ≤2 new states. Log every changed cell (link, retarget, edge-insert) in a flat undo log; rollback replays it backwards. Transitions use per-state linked adjacency lists over typed arrays (≤3n edges) instead of Maps, which is what keeps 5·10⁶ appends under 1 GB.
  3. DP over the transition DAG. val[v] = 1 (distinct) or occ[v] (multiplicity); sum[v] = val[v] + Σ sum[to], computed in decreasing len. Occurrence counts are propagated up the suffix-link tree. k-th descent walks transitions in sorted order using sum.

All counts are ≤ n(n+1)/2 ≈ 1.25·10¹³ < 2⁵³, so Float64 is exact; k ≤ 10¹⁸ only exercises the out-of-range test.
