Fix: TS2300 Duplicate GroundingCaseFamily + TS2322 constraint-guarded in test dataset

Problem class: typescript-test-tsconfig-semantic-gap Repo: dexdat/eduos.dexdat.com.co — apps/api pnpm monorepo Task: BETA-GATE-005 Commit under repair: 0b3988f81726b22cafe3308053aafd3b13d90d74 File: apps/api/src/modules/ai-tutor/__tests__/grounding-eval-dataset.ts Toolchain: pnpm, TypeScript, Vitest 4.1.11

1. Symptom

Functional tests were green under Vitest, but a direct semantic compile of the test source failed:

TS2300  Duplicate identifier 'GroundingCaseFamily'.
TS2322  Type '"constraint-guarded"' is not assignable to type 'GroundingCaseFamily'.

Both errors came from a single test-only file. Nothing in application code failed, and the normal package build / tsc -p run stayed clean.

2. Root-cause analysis

Three separate mechanisms combined into a false-green signal:

2.1 Vitest is transpile-only, not type-checking

Vitest (like Jest with ts-jest in transpile mode) runs test files through esbuild / SWC transform, which strips types without checking them. isolatedModules-style transforms never evaluate type aliases, duplicate identifiers, or assignability. Therefore a type error in a test file cannot fail a Vitest run.

2.2 The application tsconfig excludes test sources

apps/api/tsconfig.json owns include/exclude for the production program. Test directories (__tests__/, *.test.ts, *.spec.ts) are deliberately excluded so test-only dependencies never leak into the app build. Consequence:

pnpm --filter @eduos/api exec tsc -p tsconfig.json --noEmit   # succeeds, but never sees the test file

The standard type-check gate never compiled grounding-eval-dataset.ts, so it was invisible to CI.

2.3 The actual code defect — a duplicate exported alias

grounding-eval-dataset.ts declared the same exported type alias twice. The obsolete declaration was left in place when the family union was reworked, while the new canonical union added the "constraint-guarded" family:

// ── obsolete declaration that should have been deleted ──────────────
export type GroundingCaseFamily =
  | "factual"
  | "inference"
  | "refusal";

// ── canonical declaration (new families added) ──────────────────────
export type GroundingCaseFamily =
  | "factual"
  | "inference"
  | "refusal"
  | "constraint-guarded";

// ...later in the dataset...
const evalCase = { family: "constraint-guarded" } as const;

TypeScript reports one TS2300 per duplicate declaration site, and because the duplicate name is ambiguous, the literal "constraint-guarded" is checked against a union that does not contain it → TS2322. The TS2322 is a downstream artifact of the TS2300, not an independent bug. Removing the obsolete alias leaves the canonical union (which already contains "constraint-guarded") and clears both errors.

2.4 Why it slipped through

Gate Sees test file? Checks types? Result
Vitest run yes no green
tsc -p apps/api/tsconfig.json no yes green
direct tsc on test source yes yes TS2300 + TS2322

The single gate that would have caught it — semantic compilation of test sources — did not exist.

3. Exact fix

3.1 Locate and delete the obsolete alias

Find both declaration sites:

cd apps/api
rg -n "type GroundingCaseFamily" src/modules/ai-tutor/__tests__/grounding-eval-dataset.ts

Expected: two hits (plus usage sites). Delete the obsolete block — the one that is not referenced by the rest of the dataset and does not include "constraint-guarded" (or whichever canonical union is actually used by the case objects). Keep exactly one declaration.

Before

// obsolete — remove this entire block
export type GroundingCaseFamily =
  | "factual"
  | "inference"
  | "refusal";

export type GroundingCaseFamily =
  | "factual"
  | "inference"
  | "refusal"
  | "constraint-guarded";

After

export type GroundingCaseFamily =
  | "factual"
  | "inference"
  | "refusal"
  | "constraint-guarded";

If the surviving canonical union is genuinely missing "constraint-guarded" and the case value is correct, add the literal to the single surviving union instead of deleting it. Never keep two aliases. Do not // @ts-ignore or cast the literal to any.

3.2 Harden the gate: dedicated test tsconfig

So the type error can never be invisible again, add a program that includes the tests. Create apps/api/tsconfig.test.json:

{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "noEmit": true,
    "types": ["node", "vitest/globals"]
  },
  "include": [
    "src/**/*.ts",
    "src/**/*.tsx"
  ],
  "exclude": [
    "node_modules",
    "dist",
    "coverage"
  ]
}

Because it extends the base config, it inherits strict, moduleResolution, path alias/paths, and every other compiler option; overriding include/exclude is what pulls __tests__ back into the program. If apps/api has no base tsconfig paths for test imports, add the Vitest global types as shown.

3.3 Wire it into scripts and CI

apps/api/package.json:

{
  "scripts": {
    "typecheck": "tsc -p tsconfig.json --noEmit",
    "typecheck:tests": "tsc -p tsconfig.test.json --noEmit",
    "test": "vitest run"
  }
}

CI (or the root typecheck aggregate):

pnpm --filter @eduos/api run typecheck
pnpm --filter @eduos/api run typecheck:tests   # closure evidence alongside Vitest
pnpm --filter @eduos/api run test

3.4 One-shot minimal command (when a tsconfig is overkill)

The direct single-file invocation used to expose the bug, usable as an ad-hoc check:

cd apps/api
pnpm exec tsc --noEmit \
  --strict \
  --target ES2022 \
  --module ESNext \
  --moduleResolution bundler \
  --types node,vitest/globals \
  --skipLibCheck \
  src/modules/ai-tutor/__tests__/grounding-eval-dataset.ts

--skipLibCheck only skips .d.ts checking; it still fully semantically checks the target .ts source, which is what surfaces duplicate identifiers and invalid literals.

5. Why this is the correct closure

  • Deletes the actual defect, not the symptom: the obsolete duplicate alias is removed; the surviving union already contains "constraint-guarded", so the TS2322 disappears as a consequence.
  • Closes the semantic gap permanently: typecheck:tests runs real tsc over __tests__, so transpile-only Vitest can no longer hide type errors in test sources. The application tsconfig stays clean (tests still excluded from the production build).
  • No weakened checking: no @ts-ignore, as any, or skipLibCheck scoped to project source. skipLibCheck in the one-file recipe only affects dependency .d.ts files.
  • Verified by two independent signals — semantic compilation (tsc) and runtime execution (Vitest focused + root suite) — which is exactly the closure evidence requested.

6. Regression-prevention checklist

  1. Keep exactly one exported alias per name; rg "type GroundingCaseFamily" must return one hit.
  2. Any change to a family union must be accompanied by pnpm --filter @eduos/api run typecheck:tests.
  3. Add typecheck:tests to the same CI job/stage that runs Vitest so neither can pass alone.
  4. Treat a green Vitest run as runtime evidence only; never as type evidence.
