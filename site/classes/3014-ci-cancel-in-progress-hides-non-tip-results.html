Diagnosis (confirmed against live gethilo/hilo data)

The workflow's concurrency: group: ${{ github.workflow }}-${{ github.ref }} + cancel-in-progress: true means every new push to master cancels the in-progress run for that ref. Because the automation pushes a board-closeout commit every tick, only the final (tip) run of a burst ever reaches a terminal conclusion. Live proof from the 2026‑10‑27 incident:

  • fix commit 875072167c (run 965) → cancelled at Build, Clippy/Test skipped
  • every intermediate board commit → cancelled
  • tip b31f03792c (run 969) → success with all 9 steps green, including Test = cargo test --workspace
  • compare/875072167c...b31f03792c → merge_base=875072167c, so the tip contains the fix

The tracker's bug was selecting runs by headSha == fix_sha and requiring a terminal success there — an unsatisfiable predicate for any non-tip commit.

The fix (three rules)

  1. Certify on the ref tip run (newest run_number), verifying git merge-base --is-ancestor <fix_sha> <tip_sha>.
  2. cancelled is a supersession, never CI-red. But a completed failure is always a real red — cancel-in-progress only aborts in-progress runs, so failure rows aren't laundered into "just a supersession."
  3. Keep red_sha separate from fix_sha/cert_sha/cert_run_id; never overwrite the failure receipt when closing the row.

ci_certify.py implements this as a pure, unit-testable classifier plus a thin gh wrapper.

Verification

  • 10/10 tests pass, including 3 frozen real-data regressions from the incident and 7 synthetic cases (tip-success certifies; cancelled never red; tip-failure is red; in-progress→pending; force-push success doesn't cover fix).
  • Classifier run on the real snapshot returns CERTIFIED (run 969) with reds: [] despite the fix run being cancelled.
  • Ancestry proven via GitHub's compare API.
