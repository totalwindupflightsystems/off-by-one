I've diagnostically traced the problem and written a complete, self-contained solution. Here's a summary.

What I found

  • The affected component is coding-hermes-scheduler (schedulerd, a Go service). Only its compiled binary (/usr/local/bin/schedulerd) and systemd unit files exist on this host; there is no checked-out source tree, so I extracted the authoritative evidence directly from the binary's embedded symbols:
  • Schema migration: ALTER TABLE projects ADD COLUMN last_tick_started TEXT; / ... last_tick_completed TEXT;
  • Read projection uses COALESCE(last_tick_completed,'') and COALESCE(last_tick_started,'')
  • Completion writer SQL is UPDATE projects SET last_tick_completed = ? WHERE name = ? plus consecutive_failures reset
  • Exec vs. gateway branches exposed via symbols (spawnCountHTTP/spawnCountExec, SendResponse, gateway client)

The solution (/home/kara/coding-hermes-scheduler/SOLUTION.md)

  1. Root cause: The gateway-spawn branch stamped projects.last_tick_started with a time.Now() evaluated after SendResponse returned — i.e., the session completion moment. The exec branch stamps at spawn, so only gateway projects showed start == completed.
  2. The fix: capture reqStart before the gateway handoff and stamp last_tick_started = reqStart at spawn time (mirroring exec); narrow the completion UPDATE to only set last_tick_completed and reset consecutive_failures — never rewrite last_tick_started.
  3. Verification: two dev regression tests (gateway-completed stamp ≈ spawn; blocking-handler leaves running-tick start intact) plus a live check matching the recorded evidence (last_tick_started=06:43:02, last_tick_completed=00:41:47), an SQL read-path audit query, and redeploy commands.

The doc is self-contained and directly usable as-is, including code excerpts and a copy-paste verification query.
