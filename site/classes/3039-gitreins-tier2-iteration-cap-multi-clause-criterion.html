Fix: gitreins Tier‑2 Cap exceeded: Iteration cap (100) reached on a multi‑clause criterion

Problem class: gitreins-tier2-iteration-cap-multi-clause-criterion Environment: GitReins Tier‑2 LLM judge on a local Go checkout (trouble-agent/mischief) Observed error: Cap exceeded: Iteration cap (100) reached (100.6 used). Increase max_iterations or split criteria.

Root cause

EvalCap (engine/eval_cap.py) charges 1.0 per LLM reasoning turn and 0.1 per tool call against max_iterations (default 100). The check is lenient: at 99.9 one more full turn is allowed, so usage is reported as 100.x, never a clean 100.

A criterion written as a conjunction of 3–4 independently checkable clauses cannot be closed with one verified_<index> PASS — the judge must prove each clause with its own tool calls, re-reads and command runs. A 4‑clause conjunction (merge‑base + doc grep + drift checker + live CLI) burns the budget before the loop can emit the final verdict JSON. On cap exhaustion engine/evaluator.py returns Verdict(verdict="INCOMPLETE", summary="Cap exceeded: …"), so an all‑green conjunction still becomes a red verdict.

Two things make it sticky: task complete already stamps the task complete, and verdicts persist to .gitreins/history/ + refs/gitreins/history as an audit trail. Raising the cap only defers the problem — the cure is a bounded criterion.

Exact fix — bounded re‑create recipe

# 0. Pin the tree every verdict must bind to
TREE=$(git rev-parse HEAD); echo "tree under judgment: $TREE"

# 1. Delete the starved task (active store only; history is untouched)
gitreins task delete MSF-CAP-OLD

# 2. Re-create with a BOUNDED criterion: 1-2 clauses, each naming a concrete file
gitreins task create MSF-FIX "Bounded: answer and contract agree" \
  "internal/foo/foo.go defines Answer() returning 42" \
  "docs/CONTRACT.md states the canonical answer is 42"

# 3. Start
gitreins task start MSF-FIX

# 4. Tier-1-only completion — do not re-enter the starved Tier-2 loop
gitreins task complete --force --skip-tier2 MSF-FIX

# 5. Real Tier-2 judge, asynchronously, against the same tree
export GITREINS_LLM_API_KEY="..."
gitreins judge MSF-FIX --async            # prints a job id

# 6. Poll
gitreins judge --status <job_id>

task delete removes only .gitreins/tasks.yaml's entry — the cap‑exceeded verdict survives in history. --skip-tier2 writes an honest Tier‑1‑only verdict instead of re‑starving. judge --async adds the green Tier‑2 verdict, and because the tree is unchanged, all verdicts stamp the same commit.

Prevention: split 3+ clause criteria at creation; a one‑off GITREINS_MAX_ITERATIONS=200 gives headroom but is not a cure; cap knobs live under evaluator: in .gitreins/config.yaml. A 100.x reading means budget exhaustion — a per‑criterion FAIL with real file:line evidence is a code bug, and this runbook does not apply to it.
