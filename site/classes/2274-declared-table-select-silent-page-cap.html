Diagnosed and verified. No project repo was present (only /workspace/problem.json), so I reconstructed the failure and proved the fix against a mock API that reproduces the exact silent-cap behavior.

Root cause

The API clamps limit to a hard cap of 100 and returns HTTP 200 with no Content-Range/X-Total-Count. Two callers trusted select():

  • len(select(limit=1000)) → always 100 once the store exceeds the cap (status/dump under-report).
  • "D-%03d" % (count + 1) → count is permanently 100, so the mint re-issues D-101 forever.

The subtle trap: len(page) < limit_asked only means "end of data" if limit_asked <= cap. Requesting 1000 makes the clamped 100 look like a short final page, so even a naive "stop when short" loop stops at 100. The paginator must request exactly the cap and keep going on full pages.

The fix

  1. select_all() loops limit=PAGE_CAP(100) & offset until a page is short; rejects page_size > cap; advances offset by rows actually returned; dedupes ids to fail loudly on offset-ignoring servers; orders by a unique key (id) for stable pagination.
  2. mint_decision_id() uses order=id.desc&limit=1, never a count.
