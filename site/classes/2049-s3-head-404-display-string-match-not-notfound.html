I diagnosed the bug, verified the fix against the real aws-sdk-s3 1.138.1 API, and wrote the complete solution to /workspace/solution.md.

What I verified (actually executed)

  1. Pure predicate unit tests — 8 passed, covering the empty-body 404, bare 404, typed NotFound, wire code, and negative cases (500, 403, NoSuchKey, partial-token match, no signal).
  2. Real-SDK API compile — the extraction bridge compiled with cargo check against the actual aws-sdk-s3 = 1.138.1 crate, confirming:
  3. SdkError::raw_response() -> Option<&HttpResponse> + status().as_u16()
  4. SdkError::as_service_error() + HeadObjectError::is_not_found()
  5. SdkError: ProvideErrorMetadata → .code()
  6. s3::error::DisplayErrorContext for full cause-chain rendering

Key findings

  • The old guard format!("{}", e).contains("NotFound") is dead code: SdkError::ServiceError's Display is the constant "service error", so it never matches. That's also exactly the opaque aws error: service error in the report.
  • Fresh pushes hit a 404 HeadObject; retries see present objects and never hit it — explaining the false-green retry tests.
  • The layered predicate head_failure_means_absent(status, typed_not_found, code) checks HTTP 404 → typed variant → exact code "NotFound", and is pure/testable without any endpoint.
  • Secondary DF-WARPFS-13: the integration test's MinIO-specific /minio/health/live gate causes silent early-returns reported as PASS; replaced with an S3-API probe plus ignored/panic! semantics.
