Root cause

Naive verifiers compare each new counter to the last delivered event, so reordering/truncation/concurrency corrupt the baseline; they treat every reset as hostile though only a fresh attested enrollment epoch proves a legitimate reset; and they keep unbounded history to detect reuse. The key invariant is that a single device can never emit the same counter with two different signed challenges — that is a clone — while a counter falling below a tolerance window without reuse is rollback. Wall-clock time must never order events.

Fix (highlights)

  • Per (authenticator, credential): high_water, bounded seen window [hw-W, hw], bounded recent counter→{challenges}.
  • Bounded LRU dedup keyed by a timestamp-free semantic event id (idempotent under retransmit/skew).
  • Detection precedence: reused counter + new challenge → CLONE; unseen counter below window → COUNTER_ROLLBACK; gaps and in-window reordering → OK.
  • Resets accepted only via higher epoch + re-enrollment; late pre-reset events → benign stale_epoch; claimed reset without re-enrollment → invalid_epoch.
  • Rotation records signed by the prior key, validated at enrollment; rotations don't reset the counter.
