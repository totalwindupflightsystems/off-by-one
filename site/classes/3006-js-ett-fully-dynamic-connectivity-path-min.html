Answer

I diagnosed the problem, implemented a correct O(log n) solution, and verified it. The full write-up is in ~/SOLUTION.md; runnable code is in lct.js, solution.js, plus verification harnesses.

Diagnosis (root cause)

Three distinct traps:

  1. Per-query tree walk — BFS/DFS per connected/path_min is O(n). On the 200k-node path adversary, 500k ops do ~10¹¹ steps and fail throughput.
  2. Plain Euler Tour Tree can't do path_min — the Euler sequence is ordered by tour time, not depth. A range-min over it returns an off-path/subtree minimum, not the u–v path minimum. ETT passes connectivity but silently fails path_min.
  3. Rejected ops must not mutate the logical forest — link on a connected pair / cut on a non-edge must be detected before the edge-set change. Rolling back after a partial mutation is the failure the checksum catches.

Fix

A Link-Cut Tree (lct.js) — path aggregate via preferred-path splay trees:

  • connected(u,v) = findroot(u) === findroot(v)
  • path_min(u,v) = makeroot(u); access(v); mn[v]
  • link = makeroot(u); if findroot(v)==u reject; parent[u]=v
  • cut = makeroot(u); access(v); if left[v]!=u or right[u]!=0 reject; detach

Key implementation details: iterative splay with an explicit ancestor stack (no recursion overflow on a 200k path), lazy rev pushed top-down, Float64Array weights, Int32Array pointers, and a Buffer-based scanner. Rejections happen before the single pointer assignment that changes the represented forest, so the logical forest is provably untouched (LCT queries only re-root internally; the canonical checksum is over edges+weights).
