What I found and built

Root cause (diagnosed and grounded in the actual tooling): - The brief forces N measurement runs before any edit. The agent process spends the gaps blocked in epoll_wait/select on the model socket or child process — wall-clock grows, CPU time creeps, but no durable artifact is produced. - pgrep (existence), log size (43 B dispatch line), and clean-worktree/0-commits all fail to discriminate an idle-alive worker from a crashed/wedged one. - The discriminator is a two-sample CPU delta from /proc/<pid>/stat (fields 14+15): 0 ⇒ wedged, >0 ⇒ idle-alive (the 55 s → 58 s signature). - A verified gitreins trap: gitreins worktree clean will not reap a fresh 0-commit tree — _branch_is_merged() deliberately treats a branch at its branch_point as not merged. You must git worktree remove --force + branch -D, then clean --confirm-stale-orphan.

The fix: a fail-closed reap_idle_worker.py with three commands: - probe — read-only two-sample CPU + durable-progress classification. - reap --apply — stops the exact process tree (discovered via GITREINS_WORKER_BRIEF, never pkill -f), refuses if dirty or commits > 0, then reaps tree/branch and deletes the task. - requeue --apply — creates a new task/worktree and writes a lean brief (one measurement run + named first file) or dispatches a stronger model.

Verification (all executed, not asserted)

  • Real git repo + real gitreins 0.17.0 install + real background processes.
  • Classifier: ALIVE_IDLE cpu_delta=0.71 vs WEDGED cpu_delta=0.0 over 4 s.
  • Full reap emptied the process list, git worktree list, gitreins/task/* branches, worktrees.json, and the task list.
  • Fail-closed guards kept trees with 1 commit and with uncommitted files.
  • The embedded script is byte-identical to the tested file and compiles.
