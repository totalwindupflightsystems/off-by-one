Fix: legacy-id collision in the Hermes-Canopy JSONL appender (board_append.py / append-jsonl-row.py)

Problem class: hermes-canopy-jsonl-appender-legacy-id-collision Environment: coding-hermes foreman tick · Language: Go (algorithm shown in Go + Python)

1. TL;DR

The appender mints the next event id from the file tail and validates it with a substring scan of the whole file. The Hermes-Canopy events.jsonl contains a legacy era whose ids were planted in a different namespace ("id":"347".."349" as strings, and "id":null + "seq":350..360), while the modern era restarted numeric id at 347 and is now at 1054. A tail-derived candidate therefore lands on an id that already exists (real old row) or on a number that merely appears as a substring in free text (e.g. seq:3500 contains 350). On REFUSE the code re-derives the candidate from a global max — which is both structurally wrong (it ignores the legacy seq namespace / string ids, so max(id)+1 can still be occupied) and non-deterministic under concurrent writers.

Fix: build the used-id set from parsed ids only (id ∪ legacy seq, ints normalized), and on REFUSE probe the refused id and walk upward one integer at a time until a genuinely free id is found. A substring false positive is therefore accepted (it is genuinely free); a real old row is skipped. Never re-derive from a global max.

2. Root-cause analysis

2.1 The real board shows the legacy namespace

hermes-canopy/.coding-hermes/board/events.jsonl (HEAD 5817b36, 1094 lines):

line 347  {"id":"347","seq":null,"task_id":"DF-HERMES-CANOPY-2/3/4"}   <- string id
line 348  {"id":"348","seq":null,...}
line 349  {"id":"349","seq":null,"task_id":"PL01-P1"}
line 350  {"id":null,"seq":350,...}                                    <- id planted in seq
...
line 360  {"id":null,"seq":360,...}
line 361  {"id":347,"event_type":"task_created","task_id":"DEPS-001"}   <- modern era restarts at 347
...
line 1094 {"id":1054,"event_type":"close","task_id":"RVW2-CANOPY-103"}

Measured over the whole file: max used (id ∪ seq) = 1054, max used id = 1054, and ids 340..365 are all occupied by a mix of id and seq rows. The gap set is only {145, 146}. This is exactly the "legacy era planted lower ids" shape: the legacy ids are not in the same namespace/scale as the modern ids, and boardctl validate deliberately tolerates the resulting duplicates on live boards.

2.2 Four independent defects

  1. Tail-derived candidate. next_id = last_row_id + 1. If the last physical line is a legacy row (string id, or id:null with seq), the derived start is low/zero and immediately collides with the occupied legacy range.
  2. Substring duplicate detection. if str(candidate) in file_text: is a substring test, not an identity test. "350" in ... matches "seq":3500, "id":3500, "...350..." in any detail/worker_summary prose. Result: a false REFUSE for an id that is actually free.
  3. Global-max fallback. On REFUSE, the code recomputes max(int(e["id"]) ...) + 1. That max ignores the legacy seq field and string ids, so max(id)+1 can itself be occupied (e.g. numeric max 400, legacy seq 401 ⇒ fallback returns the occupied 401). It can also loop when the max re-derives the same refused value, and it is unstable under concurrent writers.
  4. Namespace confusion. Legacy rows carry the id in seq and/or as a digit-string. A correct used-id set must normalise "347" → 347 and must union both keys.

2.3 Why "walk upward from the refused id" is the correct fallback

The id sequence is append-only and monotonic above the refused point. Once a candidate is refused:

  • if the refusal was a substring false positive, the exact probe proves the id is free and it is used unchanged;
  • if it was a real old row, the next legal id is the first free integer at or above it.

Walking upward is local, deterministic, and independent of the global maximum's namespace/parse quirks. It can never return an occupied slot and never skips a free slot that lies between the refused id and the next used id.

3. The exact fix

3.1 Algorithm (language-agnostic)

used   = { normalise(row.id) for every well-formed row }
         ∪ { normalise(row.seq) for every well-formed row }      # exact, never substring
start  = tail_candidate(rows)            # last row's id (id else seq) + 1
cand   = start
while cand in used:                      # REFUSE -> probe and WALK UPWARD
    cand = cand + 1
append(row with id = cand)               # no global-max recomputation

Refusal entry point:

resolve_next_free_id(refused):
    cand = refused
    while cand in used: cand += 1        # substring FP -> refused stays; real row -> skip
    return cand

3.2 Python patch for board_append.py / append-jsonl-row.py

Drop this in (and delete the substring test + global-max fallback):

import json, os, fcntl

def _as_int(v):
    # handles JSON int, digit-string legacy ids ("347"), ignores bool/None/prose
    if isinstance(v, bool):
        return None
    if isinstance(v, int):
        return v
    if isinstance(v, str) and v.strip().isdigit():
        return int(v)
    return None

def used_ids(lines):
    """Exact parsed-id set: `id` UNION the legacy `seq` field. Never substring."""
    used = set()
    for line in lines:
        line = line.strip()
        if not line:
            continue
        try:
            row = json.loads(line)
        except ValueError:
            continue                      # tolerant: skip torn/malformed lines
        if not isinstance(row, dict):
            continue
        for key in ("id", "seq"):         # legacy rows plant the id in `seq`
            n = _as_int(row.get(key))
            if n is not None:
                used.add(n)
    return used

def tail_candidate(lines):
    """Buggy basis preserved as the START only: last row's id (id else seq) + 1."""
    for line in reversed(lines):
        try:
            row = json.loads(line)
        except ValueError:
            continue
        base = _as_int(row.get("id"))
        if base is None:
            base = _as_int(row.get("seq"))
        if base is not None:
            return base + 1
    return 1

def next_free_id(lines, start=None):
    """First free id >= start. On REFUSE pass the refused id as `start`:
    a substring false positive is returned unchanged; a real old row walks up.
    Never re-derives from a global max."""
    used = used_ids(lines)
    cand = tail_candidate(lines) if start is None else start
    while cand in used:
        cand += 1
    return cand

Replace the buggy block:

# ---- BEFORE (buggy) ---------------------------------------------------
next_id = last_row["id"] + 1
if str(next_id) in open(events).read():                 # substring FP
    next_id = max(int(e["id"]) for e in rows) + 1        # ignores `seq`/strings
# -----------------------------------------------------------------------

# ---- AFTER (fixed) ----------------------------------------------------
with open(events, "a+", encoding="utf-8") as fh:
    fcntl.flock(fh, fcntl.LOCK_EX)      # read-compute-append must be serialised
    fh.seek(0)
    lines = fh.readlines()              # re-read UNDER the lock (fresh set)
    next_id = next_free_id(lines)       # tail start, then walk upward on REFUSE
    event["id"] = next_id
    fh.seek(0, os.SEEK_END)
    fh.write(json.dumps(event, ensure_ascii=False, separators=(",", ":")) + "\n")
    fh.flush(); os.fsync(fh.fileno())
    fcntl.flock(fh, fcntl.LOCK_UN)
# -----------------------------------------------------------------------

If the caller already has a separate refusal function that prints REFUSE id=..., route it through the probe instead of recomputing:

next_id = next_free_id(lines, start=refused_id)   # exact probe; walk upward

3.3 Go implementation (boardctl-style appenders / append-jsonl-row.go)

// idOf reads the integer id from the modern `id` field, else the legacy `seq`.
func idOf(row map[string]any) (int64, bool) {
    if v, ok := row["id"]; ok {
        if n, ok := toInt(v); ok {
            return n, true
        }
    }
    if v, ok := row["seq"]; ok {
        if n, ok := toInt(v); ok {
            return n, true
        }
    }
    return 0, false
}

func toInt(v any) (int64, bool) {
    switch t := v.(type) {
    case float64:
        return int64(t), true
    case json.Number:
        n, err := t.Int64()
        return n, err == nil
    case string:
        n, err := strconv.ParseInt(t, 10, 64)
        return n, err == nil
    }
    return 0, false
}

// nextFreeID is the fix: walk upward from the refused/tail candidate until an
// id that is not an EXACT member of the used set is found. Never substring,
// never a fresh global-max derivation.
func nextFreeID(candidate int64, used map[int64]bool) int64 {
    for used[candidate] {
        candidate++
    }
    return candidate
}

Boardctl's internal/board/write.go::appendEventLocked currently scans only r.Int("id") and then does nextID := maxID + 1, so a legacy seq at maxID+1 is silently overwritten. Harden it by unioning seq and walking:

used := map[int64]bool{}
var last *Row
for _, r := range rows {
    if id, ok := r.Int("id"); ok {
        used[id] = true
        last = r // style/timestamp template = last NUMERIC id row (SCHED-GAP-1572)
    }
    if id, ok := r.Int("seq"); ok { // legacy namespace must be part of the set
        used[id] = true
    }
}
var maxID int64
for id := range used {
    if id > maxID {
        maxID = id
    }
}
nextID := nextFreeID(maxID+1, used)

4.4 Regression guards to keep

  1. Exact membership only — forbid str(id) in file_text in review; require a parsed-id set (id ∪ seq, int-normalised).
  2. On REFUSE, assert candidate not in used before writing; the write loop must be while cand in used: cand += 1.
  3. No global-max fallback — grep -n "max(.*id" board_append.py must not find an id recomputation in the refusal branch.
  4. Lock + re-read — hold flock(LOCK_EX) across read-compute-append so two concurrent foremen cannot mint the same id.
  5. Add a CI test with the fixture above asserting next_free_id() == 402 and that next_free_id(start=<substring-only id>) returns that id unchanged.

5. Rollout notes

  • The fix is append-only and changes no existing rows; the board's historical duplicate ids (id vs legacy seq) remain untouched (validate already tolerates them). Only the next id changes: it is now the first genuinely free slot above the refused candidate instead of global_max+1.
  • Because the used set includes legacy seq, no new id can ever shadow an old legacy row again — the exact failure the problem statement reports.
  • Deploy by replacing the id-resolution block in the appender(s); no data migration is required. Re-run the appender once and confirm the appended line's id is absent from used_ids().
