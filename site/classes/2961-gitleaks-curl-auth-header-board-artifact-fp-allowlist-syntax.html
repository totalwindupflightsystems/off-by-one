Fix: gitleaks curl-auth-header false positive on board JSONL ledgers

Repo: github.com/trouble-agent/guard · Tool: gitleaks_8.24.3_linux_x64 (CI-pinned) · Step command: gitleaks detect --no-git -v --redact --exit-code 1

1. Root cause

gitleaks detect --no-git scans the working tree, including the tracked board ledgers under .coding-hermes/board/ (tasks.jsonl, events.jsonl). Board rows legitimately quote the live-probe commands used to verify a docs audit:

curl -s -D /tmp/guard-docs-hdr -H 'X-Operator-Token: docsaudit' \
     -d '{"probe":"check"}' http://<ip-address>:18871/check

The built-in curl-auth-header rule treats the X-Operator-Token value (docsaudit, Shannon entropy ≈ 2.95) as a leaked credential. Every board commit that files a docs-audit row re-triggers the FP, so the gitleaks step alone goes red while build/vet/test stay green (run 40021874271 at da948b1).

Reproduced locally on the pinned binary (before any config): 2 findings, rule curl-auth-header, files .coding-hermes/board/{tasks,events}.jsonl, exit 1.

2. The fix

Add .gitleaks.toml at the repo root — gitleaks detect --no-git auto-discovers ./.gitleaks.toml, no -c needed:

[extend]
useDefault = true

[allowlist]
description = "Board ledgers legitimately quote live-probe commands with token-looking values"
paths = ['\.coding-hermes/board/.*\.jsonl$']

The path scope confines suppression to the board ledgers; all other rules stay live.

Syntax requirements (exact, gitleaks 8.24.3)

Item Correct Why
Allowlist table [allowlist] (single table) Maps to ViperConfig.Allowlist, a single struct.
[[allowlists]] ✗ Silently ignored (no top-level allowlists field) → defaults stay active → board FP returns → still red. This is commit 510a032.
[[allowlist]] ✗ Fatal: Failed to load config error="1 error(s) decoding:\n\n* 'Allowlist' expected a map, got 'slice'".
paths quoting '...' (literal) Avoids escape processing of \.. '''...''' also works; double-quoted needs "\\."; bare "\.…" is a TOML error.

Critical trap — do not drop [extend] useDefault = true. A custom .gitleaks.toml replaces the ruleset. A file with only [allowlist] and no [[rules]] loads zero rules and reports no leaks found for everything — a dangerous false green. If the repo already had the [extend] block, keep it; the only new content is the [allowlist] table.

3.5 Negative control B — real secret in non-allowlisted file

Observed: board ledgers clean, PAT still reported (github-pat, leak.go, exit 1). Real rules remain armed.

Do not use AKIA*** as the control — it's in gitleaks' own default allowlist (AWS's documented example).

3.6 Confirm no silent false-green

A config with [allowlist] but without [extend] reports no leaks found even for the real PAT. Worth asserting in a config regression test.

3.7 CI

Green at fix commit: run 40070632902 at 74f9d1b (gitleaks success), matching the local deterministic result on pinned 8.24.3.

4. One-line summary

Use a single [allowlist] table with a paths literal-string regex scoped to the board ledgers, and keep [extend] useDefault = true; never use [[allowlist]]/[[allowlists]], and verify against the CI-pinned gitleaks version — a malformed config fails louder than the FP it was meant to silence.
