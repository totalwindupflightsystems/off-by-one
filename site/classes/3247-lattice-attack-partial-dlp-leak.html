Diagnosis (root cause)

The problem as stated is ill-posed: a single DH public key plus 64 known LSBs of a 256-bit exponent is not an HNP/lattice instance. After removing the known bits there are still 192 unknown bits, and recovering them is a 192-bit discrete log. No lattice reduction applies to one equation.

The solvable version requires an ensemble of d modular equations with one secret and known multipliers t_i:

v_i = α t_i mod q,   v_i mod 2^k known   (i = 1..d)

LSB leak → HNP by 2^{-k}-scaling: α' t_i ≡ a_i' + m_i (mod q) with α' = 2^{-k}α and |m_i| < q/2^k.

Exact fix

Lattice Λ = qZ^d + Zt (covolume q^{d-1}), with the rank-safe basis {q e_1…q e_{d-1}, w}, w = (t_d^{-1}t_1,…,t_d^{-1}t_{d-1},1). Solve CVP for target a', then α' = p_d·t_d^{-1} mod q, α = 2^k α' mod q. The file contains a self-contained pure-stdlib lll+babai implementation (optional fpylll fast path).

  • Info-theoretic threshold: d·k > 256 (with k=64, d ≥ 5; d=4 is exactly ambiguous).
  • Why LLL fails near threshold: LLL's Hermite factor 2^{(d-1)/4} forces an extra margin ½log₂d + (d-1)/4 bits/sample, so reliable recovery starts a few bits above dk = n.
  • Non-consecutive leaks: uniqueness bound is d·ρ > 1, i.e. ρ > 1/d, independent of which bits leak. Every-5th-bit ⇒ ρ=1/5 ⇒ attack stops at d ≤ 5, works at d ≥ 6. (A sparse pattern additionally needs a generalized multi-modulus lattice; the density bound is the hard limit.)

Verification (actual output, 256-bit group, k=64)

d=4  d*k=256  success=0/6     # exactly at threshold
d=5  d*k=320  success=6/6
d=6  d*k=384  success=6/6

d=5 sweep: k=51 (margin -1) 0/6 | k=52 (margin +4) 4/6 | k=56 6/6

density: d=2,ρ=1/3 → ~64 secrets/signature ; d=3,ρ=1/3 → ~1 ; d=6,every-5th → 1

The last line confirms #candidates = 2^{n(1-dρ)} and the exact dρ = 1 boundary.
