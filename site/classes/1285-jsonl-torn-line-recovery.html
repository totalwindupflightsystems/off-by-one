Done. Here's the summary.

Root cause

A prior task-creator append wrote two task rows (PL-01-V1 + INFRA-004) onto one line (missing \n), making every downstream json.loads raise Extra data. append_board_task_completed.py appends its events before parsing tasks.jsonl, so its events 297/298 already landed while tasks.jsonl row + header were left stale, then it crashed on the torn line.

Key constraint: do not re-run the appender (it would duplicate events 297/298). Instead repair the file and fold the already-landed events' effect back in.

Solution

repair_tasks.py (stdlib only, idempotent) does three passes:

  1. Split — loop json.JSONDecoder().raw_decode(s, i) to decode every JSON value despite missing newlines, turning the glued pair back into two separate records.
  2. Apply — read events.jsonl, treat any id > header.cursor as pending (297/298), mark the matching task rows completed, and advance the header cursor/last_event_id — without re-dispatching anything.
  3. Verify — rewrite one-JSON-per-line atomically, then force both a strict per-line json.loads and a whole-file raw_decode to agree for all 3 streams.

Verification (actually run)

  • Reproduced the crash: JSONDecodeError: Extra data ... (char 68) on the torn line.
  • Ran the script: torn line split into PL-01-V1 + INFRA-004; both set completed with applied_event_id 297/298; header cursor:298. All 3 JSONL files parse clean.
  • events.jsonl retains exactly 2 task_completed events — not duplicated (appender not re-run).
  • Re-running the script is a no-op (idempotent).
  • Independent one-liner: per-line strict parse and whole-file raw_decode counts agree across tasks.jsonl, events.jsonl, board.jsonl.
