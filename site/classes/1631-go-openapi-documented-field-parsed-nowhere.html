Answer

Diagnosis and fix are complete and verified. The full, self-contained solution is written to /home/kara/solution.md (and /workspace/solution.md).

Root cause

ttl_seconds was documented in the OpenAPI for POST /agents/{id}/inbox but implemented nowhere:

  1. deliverRequest had no ttl_seconds field — Go's JSON decoder silently drops unknown keys.
  2. Both stores hard-coded ExpiresAt = CreatedAt + 24h (memory_store.go, postgres_store.go), which also overwrote the zero value, making "never" inexpressible.
  3. deliverResponse never reported expires_at.
  4. No "never expires" representation existed for consume paths: zero time.Time is Before(now), so Retrieve/Stats/PurgeExpired would treat it as long expired; Postgres's NOT NULL CHECK (expires_at > created_at) column can't hold it.

Plus RemoteStore.Deliver dropped the field entirely.

The fix (commit ea0d5ea)

  • Pointer DTO: TTLSeconds *int on deliverRequest and InboxEntry (absent ≠ explicit 0), with maxTTLSeconds = MaxInt64 / int64(time.Second) bounds; negative/overflow → 400.
  • One resolver resolveMessageExpiry in store.go (DefaultMessageTTL = 24h), shared by both backends: nil→24h, 0→zero time (never), n→CreatedAt+n, <0→ErrInvalidStoreInput. Idempotent.
  • Memory store: resolver + !entry.ExpiresAt.IsZero() && exp.Before(now) guards in Retrieve, Stats, PurgeExpired.
  • Postgres store: pgTimestamptz writes timestamptz 'infinity' for never (satisfies the CHECK, never purged, always claimable); expiryFromTimestamptz normalizes infinity back to zero on scan. No schema change.
  • RemoteStore: forwards ttl_seconds verbatim (only when set).
  • Handler: resolves expiry and echoes it in the 201; OpenAPI updated with bounds + expires_at.
