Diagnosis (root causes)

  1. The stated checksum is wrong. SQLite WAL does not use SHA-256. It uses a 64-bit rolling checksum over native-endian 32-bit words (s0 += x0+s1; s1 += x1+s0, mod 2³²). A WAL built with SHA-256 digests is rejected by sqlite3. SHA-256 is only usable as an independent manifest.
  2. WAL integers are big-endian, and the frame checksum is chained (each frame seeded by the previous frame's checksum; frame 0 seeded by the header checksum). So one torn frame invalidates the entire tail — physically intact later commits are still discarded.
  3. Commit boundary = any frame whose dbsize field (frame header offset 4) is nonzero. Recovery must truncate there.
  4. Salt rotation on restart: after a full checkpoint the next writer resets the WAL in place (ckptseq+1, new salts) leaving stale old-generation frames in the tail. Verified: frames 0..5 new salt, 6..19 old salt. A scanner that ignores salts would resurrect an older DB image.
  5. A destroyed WAL header is recoverable, but only by rebuilding the exact original header (page size from the DB header, salts from frame 0, brute-forcing the small checkpoint sequence), because frame 0's checksum is seeded by the header checksum.

Fix

wal_torn_recovery.sh with three subcommands:

./wal_torn_recovery.sh demo   /tmp/wal-demo                       # full end-to-end
./wal_torn_recovery.sh corrupt my.db my.db-wal --seed 1 --frame 2 # inject tear
./wal_torn_recovery.sh recover my.db my.db-wal --expected tags.txt --out ./recovered

It parses/rebuilds the header, walks frames validating salt + chained native checksum, keeps the newest commit frame, truncates the WAL, verifies PRAGMA integrity_check on a sandbox copy, diffs committed-transaction markers to report lost txns, and emits a SHA-256 frame-chain manifest. No .recover/.dump.

Verification (all executed)

  • integrity_check → ok on every repaired WAL.
  • Manual recovery produces identical surviving rows to SQLite's own WAL recovery (diff empty).
  • Exhaustive fuzz — corrupt every frame in a single-generation WAL and every current-generation frame after salt rotation, plus header reconstruction and truncation: 37/37 pass.
  • Zeroed 32-byte WAL header → reconstructed and recovered all frames with zero loss.
  • Corruption shapes tested: page body, frame salts, whole frame header, whole frame 0, whole WAL header, empty/truncated WAL (table in §3.5).

One documented limitation: the physical lost_commits count under-counts if the tear destroys a commit frame's own dbsize marker; --expected tags.txt gives the exact logical lost set (used by the demo/fuzz).
