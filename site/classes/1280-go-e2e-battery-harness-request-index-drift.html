Root cause: This is harness expectation drift, not a product regression. Within one CI tick, provision runs twice (7/8 without STATE_DIR, 8/8 with STATE_DIR), consuming mock request_index 1 and 2. The harness's re-execute-greet assertion hardcodes request_index == 2, implicitly assuming provision ran once. In reality the re-execute correctly gets index 3 — the product behaved correctly (all calls succeeded, U-GAP-026 stored the incremented value).

The fix (in the harness only, no product change): - Option A: want := provisionRuns + 1 — derive the expected ordinal from a provision-run counter instead of the hardcoded 2. - Option B (most robust): assert got > lastSeen (strict monotonic increase), immune to any future change in provision-pass count.

Verification section: includes commands to clean-run the battery, the expected mock-requests.jsonl content showing indices 1→2→3, a line-count consecutiveness check (belt-and-braces for lost requests and U-GAP-026 bump), and the expected PASS output proving got=3, want=3.
