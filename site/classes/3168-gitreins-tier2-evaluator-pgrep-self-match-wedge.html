Summary

Root cause: pgrep -f PATTERN matches a process's full /proc/<pid>/cmdline. The evaluator's poll loop (sh -c 'sleep 29; ...; pgrep -f "go test -count=1 ..." && echo RUNNING || echo DONE') embeds that pattern in its own command line, so pgrep always finds the poller itself. DONE is unreachable, even after the test exits — a permanent wedge. pkill -f during recovery self-matches the same way.

Fix (primary): Change the tier-2 evaluator prompt to a deterministic completion contract: - Captured PID: launch the test in background, poll kill -0 "$tpid". - Sentinel file: launch ( <test> >log 2>&1; echo $? > /tmp/agent_test.done ) &, poll [ -f done ]. - Every poll loop must be bounded (emit TIMEOUT) and fail closed to verdict=none:<reason>, never loop forever.

Also shipped a drop-in agent-wait helper and an optional poll_guard preflight, plus an exact-PID recovery runbook (kill -TERM judge + poller, then gitreins judge --status <job-hex>).

Verified in-sandbox: - Buggy poller → 3/3 RUNNING with no test process present (self-match). - kill -0 fix → transitions to DONE on exit (4/4 correct). - Sentinel fix → DONE rc=0 once marker appears. - pgrep ... | grep -v $$ shown insufficient when the parent shell also holds the pattern (3/3 RUNNING). - Exact-PID detection via ps --ppid + kill reaped the poller without collateral (CPU ~0%, read_bytes unchanged). - agent-wait helper smoke-tested: prints DONE rc=0.

Note: the installed gitreins symlink is broken in this sandbox (&lt;tool&gt; → missing pipx venv), so verification targeted the shell semantics that cause the wedge, not a live gitreins run.
