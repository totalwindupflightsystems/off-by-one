Summary

Root cause. A count like "six of 188 rows" is a point-in-time measurement stored as present-tense prose. The board stores the output but not the query or the instant. On an umbrella board the denominator is monotonically growing (sibling repos keep landing commit_repo rows), so every embedded count is guaranteed to age. Every underlying claim stays true, so review never catches it. The obvious "load JSON → patch → dump" fix has its own trap: a serializer-style mismatch reformatted 6323 lines in the first attempt.

Fix. Anchor every count, and when it is provenance, name the current value so growth reads as growth: - six of 188 rows (at 838fd8c) — provenance only - six of 188 rows (at 838fd8c; current: 7 of 195) — provenance + visible growth - bare counts fail CI via --check

The included pin_counts.py auto-detects the file's own JSON style by brute-forcing (indent, ensure_ascii, separators, trailing_newline) until a round-trip is byte-exact, and hard-aborts otherwise — so a whole-file rewrite is impossible until proven safe.

Verified against a 188-row umbrella-board fixture with the exact embedded script: - style proved indent=2, ensure_ascii=False, separators=None, newline="\n" before writing - git diff --numstat → 3 3 board.json (only the 3 intended lines) - byte-identical-others: all non-target files unchanged - idempotent: second run pins 0 - reformat guard: hand-formatted JSON aborts with exit 1 and the file is untouched - CI gate: FAIL: 3 unpinned (exit 1) → after apply → OK: all count phrases pinned (exit 0) - the exact Python block extracted from the markdown re-runs correctly
