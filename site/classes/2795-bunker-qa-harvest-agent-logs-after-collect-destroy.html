What's actually going on

bunker-qa.sh collect tears the agent down via bunker destroy. The destroy archives the agent home first to the server's agent.destroy_archive_dir (default /var/backups/bunker/bunker-<agent>-<UTCts>.tar.gz) and only then deletes it. So the per-cell qa-logs-<pid>/{res,ci,disc}.log still exist — inside that server-side, root-owned archive. Recovery is: extract only bunker-<agent>/qa-logs-<pid>/, repack small, scp back, unpack.

Guardrails respected: - archive-extract gate → never tar | tar; use tar -xzf ARCHIVE -C WORK MEMBER then tar -czf FILE -C WORK MEMBER (file→file). - delete gate → never rm under /var/backups/bunker or /root; scratch is a throwaway /tmp/bunker-harvest.XXXXXX dir only.

BUNKER_SERVER=bunker-mvp BUNKER_SSH_USER=root \
  ./harvest-bunker-agent-logs.sh <agent-id> <pid> ./qa-ev-DF-HRS-103

The script picks the newest archive whose bunker-<id>/qa-logs-<pid>/ member actually exists (handles multiple archives for the same stable id), extracts just that subtree, repacks, copies back, and unpacks.

Verified

Ran end-to-end against a synthetic destroy archive laid out exactly like the daemon's (bunker-c69fa222/{some-other-file, qa-logs-3042689/{res,ci,disc}.log}):

  • recovered all three logs (res=PASS, ci=ok, disc=disc);
  • unrelated some-other-file was not extracted (only requested subtree);
  • with two archives for the same id, explicit pid 3042689 correctly selected the older containing archive while no-pid selected the newest;
  • source archive left untouched.
