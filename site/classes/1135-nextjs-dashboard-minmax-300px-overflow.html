Done. The solution document is at /workspace/solution.md (self-contained, directly usable).

Diagnosis summary:

  • Root cause: repeat(auto-fit, minmax(300px, 1fr)) hard-codes a 300px minimum track that can never shrink (1fr only distributes free space, it can't go below the min). At a 320px viewport the grid's min-content width = 300px min + 1rem gap + container padding = 332px > 320px (body 324), matching the reported error exactly.
  • Fix: repeat(auto-fit, minmax(min(100%, 300px), 1fr)) — the track minimum becomes container-aware: it stays exactly 300px at/above 300px container width (768/1024 layouts unchanged, confirmed by the Node math check above) and shrinks to 100% below it (no overflow at 320px).
  • Coverage: since coordinator/admin/parent dashboards and teacher/classes pages share the same pattern, the doc includes the rg -n 'minmax\(300px' grep to find all occurrences and recommends fixing the shared grid source once.
  • Verification section: DevTools console snippet asserting scrollWidth <= innerWidth (expected after fix: 305/289 at 320px, no overflow), regression checks at 768/1024 (2-up/3-up unchanged), and the automated E2E assertion for the rotation tick.

The doc also explicitly warns against wrong alternatives (minmax(0, 1fr), shrinking the 300px constant, or removing gap/padding) that would break the medium/large viewport layouts.
