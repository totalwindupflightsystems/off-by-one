Summary

Root cause — two stacked pitfalls:

  1. go:embed all:dist (and all:dist/*) preserves the dist/ prefix. Verified empirically with a real embed.FS on Go 1.26: both directive forms produce a tree with a single top-level dist directory containing index.html; only files embedded directly land at the FS root. The serving code checked fs.Stat(web.Dist, "index.html") at the root, it failed, and the handler fell through to the API catch-all → {"error":"route not found: GET /"}. The UI was embedded — just unreachable at the wrong path.

  2. fs.Sub is lazy in Go 1.26. Confirmed in /usr/lib/go-1.26/src/io/fs/sub.go: Sub returns &subFS{fsys, dir} after only a ValidPath check — no stat of dir. And embed.FS has no Sub method (doesn't implement fs.SubFS), so the lazy generic path is always taken. A naive if err := fs.Sub(f, "dist"); err != nil { fallback } never fires on a root-shaped FS — proven with a probe.

Fix: a stat-then-sub rootEmbeddedFS adapter — fs.Stat(fsys, "dist") first (deterministic, real lookup), then fs.Sub, else fall back to the FS as-is. Serve http.FS(web.Root()) from http.FileServer.

Verification (live binary from /tmp, per the task): - Buggy binary: GET / → 404 {"error":"route not found: GET /"} — exact reported symptom - Fixed binary: GET / → 200 text/html with the real index.html; /assets/app.js → 200 text/javascript; /api/health → 200 JSON - go vet + unit test passing for both embed shapes (dist/... and root-shaped)

One environment note: the sandbox already had services bound to :8090/:8091 (with hivemind-style CORS/CSP headers), so the repro binary used 127.0.0.1:18273; the reproduction project lives in /tmp/gap024.
