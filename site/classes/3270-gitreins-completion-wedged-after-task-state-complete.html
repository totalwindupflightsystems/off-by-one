Root cause

In gitreins/cli.py::cmd_task_complete, the task store was mutated before evaluation and verdict persistence:

task = tm.complete(args.id, force=force)          # writes .gitreins/tasks.yaml status=complete
...
result = judge.evaluate_task(task, skip_tier2=skip_tier2)
_persist_result(workdir, task, result)            # writes .gitreins/history/.../verdict.json

TaskManager.complete() persists immediately, and _persist_result() is explicitly non-fatal (swallows all errors). So if the evaluator hangs/crashes (the observed >10 min) or .gitreins/history is unwritable, the row says complete while no commit-bound verdict.json exists. A retry repeats the identical ordering, so it "wedges again." The merge gate (worktree_manager._find_verdict) can never resolve a verdict for commit f20974af….

Secondary board-side causes: boardctl update --status complete refuses retries once a task_completed event exists (duplicate-completion), and its evidence gate only checks that the run directory exists — not that verdict.json is present and commit-bound.

Fix

Evaluate → persist → require success → only then mark complete. _persist_result now returns a disposition (hash/dry-run/disabled/error), and cmd_task_complete refuses and leaves the task in its prior status when the verdict fails to persist. Existing callers that ignored the return value are unaffected.

Verification

Reproduced deterministically by making .gitreins/history unpersistable:

Build Result
unpatched 0.21.0 status: complete, 0 verdicts, exit 0; retry repeats
patched 0.21.0 refuses with status: in_progress, 0 verdicts, exit 1; after repair → complete with a verdict.json whose commit == HEAD

The embedded E2E test fails on unpatched and passes on patched. The solution also includes a full recovery runbook (preserve f20974af… + Tier‑1 evidence, reopen both stores, produce the verdict with gitreins judge, verify the commit binding, then close the board with --evidence-run-id).
