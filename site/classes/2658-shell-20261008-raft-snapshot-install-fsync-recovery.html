Root cause

The classic temp → rename → manifest → truncate log sequence has seven reachable crash states (F1–F7). The fatal ones are:

  • F4/F5 — trusting a filename (snap-<idx>) or a stale .tmp/directory entry, so a torn or leftover file is loaded as a valid snapshot and commitIndex is set from its name.
  • F6 — a separate manifest can be fsynced before/after the data it references; no write ordering makes that safe across filesystems.
  • F7 — when the chosen snapshot fails validation, code clamps commitIndex downward. That silently loses committed entries — the actual safety violation.

The fix

Make the snapshot one self-describing, checksummed file (512-byte header with index/term/length/sha256/commit, then payload, then DATAEND trailer), so data and its commit metadata are durable or torn together. The single commit point is one atomic rename inside one directory:

fsync(temp)      # bytes durable BEFORE the name      (Rule 1)
rename -> final  # atomic, same FS
fsync(dir)       # name durable                       (Rule 2)
write_stable(commit = max(commit, idx))               # only after Rule 2
truncate log > idx                                    # idempotent, last

Recovery wipes staging, validates every candidate, keeps the highest valid snapshot, quarantines the rest, discards the torn log tail, and computes:

commit   = max(stable.commit, snapshot.index)
coverage = max(snapshot.index, lastIntactLogIndex)
if commit > coverage: NEEDS_RESYNC = 1   # I6 — never clamp, never roll back
