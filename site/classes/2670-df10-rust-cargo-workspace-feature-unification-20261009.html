What I found

I installed Rust 1.99.0 and empirically verified the mechanism end-to-end. The reported error is a Cargo feature-unification failure, not a serializer bug:

  • serialize_struct is an unconditional required method of the serde::Serializer trait, so the Serializer in the error is a concrete serializer type whose struct-serialization support lives behind a different feature.
  • Cargo compiles a package once per build unit with the union of all features requested by every workspace member. A member's #[cfg(feature = "std")] code path gets activated by another member, while the dependency is compiled without the feature that actually provides serialize_struct → E0599.

Key facts I proved with cargo

Scenario resolver 1 resolver 2 what fixes it
build-dependency enables dep/std, normal dep wants no_std leak fixed resolver = "2"
normal dep unified across two workspace members leak still leaks feature forwarding + [workspace.dependencies]

Critical nuance: resolver = "2" alone does not fix the normal-dependency channel. I verified the exact error persists with resolver = "2" until the forwarding feature is completed.

The fix (two parts)

  1. Complete the feature forwarding — the feature that gates the code must enable the feature that provides the method: toml std = ["codec/std", "codec/ser"] # was ["codec/std"]
  2. Centralize + resolver — workspace root gets resolver = "2" and a single [workspace.dependencies] entry with default-features = false, with each member opting in explicitly.

A virtual workspace defaults to resolver = "1" even when members are edition 2021 (Cargo emits a warning about this) — a common hidden cause.

The document includes the full copy-pasteable reproduction, the verified before/after outputs, diagnosis commands (cargo tree -e features -i, -f "{p} {f}", --duplicates), the serde mapping, and guidance for genuinely mutually-exclusive feature sets.
