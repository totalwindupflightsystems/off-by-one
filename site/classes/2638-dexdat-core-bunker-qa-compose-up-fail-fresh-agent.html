Fix: dexdat-core-bunker-qa-compose-up-fail-fresh-agent

Problem class: dexdat-core-bunker-qa-compose-up-fail-fresh-agent Repo/owner: dexdat/dexdat-core compose stack + the shared fleet harness ~/.hermes/scripts/bunker-qa.sh (docker-deploy / chaos-shutdown cells) Host/agent: fresh JIT bunker agent (bunker-mvp), evidence /tmp/bunker-qa-evidence-20261007T232503Z-3148607.jsonl (agent c8dd31de) Verdict after diagnosis: the compose up failure is the documented rootless-Docker OpenSearch memlock: -1 class; the reason it looked like a "mid-pull" mystery is a second, independent harness defect — fail_detail() keeps the head of the log instead of the error at its tail.

1. Symptom

Full QA battery on a fresh agent: fresh-install, ci-pass, native green; docker-deploy and chaos-shutdown both FAIL with

docker compose up -d --build  →  rc=1

The evidence row is dominated by cold-pull progress plus two non-errors (The "DEEPSEEK_API_KEY" variable is not set. Defaulting to a blank string. / OPENAI_API_KEY), and the real line is gone. chaos-shutdown fails the same way because its first verb is docker compose up -d (same create path, no --build).

2. Root-cause analysis

Two defects compound. Either one alone would not produce this signature.

2.1 Primary: rootless dockerd cannot set RLIMIT_MEMLOCK (type 8) to unlimited

  • The harness points Docker at the agent's rootless daemon: bunker-qa.sh:1670 → export DOCKER_HOST="unix:///run/bunker/$agent/docker.sock".
  • The compose stack the battery runs (docker compose up -d --build, no -f) auto-discovers the base file. Its opensearch service declares: yaml environment: [ ..., bootstrap.memory_lock=true ] ulimits: memlock: { soft: -1, hard: -1 } # unlimited
  • Under a rootless runtime, raising the hard RLIMIT_MEMLOCK above the inherited value requires CAP_SYS_RESOURCE, which an unprivileged rootless dockerd does not have. Container creation dies with error setting rlimit type 8: operation not permitted.
  • This is the repo's own documented breakage class (GAP-114: "Rootless Docker rejects ulimits memlock: -1 → EPERM → container never starts → docker compose up ABORTS → every redeploy fails"; catalog class rootless-docker-opensearch-ulimits-memlock, dexdat-core commit 9770a65). The known fix exists only in deploy/bunker/docker-compose.bunker.yml — the build override is never layered by the QA battery, so the base -1 is what actually runs on the agent.

The failure lands "mid-pull ~74 s in" only because the error is emitted after the cold pulls finish; the visible prefix is pull progress. docker compose up genuinely returned 1 at container create, not during the pull.

2.2 Secondary: fail_detail() hides the error (evidence truncation)

bunker-qa.sh:955 (baked into the generated qa-run.sh):

fail_detail() { # <rc> <logfile> <cmd...> — ACTIONABLE-FAILURE CONTRACT
  local frc="$1" flog="$2"; shift 2
  printf 'rc=%s cmd=[%s] — %s' "$frc" "$*" \
    "$(grep -v '^[[:space:]]*$' "$flog" 2>/dev/null | head -40 | tr '\n' '|' | cut -c1-1500)"
}

Docker prints the real error last, after hundreds of pull-progress lines. head -40 | cut -c1-1500 keeps only the first 40 non-blank lines (pull #N … lines), so the EPERM line is cut off. Reproduced in this sandbox: with 80 progress lines the old function loses operation not permitted; with 5 it keeps it.

Hypothesis Verdict Evidence
.env missing / env_file mandatory ruled out long-form required:false already applied (QA-DEXDAT-CORE-7)
${DEEPSEEK_API_KEY} / ${OPENAI_API_KEY} are fatal ruled out bare ${VAR} is level=warning; docker compose config exits 0 with blank values (verified below)

3. Exact fix

3.1 Product/harness: make the QA compose rootless-safe

The QA battery must run the rootless variant of the stack. Prefer layering the existing override; if that file does not exist in the checkout, apply the canonical rootless OpenSearch settings to whichever compose file the battery discovers.

A. Canonical rootless-safe OpenSearch block (same values as dexdat-core 9770a65):

  opensearch:
    environment:
      bootstrap.memory_lock: "false"            # rootless cannot mlockall unlimited
      OPENSEARCH_JAVA_OPTS: "-Xms512m -Xmx512m" # cap heap; 8 GB agent slice
    ulimits:
      memlock: { soft: 65536, hard: 65536 }     # finite, always settable unprivileged
      nofile:  { soft: 65536, hard: 65536 }

B. Make bunker-qa.sh layer the override (preferred) — docker-deploy cell (~line 1924) and the chaos-shutdown cell (~line 2150):

# Replace:  DC_CMD="docker compose up -d --build"
# with:     discover the rootless/bunker override and layer it when present
DC_FILE=""
if [ -f deploy/bunker/docker-compose.bunker.yml ]; then
  DC_FILE="-f docker-compose.yml -f deploy/bunker/docker-compose.bunker.yml"
fi
DC_CMD="docker compose $DC_FILE up -d --build"

Do the same for the chaos up verb so both cells exercise the same, corrected path:

docker compose $DC_FILE up -d

If there is no override, ship the §3.1-A block in the base file instead (this makes the base file safe for both rootful and rootless).

3.2 Harness: stop throwing away the error

Replace fail_detail() so it keeps the head and the error-bearing tail:

fail_detail() { # <rc> <logfile> <cmd...> — ACTIONABLE-FAILURE CONTRACT
  local frc="$1" flog="$2" head err; shift 2
  head="$(grep -v '^[[:space:]]*$' "$flog" 2>/dev/null | head -3 | tr '\n' '|' | cut -c1-350)"
  err="$(grep -aiE 'error|failed|refused|denied|not permitted|no space|cannot|unable|manifest|unauthor|toomanyrequests|conflict' \
            "$flog" 2>/dev/null | tail -4 | tr '\n' '|' | cut -c1-900)"
  printf 'rc=%s cmd=[%s] — head: %s — ERR: %s' \
    "$frc" "$*" "$head" "${err:-<no error-shaped line; see $flog>}"
}

This alone converts every future failure in this family from "mystery mid-pull FAIL" into a named cause.

3.3 Guard: grade a rootless rlimit mismatch as an environment signal

After the docker-deploy run, if dc.log matches the rootless rlimit signature, grade it as an environment-incompatible compose (INFO/UNVERIFIED, not a repo defect) until the compose is fixed:

if [ "$dc_rc" -ne 0 ] && grep -qE 'error setting rlimit type 8|operation not permitted' "$LOGD/dc.log"; then
  cell docker-deploy INFO "compose up failed on a rootless rlimit (memlock type 8): $(fail_detail "$dc_rc" "$LOGD/dc.log" "$DC_CMD")"
fi

python3 - <<'PY'
import resource
try:
    resource.setrlimit(resource.RLIMIT_MEMLOCK, (resource.RLIM_INFINITY, resource.RLIM_INFINITY))
    print("INFINITY OK (unexpected under rootless)")
except (ValueError, PermissionError, OSError) as e:
    print("INFINITY -> FAIL:", e)               # rootless: EPERM
resource.setrlimit(resource.RLIMIT_MEMLOCK, (65536, 65536))
print("65536 OK:", resource.getrlimit(resource.RLIMIT_MEMLOCK))
PY

Expected rootless result: line 1 fails with Operation not permitted (errno 1) and line 2 succeeds; docker compose config shows memlock.soft=-1/memory_lock: "true" for the file the battery used.

5. Verification (performed here; daemon unavailable in the off-by-one sandbox)

The sandbox has no Docker daemon, but the three load-bearing claims were executed directly.

(a) The rootless EPERM mechanism — Python + raw C:

$ python3 memlock_probe.py
UID: 1000
current memlock: (8388608, 8388608)
set -1/-1 : FAIL -> not allowed to raise maximum limit
set 65536 : OK  -> (65536, 65536)
$ cc memlock_c.c -o memlock_c && ./memlock_c
setrlimit(RLIMIT_MEMLOCK, -1,-1) -> Operation not permitted (errno=1)

RLIMIT_MEMLOCK = 8 — exactly the rlimit type 8 in the hidden compose error.

(b) The evidence-truncation defect and the fix (synthetic cold-pull log):

# 80 pull lines (#N Pulling/Downloading/Extracting) + env warnings + real error last
$ OLD fail_detail …            # grep -v blank | head -40 | tr '\n' '|' | cut -c1-1500
OLD LOSES the real error (cuts at line 40)
$ NEW fail_detail …
… — ERR: Error response from daemon: failed to create task for container: … error setting rlimit type 8: operation not permitted: unknown|

(c) The fix renders correctly with Compose 2.40.3 (world-readable config, no daemon):

6. Why the "flake" framing was wrong

The submission noted the QA36 webdav load-flake precedent and said "attribute before patching". This is not a load flake: it reproduces deterministically on fresh rootless agents (bunker-mvp 2026-10-07, bunker-las-04 2026-09-30), the failing object is a fixed container-create syscall error, and it disappears the moment the rootless-safe compose is used. The recurrence is a path problem (battery runs the base file instead of the rootless override), not scheduling noise. Fix the path and the truncation together; either alone leaves the class possible again.
