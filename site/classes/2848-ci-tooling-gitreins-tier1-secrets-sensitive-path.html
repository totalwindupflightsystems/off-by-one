Fix: GitReins Tier‑1 secrets false positive on a tracked .env.example

Problem class: ci-tooling-gitreins-tier1-secrets-sensitive-path Package in play: gitreins 0.17.0 Rule: REVIEW-GITREINS-027 — SENSITIVE PATH (credential-store path class) Symptom: judge verdict passed=false with the only failed step being Tier‑1 secrets, reporting .env.example: SENSITIVE PATH (credential-store path class), even though the judged change never touched .env.example and gitreins guard reports the secrets lane clean.

Do not read passed=false as an implementation failure. When the only failed step is secrets and the finding is this marker, the agent's diff is almost certainly fine. The gate is failing on a pre‑existing tracked path, not on the change under review.

1. Root cause analysis

The finding is scope-dependent, not content-dependent.

The rule is a PATH test, never a content test. In engine/guard_manager.py:

# engine/guard_manager.py  (gitreins 0.17.0)
SENSITIVE_PATH_PATTERNS: tuple[str, ...] = (
    ".env",
    ".env.*",          # <-- matches ".env.example"
    ...
)

_SENSITIVE_PATH_MARK = "SENSITIVE PATH (credential-store path class)"   # line 164
_SENSITIVE_OVERRIDE_PREFIX = "sensitive-path override applied: "        # line 168 (the ~:166 rule region)

is_sensitive_path(".env.example") returns True unconditionally — no file content is read.

The judge scans the whole tracked tree; gitreins guard scans the change set only.

  • gitreins guard (diff scope) → GuardManager._check_secrets() scans the staged index (staged_only=True) or, with --scope working-tree, exactly self.changed_files. A tracked, unchanged .env.example is not in that set, so the lane is clean.
  • The judge's Tier‑1 secrets step is built by engine/pipeline.py::_secrets_step_run() and runs:

python # engine/pipeline.py (gitreins 0.17.0) — the judge path, ~line 1681 gm = GuardManager('.') r = gm._builtin_secrets_scan(staged_only=False) # whole workdir

staged_only=False walks every tracked file (_workdir_files() + _worktree_tracked_paths()). Every tracked path matching SENSITIVE_PATH_PATTERNS fails the step regardless of content — the designed behaviour for real credential stores, but a false positive on a committed, secret-free template.

The whole-workdir scan is intentional (DF-012): the judge grades already-committed changes, so gitleaks protect --staged cannot see them. Do not "fix" this by narrowing the judge to the diff — that reintroduces DF‑012. Fix the class membership instead.

Evidence trail (how to confirm in seconds):

# Which Tier-1 step failed, and with what marker?
jq -r '.stages.tier1.steps[]
       | select(.id=="secrets")
       | "exit=\(.data.exit_code)\n\(.data.output)"' .gitreins/history/**/verdict.json

# The flagged path is tracked but NOT part of the judged change:
git ls-files --error-unmatch .env.example
git diff --name-only HEAD~1..HEAD        # README.md only — .env.example absent

Conclusion: scope mismatch between the judge's whole-tree path class and the change-set guard.

2. Fixes

Two independent, composable fixes. Use A to unblock immediately with zero engine changes; adopt B to kill the false positive fleet-wide.

Fix A — per-repo documented override (immediate, non-silent)

The engine ships an explicit, auditable override read from .gitreins/config.yaml by _sensitive_path_override_globs(). Add the narrow template glob:

# .gitreins/config.yaml
guards:
  secrets: true
  # REVIEW-GITREINS-027 documented override. .env.example is a committed,
  # secret-free template (key names / placeholders only), not a credential
  # store. The override is recorded in the secrets output — never silent.
  sensitive_paths:
    allow:
      - ".env.example"

Then commit the config change:

git add .gitreins/config.yaml
git commit -m "config: allow .env.example sensitive-path template (REVIEW-GITREINS-027)"

Notes:

  • allow globs are matched with fnmatch against both the full workdir-relative path and the basename, so ".env.example" also covers frontend/.env.example.
  • Use the narrow name. Do not allow ".env.*" — that would also suppress the path class for .env.production, .env.local, etc., which are real credential stores.
  • .gitreins/** is harness state and is already excluded from the secrets scan.
  • The override is not a whole-file free pass: it suppresses only the path-class finding. Content patterns still run, so a real key pasted into an allowed template still fails.

Fix B — durable engine-level template exemption (fleet-wide)

Conventional, secret-free dotenv templates should be exempt from the path class exactly like the existing test-fixture exemption (_is_sensitive_fixture_path). Patch engine/guard_manager.py in the deployed source (e.g. ~/gitreins/engine/guard_manager.py) or in the installed package:

4. Operational guidance

  1. Triage before patching. Read verdict.json → stages.tier1.steps[].data.{exit_code,output}. If the only failing step is secrets and the output contains SENSITIVE PATH (credential-store path class), the diff is not the problem — check the path's membership in the change set (git diff --name-only) vs git ls-files.
  2. gitreins guard clean + judge secrets FAIL is expected whenever a tracked sensitive-class path exists outside the diff. The guard is diff-scoped; the judge is tree-scoped (DF-012).
  3. Prefer the narrowest fix. Fix A for a single repo, Fix B when many repos share the same .env.example. Never allow ".env.*" wholesale, and never narrow the judge to the diff.
  4. Overrides are loud. A suppressed finding leaves a sensitive-path override applied: <path> line in the step output; grep the verdict for it during review. An override is never silent, so it remains audit-visible.
  5. No silent weakening. Both fixes leave the content scanner and every other sensitive path (.env, .env.* other than the four template names, *.pem, *.key, .ssh/**, credentials*, service-account*.json, config/database.yml) fully enforced.
