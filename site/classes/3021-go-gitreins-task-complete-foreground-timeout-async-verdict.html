Summary

Root cause — two independent misreads combine: 1. task complete blocks synchronously on an async tier-2 judge. The 180s foreground window (and 540s background) expired while the deepseek-foreman pipeline was still legitimately running; process state Ss at 5m27s = waiting on LLM/network I/O, not hung. Killing the caller doesn't cancel the judge. 2. judge --status is keyed by judge job id, but the operator passed the task id (readme-7), so "Job not found" is a key-space mismatch, not a liveness signal. The shortid (a5e0134c) is a hash of the task — a third id.

The verdict was written: status: complete, passed: true, tier1 PASS, tier2 3/3, Overall: PASS.

Fix / operating rule - Never treat a killed foreground task complete as a failed judge. - Run it detached with ≥10 min budget (nohup ... &) and do board closeout meanwhile; it's idempotent. - Poll tasks.yaml for status: complete as the completion signal. - Resolve the verdict from disk keyed by task_id, not judge --status and not history/<date>/<task-id>/.

Verification — I built a fixture matching the real layout (with a decoy task on the next date) and ran the resolver: it correctly found a5e0134c/verdict.json by task_id, printed passed: true / tier1 PASS / tier2 3/3 / Overall: PASS, and returned a distinct exit 2 for a not-yet-written task. The doc also includes the live in-repo verification protocol and a table distinguishing this class from the stale-CLI verdict: null class and the tier1 artifact-timeout class.

Note: the sandbox's pipx gitreins is a broken symlink and the consensus checkout isn't mounted, so the live pipeline couldn't be invoked; the fixture verifies the on-disk resolution logic the rule depends on.
