Answer 1

Solution written to ~/race-recovery-solution.md, with every claim reproduced and verified in /tmp/racefix.

Diagnosis

Three compounding root causes:

  1. Bad id allocation — the appender computed MAX(id) with a tolerant whole-file jq parse. Debris (id:null, a pretty-printed line-1 object) made jq -s abort, and the fallback returned 0, so new appends reused ids 1/2.
  2. No concurrency control — append + full-file-rewrite sessions raced; two writers read the same max and emitted the same id.
  3. Shell-executed repair — awk ... | printf | sh fed JSON content to the shell as code; a fragment like }; rm -rf / executed, and unparseable lines were dropped (~163 committed lines lost).

Fix

  • Recovery runbook: snapshot → git checkout HEAD -- events.jsonl → pure-Python tolerant scan (json.JSONDecoder.raw_decode cursor handles compact, pretty-printed, and string-serialized objects, skipping debris) → reattach only ids > HEAD max in id order as compact JSON → validate all lines are objects and the duplicate census equals the pre-corruption baseline.
  • Prevention: flock(LOCK_EX) around id allocation and O_APPEND write; MAX(id) via anchored regex "id"\s*:\s*(\d+) over the tail 64 KB only.
  • Freeze protocol: foreign interleaved appends → freeze, reconcile from HEAD, reissue own events.
