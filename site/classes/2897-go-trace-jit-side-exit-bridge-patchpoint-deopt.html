Tracing JIT for a Register VM: hot-loop recording, guard side exits, bridge compilation, and patchpoint invalidation

1. Problem

We need a tracing JIT for a small register-based bytecode VM:

  • detect hot loops,
  • record one loop trip and linearize it into IR,
  • emit guards for every assumption (types, array bounds, integer overflow, call targets),
  • compile the trace to native Go code rather than interpreting bytecode,
  • handle guard failure by resuming the interpreter at the exact pc with the exact register state,
  • support nested side exits and bridge compilation,
  • invalidate/repair already-compiled traces when type feedback changes (patchpoints), and
  • prove equivalence with the pure interpreter on a fuzz corpus and show a real speedup on a benchmark that starts monomorphic and becomes polymorphic mid-run.

The working implementation is in ~/tracejit (module tracejit).

2. Root-cause analysis

A naive tracing JIT fails for several reasons that are easy to miss:

  1. Recording the wrong value for a branch guard. A conditional branch guard must record the observed condition value, not the jump decision. If jmpifnot records !cond, the first execution of the trace immediately fails because the condition has not changed; the JIT then side-exits on every iteration and never runs the trace. The recorded branch direction is encoded by the next IR instruction, so the guard must check cond == observed.

  2. Re-entering a trace after a side exit at the trace entry. If a guard fails at the first instruction of the trace (which is also the loop header), setting vm.PC = sideExit.PC and looping back to TryExecute finds the same trace again. The JIT must execute the failing instruction in the interpreter to make progress. This is what caused the original overflow test to spin and hit the step limit.

  3. Bridge recording mutating state on failure. Bridge recording executes bytecode. If the path does not return to the loop header (or throws), the recording attempt must restore the VM snapshot, otherwise the next interpreter step starts from a corrupted state.

  4. Retrying an unrecordable loop forever. If recording fails because the observed path leaves the loop, the header's hot counter must be cleared or the header blacklisted; otherwise ShouldRecord returns true on every iteration and recording is retried forever.

  5. Stale traces after type-feedback changes. A call site that was monomorphic when the trace was compiled must not keep using the old inlined target when dynamic feedback changes. Feedback needs a patchpoint: a mutable validity flag referenced by the compiled call guard. When a new function is observed at the site, the old patchpoint is invalidated and the trace that uses it is discarded and recompiled.

The implementation below fixes all five points.

3.1 Branch guards record the condition value

vm/jit.go:

case JmpIf, JmpIfNot:
    v := vm.Regs[in.A]
    if v.K != KBool {
        return nil, fmt.Errorf("record: branch on non-bool")
    }
    // The guard records the value of the condition, not the jump
    // decision.  The direction of the branch is already encoded by
    // which instruction follows in the trace.
    return []IR{{Kind: IRGuardBool, A: in.A, Want: v.B, PC: pc}}, nil

The compiled guard then checks v.B == n.Want.

3.2 Guard compilation and side exits

Each IR node that can fail gets one or more side-exit ids. compileTrace allocates them:

switch n.Kind {
case IRAdd, IRSub, IRMul:
    n.ExitType = t.addExit(n.PC, "type")
    n.ExitOverflow = t.addExit(n.PC, "overflow")
case IRDiv:
    n.ExitType = t.addExit(n.PC, "type")
    n.ExitDivZero = t.addExit(n.PC, "divzero")
case IRAGet:
    n.ExitType = t.addExit(n.PC, "type")
    n.ExitBounds = t.addExit(n.PC, "bounds")
case IRGuardBool:
    n.ExitGuard = t.addExit(n.PC, "guard")
case IRCall:
    n.ExitType = t.addExit(n.PC, "type")
    n.ExitOverflow = t.addExit(n.PC, "overflow")
    n.ExitCall = t.addExit(n.PC, "call")
}

The IR is compiled into a chain of Go closures that call the next operation directly. There is no bytecode or IR dispatch at run time:

case IRAdd:
    next = func(vm *VM) (int, error) {
        a, b := vm.Regs[n.B], vm.Regs[n.C]
        if a.K != KInt || b.K != KInt {
            return n.ExitType, nil
        }
        x, y := a.I, b.I
        r := x + y
        if (r > x) != (y > 0) {
            return n.ExitOverflow, nil
        }
        vm.Regs[n.A] = Int(r)
        vm.JITSteps++
        return nxt(vm)
    }

A side exit carries the interpreter pc to resume at and the register state is already correct because the guard failed before its instruction was executed.

3.3 Side exit handling, nested exits, and bridges

TryExecute runs a trace and, on a side exit, either follows an existing bridge, records a new bridge when the exit is hot, or makes progress by executing exactly one interpreter instruction:

if se.Bridge != nil && se.Bridge.Valid && se.Bridge.Code != nil {
    t = se.Bridge
    continue
}
if se.Hits >= j.bridgeThreshold && !j.recording {
    // snapshot VM, record a bridge from se.PC to the original header
    // ...
    br := j.record(vm, se.PC, header, depth+1)
    if br != nil {
        se.Bridge = br
        vm.PC = header
        return true, nil
    }
    // restore snapshot on failure
    // ...
}
// Execute the failing instruction in the interpreter so Run makes
// progress even when the side exit is at the trace entry pc.
vm.PC = se.PC
if stepErr := vm.step(); stepErr != nil {
    return true, stepErr
}
return true, nil

The nested-side-exit test (vm/nested_test.go) produces two successive divergence points and verifies that two bridges are compiled and that the second bridge is executed (BridgeRuns > 0).

3.4 Patchpoints for call-site type feedback

ObserveCall records the observed builtin id at a call site. When the id changes, the old patchpoint is invalidated and every trace that references it is marked invalid:

func (j *JIT) ObserveCall(pc int, fn int32) {
    cs := j.getCallSite(pc)
    cs.Seen[fn]++
    if cs.Patch == nil {
        cs.Patch = &Patchpoint{PC: pc, Fn: fn, Valid: true}
        return
    }
    if cs.Patch.Fn == fn {
        return
    }
    old := cs.Patch
    old.Valid = false
    j.Stats.PatchpointInvalidations++
    j.invalidateTracesUsing(old)
    cs.Patch = &Patchpoint{PC: pc, Fn: fn, Valid: true}
    j.Stats.Recompiles++
}

The compiled call guard checks the patchpoint validity before comparing the function id:

case IRCall:
    next = func(vm *VM) (int, error) {
        if n.Patch != nil && !n.Patch.Valid {
            return n.ExitCall, nil
        }
        fn := vm.Regs[n.B]
        if fn.K != KFunc || fn.F != n.Fn {
            return n.ExitCall, nil
        }
        // ...
    }

Invalidated traces fall back to the interpreter; the next hot iteration recompiles a trace for the new feedback value. This is the "discard-and-recompile" form of patchpoint repair.

5. Using the implementation

The VM exposes:

  • vm.NewVM(program) and vm.RunPure(program, limit) for the interpreter,
  • vm.NewJIT(program) for the tracing JIT,
  • vm.Value, vm.Instr, vm.Program to build bytecode,
  • vm.PolyProgram(n) and vm.NestedProgram(n) for the built-in benchmark programs.

To run a program with the JIT:

p := vm.PolyProgram(200000)
v := vm.NewVM(p)
j := vm.NewJIT(p)
j.SetThreshold(1)
j.SetBridgeThreshold(1)
v.JIT = j
res, err := v.Run(-1)

j.Stats reports traces, bridges, invalidations, recompiles, trace runs and side-exit hits. j.TotalSideExitSites() reports the number of guard bail-out sites compiled across all live traces and bridges.
