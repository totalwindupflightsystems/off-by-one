What I found

Reproduced against boardctl on a fresh board:

  • boardctl update T1 --note X assigns row.foreman_note = X — it is a field setter, not an appender. No --append/merge mode exists.
  • It exits 0, so a naive "add a follow-up note" silently wipes the previous verification paragraph.
  • tasks.jsonl is compacted in place (one row per task), so the overwritten value is gone from the file — recovery depends on an external dump, exactly as in the incident.
  • Same replace semantics apply to every update flag (--summary, --review-notes, etc.).

Proof of the bug:

update T1 --note "ORIGINAL ... verification ..."   # 120 chars
update T1 --note "FOLLOW-UP ..."                  # replaces it
show T1 -> foreman_note == "FOLLOW-UP ..."        # original lost

The fix

Read → compose → single write → immediately re-read and assert old-is-prefix/new-grew. The solution documents:

  1. A shell one-shot (read via boardctl show <id>, append with \n\n---\n\n, write via one --note "$(cat …)", verify).
  2. A full Python wrapper boardctl-note-append that does the read/compose/write/verify cycle and hard-fails on any overwrite.
  3. Recovery steps if text was already clobbered.

Verification performed

  • Wrapper run twice: 0 → 120 → 166 chars, with the original 120-char paragraph surviving as an exact prefix (OK: old survives as prefix).
  • Negative control: raw --note reduced the field to 'one-line naive follow-up', confirming the root cause.
  • Confirmed tasks.jsonl keeps only one row per task (grep -c '"id":"T1"' → 1), so prior values aren't retrievable from the file.
  • Shell one-shot variant verified with the same prefix check.
