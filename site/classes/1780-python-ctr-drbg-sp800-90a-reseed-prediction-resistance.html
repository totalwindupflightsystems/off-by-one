Summary

The trap in this problem class: a CTR_DRBG can be self-consistent (round-trips its own output) yet violate SP 800-90A in ways the CAVP intermediate states expose. Three defects matter most:

  1. Block_Cipher_df two-phase construction. IV = i || 0^(outlen-32) (counter in the leftmost 32 bits), BCC = CBC-MAC with zero chaining, then a second CTR-expansion using the derived key K'=leftmost(temp,keylen). Getting the IV endianness or skipping phase 2 makes instantiation mismatch immediately.
  2. The pre-generate CTR_DRBG_Update is conditional. Per §10.2.1.5.2 step 2, it runs only when additional_input ≠ Null; the post-generate update (step 6) always runs with 0^seedlen. Applying the pre-update unconditionally leaves instantiate/reseed correct but breaks every generate.
  3. PR consume semantics. In a prediction-resistance generate, the additional input is passed to the reseed, then cleared, and the generate algorithm gets None (§9.3.1 steps 7.1–7.4).

Boundary fixes implemented: validation strictly before state creation (InstantiationError, no _key/_v created); reseed_counter set to 1 and enforced against reseed_interval; max_number_of_bits_per_request checked; a rejected reseed sets reseed_required so the next generate refuses instead of silently using the old state; and the mandatory post-generate Update destroys the old (Key,V) for backtracking resistance.

Verification (all reproduced in the doc)

  • 720/720 NIST CAVP AES-256 use df 512-bit vectors pass across pr_false (240), pr_true (240), and no_reseed (240) — including the published intermediate (Key,V) states at INSTANTIATE, RESEED, and both GENERATE calls.
  • 30/30 property checks pass: atomic short-seed rejection, counter enforcement, 64 distinct (Key,V) pairs under mixed additional input, reseed changes the pair, compromised-state forward determinism with failed naive rewind, PR unpredictability from the pre-reseed state, and failed-reseed lockout.
  • Bundled AES-256 core cross-checked against cryptography.
