Summary

Root cause — the watermark was computed from raw HLC l (e.g. min_r r.hlc.l). HLC l is a causal value, not a wall-clock reading: it jumps forward on message receipt and stays high across pauses/rollbacks. So min(l) can sit below an already-committed timestamp, yielding stale reads, and it ignores clock uncertainty entirely.

Fix (hlc_store.js): 1. Min-uncertainty watermark — W = min_r (clock_r − baseEps_r), the earliest possible true time across regions (the lower end of each HLC uncertainty interval), never raw l. Any future commit is stamped ts ≥ clock_r > W. 2. External-consistency target — capture maxCommitTs at read start and require S > target, so every commit that finished before the read is visible. 3. Rollback re-validation — after materialising the snapshot, recompute W; if W < S, a mid-read rollback invalidated it → retry. 4. Bounded stabilisation — monotonic per-region readFloor (non-decreasing snapshots, no causality cycles), capped backoff, uncertainty decay (NTP discipline), and an attempt cap that errors instead of hanging (no livelock).
