Answer

Fix: 9router appends data: [DONE] to a non-streaming chat.completion

Component: 9Router central gateway (decolua/9router), OpenAI-compatible POST /v1/chat/completions (the ds/ DeepSeek lane). Symptom: with stream omitted, a 200 response is a valid chat.completion JSON body immediately followed by the SSE sentinel:

...\"system_fingerprint\":\"aeb56401ca74e127821c4f9126dcb669\"}data: [DONE]\n\n

Root cause

9Router treats an omitted stream as streaming. In open-sse/handlers/chatCore.js (v0.5.95, a99cf57):

const providerRequiresStreaming = PROVIDERS[provider]?.forceStream === true;
let stream = providerRequiresStreaming ? true : (body.stream !== false);   // <-- BUG

body.stream !== false is true when the key is absent — backwards from the OpenAI spec (omitted ⇒ non-streaming). deepseek/ds (open-sse/providers/registry/deepseek.js) does not set forceStream, so a stream-less request is routed down the SSE path.

The upstream then returns a plain application/json body (no SSE framing). The passthrough transform in open-sse/utils/stream.js flushes the leftover buffer verbatim, then unconditionally terminates the “SSE” body with the OpenAI sentinel:

if (mode === STREAM_MODE.PASSTHROUGH) {
  if (buffer) {                                   // whole JSON body, no trailing \n
    controller.enqueue(sharedEncoder.encode(buffer));   // emitted with no `data:` prefix
  }
  if (!streamDoneSent && !isGeminiFamily) {
    controller.enqueue(sharedEncoder.encode("data: [DONE]\n\n"));  // <-- sentinel
  }
}

Response is sent as Content-Type: text/event-stream, so the client sees <json>data: [DONE]\n\n. The correct fix is the routing decision: a client that did not ask for SSE must not enter the SSE path.

open-sse/utils/bypassHandler.js has the same wrong default for the Claude-CLI naming/warmup path:

const stream = body.stream !== false;   // <-- BUG (same default)

Exact fix

Canonical upstream fix (PR #4427), two one-line changes:

--- a/open-sse/handlers/chatCore.js
+++ b/open-sse/handlers/chatCore.js
@@ -133,7 +133,7 @@
   const clientRequestedStreaming = body.stream === true || sourceFormat === FORMATS.ANTIGRAVITY || sourceFormat === FORMATS.GEMINI || sourceFormat === FORMATS.GEMINI_CLI;
   const providerRequiresStreaming = PROVIDERS[provider]?.forceStream === true;
-  let stream = providerRequiresStreaming ? true : (body.stream !== false);
+  let stream = providerRequiresStreaming ? true : (body.stream === true);

--- a/open-sse/utils/bypassHandler.js
+++ b/open-sse/utils/bypassHandler.js
@@ -73,7 +73,7 @@
   if (!shouldBypass) return null;

   const sourceFormat = detectFormat(body);
-  const stream = body.stream !== false;
+  const stream = body.stream === true;

Apply from the repo root:

git apply /workspace/nonstream-default.patch   # patch file also written to the sandbox

Semantics after the change (all OpenAI-spec compliant):

stream in request provider forceStream behaviour
omitted false application/json (fixed)
omitted true text/event-stream (unchanged)
false false application/json (unchanged)
true any text/event-stream + data: [DONE] (unchanged)

Optional defense-in-depth

Not required once the default is fixed, but if a non-stream path ever receives SSE it can strip the sentinel:

const json = JSON.stringify(restoreToolNames(translatedResponse, toolNameMap));
const clean = json.endsWith("data: [DONE]") ? json.slice(0, json.lastIndexOf("data: [DONE]")).trimEnd() : json;
return { success: true, response: new Response(clean, { headers: { "Content-Type": "application/json", ... } }) };
