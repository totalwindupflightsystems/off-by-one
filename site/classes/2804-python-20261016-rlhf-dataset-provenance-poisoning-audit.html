What was wrong

/workspace/problem.json was a bare problem class with no starter code, dataset, error message, or stack trace — so I diagnosed the class from first principles and built the entire pipeline from scratch.

Root cause: the shard merge treats each preference record as an independent, id-keyed atom of evidence, but the attack operates on the semantic equivalence class of a comparison and on multiplicity:

  1. Identity = id/exact-hash → paraphrased and fresh-id copies escape dedup.
  2. Independence assumption → k copies of one flipped comparison become k correlated votes; effective sample size is clusters, not records.
  3. Pairwise, not transitive, matching → A~B, B~C can hold while A/C differ; only the transitive closure captures amplification. Naive closure is O(N²) time/memory — infeasible, so teams skip it.
  4. Label direction treated as identity → chosen/rejected swaps are new records.
  5. Provenance/privacy collapse → witnesses usually leak raw prompts/user ids; independent-record CIs understate uncertainty under duplication.

The fix

A pure-stdlib pipeline (provenance_audit.py):

  • Relabel-invariant canonical form (sorted responses) → exact-equality union channel + HMAC input.
  • MinHash (128) + 32×4 banded LSH → candidate pairs only; exact-Jaccard confirm on candidates; Union-Find transitive closure. No O(N²) graph.
  • Influence amplification: cluster size, N/C, max_cluster_size, transitive_chain (edges ≤ size−1).
  • Adversarial relabel detection at pair-key and cluster level (so paraphrased flips are caught).
  • Stratified cluster-robust bootstrap for Δ = mean(observed) − mean(de-poisoned), plus naive bootstrap to expose the design effect.
  • Greedy minimal witness (cluster + one record per label), emitted as HMAC commitments only.
  • Privacy: salted HMAC content commitments, contributor pseudonyms, k-anonymity suppression, key never emitted.
