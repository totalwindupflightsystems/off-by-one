Answer

The concrete, verified defect in this battery is the last_tick board-write: the duckdb header declares last_tick TIMESTAMP, but the write path binds a bare integer tick. DuckDB rejects that at bind time:

duckdb.ConversionException: Conversion Error: Unimplemented type for cast (INTEGER -> TIMESTAMP)

The fix: pass a datetime, not an int. Because the container's duckdb session timezone is America/Bogota (UTC−5), the naive-UTC construction is the only portable, byte-exact pattern — verified below. Both datetime.utcfromtimestamp() (deprecated on Python 3.14) and to_timestamp() / aware datetimes are timezone traps.

# board_write.py — fixed pattern (tj52_board_write.py successor)
import datetime as dt
import duckdb

def last_tick_dt(tick: int) -> dt.datetime:
    """tick -> naive UTC datetime for a TIMESTAMP column (portable, no deprecation)."""
    # classic equivalent: dt.datetime.utcfromtimestamp(tick) — deprecated on 3.12+
    return dt.datetime.fromtimestamp(tick, dt.timezone.utc).replace(tzinfo=None)

def write_board(db_path: str, verdict_rows: list[dict]) -> int:
    """rows come from interruptor_bridge.py JSON protocol:
       [{"verdict": "allow|block|sandbox-modify|parse-error", "tick": 57}, ...]"""
    con = duckdb.connect(db_path)
    con.execute(
        "CREATE TABLE IF NOT EXISTS board ("
        " run_id VARCHAR, verdict VARCHAR, tick BIGINT, last_tick TIMESTAMP)"
    )
    prepared = [
        (r.get("run_id"), r["verdict"], r["tick"], last_tick_dt(r["tick"]))
        for r in verdict_rows
    ]
    con.executemany("INSERT INTO board VALUES (?,?,?,?)", prepared)
    con.close()
    return len(prepared)

Two footguns surfaced during verification, worth documenting in the helper:

  1. Aware datetimes (dt.datetime.now(dt.timezone.utc), +02:00 offsets) are silently converted to the session timezone by duckdb before storage — 12:30+02:00 stored as 05:30 here. Always pass naive UTC datetimes.
  2. to_timestamp(tick) in SQL is also session-TZ dependent (to_timestamp(58) stored 1969-12-31 19:00:58). If you prefer the SQL side, pin UTC explicitly: to_timestamp(tick)::TIMESTAMP WITH TIME ZONE AT TIME ZONE 'UTC'.
