What the writeup contains

Root-cause analysis — the coordination service computes a correlation each 60s cycle (hence the correlations=1 log) but nothing persists because (1) no correlations table exists in the sqlite migration set, (2) persistCorrelations is un-wired (main.go never calls SetCorrelationRepository, so the write path is a silent no-op), and (3) there's no dedup to prevent duplicate open-correlation inserts across cycles.

Exact fix — complete file contents: - migrations/sqlite/028_correlations.{up,down}.sql — dedicated table (a correlation spans N incidents; incident_log is per-incident), plus indexes and a stable correlation_key. - internal/models/correlation.go — Correlation, CreateCorrelationInput.Validate(), CorrelationType/Status constants, and a fingerprint method used for dedup. - internal/database/repository/correlation_repository.go — interface + sqlite impl: Create, GetByID, ListOpen, ListByPrimaryIncident, UpdateStatus. - skynet.go — SetCorrelationRepository setter, rewritten persistCorrelations that skips any identical open correlation (cycle 2 → 0 inserts, no re-INSERT every 60s) and fails loudly with ErrCorrelationRepoNotSet rather than logging "complete" over a dead store, plus the adapter. - cmd/coordination/main.go — the missing wiring call. - RED-GREEN test TestCoordinationCorrelationPersisted against a real migrated sqlite temp DB: asserts exactly 1 open row after cycle 1 and still 1 after cycle 2 (dedup), and exercises ListByPrimaryIncident.

Verification section — sqlite3 count checks across two 60s cycles (expect 1 then 1), the go test run (RED before, GREEN after), plus full build/test/vet regression steps.

Caveat stated in the doc: no Helios checkout exists on this machine, so I couldn't compile/execute against the real repo — the code is written to the exact interfaces/paths named in tick #351 and should be dropped into the real tree and verified with go build ./... and the RED-GREEN test.
