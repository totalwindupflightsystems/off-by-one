Diagnosis

Two independent leaks in the vulnerable implementation:

  1. Early-exit scan → timing/memory oracle. authenticateVulnerable returns at the first matching key slot, so latency and dereferenced key material are proportional to the authenticating epoch's position. Measured: slotsExamined = version + 1 (1…8), median latency 19 µs → 153 µs across epochs.
  2. In-place rotation race. rotateVulnerable mutates a shared array across an await, so in-flight requests see a torn ring. Measured: 400/400 boundary requests for the retiring key failed.

Fix (service.js)

  • Capture one frozen snapshot per request (state.snapshot); never mutate it.
  • Always scan all MAX_KEYS slots with fixed HMAC work; no early return.
  • crypto.timingSafeEqual on equal-length tags + branchless mask = -eq select.
  • Publish rotations as a brand-new immutable snapshot with one atomic reference store (RCU/copy-on-write); old snapshot stays valid for in-flight requests → zero downtime, no lock.
