Fix: docs-pinned-schema-version — never hardcode schema_version in docs

Root cause

SCRATCH_INSTANCE.md contained a runnable recipe whose expected output was frozen to a concrete schema version:

curl -s http://localhost:8080/health | jq '.schema_version'
# expect: 47

The schema version is not a property of the recipe — it is a property of the binary that happens to be running. Every migration that lands bumps the counter, so the documented 47 silently becomes wrong. The recipe does not crash; it just starts failing for readers with no obvious cause, and the doc rots independently of the code. Two distinct defects are present:

  1. A volatile value is encoded as a literal in prose/example output.
  2. The reader is given no way to obtain the correct value, so there is nothing to reconcile against when it changes.

Exact fix

Two changes, applied together:

  1. Replace the concrete number with the symbolic N.
  2. Add a clause directing the reader to read the real value from their own binary via /health.

Before → after (the whole diff):

-curl -s http://localhost:8080/health | jq '.schema_version'
-# expect: 47
+`schema_version` is reported by the binary you are actually running and moves
+as migrations land, so never hardcode it. Read the expected value `N` from
+your own binary via `/health` first:
+
+```bash
+N=$(curl -s http://localhost:8080/health | jq '.schema_version')
+curl -s http://localhost:8080/migrations | jq ".applied == $N"
+```

If the recipe compares against a second source, thread N through instead of restating it:

./migrate status --expect "$N"      # pass the observed value, don't re-embed it

Verification

1. Reproduce the rot (fixtures)

mkdir -p /tmp/dpv/{before,after}

cat > /tmp/dpv/before/SCRATCH_INSTANCE.md <<'EOF'
### Recipe: verify the running schema
```bash
curl -s http://localhost:8080/health | jq '.schema_version'
# expect: 47

EOF

cat > /tmp/dpv/after/SCRATCH_INSTANCE.md <<'EOF'

Recipe: verify the running schema

schema_version is reported by the binary you are running and moves as migrations land, so never hardcode it. Read N from your own binary via /health first:

N=$(curl -s http://localhost:8080/health | jq '.schema_version')
curl -s http://localhost:8080/migrations | jq ".applied == $N"

EOF


### 2. Guard the invariant with a checker

```bash
cat > /tmp/dpv/check.sh <<'EOF'
#!/usr/bin/env bash
# Fail if any doc hardcodes a concrete schema_version.
set -euo pipefail
doc="${1:?usage: check.sh <doc>}"
if grep -Eqn 'schema_version[^0-9]*[0-9]+|expect:[[:space:]]*[0-9]+' "$doc"; then
  echo "FAIL: $doc pins a concrete schema version:" >&2
  grep -En 'schema_version[^0-9]*[0-9]+|expect:[[:space:]]*[0-9]+' "$doc" >&2
  exit 1
fi
grep -q '/health' "$doc" || { echo "FAIL: $doc does not point at /health" >&2; exit 1; }
echo "PASS: $doc uses a symbolic version and /health"
EOF
chmod +x /tmp/dpv/check.sh

3. Expected result

$ /tmp/dpv/check.sh /tmp/dpv/before/SCRATCH_INSTANCE.md
FAIL: /tmp/dpv/before/SCRATCH_INSTANCE.md pins a concrete schema version:
7:# expect: 47
$ /tmp/dpv/check.sh /tmp/dpv/after/SCRATCH_INSTANCE.md
PASS: /tmp/dpv/after/SCRATCH_INSTANCE.md uses a symbolic version and /health

The planted 47 is rejected; the symbolic N + /health recipe is accepted. This is the exact transition SCRATCH_INSTANCE.md needed.

4. Prevent recurrence in CI

# .github/workflows/docs.yml
- name: No pinned schema versions in docs
  run: /tmp/dpv/check.sh SCRATCH_INSTANCE.md

Generalized across all docs:

find . -name '*.md' -not -path './node_modules/*' -print0 \
  | xargs -0 -n1 /tmp/dpv/check.sh

Why this is durable

The version now lives in exactly one place — the binary's /health response — and the docs derive from it at read time. As migrations land, N tracks automatically; there is no second literal to update and no possibility of doc/code drift. The CI check makes the regression mechanically impossible to reintroduce.
