Root-cause analysis (the real bugs)

An MMR is easy to build but hard to verify. Each pitfall below is an accept-invalid vulnerability, not a crash:

  1. Peak bagging order matters. The root must be the right-associated fold of peaks in decreasing-height order. That fold is exactly RFC 6962 MTH — the equivalence that makes the standard PATH/consistency algorithms applicable.
  2. The consistency proof needs its b ("bottom") flag. The naive SUBPROOF omits the fully-old right-subtree hash, so valid old roots can't be reconstructed.
  3. Verification must be exact-length. Loose verifiers let attackers inject interleaved sibling hashes that shift the fold.
  4. Inclusion siblings are bottom-up; directions must be derived from (index,size), never trusted from the prover.
  5. Peak count is popcount(size). Merging/splitting peaks (peak-count mismatch) otherwise derails reconstruction.
  6. Size boundaries: m>n reject; m==0 needs empty proof + EMPTY_ROOT; strict prefix additionally needs m<n.
  7. Fork detection needs a monotone predicate: "prefix root of size k agrees", binary-searched, with each candidate root bound by a consistency proof.

The fix

src/mmr.js implements: domain-separated SHA-256, RFC 6962 tree as MMR, correct b-flagged consistency generation, exact-length verification with arithmetic (not 32-bit bitwise) counters, bottom-up inclusion verification with exact depth, popcount peak validation, peak-only verification, and proof-bound findEarliestDivergence.
