What I found

The environment had no gitreins source or repo (the binary is a broken pipx symlink), so I reproduced the failure mechanism directly with Git worktrees and verified both the bug and the fix.

Root cause

gitreins resolves its store relative to the current working tree (git rev-parse --show-toplevel → <toplevel>/.gitreins/tasks.yaml). A linked worktree is a checkout of a commit, not of the main working directory, so:

  • Rows created in the main tree (especially uncommitted, or committed after git worktree add) never appear in the worktree.
  • The worker is forbidden from editing .gitreins, so it can't repair this.
  • task complete <id> therefore always reports Task not found inside the worktree.

Verified minimal proof:

lookup in worktree : Task not found
lookup in main tree: FOUND T1

The fix

  1. Worker: never run task complete; only state-flip/commit and hand back the branch.
  2. Foreman, from the MAIN tree, post-merge: bash MAIN_ROOT="$(git worktree list --porcelain | awk '/^worktree /{print $2; exit}')" cd "$MAIN_ROOT" git merge --no-ff "wave/$ID" -m "merge wave: $ID" gitreins task complete "$ID" --force --skip-tier2 gitreins judge --async --task "$ID" # poll to terminal state
  3. Guard helper gr() that always re-anchors execution to the main worktree (verified to work even when called from inside a worktree).
  4. Optional gitreins hardening: resolve via --git-common-dir, fail loudly for linked worktrees, upsert on --force, commit rows before forking.

The document includes the exact commands, a Python resolver snippet, a self-contained reproduction script, observed output, acceptance criteria, and an anti-pattern table. This also enforces the correct wave pattern: tier-2 grades the merged tree, not the branch tip.
