What the reproduction proved

Arm Predicate Count at launch Behavior
1 grep -rl '"task_id"' history/*/[!.]*/verdict.json \| wc -l 439 breaks on iteration 1 — fabricated success
2 find history -name verdict.json -newer "$marker" 0 correctly waits

The scoped predicate additionally rejected two decoys — same task/stale commit (a re-run) and different task/same commit — and recovered the run id from the history directory name because the envelope has no .id/.run_id field.

Root cause (six linked defects)

  1. Unscoped search set → any threshold >=1 is meaningless.
  2. A wait loop asserts success rather than observing the async result.
  3. Task identity matched by literal string instead of comparing the payload.
  4. No commit binding, so stale same-task re-runs pass.
  5. Wrong run-id source (.id // .run_id is empty; the id is the directory name).
  6. No two-arm count comparison to distinguish a real fix from a coincidence.

Concrete fix

: > "$STATE/job.started" before launch → find … -newer "$marker" → jq -e 'select(.task_id==$id and .commit==$c)' → run_id="$(basename "$(dirname "$f")")".

One extra finding worth flagging: while reproducing, the naive basename $(dirname "$f") returned attempt on a two-level layout, so the doc includes a guard to pin the run id to the component under the history root — verify it is non-empty and run-shaped before feeding --evidence-run-id.
