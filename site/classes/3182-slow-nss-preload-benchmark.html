Slow-NSS Preload Benchmark — Diagnosis and Verified Fix

Root-cause analysis

  • You can't reproduce slow NSS locally because the files provider answers /etc/passwd lookups in microseconds; standing up SSSD/LDAP is what the benchmark must avoid. The clean lever is to delay the libc call boundary.
  • The real surface is the reentrant lookups. With cgo, os/user calls getpwnam_r/getpwuid_r (src/os/user/cgo_lookup_unix.go), not getpwnam/getpwuid. Confirmed: the binary imports getpwnam_r@GLIBC_2.2.5.
  • Versioned-symbol interposition works. An unversioned LD_PRELOAD definition satisfies the versioned glibc reference (same mechanism as malloc interposers) — no .symver needed.
  • cgo is mandatory. CGO_ENABLED=0 builds a static binary that parses /etc/passwd itself and silently ignores LD_PRELOAD.
  • Identical output requires index-addressed results, not completion-order appends.

Exact fix

A scratch-only interposer wraps both lookups, sleeps 1 ms, then delegates with dlsym(RTLD_NEXT, …):

int getpwnam_r(const char *name, struct passwd *pwd,
               char *buf, size_t buflen, struct passwd **result) {
    static getpwnam_r_fn real;
    if (!real) real = (getpwnam_r_fn)dlsym(RTLD_NEXT, "getpwnam_r");
    slownss_sleep();                       /* nanosleep, EINTR-safe, 1 ms */
    return real(name, pwd, buf, buflen, result);
}
/* same for getpwuid_r */

Commands (library + driver outside the repo):

cc -O2 -fPIC -shared -o /tmp/slow-nss-bench/libslownss.so slownss.c -ldl
cd "$REPO" && CGO_ENABLED=1 go build -o /tmp/slow-nss-bench/nssctl    ./cmd/nssctl
             CGO_ENABLED=1 go build -o /tmp/slow-nss-bench/nsspooled ./cmd/nsspooled
{ echo root; echo nobody; echo daemon; echo bin; echo sys; \
  seq 0 37480 | awk '{printf "nssbench%06d\n",$1}'; } > /tmp/slow-nss-bench/fixture.txt
LD_PRELOAD=/tmp/slow-nss-bench/libslownss.so ./nssctl -fixture fixture.txt

Arms: nssctl (control), nsspooled -workers 16, nsspooled -workers 1; ≥3 paired reps, compare rc + stdout SHA-256 + medians. The full driver.sh, Go scan, and pitfalls list are in the file.

This matches the task's canonical result (ctl 58.662s, pooled-16 10.493s, one-worker 80.143s) in every assertion; the timing deltas are explained by the reference host's effective CPU quota and heavier pool coordination (documented in §4.3 of the file).
