Fix: panic: close of closed channel in PostgresEventWriter.flush

Problem class: go-close-of-closed-channel-nil-after-close Component: internal/realtime/writer.go — PostgresEventWriter.flush Verified fix: 2026-11-02 &lt;project&gt;-memory e938ece3 Symptom: Intermittent panic: close of closed channel in the flush/ticker path (2/5 full-suite runs; also seen as a bare FAIL with no named failing test under -race/guard runs).

1. Root cause

The writer uses a single chan struct{} field as a one-shot, broadcast "flush completed" barrier:

type PostgresEventWriter struct {
    mu        sync.Mutex
    flushDone chan struct{} // closed when the current/last flush finishes
    // ...
}

Lifecycle assumed by the rest of the type:

  1. A flush arms a completion channel (creates one if the field is nil).
  2. Waiters take the current channel and block on it.
  3. The flusher closes the channel to release everyone, then resets the field so the next flush starts clean.

The buggy code omitted the reset in step 3:

defer func() {
    w.mu.Lock()
    close(w.flushDone) // BUG: field is never set back to nil
    w.mu.Unlock()
}()

Because flushDone kept pointing at an already-closed channel, the next ticker-driven flush closed the same stale channel again → panic: close of closed channel.

Why intermittent: it only fires when a second flush arrives after a prior flush completed; ticker interval vs. DB latency decides whether a run hits it (2/5 runs, occasional unnamed guard FAILs). It is not a Go memory-model data race, so -race alone doesn't flag it.

Secondary impact: a stale closed channel makes waiters return immediately instead of waiting for the next flush, breaking barrier semantics.

2. The fix

Assign nil to the field in the same critical section as close, closing a local copy so the close is provably single-shot:

     defer func() {
         w.mu.Lock()
-        close(w.flushDone)
+        // Close exactly the channel waiters are blocked on, then clear the
+        // field so the next flush arms a fresh channel. Same critical
+        // section => no window where a concurrent flush can re-close it.
+        done := w.flushDone
+        w.flushDone = nil
+        close(done)
         w.mu.Unlock()
     }()

Waiters captured the channel under the mutex before the close, so they are still released exactly once, and waiters install a fresh channel per wait so nothing is lost.

3. Verification

3.1 Deterministic red-proof (white-box)

No concurrency needed — two sequential flushes suffice. Pre-fix the second flush panics deterministically; post-fix it passes.

// TestFlush_ClearsCompletionChannelAfterClose is the red-proof for
// go-close-of-closed-channel-nil-after-close.
func TestFlush_ClearsCompletionChannelAfterClose(t *testing.T) {
    w := newTestPostgresEventWriter(t)

    if err := w.flush(context.Background()); err != nil {
        t.Fatalf("first flush: %v", err)
    }

    w.mu.Lock()
    leftover := w.flushDone
    w.mu.Unlock()
    if leftover != nil {
        t.Fatalf("flushDone not cleared after flush (leftover %p)", leftover)
    }

    // Pre-fix this is the deterministic panic line.
    if err := w.flush(context.Background()); err != nil {
        t.Fatalf("second flush: %v", err)
    }
}

go test ./internal/realtime/ -run TestFlush_ClearsCompletionChannelAfterClose -count=100

Expected ok; pre-fix panic: close of closed channel.

3.2 Concurrency stress (ticker + waiters)

Guards the production ticker shape and the DM-GAP-117 variant (multiple waiters overwriting a fresh channel):

func TestFlush_TickerAndWaiters_NoDoubleClose(t *testing.T) {
    w := newTestPostgresEventWriter(t)
    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    defer cancel()

    var wg sync.WaitGroup
    for i := 0; i < 4; i++ { // ticker-driven flushers
        wg.Add(1)
        go func() {
            defer wg.Done()
            tick := time.NewTicker(time.Millisecond)
            defer tick.Stop()
            for {
                select {
                case <-ctx.Done():
                    return
                case <-tick.C:
                    _ = w.flush(ctx)
                }
            }
        }()
    }
    for i := 0; i < 8; i++ { // durability-barrier waiters
        wg.Add(1)
        go func() {
            defer wg.Done()
            for {
                select {
                case <-ctx.Done():
                    return
                default:
                    _ = w.WaitFlush(ctx)
                }
            }
        }()
    }
    wg.Wait()
}

go test -race ./internal/realtime/ -run TestFlush -count=50

Expected ok, no panic, no DATA RACE.

4. Related latent issue

DM-GAP-117 — multiple waiters concurrently installing a completion channel can overwrite a freshly-armed one. Ensure waiter channel installation happens under w.mu and only when w.flushDone == nil; track separately.
