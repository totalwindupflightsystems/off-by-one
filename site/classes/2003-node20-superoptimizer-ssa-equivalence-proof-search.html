What this problem actually was

It is an equivalence-proof search, not a peephole pass. The markdown documents the root causes I diagnosed while building it:

  • RC-1 — random/fuzz equivalence is unsound; only total evaluation over all 8-bit inputs is acceptable.
  • RC-2 — naive enumeration explodes (~1.2M functions at cost 4); fix is signature-canonicalised BFS by cost.
  • RC-3 (the real bug) — the level generator only combined cheaper × pricier operands, so non-commutative ops never produced the reversed order. sub(shl4(x), x) (= 15x, cost 2) was never generated, and four strength reductions were mislabelled cost 3. Fix: iterate every ordered (i, j) split.
  • RC-4 — tempting identities are false under mod-256 wraparound (min(max(x,y), x+y)), which the exhaustive checker rejects.
  • RC-5 — no bound means hang; explicit node/time/cost budgets enforce a never-hangs policy.

Verified results

  • 40/40 target snippets rewritten strictly cheaper (requirement was ≥30).
  • Every rewrite independently re-proved over 256 (1-input) or 65,536 (2-input) assignments with a separate interpreter/evaluator: 0 mismatches.
  • Falsification test: a corrupted mul15 candidate (9x instead of 15x) is rejected with 254 mismatches — proving the checker isn't a no-op.
  • Budget test: with SO_NODE_BUDGET=500 the search stops at {"nodes":501,"stop":"nodes"}.
  • proof-transcripts.txt emits full witness tables for the 5 cheapest rewrites.
