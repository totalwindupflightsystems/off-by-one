Solution summary

Root cause: Plain LRU is not scan-resistant. A one-pass scan of 100,000 distinct cold keys through a 10,000-slot cache means every cold insert evicts the LRU end — the 1,000 hot keys are re-accessed far less often than the ~10,000-insert eviction horizon, so they're always gone by re-access. Measured LRU hot ratio on the exact acceptance trace: 0%.

The fix (/home/kara/lru2q/): a generic, thread-safe 2Q cache (lru2q package):

  • recent (A1in): small FIFO absorbing every first-time Set — the entire scan dies here.
  • reusable (Am): LRU queue; a second access (Get or Set hit in recent) promotes into it. Scan keys (one touch) can never reach it.
  • out (A1out): bounded ghost directory of evicted keys; a Set for a ghosted key re-admits directly into reusable.
  • TTL: lazy expiration on every touch (never returns expired values) + an explicit Cleanup()/optional background loop driven by an O(1)-amortized timing wheel.
  • Concurrency: single sync.Mutex (2Q is a global policy), so everything is race-free; O(1) amortized Get/Set/Delete.

Verification (Go 1.26, -race, 13 tests, all passing):

2Q   hot-key hit ratio: 100.00%  (20000/20000)   — required > 85%
LRU  hot-key hit ratio:  0.00%   (0/20000)       — collapsed < 10% (baseline)

Also verified: exact model parity over 200k random ops ("Get returns the latest Set value at every interleaving point"), ghost promotion/eviction semantics, TTL sweep correctness, structural invariants under random ops, and 16-goroutine concurrent stress under -race (including a background cleanup loop and post-concurrency hot-ratio re-check at 100%).

One interesting bug found during verification: my first concurrent test asserted Get == value immediately after SetWithTTL with TTLs as low as 1 ms. Under 16 goroutines + race detector, the entry legitimately expired during scheduler preemption between the two calls (confirmed via a removal stack dump: the miss came from Get's own lazy-expiry path). The cache was correct; the test now asserts a miss is only an error if the TTL could not have elapsed.
