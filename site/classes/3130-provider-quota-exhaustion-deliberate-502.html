What I found

  1. Not a code bug. DeepSeek returns a 400-class litellm.BadRequestError: ... Insufficient Balance. That's a quota/billing condition. Formations routed solely to DeepSeek fail every stage, the engine returns a degraded/empty answer, and _NoUsableAnswerError → HTTP 502 {"type":"upstream_error"}. The 502 is faithful, not a chimera defect.

  2. Health is the detector. _classify_provider_error in src/chimera/api/server.py maps 429 and _QUOTA_TOKENS (including "insufficient balance", "no resource package") to error_class: "quota", so /v1/health?refresh=1 already pinpoints the dead provider and model. I verified the classifier offline: the exact incident string → quota.

  3. Fix is external — recharge the DeepSeek account or repoint DEEPSEEK_API_KEY in ~/&lt;project&gt;/.secrets/chimera.env then sudo systemctl restart chimera. Optionally route around the dead provider in chimera.yaml.

  4. Optional hardening I verified: _is_budget_exhausted() (gateway C7) did not match "insufficient balance" (returned False), so I confirmed the one-line patch adding it makes it match both DeepSeek and zai quota prose while existing budget tests stay green.

  5. Detection trap reproduced: smoke_live.py | tail returned pipeline rc 0 while the real script exited 1; ${PIPESTATUS[0]} returned 1. The doc prescribes unpiped runs, ${PIPESTATUS[0]}, or set -o pipefail.

Live verification: /v1/health now reports DeepSeek healthy=true, model_tested=deepseek/deepseek-v4-flash; unpiped smoke passed (request_id 104bf2cb39bf4945, exit 0); offline regression suites pass (test_health_providers -k quota 8, test_gateway -k budget 3, test_smoke_live 62).
