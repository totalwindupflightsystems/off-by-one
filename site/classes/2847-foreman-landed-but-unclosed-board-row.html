Fix: foreman-landed-but-unclosed-board-row

Symptom class: false-negative work detection in the coding-hermes JSONL foreman board.

One-line root cause: the foreman treated "the worker's wt/<ID> ref has 0 commits ahead of main" as proof that no work was done, but ahead == 0 is equally true when the work was already landed on origin/main by a path that never advanced the wt/<ID> bookkeeping ref.

1. Symptom

  • git log --oneline main..wt/<ID> → 0 commits (looks like nothing happened)
  • git rev-list --left-right --count main...wt/<ID> → 2 0 (branch fully contained in main)
  • git branch --contains <worker-commit> → main (worker commit reachable from main, not from wt/<ID>)
  • worktree git status --porcelain → clean
  • board row still status=pending, commit_hash=null

The next tick sees a pending row on a clean, contained worktree, concludes "worker produced nothing", and re-dispatches already-landed work.

2. Root cause

The foreman's check was effectively:

ahead := gitCount("rev-list", "--count", "origin/main.."+branch)
if ahead == 0 { return NoWork }   // BUG: false negative

ahead == 0 is ambiguous:

wt/<ID> state main..wt/<ID> --is-ancestor wt/<ID> main Real meaning
never advanced 0 true no work
fully merged / landed 0 true work landed
committed, not merged >0 false pending
diverged >0 false needs attention

When main is advanced directly (commit on main, cherry-pick, integration merge done in another checkout, or a merge that does not update the local wt/<ID> ref), the ref stays at the pre-dispatch base while the work is reachable from origin/main. The source of truth must be origin/main + the landing/merge commit, never the stale worktree ref.

3. Corrected predicate

landed := contained(branch, base) && ahead(branch, base) == 0 && attributable(base)
  • contained = git merge-base --is-ancestor <branch> <base> exits 0
  • ahead = git rev-list --count <base>..<branch>
  • attributable = a landing commit reachable from base: a Merge wt/<ID> merge commit (preferred), else a commit in merge-base(branch,base)..base whose subject contains <ID>

landingSHA = mergeSHA ?? workerSHA ?? base.

Exact commands:

branch=wt/$ID; base=origin/main
git fetch --quiet origin
contained=$(git merge-base --is-ancestor "$branch" "$base" && echo yes || echo no)
ahead=$(git rev-list --count "$base..$branch")
merge=$(git log --merges -n1 --format=%H --grep="Merge $branch" "$base")
mb=$(git merge-base "$branch" "$base")
worker=$(git log -n1 --format=%H --grep="$ID" "$mb..$base")
landed=no
if [ "$contained" = yes ] && [ "$ahead" = 0 ] && { [ -n "$merge" ] || [ -n "$worker" ]; }; then
  landed=yes
fi
landing_sha=${merge:-${worker:-$base}}

4. The fix

4.1 Foreman detection (Go)

// Landed reports whether the worker's changes are already reachable from the
// integration branch, even when the wt/<ID> ref itself never advanced.
// Rule: contained && ahead==0 && attributable.  ahead==0 alone is not enough.
func Landed(repo, id, baseRef, branch string) (landingSHA string, ok bool) {
    if !isAncestor(repo, branch, baseRef) {
        return "", false // commits not in main (or branch missing)
    }
    if ahead(repo, baseRef, branch) != 0 {
        return "", false // ahead of main; not merged
    }
    if sha := gitLine(repo, "log", "--merges", "-n", "1", "--format=%H",
        "--grep=Merge "+branch, baseRef); sha != "" {
        return sha, true
    }
    if sha := gitLine(repo, "log", "--merges", "-n", "1", "--format=%H",
        "--grep="+id, baseRef); sha != "" {
        return sha, true
    }
    mb := gitLine(repo, "merge-base", branch, baseRef)
    if sha := gitLine(repo, "log", "-n", "1", "--format=%H",
        "--grep="+id, mb+".."+baseRef); sha != "" {
        return sha, true
    }
    return "", false // contained but nothing attributable => genuine no-op
}

Tick logic:

if sha, landed := Landed(repo, row.ID, "origin/main", branch); landed {
    CloseRow(row, sha) // commit_hash=sha, status=complete, worker_status=complete, completed_at=now
    continue
}
if ahead != 0 || dirty(worktree) { continue } // in flight / needs attention
// only now re-dispatch

4.2 Reconcile existing stale rows

go build -o /tmp/landedctl ./cmd/landedctl
/tmp/landedctl -repo /path/to/repo           # dry-run
/tmp/landedctl -repo /path/to/repo -apply    # close rows

For every status=pending row it reads branch (or wt/<ID>), applies the predicate, and sets status=complete, worker_status=complete, commit_hash=<landingSHA>, completed_at=<now> + a task_completed event. It snapshots tasks.jsonl, rewrites only the target line(s), and asserts the line count is unchanged before writing.

4.3 Safe worktree reap gate

Never reap on ahead == 0 alone. Reap only when all hold:

ahead=$(git rev-list --count origin/main.."wt/$ID")     # == 0
git merge-base --is-ancestor "wt/$ID" origin/main       # contained/landed
[ -z "$(git -C "$WT" status --porcelain)" ]             # clean
git -C "$WT" diff --quiet                               # content-identical to HEAD

Then git worktree remove "$WT" (no --force), and optionally git branch -D "wt/$ID" after the row is closed.

4.4 Prevention

  1. Record the dispatch base_sha on the row/event at worktree creation.
  2. Record commit_hash at integration time (when Merge wt/<ID> is created), not later from the ref.
  3. Make the tick idempotent: a pending row with commit_hash != null or a landed worktree is never re-dispatched.
  4. Never use ahead == 0 alone as a "no work" signal anywhere.
