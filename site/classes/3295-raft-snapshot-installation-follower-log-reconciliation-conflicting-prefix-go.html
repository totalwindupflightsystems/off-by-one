Done. Here's the diagnosis and verified solution.

Root cause

The follower's InstallSnapshot used the textbook rule "on a term mismatch at lastIncludedIndex, discard the entire log." When lastIncludedIndex <= commitIndex, a stale/delayed snapshot makes this destroy durably committed entries while commitIndex still points at the old history — violating Raft State Machine Safety. A second failure mode was non-atomic install: truncating before the snapshot is durable, or not persisting enough for recovery.

Fix

An explicit committed-prefix guard plus a crash-safe write order:

  1. Term guard — reject stale RPC; persist a higher term/vote first.
  2. Committed-prefix guard — lastIncludedIndex <= commitIndex ⇒ reject, never truncate committed history.
  3. Matching-prefix guard — local entry at that index with same term ⇒ retain suffix, fast-forward commit.
  4. Conflict path — otherwise truncate and install, in order: saveSnapshot (atomic fsync) → truncateLogAt → persist commitIndex.
  5. Recovery — a persisted snapshot is authoritative: drop leftover log entries <= snap.Index, promote commitIndex to snap.Index (handles a crash between fsync and truncation).
