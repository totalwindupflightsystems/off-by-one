Fix: seed the existing hole queue during ledger recovery (seq gap audit trail)

Problem class: go-ledger-recovery-seq-gap-audit-trail

Symptom

On restart, a ledger whose HEAD hint (HEAD.last_seq) is ahead of the authoritative day file resumes seq allocation at HEAD.last_seq + 1 — correct — but the skipped range [fileMax+1, HEAD.last_seq] is never written to the audit trail. verify later reports seq_holes, and nothing explains them.

$ go test ./...
--- FAIL: TestRecoverySeedsHoleForHeadGap (0.00s)
    ledger_test.go:93: want exactly 1 hole record, got 0: []
FAIL

Non-negotiable contract (read before changing anything)

next_seq = max(HEAD.last_seq, highest_seq_in_authoritative_files) + 1

HEAD is not the bug. Using file-max alone when HEAD is ahead would re-issue permanent seq locators. The audit mechanism already exists for failed batches: the writer keeps a hole queue drained into a single lifecycle{op:"hole",from,to} record with the next successful batch. Recovery simply never seeded it.

Root cause

Recover computed NextSeq from max(HEAD, fileMax) and returned, discarding HEAD.last_seq - fileMax. Allocation intentionally skips that range, so the result is a permanent, undocumented seq hole.

Avoid two bad fixes: (1) dropping HEAD from allocation (re-issues locators, breaks the pinned test); (2) writing the hole out-of-band during recovery (second fragile write path). Reuse the writer's hole queue.

Exact fix

Carry the recovered gap into the existing hole queue, gated on a non-degraded index build. In Recover (ledger.go):

    base := head.LastSeq
    if idx.MaxSeq > base {
        base = idx.MaxSeq
    }
-   return &State{NextSeq: base + 1, Index: idx, Head: head}, nil
+
+   st := &State{NextSeq: base + 1, Index: idx, Head: head}
+
+   // A HEAD hint ahead of the authoritative file means seqs
+   // [fileMax+1, HEAD.last_seq] were handed out but are not in this file.
+   // Allocation deliberately keeps using HEAD, so the gap must be
+   // documented via the existing hole queue, drained into one
+   // lifecycle{op:"hole",from,to} record with the next successful batch.
+   //
+   // Gate on a non-degraded index: a degraded scan may have understated
+   // fileMax and a hole seeded from it could never be retracted.
+   if !idx.Degraded && head.LastSeq > idx.MaxSeq {
+       st.HoleQueue = append(st.HoleQueue, Hole{From: idx.MaxSeq + 1, To: head.LastSeq})
+   }
+
+   return st, nil
 }

Unchanged machinery used: State.HoleQueue, Writer.Append draining mergeHoles(...) into one op:"hole" record before the batch, and BuildIndex setting Index.Degraded on unreadable files / corrupt lines / newer-schema lines / budget truncation.

Why the gate: DEGRADED means the scan may not have seen the true max. If fileMax is understated, HEAD > fileMax is not evidence of a real gap; seeding would fabricate a permanent hole. Never create an audit lie to satisfy an audit check.

Applying to the real tree

  1. Find the recovery entry point building state from HEAD + the authoritative-file index.
  2. Append the guarded st.HoleQueue = append(...) immediately after NextSeq is computed.
  3. Do not touch next_seq = max(HEAD, fileMax) + 1.
  4. Ensure the index result exposes a degraded/trustworthy flag; if not, add one before enabling the seed — the gate is required.
  5. Add the gap + control regression tests (and degraded test if the flag is new).
