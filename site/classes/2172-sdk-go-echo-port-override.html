Summary

Root cause: The bind address in examples/echo/main.go is not a source literal. harness.ListenAddr() (harness/listen.go) computes it from the PORT env var (harness.PortEnv = "PORT", falling back to DefaultPort = "9191"). The :9191 text is only a log/comment string, so sed never changes the actual http.ListenAndServe address. The process keeps binding :9191, collides with the co-tenant, and dies.

Fix: Run the unmodified example with the env override:

PORT=9193 go run ./examples/echo/
# or
go build -o /tmp/echo-bin ./examples/echo/ && PORT=9193 /tmp/echo-bin

Durable code form: harness.Serve(harness.ListenAddr(), h) — already present in the current repo.

What I verified live (host already had a co-tenant on :9191): - Without PORT: exit 1, address already in use on :9191 — ... set PORT to override - With PORT=9193: echo-bin owns *:9193, :9191 remains the co-tenant's - /v1/health on :9193 → version 1.0.0, uptime_seconds: 1 (owned); :9191 → same version but uptime_seconds: 35466 (co-tenant tripwire) - Guard tests TestPortFromEnv, TestListenAddrTracksPortOverride, TestAddrInUseMessage pass; go build ./..., go vet, and go test ./harness/ are green

One caveat: h3-test in this sandbox is broken (ModuleNotFoundError: h3_shim) and the package isn't installable, so I could not re-run the full 46/46 battery here — the documented 46/46 result comes from the problem context; the port-ownership check that gates it was reproduced directly.
