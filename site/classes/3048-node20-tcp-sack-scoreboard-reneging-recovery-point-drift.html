Fixing TCP SACK scoreboard recovery-point drift under reneging

Problem class: node20-tcp-sack-scoreboard-reneging-recovery-point-drift · Runtime: Node 20 (plain CommonJS)

Root-cause analysis

A naive scoreboard keeps one RecoveryPoint = HighData from fast-recovery entry and then:

  1. Mistakes an absent SACK block for a renege. A SACK option carries at most 4 blocks and receivers need not repeat old ones. Removing a block from the scoreboard changes IsLost() for every earlier hole and inflates pipe.
  2. Never rolls RecoveryPoint forward. When the receiver explicitly withdraws SACKed data, the holes sit below the old recovery point; the next cumulative ACK that only covers the old point ends recovery while those holes are still outstanding → stall until RTO.
  3. Uses the coarse HighRxt gate for eligibility. NextSeg requires S2 > HighRxt, so a withdrawn/re-lost range below it can never be selected again.
  4. Treats a DSACK as loss evidence, letting it inflate dupAcks and re-declare held data lost.

This is recovery-point drift: point and retransmit set diverge from the real holes.

The exact fix (sack.js)

  • Wrap-safe unwrapped coordinates — convert each wire seq once with signed 32-bit math (base + ((seq - base) | 0)); all coalescing/sorting happens in monotonic space, wrapping back only at the API.
  • Per-octet retransmit marks instead of the HighRxt gate for NextSeg eligibility (HighRxt is still kept for pipe accounting).
  • Explicit renege: remove from SACK, clear retransmit mark, record in a reneged set; reneged octets are IsLost()==true (definitively lost), still-SACKed octets are never lost; if in recovery, RecoveryPoint = max(RecoveryPoint, HighData).
renege(l, r) { this.sacked.remove(l, r); this.retrans.remove(l, r); this.reneged.add(l, r); }

isLostU(seq) {
  if (this.sb.isSacked(seq)) return false;   // still held => never lost
  if (this.sb.isRenege(seq)) return true;    // withdrawn  => definitely lost
  return this.sb.sackedBytesAbove(seq) > (this.dupthresh - 1) * this.smss
      || this.sb.countRangesAbove(seq) >= this.dupthresh;
}
  • DSACK undo, exactly once (RFC 2883 §5/§5.2 classification; RFC 3522/4015 restore):
classifyDsack(first, uAck) {
  if (!first) return false;
  if (seqLE(first.right, this.w(uAck))) return true;                  // below cumACK
  const ul = this.u(first.left), ur = this.u(first.right);
  if (this.sb.isSacked(ul) && this.sb.isSacked(ur - 1)) return true;  // dup block
  return this.sb.retrans.bytesIn(ul, ur) === (ur - ul) && ur > ul;    // reorder
}
doUndo(events) {
  if (this.undoDone || !this.reducedOnce) return false; // exactly once
  this.undoDone = true;
  const before = this.cwnd;
  this.cwnd = this.savedCwnd; this.ssthresh = this.savedSsthresh;
  events.cwndDelta += this.cwnd - before; events.undo = true;
  return true;
}

NextSeg() implements RFC 6675 rules (1)–(4) with dupthresh=3; SetPipe() implements the IsLost/SetPipe accounting; runSendLoop caps transmissions at maxburst=10.

Why it works: held data is protected by isSacked() short-circuiting loss and by the reneged set being disjoint from the SACK set; withdrawn data stays eligible because marks are per-octet; recovery can’t end early because the point moves forward on renege; and a spurious retransmit is billed once.
