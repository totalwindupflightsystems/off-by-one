Summary

Diagnosis: The guard's root/operation gate only tested for sequencer directories (rebase-merge / rebase-apply), while the standalone probe tested the bare REBASE_HEAD pseudo-ref. The gate and probe enumerated markers independently, so they disagreed — gate passed, probe fired. A missing rebase directory means teardown finished; it does not mean every pseudo-ref was removed. Git can leave a bare REBASE_HEAD after an interrupted/crashed pull --rebase, and git rebase --quit refuses to clean it once the directory is gone.

Verdict: Stale-marker classification + ownership barrier — not authorization to delete. The marker is provably stale (content/mtime pin it to rebase start, a finish is attested 22s later, HEAD advanced, no sequencer dir, no live owner), but the only removal path is destructive and unattributable, so it stays gated.

Fix (read-only at tick time): 1. guard_rebase_marker.py — single canonical marker set (REBASE_HEAD, MERGE_HEAD, CHERRY_PICK_HEAD, REVERT_HEAD, BISECT_LOG, AUTO_MERGE) imported by both gate and probe. gate_passes() is now false whenever any marker/dir/lock is present. 2. guard-rebase-marker-probe.sh — portable classifier that excludes the observer process from owner detection (this was the exact_root_fd=1 red herring) and returns UNOWNED_STALE_MARKER / GATED_OWNER_REQUIRED. 3. Cleanup stays behind an explicit owner disposition.

Verified in a faithful reproduction: - Stale scenario → classification=UNOWNED_STALE_MARKER, disposition=GATED_OWNER_REQUIRED, gate_passes=false, exit 3, marker and HEAD untouched. - Mid-conflict rebase → OPERATION_ACTIVE / GATED, exit 4. - Clean repo → CLEAR / PROCEED, exit 0. - git update-ref -d REBASE_HEAD confirmed as the only (destructive) removal path, documented but withheld.

Files: - /workspace/solution.md - /workspace/guard_rebase_marker.py - /workspace/guard-rebase-marker-probe.sh
