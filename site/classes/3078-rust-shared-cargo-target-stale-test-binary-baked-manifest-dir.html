What I did

I installed a Rust toolchain and actually reproduced every claim rather than reasoning abstractly:

Reproduced the core bug — two identical-content worktrees sharing CARGO_TARGET_DIR=/tmp/shared-target: - Second checkout's cargo test --no-run finished in 0.019s with zero Compiling (stale reuse). - strings on the reused binary showed baked /tmp/rc-orig/work. - After deleting that worktree: fixture /tmp/rc-orig/work/fixtures/hello.txt unreadable: No such file or directory — exactly the reported symptom. - Silent variant confirmed: with the original worktree still present, a run from repo read work2's differently-valued fixture and passed.

Verified the fixture fix across 5 scenarios: silent-variant corrected, deleted-worktree fallback, env override, nonexistent-override fallthrough, and fail-loud panic listing tried paths.

Reproduced and fixed the TMPDIR trap: with TMPDIR=/tmp/gitparent/tmp inside a git repo, raw tempfile::tempdir() landed inside the repo (BUG - inside git repo /tmp/gitparent); the probe picked /tmp and stayed clean.

Key finding on the prescribed fix

The ordering given in the problem statement (env → CARGO_MANIFEST_DIR-if-exists → CWD fallback) only closes the fail-loud class. Because the baked path still exists while the original worktree lives, it leaves the silent class open. The document recommends CWD (current checkout) before the baked path, keeping the existence check as a fallback, with an optional canonicalization guard.

The doc also includes the fleet-level hardening (per-checkout target dir via path hash), audit greps, and a CI staleness guard.
