What I diagnosed

The failure class has six distinct root causes, all stemming from letting an attacker-controlled string be interpreted differently at validation time vs. socket-connect time:

  1. Parser differentials — 2130706433, 0x7f.0.0.1, 0177.0.0.1, 127.1, %31%32%<ip-address>, <ip-address>\@evil.com all mean <ip-address> to WHATWG but something else to naive string checks.
  2. IPv6-wrapped IPv4 — ::ffff:<ip-address>, <ip-address> (NAT64), <ip-address> (6to4), Teredo.
  3. Split-horizon / name bypass — public-looking hosts resolving to RFC1918, or mixed public+private answers.
  4. Redirect bypass — first hop public, 302 Location: http://<ip-address>/ internal.
  5. DNS rebinding (TOCTOU) — resolving once to validate and again to connect.
  6. Credential/scheme tricks — userinfo @, file:/gopher:, zone IDs.

The fix

A dependency-free ssrf-guard.js that: - Canonicalizes only with WHATWG new URL, allowlists http/https, and rejects userinfo. - Parses hosts to raw bytes and classifies full reserved ranges, recursing into every IPv4-embedding IPv6 form (mapped/compatible/NAT64/6to4/Teredo). - Resolves all A/AAAA answers and rejects if any is non-public. - Re-validates every redirect hop (manual loop, max 5). - Pins the validated literal IP into the socket while preserving Host + TLS SNI/cert hostname — closing the rebinding window — and re-checks remoteAddress after connect.
