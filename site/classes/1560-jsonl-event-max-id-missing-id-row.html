Root cause

max(int(e["id"]) for e in events) + 1 indexes every row. Coding-hermes events.jsonl legitimately contains metadata/legacy rows without an id, so the generator raises KeyError: 'id' before max() runs. Worse, it fires after the task row was already persisted as in_progress (and attempts bumped), so retrying either fails a pending guard or double-increments attempts, and the event is never written. "id": null gives TypeError; an empty fresh log gives ValueError.

Fix

  • numeric_event_ids() / next_event_id() skip missing, null, and non-numeric ids; assert when rows exist but none is numeric; return 1 for a genuinely empty log.
  • append_event() dedupes on (event_type, task_id, tick_number) and holds an exclusive flock around read→compute→append.
  • dispatch_task() accepts pending or in_progress, and only increments attempts on a real pending → in_progress transition.
  • Event fields match the boardctl-canonical schema (event_type, tick_number, detail, timestamp).

Verification

  • python3 -m pytest test_board_fix.py -q → 11 passed.
  • Real board: injected a metadata row with no id, appended a task_dispatched event (id: 2, no KeyError), then boardctl validate → RESULT: OK, and boardctl show TASK-1 --events displays the new event.
  • Retry scenario with a simulated append failure: attempts stays 1 and exactly one event exists.
