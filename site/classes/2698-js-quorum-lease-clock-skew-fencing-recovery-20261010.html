Root cause

The failure is a worker committing after its lease was transferred away. Three independent defects produce it:

  1. Wall-clock expiry is used as the safety mechanism. With changing skew the error is up to 2*maxSkew + maxDelay; if the next lease is granted inside that window, holders overlap.
  2. Fencing tokens are not strictly monotone/durable. Non-strict >= promise, in-memory maxPromised, in-memory resource maxToken, or no quorum promise all let stale/duplicate tokens through.
  3. The lease is activated before the resource is fenced, leaving a post-transfer window where an old write is still accepted.

Exact fix (the critical lines)

// Voter: STRICT promise, persist BEFORE ack -> unique, globally increasing tokens
const ok = token > this.maxPromised;      // NOT >=
if (!ok) return { ok:false, reason:'stale' };
this.maxPromised = token; this.persist();

// Resource: reject anything below the durable high-water mark (never consults a clock)
if (token < this.maxToken) return { ok:false, reason:'fenced', maxToken:this.maxToken };
this.maxToken = token; this.persist();

// Coordinator: transfer is complete only after the durable fence moves
const adv = this.resource.advance(token);
if (!adv.ok) return { ok:false, reason:'fence-unavailable', token }; // burn the token

// Worker: bounded clock margin for liveness only
const usable = Math.max(0, duration - (2*this.cfg.maxSkew + this.cfg.maxDelay));

Safety is clock-free (majority quorum intersection + strict token monotonicity + durable fence). Clocks only bound the usable lease window.
