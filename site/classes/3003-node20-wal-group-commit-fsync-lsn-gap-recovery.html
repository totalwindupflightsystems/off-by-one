Done. The verified solution is written to ~/wal-solution/SOLUTION.md (self-contained, with all code inline), alongside the working modules and test.

Root cause (four coupled hazards)

  1. Completion-boundary race — resolving waiters using the LSN at fsync completion marks records durable that the in-flight fsync never covered. The fix is to snapshot the boundary before calling fsync and only advance to that.
  2. Directionality — a later fsync does cover earlier LSNs, but never the reverse. Solved with a monotonic durableLsn and w.lsn <= durableLsn.
  3. Torn tail — a write torn while the CRC is landing leaves a plausible length prefix + partial CRC. Storing the CRC last, covering everything before it, makes torn writes fail validation.
  4. Recovery truncation trap — after a crash you can't tell "never fsynced" from "covered by a later group's fsync." Naively truncating to a remembered commit point destroys records a later fsync made durable. Correct rule: trust any complete, CRC-valid record, truncate only the first proven-torn one, and report the max LSN of the surviving prefix (LSN gaps are not corruption).

Deliverable

  • wal.js — group-commit writer (setImmediate batch coalescing, single in-flight fsync, monotonic durableLsn, serialized writes) + recover.
  • record.js / crc32.js — record framing with CRC-last layout and a scanner that classifies complete / partial / corrupt.
  • storage.js — real FileStorage plus FaultyStorage that persists a deterministic prefix inside fsync and then throws (fault injection in the wrapper, not post-hoc truncation).
  • test.js — 8 tests.

The fault loops sweep every byte offset (109 values) for two different faulted fsyncs and assert, for each resolved caller, that its record is present and byte-identical in the recovered image — proving no caller was told "durable" while its bytes were absent — while also confirming recovery keeps complete records persisted by a failed/later fsync.
