Answer

Fix: aggregate health must degrade for expected-but-dead sources

Root cause

lifecycle.Health (internal/lifecycle/health.go) builds the single authoritative HealthResponse. It folded in stalled state, degraded sensors, unbuilt/refused subsystems, RSS budget, build stamp, hub degradation, and explicit DegradedReasons — but it never read HealthInputs.Sources. The app composition (internal/types/spec12.go → HealthInputs.Sources) already passed the producer's SourceLiveness rows through verbatim, and they were emitted in the response, so GET /health.json could show:

{ "status": "ok",
  "sources": [ { "expected": true, "alive": false, ... } ] }

That contradicts the documented contract: docs/operations.md says an expected dead source means events are not reaching the ledger, and SPEC-12 §3.3 says health is aggregated. The missing_rules_dir boot test exposed it (psi/journald expected alive=false while status="ok"). The bug is in the assembly, not the source producer.

Fix

1. internal/lifecycle/health.go

Add a source-coverage pass right after the degraded-sensors loop. It degrades once per Expected && !Alive source, never overrides the more severe stalled state, and records the single-valued detail key as host_id:source:

    for _, s := range in.Sources {
        if !s.Expected || s.Alive {
            continue
        }
        if status != "stalled" {
            status = "degraded"
        }
        detail["source_not_alive"] = s.HostID + ":" + s.Source
    }

Non-expected sources and alive expected sources are skipped entirely, so they cannot change status or add detail.

2. internal/lifecycle/health_test.go

Pin the exact marshaled HealthResponse JSON for both cases (encoding/json added to imports):

  • expected dead source → "status":"degraded" and "detail":{"source_not_alive":"host-a:journald"}
  • expected alive source → "status":"ok" and no detail block

Also extend TestHealthStalledBeatsSubsystemDegrade with a dead source and assert the stalled response still carries detail.source_not_alive == "host-a:journald".

The full test is TestHealthExpectedSourceLivenessJSON, using in.Sources = []types.SourceLiveness{{HostID:"host-a", Source:"journald", Zone:"host", Expected:true, Alive:tc.alive, MaxAgeS:300}} and comparing string(json.Marshal(Health(*defaults(), in))) to the literal.

3. internal/app/missing_rules_dir_test.go

Replace the unconditional status == "ok" assertion with a coverage-aware check: collect host_id:source for every expected dead source; if any exist, require status != "ok" and detail.source_not_alive to be one of them; otherwise require status == "ok" and no source_not_alive key. The sensor-specific checks (no sensor_degraded, inotify names the absent dir) are preserved.

4. docs/operations.md

Update the "events are reaching the ledger" daily-check row to document that an expected dead source makes top-level status degraded (unless stalled), that detail.source_not_alive names host_id:source, and that non-expected sources do not degrade health.

The lifecycle suite is green and the exact-JSON tests confirm the degraded+detail and ok outputs. In the sandbox here the live TestMissingRulesDirBootsToHealthOK still reports one failure from a pre-existing environmental condition — journald probe returns access_denied (TROUBLE-SENSORS-024) (no journal access in the container). After the fix the status error is gone; only the environment-caused sensor assertion remains, and the new source_not_alive assertions pass, showing the dead-source check works.
