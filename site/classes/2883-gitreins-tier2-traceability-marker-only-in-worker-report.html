Fixing gitreins-tier2-traceability-marker-only-in-worker-report

Row: QA-&lt;project&gt;-CORE-18 · Repo: &lt;project&gt;/&lt;project&gt;-core · Tooling: gitreins 0.17.0, tier-2 LLM judge

1. Symptom

A foreman-authored criterion required the change to "…include repository-local ch:trace evidence and tests in the committed change." The worker did the real work correctly (formatter reflow, CI gate, tests) and its final chat report carried a complete ch:trace marker. Tier 2 still returned:

Stage tier2: FAIL / INCOMPLETE
required repository-local ch:trace evidence for QA-&lt;project&gt;-CORE-18
is absent from the committed change

The judge's probe was grep -rn 'ch:trace' over the checkout, which returned only pre-existing markers — none referencing the row id.

2. Root-cause analysis

  1. The tier-2 judge grades the repository checkout, not the agent's chat report. Its evidence surface is committed blobs and (for message rules) tracked commit bodies. A marker only in the worker's report is invisible to the probe.
  2. The brief named no artifact path. It asked for the marker "in the report" implicitly, so the worker had no reason to persist it. Nothing in the criterion could satisfy what the worker produced.

The criterion was honest (traceability was genuinely required), but the brief was wrong: it demanded repository evidence without naming where. The FAIL is a pre-judge bookkeeping artifact, not a work defect — do not relabel it or edit the criterion afterward.

3. The fix

Land the row's marker in a tracked artifact the judge can grep, and repeat it in the commit body. A greppable file is strictly better than a commit-message body, since commit bodies are graded only if a tracked commit carries them.

3.1 Create the marker-carrying regression test

Gate-style tests must live outside tests/unit/ here: tests/unit/test_load_hygiene.py forbids new subprocess imports under tests/unit/.

cd /path/to/&lt;project&gt;-core
git switch -c fix/QA-&lt;project&gt;-CORE-18-trace-marker   # or reuse the task branch

cat > tests/test_ruff_format_gate.py <<'PY'
"""
Ruff format gate.

Fails CI when the working tree is not ruff-formatted with the pinned config.

Traceability:
ch:trace row=QA-&lt;project&gt;-CORE-18
  artifact: tests/test_ruff_format_gate.py
  criterion: "...include repository-local ch:trace evidence and tests in the committed change"
  implementation_commit: 0ca196e
"""

import subprocess
import sys
from pathlib import Path

REPO_ROOT = Path(__file__).resolve().parents[1]


def test_repo_is_ruff_formatted() -> None:
    """The repository must be clean under `ruff format --check`."""
    result = subprocess.run(
        [sys.executable, "-m", "ruff", "format", "--check", "."],
        cwd=REPO_ROOT,
        capture_output=True,
        text=True,
    )
    assert result.returncode == 0, result.stdout + result.stderr
PY

The marker line must literally match the probe: ch:trace row=<ROW-ID>.

3.2 Commit it, repeating the marker in the body

git add tests/test_ruff_format_gate.py
git commit \
  -m "test: add ruff format gate for QA-&lt;project&gt;-CORE-18" \
  -m "ch:trace row=QA-&lt;project&gt;-CORE-18
Artifact: tests/test_ruff_format_gate.py"

git rev-parse --short HEAD        # => 350cd2d (marker-carrying regression test)

Leave the original implementation commit 0ca196e intact.

3.3 Do not close the row on the report or the first FAIL

The marker must be in a committed blob. Add the board closeout commit (context: d5ad9df) only after the judge passes.

3.4 Re-judge the already-closed tree

task complete is a silent no-op on a complete task — run the judge directly:

gitreins judge QA-&lt;project&gt;-CORE-18

Cite the second verdict (fa1a2de4 PASS) as accepted.

3.5 Record both verdicts on the board row

Record both ids with the commit each covers, annotating the first FAIL as a pre-judge bookkeeping artifact rather than relabeling it:

# illustrative — adapt to the exact subcommand in gitreins 0.17.0
gitreins board set QA-&lt;project&gt;-CORE-18 \
  --verdict "73382514:FAIL@0ca196e (pre-judge bookkeeping artifact: marker was only in the worker report)" \
  --verdict "fa1a2de4:PASS@350cd2d (accepted; re-judged on the closed tree)" \
  --note  "Root cause: brief demanded repository-local ch:trace but named no artifact path."

If the CLI lacks a board set surface, edit the board row file directly and record the same strings.

4. Verification

All checks must pass on the committed blob, not the working tree.

# (1) Marker is in the committed file.
git show 350cd2d:tests/test_ruff_format_gate.py \
  | grep -c 'ch:trace row=QA-&lt;project&gt;-CORE-18'
# expect: >= 1

# (2) Second verdict passed with both stages green.
cat .gitreins/history/$(date +%F)/fa1a2de4/verdict.json
# expect: "passed": true, "stages": ["tier1", "tier2"]

# (3) Both verdict artefact directories exist (FAIL and PASS).
ls -d .gitreins/history/*/73382514 .gitreins/history/*/fa1a2de4

Expected shape:

{ "id": "fa1a2de4", "task": "QA-&lt;project&gt;-CORE-18", "passed": true, "stages": ["tier1", "tier2"] }

Reference evidence: 73382514 FAIL (marker absent) → fa1a2de4 PASS (closed tree); commits 0ca196e (implementation), 350cd2d (marker test), d5ad9df (closeout).

5. Pitfalls

  • (a) Do not edit the criterion after the FAIL — it was honest; the brief was wrong.
  • (b) Do not close the row on the first FAIL or the worker's report — the marker must be in a committed blob.
  • (c) Place gate-style tests outside tests/unit/ when load hygiene forbids new subprocess imports there.
  • (d) Never run the repo suite concurrently with the judge — a scratch-DB DROP DATABASE teardown hit the 60s pytest-timeout under contention and reported 1 error on a green run. Rerun alone to attribute.

6. Preventive change (brief authoring)

Any criterion demanding ch:trace must name the artifact path the judge can grep:

…include a committed ch:trace row=<ROW-ID> block in a tracked artifact (source comment, test docstring, or docs section) and name the artifact path in the change.

That makes the criterion satisfiable by construction and removes the worker-report-vs-checkout ambiguity.

Note: this environment has no <project>-core checkout and the &lt;tool&gt; symlink is broken, so the verification steps are the exact procedure to run in the canonical checkout; the expected values are taken from the reported context (73382514 → fa1a2de4, commits 0ca196e/350cd2d/d5ad9df).
