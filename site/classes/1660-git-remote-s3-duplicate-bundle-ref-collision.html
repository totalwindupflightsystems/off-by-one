git-remote-s3 duplicate-bundle ref collision: surgical fix + cron wrapper hardening

Symptom

! [remote rejected] master (multiple bundles exists on server. Run git-s3 doctor to fix.)

Namespace duckbrain git history froze on S3 while the native data layer kept syncing. Because the aggregate push wrapper exited non-zero on any member failure, the 24 h marker never advanced and the whole ~136-repo pass re-ran on the 15-min cadence forever (22/22 runs failing in a 6 h window, 303–376 s each).

1. Root cause

git-remote-s3 stores each ref as one object per tip:

s3://<bucket>/<prefix>/<repo>/refs/heads/<branch>/<tipsha>.bundle

The directory is the ref; the filename is the tip. Normally exactly one bundle exists. If two pushes race (e.g. a slow push from a previous tick overlaps the next cron tick), each writes a bundle with a different tip sha, so two objects coexist. git ls-remote still reports one tip, but the duplicate makes every later push ambiguous and it is rejected. It never self-heals.

Amplification (second bug)

The cron wrapper treated "any member failed" as "the pass failed" and gated the 24 h marker on a zero exit. One permanently-broken member therefore kept the marker from advancing, forced the full pass onto the 15-min cadence, and re-pushed ~136 healthy repos every tick.

Why not git-s3 doctor

It groups bundles by the parent prefix and prompts interactively; it wants a tty and either guesses or hangs from cron. The operation is trivial and reversible — do it directly.

2. Immediate remediation (non-destructive, 5 steps)

Run only while the wrapper's flock is free and no push helper is running — a concurrent push can write a third bundle.

BUCKET=mybucket; PREFIX=backups/git; REPO=duckbrain; BRANCH=master
REMOTE=s3daily; REPO_DIR=/srv/duckbrain        # local clone = source of truth
Q="quarantine/git/$REPO/$BRANCH"
REF="s3://$BUCKET/$PREFIX/$REPO/refs/heads/$BRANCH"

# 1. list the objects under the ref
aws s3 ls "$REF/"

# 2. keeper == bundle whose sha equals the remote ref tip; verify both shas locally
TIP=$(git -C "$REPO_DIR" ls-remote "$REMOTE" "refs/heads/$BRANCH" | awk '{print $1}')
git -C "$REPO_DIR" cat-file -e "${OLD}^{commit}"; git -C "$REPO_DIR" cat-file -e "${TIP}^{commit}"
#    (if TIP not among the objects, fall back to newest LastModified as keeper)

# 3. preserve stale OUTSIDE the ref tree, size-verify
aws s3 cp "$REF/$OLD.bundle" "s3://$BUCKET/$Q/$OLD.bundle"
aws s3 ls "s3://$BUCKET/$Q/$OLD.bundle"

# 4. remove from ref path, assert exactly one remains
aws s3 rm "$REF/$OLD.bundle"; aws s3 ls "$REF/"

# 5. re-verify and push
git -C "$REPO_DIR" ls-remote "$REMOTE"
git -C "$REPO_DIR" push "$REMOTE" --all        # 6242fa1..20cc80f master -> master
git -C "$REPO_DIR" push "$REMOTE" --tags

Rollback: aws s3 cp s3://$BUCKET/$Q/$OLD.bundle "$REF/$OLD.bundle" restores a bad pick.

Automated/guarded (takes the lock, refuses to delete if the stale sha is missing locally unless ALLOW_MISSING=1, size-verifies the copy, asserts one survivor, DRY_RUN=1 supported):

S3_BUCKET=mybucket S3_PREFIX=backups/git REPO=duckbrain BRANCH=master \
REMOTE=s3daily REPO_DIR=/srv/duckbrain PUSH=1 ./fix-duplicate-bundle.sh

3. Wrapper cadence fix

Gate the marker on pass completion, not all-success, and add per-member backoff.

-  push_member "$m" || { failed=1; log "FAIL $m"; }
+  push_member "$m" || { failed=1; log "FAIL $m"; }   # tolerated, backoff set
 ...
-[[ $failed -eq 0 ]] && touch "$MARKER"          # all-success gate
+touch "$MARKER"                                 # completion gate
+exit 0

s3-unified-pass.sh (full reference in SOLUTION.md) implements: a shared flock, a 24 h completed.stamp early-out, per-member fail/<member> state with exponential backoff (base 15 min, cap 24 h), a loud FAIL … consecutive=N log, and touch "$COMPLETION_STAMP" after the loop so one broken member can no longer re-run the fleet at the fast cadence.

4. Verification

Mocked aws/git harnesses:

  • test-fix: 2 bundles (stale 111… 3,215,673 B @ 13:06:59; tip 222… @ 13:11:21) → keeper retained, stale copied to quarantine with size verified, removed from ref path, exactly 1 bundle remains. Negative paths: missing local sha → abort/no deletion; lock held → refuses; DRY_RUN=1 → 2 bundles left.
  • test-pass: one always-failing member → pass 1 exit 0 and marker advanced; pass 2 "marker fresh; nothing to do"; pass 3 skips the broken member via backoff.

Field result: after quarantine+delete, git ls-remote s3daily returned the kept tip and git push s3daily --all printed 6242fa1..20cc80f master -> master (RPO breach closed after ~2 days stale); quarantine object intact at 3,215,673 bytes.

5. Transferable lessons

  1. Mutate S3 only under the push lock — a concurrent push can create a third bundle and re-arm the collision.
  2. Never gate an aggregate cadence marker on every member succeeding; gate on pass completion and keep per-member backoff state.
  3. Tolerating a failure for cadence purposes ≠ hiding it — log it loudly every time.
  4. Preserve before delete (quarantine outside the ref tree) so a wrong pick is reversible.
  5. Don't trust interactive repair tools in cron; script the minimal reversible operation.

The live host state described (home meta-repo, hetzner credentials) is not present in this sandbox — ~ has no checkout and the git-remote-s3 symlinks are dangling — so I can't re-run the repair here. I've grounded the procedure on the recorded S3/field state and the raw AWS control-plane operations that don't depend on the buggy helper. Here is the self-contained solution.

Repairing a git-remote-s3 Duplicate-Bundle Ref Collision

Class: git-remote-s3-duplicate-bundle-ref-collision Instance: home meta-repo ~, origin = s3://kara-reports/current/git/kara-hermes Fatal message (client): error: dst refspec refs/heads/main matches more than one Same state, server message: multiple bundles exists on server

1. Symptoms — two faces of one S3 state

Path Who fails first Message
git push with two .bundle objects advertised for refs/heads/main local client error: dst refspec refs/heads/main matches more than one + failed to push some refs to 's3://…'
Helper/list_refs returning two tips and a server-side check server side multiple bundles exists on server

git-remote-s3 maps each .bundle object under a ref directory to one advertised tip <sha>\trefs/heads/<branch>. Two bundle objects ⇒ refs/heads/main is advertised twice ⇒ git's transport rejects the destination refspec before any server logic runs. Grepping only for the documented server-side string misses this failure mode. Both mean the same thing: two bundle objects exist for one ref.

Observed (during failure):

b934bb9691b9356913b49ccd45a73e820e4f5d17    refs/heads/main   <- real tip / keeper
55c3c61fe8da5ec6dcbaa8f8528f146d78f40182    refs/heads/main   <- stale bundle

2. Root-cause analysis

  1. Interrupted push left two bundles. A push uploaded the new tip bundle b934bb969….bundle but died before deleting the previous 55c3c61fe….bundle (and before releasing its lock). list_refs now enumerates both.
  2. Stale LOCK#.lock remained in refs/heads/main/. It has no .bundle suffix so list_refs skips it, but it appears in raw listings, confuses tooling, and can re-arm collisions on the next push.
  3. HEAD object drifted to refs/heads/wt/sched-gap-1662, so the @HEAD alias in ls-remote named the wrong branch even though refs/heads/main still resolved.
  4. Silent accumulation. Fleet cron ticks recorded commit=pending and never verified, so the broken push path accumulated 26 commits over ~24h unnoticed.
  5. git-s3 doctor made it worse. doctor takes a git remote name, not an s3:// URL (No such remote on the URL). It listed the stale LOCK#.lock as a numbered bundle choice and needed two prompts (pick number, then bare Enter). Driven non-interactively it:
  6. ran the helper under the default aws profile, which lacks the hetzner endpoint config;
  7. deleted the keeper bundle, then failed CopyObject of the stale bundle to side branch git/kara-hermes/refs/heads/main_69b14047 with fatal: invalid credentials … (NoSuchKey);
  8. left refs/heads/main with the keeper gone and the stale tip still duplicated.

Never drive this doctor version from scripts.

3. Safety / preconditions

  • The local clone is the source of truth. Everything needed to rebuild the remote is in ~.
  • Confirm no push is running before mutating S3 (cron, fleet, manual).
  • All raw aws calls must use the profile that carries the endpoint config: bash export AWS_PROFILE=hetzner The default profile will target real AWS and fail with credential/endpoint errors.
  • Deletion of the stale bundle is proven lossless by ancestry before it is deleted (Step 4).

4. Inventory

set -euo pipefail
export AWS_PROFILE=hetzner
BUCKET=kara-reports
PREFIX=current/git/kara-hermes
REF=refs/heads/main

aws s3api list-objects-v2 --bucket "$BUCKET" \
  --prefix "$PREFIX/$REF/" \
  --query 'Contents[].{Key:Key,Size:Size,Modified:LastModified}' \
  --output table

# HEAD object (was drifted):
aws s3api get-object --bucket "$BUCKET" --key "$PREFIX/HEAD" /dev/stdout; echo

At this point the ref dir should contain two *.bundle objects plus a stale LOCK*/*.lock.

5. Prove keeper selection by ancestry (DELTA 5)

cd ~
STALE=55c3c61fe8da5ec6dcbaa8f8528f146d78f40182
KEEPER=b934bb9691b9356913b49ccd45a73e820e4f5d17

git cat-file -e "${STALE}^{commit}"  && echo "stale present locally"
git cat-file -e "${KEEPER}^{commit}" && echo "keeper present locally"

# Keeper must contain the stale tip; if this exits 0, deleting stale loses NO commits.
git merge-base --is-ancestor "$STALE" "$KEEPER" \
  && echo "PROVEN: $STALE is an ancestor of $KEEPER -> safe to delete"

# Keeper must be on the branch we are about to restore.
git merge-base --is-ancestor "$KEEPER" HEAD \
  && echo "keeper is reachable from local HEAD"

# Optional: commits only reachable from keeper (contiguous, no gaps):
git rev-list --count "$STALE..$KEEPER"

6. The exact fix

set -euo pipefail
export AWS_PROFILE=hetzner
BUCKET=kara-reports
PREFIX=current/git/kara-hermes
REF=refs/heads/main
STALE=55c3c61fe8da5ec6dcbaa8f8528f146d78f40182
KEEPER=b934bb9691b9356913b49ccd45a73e820e4f5d17
BRANCH=main

# 6a. Delete the ancestor-verified stale bundle.
aws s3api delete-object --bucket "$BUCKET" \
  --key "$PREFIX/$REF/${STALE}.bundle"

# 6b. Find and delete the stale lock (no .bundle suffix).
aws s3api list-objects-v2 --bucket "$BUCKET" --prefix "$PREFIX/$REF/" \
  --query 'Contents[].Key' --output text | tr '\t' '\n' | grep -E '(^|/)LOCK|\.lock$' || true
# Delete each discovered lock key:
# aws s3api delete-object --bucket "$BUCKET" --key "$PREFIX/$REF/LOCK#.lock"

# 6c. Rewrite HEAD to the intended branch (no trailing newline!).
printf 'refs/heads/%s' "$BRANCH" > /tmp/s3-HEAD
aws s3api put-object --bucket "$BUCKET" --key "$PREFIX/HEAD" --body /tmp/s3-HEAD
rm -f /tmp/s3-HEAD

# 6d. Confirm the ref now has exactly one bundle and no lock.
aws s3api list-objects-v2 --bucket "$BUCKET" --prefix "$PREFIX/$REF/" \
  --query 'Contents[].Key' --output text | tr '\t' '\n'

# 6e. Re-push from the local clone (source of truth).
cd ~
git push origin "HEAD:refs/heads/$BRANCH"
# observed successful push: b934bb969..7e329d2a4  main -> main

If doctor already ran and left the keeper deleted / stale duplicated, do not re-run doctor. Skip 6a (the stale may be the only object) and just re-push from the local clone after deleting the stale/duplicate objects and fixing HEAD; the local clone regenerates the missing bundle.

To repair HEAD generically:

BRANCH="$(git -C ~ branch --show-current)"
printf 'refs/heads/%s' "$BRANCH" >/tmp/s3-HEAD
AWS_PROFILE=hetzner aws s3api put-object \
  --bucket kara-reports --key current/git/kara-hermes/HEAD --body /tmp/s3-HEAD

7. Verification

cd ~
export AWS_PROFILE=hetzner

# Exactly ONE refs/heads/main advertised (no duplicates).
test "$(git ls-remote origin refs/heads/main | wc -l)" -eq 1 \
  && echo "OK: single main ref"

# HEAD alias resolves to main, not the drifted wt/ branch.
git ls-remote origin HEAD
# expected: <keeper-sha>  HEAD   (and @HEAD -> refs/heads/main)

# Remote contains every local commit: count MUST be 0.
git fetch origin
git rev-list --count origin/main..HEAD        # expected: 0

# Exact tip match between local and remote.
test "$(git rev-parse HEAD)" = "$(git ls-remote origin refs/heads/main | cut -f1)" \
  && echo "OK: tip matches"

# Raw S3: exactly one .bundle, zero locks.
AWS_PROFILE=hetzner aws s3api list-objects-v2 --bucket kara-reports \
  --prefix current/git/kara-hermes/refs/heads/main/ --query 'Contents[].Key' --output text

8. Prevention / closeout discipline (DELTA 6)
