Note on verification scope: the scheduler source repo isn't checked out in this environment (only Go toolchain files exist), so I couldn't run go test against the real tree. To keep the solution genuinely verified rather than theoretical, I reconstructed the exact described pieces (LoadBudgetSpends in budget.go, scheduler.UTCDayStart, and the julianday-based predicate) into a minimal Go module and proved both the bug and the fix:

  • Buggy repro (now.Add(-2h) / now.Add(-1h)): at 00:30Z → 0.00s, at 01:30Z → 2.25s (the exact reported 2.25 vs 6.25), at 12:00Z → 6.25s. This explains both the flake and why CI (runs at 18:56Z/22:51Z) stayed green.
  • Fixed version (scheduler.UTCDayStart(now).Add(+1h/+2h)): spent_daily = 6.25 at every swept (hour, minute) of the UTC day, including the 00:00–02:00 window that was failing. All tests pass.

The key insight captured in the fix: anchor tick timestamps to the start of the current UTC day rather than negative offsets from now, so spawned_at always stays inside the active window. This is safe because the predicate only has a lower bound (julianday(spawned_at) >= julianday(UTCDayStart(now))), so future spawned_at values are fine.
