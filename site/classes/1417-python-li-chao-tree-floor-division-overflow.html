Root cause

The original code located line intersections in floating point and truncated with int(). Two compounding errors: 1. int() truncates, not floors — negative crossings are off by one by construction. 2. Intercepts up to 10¹⁸ exceed 2⁵³, so (b1−b2) already carries float error (~64), and the quotient can round onto the wrong side of the integer routing boundary. A crossing at 10⁹ − 10⁻⁹ (e.g. from m=(10¹⁸, 10¹⁸−10⁹), b=(0, 10¹⁸−1)) computes as exactly 1e9 → int() → 1_000_000_000 ≥ r → the new line is discarded, so the isolated query at x=10⁹ returns 10²⁷ instead of 10²⁷−1.

The fix

  • Primary — endpoint comparisons with exact big-int arithmetic (m1*x+b1 < m2*x+b2, no division at all); a dynamic node-allocating Li Chao tree, O(log N) per insert/query.
  • One-liner for the crossing-based shape: (b1 - b2) // (m2 - m1) — Python // is exact floor division for every sign, so the floor can never be off by one.

Verification (all run, all green for the fixed code)

  • Exhaustive small-domain: 400 trials, domains up to 40, parallel/duplicate/tied lines, every x vs brute force — 0 mismatches, both variants, insertion-order-independent.
  • Adversarial 1e18 slope limit (67 sets incl. the off-by-one boundary cases with denominators 10⁶…2·10⁹, interior single-point traps, 60 random huge corpora): exact trees 0 mismatches; the float version fails 4 of them with exactly the described symptom (e.g. got 1000000000000000000000000000, expected 999999999999999999999999999 at x=10⁹).
  • O(log N): instrumented max 31 node visits/insert = log₂(10⁹)+1; 200k inserts + 200k queries in ~0.4 s.
