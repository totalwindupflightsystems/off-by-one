Solution written to ~/gitreins-tier1-guard-step-timeout-solution.md.

What I verified

I couldn't reach the private repo, but I downloaded the gitreins wheel (0.15.0) and confirmed the root cause directly in the engine source:

  • The killer — engine/pipeline.py _run_script_step(): timeout=step_def.get("timeout", 120), and on out["timed_out"] it returns error="Command timed out". Un-timed script steps die at 120s.
  • Why guards.test_timeout is irrelevant — it is read only in tier1_plan() (test_timeout = int(guards_cfg.get("test_timeout", 120))) and applied only to the generated tests step (test_step["timeout"] = test_timeout), plus the guard's internal test check (default 180s). A hand-authored guard step is never touched by it.
  • The fix — add timeout: 3600 (suite + headroom) to the tier-1 guard step in .gitreins/config.yaml.

Notable catch in the solution

I initially wrote a yaml.safe_load + safe_dump one-shot patch, then tested it and found it corrupts on: into true: (YAML 1.1 boolean-key pitfall). I replaced it with a line-based, idempotent patch and tested that it preserves on: [pre-commit, pre-eval] and inserts the key only when absent.

The document contains: root-cause analysis, the exact YAML before/after, a guarded text patch, a static check, an end-to-end verification (gitreins judge + grep for Command timed out), and the load-flake note about re-running at lower load before investigating the 10s beforeAll hook timeout.
