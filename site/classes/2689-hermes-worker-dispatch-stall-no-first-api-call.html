Diagnosis

The worker wedges between "TLS established / MCP children spawned" and "session registered". The startup barrier (MCP fan-out → pre-flight) has no deadline, so a futex contention/race parks the main thread forever; API call #1 is never emitted and no sessions row appears. The scheduler then makes the policy error of equating process-alive (or unconsumed stdout) with liveness and waiting 12 minutes. A second identical dispatch works because the wedge is a transient startup race, not a bad command.

Fix

  1. Operational (works now): hermes_dispatch.py launches in its own process group (start_new_session=True), redirects stdout to a file not a pipe, baselines agent.log offset + state.db session ids, and requires first-call evidence — a new matching API call #1: model=… provider=… or a new sessions row with message_count > 0. If absent after 240 s, it SIGTERM/SIGKILLs the whole group (main + MCP children) and re-dispatches the byte-identical argv. Includes a no-deploy manual bash fallback.
  2. Durable: faulthandler.dump_traceback_later(240, exit=True) armed before MCP fan-out and cancelled after the first provider call, so a wedged startup self-kills with a thread dump naming the lock holder; plus bounded/fail-open MCP startup.

Verification (actually executed)

  • Fake attempt #1 spawned MCP-like children and wedged → dispatcher logged no first API call within 3s → killing tree, sent SIGTERM then SIGKILL.
  • Attempt #2 emitted API call #1: model=fakemodel provider=fakeprovider session=fake-session-2 → PROGRESS CONFIRMED, exit=0.
  • ps -g/pgrep showed zero leftover children; the state.db evidence path returned message_count=2; the embedded script compiles cleanly.

Encoded guardrails: liveness = first-call evidence (never ps), deadline 240 s (never 12 min), recovery = full-tree kill + identical re-dispatch, stdout to file (never an undrained pipe).
