Answer

I diagnosed the problem against the real gitreins 0.14.0 source (downloaded from PyPI) and produced a verified solution. The full markdown solution is at /workspace/solution.md, with runnable supporting files alongside it.

What I found

The class has three independent causes:

  1. Scope is frozen once, at worker start. AgenticEvaluator.evaluate() (engine/evaluator.py:997) calls _compute_allowed_files() (line ~1054) and _build_code_context() (line ~1061) before the first LLM call. Tier-1 guards run even earlier. So whole-repo criteria are graded against the dispatch-time tree.
  2. --async starts the worker immediately. _cmd_judge_worker() (cli.py:2186) calls judge.evaluate_task() (line ~2234) right away; the tick keeps committing. A pre-existing untracked file is inside the frozen snapshot; a scratch file created after dispatch is correctly identified as mid-evaluation noise.
  3. commit is HEAD at persist time, not the work commit. _persist_result() stamps HEAD (cli.py:~1717/1738), while VerdictPersister.persist() adds the real join key evaluated_at (persist.py:116). Folding by commit sha finds nothing. Also, list_verdicts() orders by directory hash, not evaluated_at, so even gitreins report order is misleading.

The exact fix

  • Land the tick's final commit before judge --async; fingerprint HEAD + git status --porcelain --untracked-files=all before/after and re-judge if it drifted.
  • Fold verdicts by task_id + newest evaluated_at, never by commit.
  • Scope criteria to paths/tests/greps; re-judge the finished tree rather than editing the criterion.

The doc includes two ready helpers: fold_verdict.py and judge_after_final_commit.sh, plus an optional additive upstream patch that records tree_changed_during_eval in the job result.

Verification (all executed)

  • repro_async_judge_snapshot.py drives the real engine.evaluator with a FakeLLM that lands a follow-up commit mid-call. It reproduces the FALSE INCOMPLETE, the board-close commit-stamp mismatch, the failed commit-sha fold, and the successful re-judge. Ran clean 5/5 times with RESULT: ALL FACTS VERIFIED.
  • The exact documented path (python -m venv → pip install gitreins==0.14.0 → run the inline harness) was tested in a clean /usr/bin/python3.12 venv and also reports ALL FACTS VERIFIED.
  • Both inline helper scripts were extracted from the markdown and exercised: the fold picks the newest evaluated_at, and the wrapper detects drift, re-dispatches, then folds the stable verdict.
