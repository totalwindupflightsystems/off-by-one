Fix: time-of-day-dependent past-due test failures (Bogota EOD cutoff)

Problem class: vitest-past-due-fixture-bogota-eod-cutoff-tod-dependence Module: apps/api/src/modules/assessment Affected tests - assessment.test.ts:502 — rejects starting attempt when quiz is past due and lateSubmissions is false - assessment.test.ts:752 — rejects submission when quiz is past due and lateSubmissions is false - gradebook.test.ts:446 — shows grade when showResultsAfter=after_due and dueDate has passed

Symptoms: AssertionError: the given combination of arguments (undefined and string) is invalid on expect(result.error).toContain('past due'), and expected undefined to be defined on the gradebook entry. Only fails when run ~00:00Z–05:00Z; green after.

Root cause

t780 (DF-EDUOS-DEXDAT-COM-CO-22, commit 58ae08a9) made due dates calendar dates in Colombia (fixed UTC-05:00, no DST). endOfDueDayUtc() in submission-service.ts computes the cutoff as the end of the due date's day:

// D = UTC calendar date of the due timestamp; cutoff = D+1 04:59:59.999Z
function endOfDueDayUtc(due: Date): Date {
  return new Date(Date.UTC(
    due.getUTCFullYear(), due.getUTCMonth(), due.getUTCDate() + 1, // next day
    4, 59, 59, 999,                                                 // 00:00 -05:00
  ));
}

Fixtures use new Date(Date.now() - 86400000) ("yesterday at this exact wall time"). With now = T and fixture UTC date D, the cutoff is D+1 04:59:59.999Z, and T ∈ [D+1 00:00Z, D+2 00:00Z):

now (UTC) cutoff vs now fixture past due?
00:00Z ≤ now < 05:00Z D+1 05:00Z > now No ❌
05:00Z ≤ now < 24:00Z D+1 05:00Z ≤ now Yes ✅

During 00:00Z–05:00Z it's still 19:00–24:00 the previous evening in Bogota — still inside the due date's Bogota day. The service is correct; the fixtures are time-of-day dependent. Verified reproduction:

now=00:00Z | 24h pastDue=false | 48h pastDue=true
now=02:00Z | 24h pastDue=false | 48h pastDue=true
now=04:00Z | 24h pastDue=false | 48h pastDue=true
now=05:00Z | 24h pastDue=true  | 48h pastDue=true

Minute sweep of a full UTC day: bad24 = 300 (exactly the 5-hour window), bad48 = 0.

Exact fix

Change the three past-due fixtures to a 48 h lookback. Do not touch endOfDueDayUtc().

assessment.test.ts (both sites) and gradebook.test.ts:446:

- const dueDate = new Date(Date.now() - 86400000);
+ // 48h lookback: always past the Bogota end-of-day cutoff, regardless of run time-of-day.
+ const dueDate = new Date(Date.now() - 2 * 86400000);

Equivalent variants:

- new Date(Date.now() - 24 * 60 * 60 * 1000)
+ new Date(Date.now() - 48 * 60 * 60 * 1000)
- addDays(new Date(), -1)
+ addDays(new Date(), -2)

48 h is safe at every wall-clock time: if due = T - 48h has UTC date D, then T ∈ [D+2 00:00Z, D+3 00:00Z), so cutoff D+1 04:59:59.999Z is always strictly before T (≥ ~19 h margin). Proven per-second under both plausible date-extraction readings.

Sweep the rest of the suite (the lesson):

rg -n "86400000|24 \* 60 \* 60 \* 1000|Date\.now\(\)\s*[-+]" \
   apps/api/src/modules/assessment/__tests__
rg -n "Date\.now\(\)\s*-|new Date\(Date\.now\(\)" apps/api/src --glob '*.test.ts'

Prefer centralizing into helpers (pastDueDate() => new Date(Date.now() - 2*86400000)). Don't blindly apply 48 h to future-date fixtures.

Why not change the product code

endOfDueDayUtc() returning D+1 04:59:59.999Z is the intended DF-22 spec (a quiz due "today" stays open until 23:59:59 Bogota). Weakening it is a product regression. Fix the fixtures, not the spec.

Prevention

When a suite gains a timezone/calendar-day cutoff convention, sweep every relative-date fixture for run-time dependence at the convention's day boundary, and pin at least one test to that boundary window (00:00Z–05:00Z for America/Bogota).
