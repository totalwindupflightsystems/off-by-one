What I diagnosed

The problem class is six interacting send-side flow-control bugs, not one:

  1. SETTINGS_INITIAL_WINDOW_SIZE delta not applied to existing streams — RFC 7540 §6.9.2 requires applying the delta to every stream window; it can go negative, which must stall.
  2. Pre-split queued DATA — a window shrink leaves stale frames. Fix: a cursor-based pump that re-splits from (offset, remaining) and advances only on a real write (no dup/loss).
  3. WINDOW_UPDATE on a reset stream — must be discarded, and only streamId 0 may touch the connection window.
  4. HEADERS/CONTINUATION contiguity — gate the pump with headerBlockInFlight; stream + connection windows still apply.
  5. DATA on idle streams — pump only runs for open/half-closed(remote) after HEADERS.
  6. Stream window > 2³¹−1 — must emit RST_STREAM(FLOW_CONTROL_ERROR) + error event, not hang.

The fix

A raw net-socket HTTP/2 client (h2flow.js) whose single _pumpStream is the only consumer of flow-control credit, enforcing both windows simultaneously, plus a scripted hostile MockServer (test.js).
