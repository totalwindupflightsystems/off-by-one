ARIES Redo/Undo Recovery with Undo-Redirect and Page-Split

Problem class: go-20261025-aries-undo-redirect-page-split-recovery Language / toolchain: Go 1.26 Status: fixed and verified (all crash-injection points converge)

1. Symptom

After a crash, recovery rolls back uncommitted transactions. When an uncommitted update is undone after the page it wrote to has been split, the rollback silently fails to remove the update: keys that belong to aborted transactions remain visible, and pages that no longer hold those keys receive bogus deletions. A second crash during recovery can make things worse by re-applying compensations or by trying to undo the page split itself.

Correct recovery produces p2/70=g p2/85=j2; the old "apply the inverse to the page named in the log record" approach produces resurrected keys:

p2/35=c p2/40=d p2/50=e p2/70=g p2/85=j2 p3/90=i

The extra keys 35, 40, 50, 90 all belong to loser transactions.

2. Root-cause analysis

2.1 Undo is a physical page-image operation. An update log record stores PageID, Key, Before, After. Naive undo applies the inverse to PageID. But a page split moves records to a new page. After the split the key is no longer on PageID, so the compensation deletes a key that is not there (no-op) and the key on the new page is never removed. Undo must be logical and resolve the current location of the key.

2.2 A page split is a structure modification that must survive abort. A split is a nested top action (NTA): it must remain in force even if the transaction that triggered it aborts, because other transactions now depend on the new page. A naive undo walks the transaction's prevLSN chain straight through the split record and undoes the split. The undo walk needs an undo-next pointer that skips an entire NTA.

2.3 Recovery must be idempotent across a second crash. If recovery crashes after applying a compensation but before the page is flushed, the next recovery must not redo committed work incorrectly, must not re-undo already-undone records, and must be able to replay the compensation. ARIES solves this with CLRs and the pageLSN check: a CLR is a redo-only record; pageLSN >= record.LSN makes redo idempotent; when undo meets a CLR it jumps to CLR.UndoNxt.

The original code had none of this: no undoNxtLSN, no split records with moved key/value pairs, no CLRs with correct prevLSN/undoNxt chaining.

3. The fix

3.1 Log record extensions

Every record carries UndoNxt: ordinary update UndoNxt = PrevLSN; page split (NTA) UndoNxt = LSN immediately before the action. Page-split records carry the exact moved key/value pairs, making split redo and key-location resolution deterministic and idempotent.

3.2 Logical undo with redirect

func (db *DB) resolvePage(rec LogRecord) PageID {
    if db.BrokenRawUndo {
        return rec.PageID
    }
    page := rec.PageID
    for lsn := rec.LSN + 1; lsn <= db.Log.LastLSN(); lsn++ {
        s := db.Log.Get(lsn)
        if s.Type != RecSplit || s.PageID != page {
            continue
        }
        for _, kv := range s.Moved {
            if kv.Key == rec.Key {
                page = s.NewPage
                break
            }
        }
    }
    return page
}

The CLR stores PageID (where the compensation was applied), OrigPage (the page named by the update), Redirected, UndoOf and UndoNxt. This is the undo-redirect record: durable evidence that an undo was redirected through a split, with UndoNxt as the continuation point.

3.3 Correct undo / CLR chaining

case RecCLR:
    lsn = rec.UndoNxt                 // already compensated: skip
case RecUpdate:
    target := db.resolvePage(rec)
    cop, val := compensationFor(rec)
    clr := LogRecord{
        TxnID: t, Type: RecCLR, Op: cop, Key: rec.Key, After: val,
        PageID: target, OrigPage: rec.PageID, Redirected: target != rec.PageID,
        UndoOf: lsn, UndoNxt: rec.UndoNxt, PrevLSN: st.LastLSN,
    }
    clrLSN := db.Log.Append(clr)      // WAL: CLR durable first
    st.LastLSN = clrLSN
    p := db.Buffer.get(target)
    applyRedo(p, clr)
    p.PageLSN = clrLSN
    lsn = rec.UndoNxt
case RecSplit:
    lsn = rec.UndoNxt                 // nested top action: never undone

The CLR is appended before the buffer-pool change, so a crash in between leaves a durable CLR that the next redo replays. Undo starts at LastLSN; if that is a CLR it jumps to UndoNxt, so no compensation is applied twice.

3.4 Three-phase recovery

  • Analysis resumes at the most recent checkpoint, restores its transaction table and dirty page table, then scans forward updating both. Losers are active or aborting transactions.
  • Redo starts at the minimum recLSN in the analysis DPT and replays every update, split and CLR. pageLSN >= LSN skips already-applied changes.
  • Undo processes losers newest-first, following PrevLSN/UndoNxt and writing CLRs, then writes an END record for each.
