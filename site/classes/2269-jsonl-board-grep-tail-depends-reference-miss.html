Fix: JSONL Board grep <id> | tail -1 Reads the Wrong Row

Problem class: jsonl-board-grep-tail-depends-reference-miss Repo: get-h3/lore · Commit: c655666 · Board: .coding-hermes/board/tasks.jsonl Artifact: /tmp/lore-enum-011.py (id-field classifier). Related skill: jsonl-foreman-board-reading rules 10/11.

Symptom

boardctl update LORE-011 --status complete reported success, but the verification command

grep 'LORE-011' tasks.jsonl | tail -1 | jq '{id,status,foreman_note,commit_hash}'

returned a row with a stale foreman_note and the wrong commit_hash, making the flip look botched. Acting on it would have "fixed" a healthy row.

Root Cause

The board is JSONL and serializes rows with status first, so ids appear anywhere in a line. A plain substring grep for LORE-011 matches:

  1. the actual LORE-011 row(s) — where .id == "LORE-011", and
  2. later rows that merely reference it in depends_on / blocks / notes.

tail -1 unconditionally takes the last physical substring hit. On the board that was LORE-012, whose depends_on: ["LORE-011"] and whose own stale note/commit got misattributed to LORE-011.

A second, compounding trap: ids can be recycled, so several physical rows may genuinely have id == "LORE-011". The authoritative row is the last id-FIELD match (last-wins), not the last substring match.

{"status": "pending",  "id": "LORE-011", ...}                       // recycled old row
{"status": "complete", "id": "LORE-011", ... "commit_hash": "c655666"} // effective row (last id-field)
{"status": "complete", "id": "LORE-012", "depends_on": ["LORE-011"], // <-- grep|tail-1 lands HERE
 "foreman_note": "stale note mentioning LORE-011", "commit_hash": "deadbeef"}

Key insight: the false alarm is itself the detector. If tail -1's row does not match on the .id field, the grep hit a reference and you must keep walking backwards.

The Fix

1. Classifier / effective-row resolver — /tmp/lore-enum-011.py

For every line containing the id, classify where it matched, then pick the last ID_FIELD match.

#!/usr/bin/env python3
"""lore-enum-011: id-field classifier / effective-row resolver for JSONL boards.
Usage: python3 lore-enum-011.py <board.jsonl> <ID>
"""
import json, sys

def classify(row, target):
    if row.get("id") == target:
        return "ID_FIELD"
    for key in ("depends_on", "blocks", "blocked_by", "dependencies"):
        val = row.get(key)
        if (isinstance(val, list) and target in val) or val == target:
            return f"{key.upper()}_REF"
    if target in json.dumps(row, sort_keys=True):
        return "FREE_TEXT"
    return None

def main():
    board, target = sys.argv[1], sys.argv[2]
    hits = []
    with open(board, encoding="utf-8") as fh:
        for lineno, raw in enumerate(fh, 1):
            if target not in raw:
                continue
            raw = raw.strip()
            if not raw:
                continue
            try:
                row = json.loads(raw)
            except json.JSONDecodeError as exc:
                print(f"{lineno:>5}  PARSE_ERROR  {exc}"); continue
            hits.append((lineno, classify(row, target), row))

    print(f"=== all physical lines containing {target!r} ===")
    id_hits = []
    for lineno, cls, row in hits:
        print(f"{lineno:>5}  {cls:<12} id={row.get('id')!r} "
              f"status={row.get('status')!r} commit={row.get('commit_hash')!r}")
        if cls == "ID_FIELD":
            id_hits.append((lineno, row))

    print(f"\nsubstring hits: {len(hits)}   id-field hits: {len(id_hits)}")
    if not id_hits:
        print(f"NO id-field match for {target!r}: only referenced, never defined."); return
    eff_lineno, eff = id_hits[-1]
    print(f"effective row = last ID_FIELD match at line {eff_lineno}")
    print(json.dumps(eff, indent=2))
    if hits[-1][0] != eff_lineno:
        print(f"\nTRAP CONFIRMED: grep|tail -1 would read line {hits[-1][0]} "
              f"({hits[-1][1]}), NOT the effective line {eff_lineno}.")

if __name__ == "__main__":
    main()

2. Quick one-liners (no script needed)

# Effective row for one id — last id-FIELD match (slurp):
jq -s -c '[.[] | select(.id=="LORE-011")] | last' tasks.jsonl

# Streaming, constant memory, last-wins:
jq -c 'select(.id=="LORE-011")' tasks.jsonl | tail -1

# Full last-wins census over the whole board:
jq -s 'group_by(.id) | map(last) | ...' tasks.jsonl

# Anchored grep: match the id FIELD, not the substring. Still must take the
# LAST id-field line for recycled ids:
grep -n '"id": "LORE-011"' tasks.jsonl | tail -1

3. The false-alarm detector (walk backwards from EOF)

grep 'LORE-011' tasks.jsonl | tac | while IFS= read -r line; do
  rid=$(printf '%s' "$line" | jq -r '.id')
  if [ "$rid" = "LORE-011" ]; then
    printf '%s' "$line" | jq -c '{id,status,foreman_note,commit_hash}'; break
  fi
  echo "skip: substring hit on depends_on of $rid" >&2
done

Rule: a grep <id> hit only counts when jq -r '.id' on that line equals <id>. Otherwise it is a reference in depends_on/blocks/free text — keep walking backwards.

jq -c 'select(.id=="LORE-011")' tasks.jsonl | tail -1

The final git diff of the board should show exactly the intended lines changed; the last-wins census confirms no unintended row was touched.

Takeaways

  1. Never resolve a JSONL row with grep <id> | tail -1. Anchor the match to the id field and take the last id-field match.
  2. Enumerate and classify every hit (ID_FIELD vs depends_on/blocks ref vs free text) before acting.
  3. Treat the false-alarm (tail-1 row whose .id differs) as the signal to walk backwards, not as a reason to "repair" a healthy row.
  4. Prefer jq -s 'group_by(.id) | map(last)' for a whole-board census, or the streaming select(.id==...) | tail -1 for a single id.
  5. If boardctl emits its own auto task_completed event, account for it in the census so the event row is not mistaken for the task row.
