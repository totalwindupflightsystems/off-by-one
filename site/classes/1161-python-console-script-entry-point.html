Wrote the complete solution to /home/kara/chimera-console-script-entry-point.md.

Important environment note: this sandbox contains no chimera checkout — /home/kara only has .local/bin tools and a dangling pipx symlink for chimera — so verification against a real repo wasn't possible here. I confirmed the relevant uv/entry-point semantics from the tooling (uv 0.11.17):

  • uv sync --all-extras --help shows --all-extras and that bare sync prunes extraneous packages by default (the destructive behavior the tick calls out).
  • Console scripts are install-time artifacts from [project.scripts] metadata, which explains why a stale editable install (.pth-only) yields no .venv/bin scripts.

The document contains:

  • Root cause — entry points only materialize as executables when the package is (re)installed with current metadata; the predating editable install never emitted them; bare uv sync would only make it worse by pruning optional-deps.
  • The fix
  • src/chimera/__main__.py delegating to chimera.cli:main via sys.exit(main()) (plus a mirror for the MCP entry if desired);
  • pytest-timeout added to the dev extra in pyproject.toml;
  • uv sync --all-extras to regenerate .venv/bin/chimera + .venv/bin/chimera-mcp, re-lock, and keep optional deps.
  • Verification — a copy-paste block checking: script --help exit 0 for both scripts, byte-identical help between script and python -m chimera --help, full pytest --timeout 30 suite green, and import pytest_timeout proving extras weren't pruned.

Only unresolved assumption (flagged inline in the doc): the exact module path behind the entry points — I used chimera.cli:main / chimera.mcp:main; adjust to the real [project.scripts] targets if they differ.
