Done. The solution is in ~/bunker-logind-wedge/RUNBOOK.md with tested supporting scripts.

Root cause (grounded in this host)

bunker's own help text named the failure mode exactly:

Every agent spawn enables systemd linger for its per-agent user. A linger entry whose user no longer exists is stale: logind keeps churning on it and thousands of stale entries starve user-manager starts host-wide (INT-CI-007/INT-HOST-001: 8024 entries for 2 live users).

Chain: spawn enables linger → destroy/cancelled-spawn/failed-rollback deletes the user without removing the linger file → thousands of dangling /var/lib/systemd/linger/bunker-* entries → systemd-logind's single D-Bus dispatch loop is saturated by GC/user_start churn → busctl introspect times out while the unit still reports active. The probe (bunker_logind_up) was correct; process-liveness (systemctl is-active) was the lie.

Fix

  • Immediate (safe/idempotent): bunker linger prune (dry-run first) then bunker homes prune; only restart systemd-logind if the bounded probe doesn't recover after ~60s. Packaged in bunker-logind-remediate.sh.
  • Prevention: remove the linger entry (via loginctl disable-linger) before userdel in the lifecycle — the real bug — plus a 15-min bunker-residue-prune.timer safety net.
  • Monitoring: a textfile probe exporting bunker_logind_up and bunker_logind_active, with the wedge alert bunker_logind_up == 0 and on(host) bunker_logind_active == 1, plus early-warning bunker_linger_entries{state="stale"} > 1000.

What I actually verified here

  • bunker linger prune --dir <fixture>: scanned 4, removed exactly the 2 stale entries, kept root/kara.
  • bunker homes --dir <fixture>: classified stale vs. live correctly.
  • The probe end-to-end against a linger fixture emitted correct metrics (total 3 / live 1 / stale 2), and BunkerLogindWedge correctly did not fire when active=0 (container has no systemd).
  • All shell scripts pass bash -n; alert YAML parses as valid YAML.

One caveat worth flagging: I could not exercise the live busctl/systemctl path or promtool because this container is not booted with systemd as PID 1. The D-Bus wedge mechanism and recovery steps are derived from the embedded tool documentation plus working fixture tests, not from a live wedged logind.
