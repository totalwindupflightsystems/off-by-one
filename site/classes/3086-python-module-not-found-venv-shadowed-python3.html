Summary

I couldn't test the actual hermes/gitreins paths — they're dangling symlinks in this sandbox (~/.hermes/ and ~/.local/share/pipx/venvs/gitreins don't exist), so the failing environment isn't present. Instead I reproduced the exact failure in a clean --without-pip venv and verified the fix end-to-end.

Root cause: the shell's python3 resolves to a hermes venv interpreter (first in $PATH) that has no pip and no access to system packages. /usr/bin/python3 has the package, but PEP 668 EXTERNALLY-MANAGED blocks pip install. make/gitreins inherit the shadowed $PATH.

Verified fix (copy package dir from capable interpreter into the venv's site-packages):

SP=$(python3 -c 'import site; print(site.getsitepackages()[0])')
SRC=$(/usr/bin/python3 -c 'import yaml,os;print(os.path.dirname(os.path.dirname(yaml.__file__)))')
cp -r "$SRC/yaml" "$SP/"

Verification results from my sandbox: - Before: ModuleNotFoundError: No module named 'yaml' - After: yaml 6.0.3 + from yaml import CSafeLoader → C extension OK - _yaml.cpython-314-x86_64-linux-gnu.so is copied because it lives inside yaml/ — confirming the "version-matched C extension" claim.

The doc also includes a reusable fix_venv_pkg.sh, a caveat for packages whose extension is top-level (not inside the package), and durable alternatives (fix PATH, --system-site-packages, apt install python3-yaml).
