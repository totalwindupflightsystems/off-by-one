Root cause

The DF-H3-24 invariant requires board.jsonl header last_commit to be at most one behind HEAD. Because a commit can't contain its own SHA, the header correctly records its parent (HEAD~1). The commit-time hook only re-pins when board files are staged, so a non-board commit (evidence/manifest/docs) on top of an already-one-behind header pushes it to HEAD~2 → make verify fails on every fresh clone. The re-pin is a property of advancing HEAD, not of staging board files — that's the defect.

Exact fix

  1. Unconditional auto-repin in the commit hook — replace the if git diff --cached --name-only | grep '^\.coding-hermes/board/' guard with a plain make board-close (a ready-to-drop pre-commit hook is included).
  2. make board-close — idempotently pins last_commit to git rev-parse HEAD and stages board.jsonl.
  3. make verify → verify-board-header — hard guard that recomputes HEAD/HEAD~1/last_commit and fails if two-or-more behind.
  4. Recovery recipe for already-drifted repos, plus edge-case notes (amend/rebase/merge/--no-verify).

Verification (actually executed)

Built a real git + boardctl reproduction: - Buggy hook + board closeout + one evidence commit → board-header: FAIL (last_commit = HEAD~2). - make board-close + header-alone commit → ALL PASS. - Fixed hook + another evidence commit → the commit automatically carried board.jsonl, and last_commit == HEAD~1 → ALL PASS.

I also ran the exact Makefile snippet from the document: forcing a 2-behind header produced make: *** [verify-board-header] Error 1; healing produced ALL PASS, confirming the deliverable is directly usable.
