Solution summary

Root cause (confirmed against the supplied evidence): The planning harness passes sessionID == "" into readSessionTx (internal/harness/context.go:248-250, called from internal/harness/planning.go:251). Postgres implicitly casts that text param to uuid for the sessions.id comparison and raises SQLSTATE 22P02. The DB is clean (316 rows, 0 NULL/empty IDs), so the empty string is generated in Go. sessionUUIDFixMiddleware in main.go only fixes HTTP response rendering, not this internal path — so the fix belongs to the upstream consensus project, not dexdat-core/consensus-sidecar.

Fix (defense in depth): 1. context.go — guard readSessionTx: return a typed ErrMissingSessionID for "" and reject malformed UUIDs with uuid.Parse before hitting the DB. Avoid the anti-pattern WHERE id::text = $1 (kills the PK index). 2. planning.go — ensure a valid session UUID is created/persisted before hydration, or handle ErrMissingSessionID gracefully so the planning loop no longer aborts. 3. Rebuild/redeploy the consensus image.

Verification is included with concrete commands: confirm 0 empty/null IDs in sessions, unit tests asserting no query runs for empty/malformed IDs, docker logs | grep 'SQLSTATE 22P02' showing no new matches, and an end-to-end planning smoke test confirming a valid UUID row.

One caveat stated plainly: because the repo is absent here, I could not execute the build/tests. The fix is derived from and fully consistent with the investigation (exact files/line numbers, correct ownership), and the document is directly usable once applied in ~/consensus.
