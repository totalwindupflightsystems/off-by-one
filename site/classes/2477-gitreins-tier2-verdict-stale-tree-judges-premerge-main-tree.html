What I found

Root cause: get_workdir() (gitreins/cli.py:274) returns the process CWD's repo root. cmd_task_complete (:1351) and cmd_judge (:2063) use it for both the task store and the judge. When a task's work is on an unmerged worktree branch, it grades the main tree — which still has the baseline (the 1357 leak findings), so Tier 1 fails before the change is ever seen.

Three supporting facts made it worse: - The verdict is stamped worktree/branch/commit of the graded tree (engine/persist.py:790), so a main-tree verdict is recorded with wrong provenance. - WorktreeManager._matching_verdicts/_find_verdict (engine/worktree_manager.py:941,961) only accept verdicts matching the worktree path + branch + commit, so the stray FAIL also blocks the intended worktree merge path. - Re-running inside the worktree doesn't work: .gitreins/tasks.yaml is gitignored and absent from linked worktrees → Task not found.

The fix (in the doc as a ready -p1 patch)

  1. _resolve_judgment_tree() — keeps the task store in canonical main, points the judge at the registered worktree (with --tree override).
  2. _warn_if_verdict_tree_mismatch() — on FAIL, compares judged HEAD vs worktree branch tip and labels mismatches STALE, so a wrong-tree verdict is never treated as a code failure.
  3. Hardening: ignore .gitreins/tasks.yaml.lock in _is_clean so a completed task isn't blocked from merging.

Verified

  • Built a scratch repo with a leak on main and a worktree commit removing it.
  • Before: task complete from main → Overall: FAIL; from worktree → Task not found.
  • After: task complete from main → Judging task worktree: … → Overall: PASS; forced --tree main → WARNING: FAIL verdict is STALE; worktree merge then fast-forwards and the leak is gone.
  • Added tests/test_task_complete_worktree.py; full run of the new test + all three worktree suites = 78 passed.
