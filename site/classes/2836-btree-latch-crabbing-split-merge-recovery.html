Latch-Crabbing B+Tree with WAL Recovery — Diagnosis and Verified Fix

The complete, self-contained solution (all source + proof) is written to ~/SOLUTION.md; the working tree is ~/btree. It was verified by extracting every Go block from the markdown into a fresh directory and running the suite there: ok bptree 0.383s.

Root-cause analysis

The failure modes are order-of-operations bugs in four primitives.

1. Data written before the WAL is durable. A 4 KiB write is not atomic. If the page reaches disk first and is torn, there is no after-image to restore it. Fix: one funnel — stamp LSN → append full-page after-image → fsync WAL → write data page. Recovery redoes every record with LSN > pageLSN or restores any page whose CRC fails.

2. Losing the parent high key on a torn split. A split sets the old node's RightSibling/HighKey and then inserts the separator in the parent. A crash in between loses the separator. Fix: (a) log the after-image of every page the split touches (R, L, P, meta); (b) make reads B-link aware (key >= HighKey && RightSibling != 0 → move right); (c) recovery recomputes each internal separator from the child's actual minimum key — that minimum is the parent's high key.

3. Deadlock from inconsistent latch order. Parent-after-child, same-rank sibling double-latch, and unprotected root reads all create cycles. Fix: strict rank rank(depth, pageID) = (depth<<40) | (pageID & (2⁴⁰−1)); every acquisition must strictly increase rank; siblings are taken in ascending pageID order. Since a thread only waits for a higher rank than it holds, the wait-for graph is acyclic — resource-ordering proof of deadlock freedom, asserted at run time.

4. Top-down delete descended into the wrong sibling. Pre-emptive deletion made a child safe, then always returned the left survivor. On redistribution the target key stays in the right node, so it was lost. Fix: return the node owning the target range (left on merge, right on redistribution of the right sibling).

5. LSN race and root race under concurrency. NextLSN() + Append is check-then-act (produced lsn mismatch); reading root before latching it lets a root change slip in. Fix: a pager mutex makes stamp+append+flush+write atomic; a rootMu read-write lock closes the read→latch window.

Exact fix (critical code)

One funnel enforces WAL ordering (pager.go):

func (pg *Pager) logAndWriteLocked(p *Page) error {
    p.LSN = pg.wal.NextLSN()
    data := p.encode()
    lsn := pg.wal.AppendPageImage(p.ID, data)
    if err := pg.wal.FlushTo(lsn); err != nil { return err } // log durable …
    return pg.writeRaw(p.ID, data, false)                    // … then data
}

Strict latch rank and run-time invariant (latch.go):

func rankFor(depth int, id uint64) uint64 { return uint64(depth)<<40 | (id & ((uint64(1)<<40)-1)) }

func (lm *LatchManager) Acquire(ch *LatchChain, id uint64, depth int, mode latchMode) {

        lm.recordViolation(fmt.Sprintf("rank order violation: page %d rank=%d after page %d rank=%d",

Deadlock-freedom proof (summary): let rank(p)=(depth(p), pageID(p)). Every acquire is checked to satisfy rank(new) > rank(last held). A deadlock cycle T1→…→Tk→T1 would require r1<r2<…<r1, a contradiction. Key direction (ascending vs descending) does not affect latch order, so both streams are safe. The run-time checker fails loudly on any violation.
