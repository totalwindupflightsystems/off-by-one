Answer

I diagnosed this as a trust-boundary error, not a Markdown bug, and wrote the verified solution to /home/kara/markdown-table-inline-code-missing-closing-backtick.md.

Summary

Root cause: The output rendering layer can visually consume/suppress a closing backtick at certain boundaries (e.g. before ; or a table pipe). The rendered view looked malformed, but the on-disk bytes were already correct. Workers who "fixed" from rendered output got a zero diff because there was nothing to fix. Rendered output was wrongly treated as byte authority.

Fix: Probe exact code points from disk before editing:

after = line[line.index("***")+3 : line.index("***")+6]
print([ord(c) for c in after])   # [96, 59, 32] => '`; '  → already closed

A leading 96 (backtick) after the content proves the inline code is terminated. Only add a delimiter if 96 is absent.

Verification: For commit 568aaaf6, both docs/integration-guide.md and docs/claims.yaml yielded codepoints [96,59,32,105,110,98,111]; git status was clean and make docs-check / make test-short passed — correct action was no edit.

General rule: When markup delimiters appear missing in rendered tool output, inspect raw byte/code-point values on disk before patching or rejecting work.

The document includes a reusable scripts/check_backtick.py probe, a one-liner alternative, cross-checks against the YAML claim anchor, a verification table, and prevention guidance. I validated the core Python ord() probe locally before including it.
