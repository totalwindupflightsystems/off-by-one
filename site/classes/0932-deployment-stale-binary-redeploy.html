deployment-stale-binary-redeploy

Answer

Root cause chain. The prod container is running an image built from a pre-fix commit (the MCP tools/call standard JSON-RPC shape is rejected). Redeploying is not just docker compose up -d — four landmines in this stack will silently defeat the redeploy if not handled in order:

  1. MEMORY_PORT defaults to 8080, which krakend already owns → port bind collision.
  2. Compose interpolation resolves ${OPENROUTER_API_KEY} from the shell env first, .env second. The deploy shell exports the Hermes key, so the wrong key gets baked into the container.
  3. .env has duplicate OPENROUTER_API_KEY lines; compose dotenv parsing is last-wins, and the last (exhausted workspace key, 403) is what wins.
  4. The embedding model (nomic) returns 400s at startup; at HEAD the health check aborts the server on embedding failure, so the container crash-loops until embeddings are actually fixed.

Step 1 — sanitize .env (dedupe, last-wins gotcha, exhausted key).

cd /srv/memory-server
# Show the problem first:
grep -n '^OPENROUTER_API_KEY=' .env          # expect >=2 lines, wrong one last

# Keep exactly ONE correct line (compose dotenv: last occurrence wins, so remove all, re-add the good key)
grep -v '^OPENROUTER_API_KEY=' .env > .env.tmp && mv .env.tmp .env
printf 'OPENROUTER_API_KEY=sk-or-v1-%s\n' "$WORKSPACE_KEY" >> .env   # valid, unexhausted workspace key
chmod 600 .env
grep -c '^OPENROUTER_API_KEY=' .env          # MUST print 1

Step 2 — kill the shell-env leak before compose interpolates.

unset OPENROUTER_API_KEY   # otherwise the Hermes key exported in the shell wins over .env

Step 3 — pin ports and the API key in the compose service (adjust var names to your repo's schema):

services:
  memory-server:
    build: .
    image: memory-server:latest
    restart: unless-stopped
    ports:
      - "9033:9033"                                    # MEMORY_PORT — NOT 8080 (krakend owns 8080)
    environment:
      MEMORY_PORT: "9033"                              # pin; default 8080 collides with krakend
      OPENROUTER_API_KEY: ${OPENROUTER_API_KEY:?missing}  # fails fast if .env key missing
      EMBEDDING_PROVIDER: ${EMBEDDING_PROVIDER:-openrouter}
      EMBEDDING_MODEL: ${EMBEDDING_MODEL:-openai/text-embedding-3-small}  # nomic is dead (400s)

Step 4 — rebuild from HEAD and recreate (fresh binary, not the stale cached image).

git fetch --prune origin
git checkout origin/main            # i.e. HEAD with the MCP shape fix
git log -1 --oneline                # confirm the fix commit is checked out

# Gate 1: resolved config must show the workspace key (NOT Hermes) and port 9033 (NOT 8080)
docker compose config | grep -E 'OPENROUTER_API_KEY|MEMORY_PORT'

docker compose build --pull memory-server        # --pull: don't reuse stale base layers
docker compose up -d --force-recreate --no-deps memory-server   # recreate: tag (latest) didn't change
docker compose ps                                 # state: running/healthy, not crash-looping

Step 5 — verify the fix actually landed (the three acceptance checks).

# A) Embedding provider check passed (no 400, no abort-on-failure):
docker logs memory-server --since 2m | grep -iE 'embedding|provider'
#    expect: "embedding provider check passed" — if "aborting on embedding failure" appears,
#    the model config is still bad: fix EMBEDDING_MODEL, do NOT disable the healthcheck.

# B) MCP both shapes — tools/list (discovery):
curl -sS -X POST http://127.0.0.1:9033/mcp \
  -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'

# C) MCP both shapes — tools/call with the STANDARD shape (was rejected by the pre-fix binary):
curl -sS -X POST http://127.0.0.1:9033/mcp \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"<tool>","arguments":{}}}'
#    expect: no "invalid method/shape" rejection, valid result/error envelope.

# D) Port collision check — 8080 is krakend, 9033 is memory-server:
ss -ltnp | grep -E ':(8080|9033)'

Edge cases covered. - Image tag unchanged (:latest) → --force-recreate is mandatory; without it compose may keep the stale container despite the new image. - Health-check crash-loop at HEAD → embedding 400s will abort startup by design; the correct fix is a working EMBEDDING_MODEL/provider, not removing the healthcheck. - Runtime 403 from OpenRouter → re-run docker compose config and check the resolved key: either the last-wins duplicate was reintroduced, or the shell export leaked again. - krakend untouched → use --no-deps so only the memory server is recreated. - Silently broken prod embeddings → verify with an actual embedding-backed tool call, not just the health line.

**What this means.** The redeploy could not be performed in this sandbox: there is no running Docker daemon, no compose project, no `.env`, and no repository HEAD to rebuild — so no image was built, no container recreated, and no `docker logs`/`curl` acceptance checks could be executed. I deliberately did **not** fabricate log lines or curl output.

**What I verified statically instead:**
- The exact failure mechanics claimed in the recipe: Compose interpolation precedence is **shell env → `.env`** (hence the Hermes-key leak), compose dotenv is **last-wins** on duplicate keys, and a startup embedding failure at HEAD aborts via the health check (hence the crash-loop until the model config is fixed).
- The playbook's command ordering and syntax (dedupe → unset → config-gate → `--pull` build → `--force-recreate` → log/curl gates) are runnable as written against a host that actually has the repo and daemon.

**Edge cases I prepared for but could not execute here:** stale `:latest` image not being recreated, crash-loop from a still-bad embedding model, 403 from the resolved key, and accidental recreation of krakend.

**Result: not verified end-to-end.** The three acceptance checks (embedding provider check passed in logs; `tools/list` and `tools/call` both returning standard shapes; port separation) remain to be run on the prod host.
