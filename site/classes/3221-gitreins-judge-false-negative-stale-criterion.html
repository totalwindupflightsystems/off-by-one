What I found

The RELEASE-020 scenario has four cooperating root causes, three in GitReins itself:

A — Judge grades the control checkout, not the worker branch. gitreins/cli.py:2463 builds Judge(llm, workdir, scan_root=scan_root) where workdir is get_workdir() — the checkout you run in. engine/persist.py:1090-1092 binds every verdict to working_tree_content_fingerprint over that tree, and :1248-1256 refuses to persist without it. Running task complete from main before merging wt/RELEASE-020 binds the verdict to the old control tree (ece2319, 0.20.0). Measured: control digest d5c992ce… vs delivered 8ea9088 digest 2e4d748c….

B — Stale editable metadata. engine/version.py:20 reads metadata.version("gitreins") before falling back to pyproject.toml. An editable install bakes the version at install time, so bumping pyproject.toml to 0.21.0 leaves metadata at 0.20.0. Verified the exact red/green: AssertionError: assert '0.20.0' == '0.21.0' before uv pip install -e ., then 4 passed.

C — Changelog ordering. 2cff40d put ## [0.21.0] under Unreleased but left ## [0.20.0] above both. 8ea9088 moved it below, restoring Unreleased → 0.21.0 → 0.20.0 → 0.19.0.

D — Thin criterion. .gitreins/config.yaml sets criteria.enforce: refuse, but RELEASE-020's criterion was narrative with no FAILIF:/PROOF:, so it never forced the metadata/order checks.

Fix (all verified)

  1. Merge-before-judge: git merge --ff-only origin/wt/RELEASE-020 (or gitreins worktree merge, which rebases then re-judges the tree). After merging, the control tree digest matched the delivered tree exactly.
  2. Refresh the editable install: uv pip install --python .venv/bin/python -e . → metadata and gitreins.__version__ both 0.21.0.
  3. Fix changelog order to Unreleased, 0.21.0, 0.20.0.
  4. Rewrite the criterion with FAILIF:/PROOF: arms for version, metadata, changelog order, and docs-drift.
  5. Re-judge to produce a new verdict bound to the delivered tree.
