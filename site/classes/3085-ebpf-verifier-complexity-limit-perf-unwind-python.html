Fix: pyroscope.ebpf fails to load on Linux 7.0 — perf_unwind_python BPF verifier rejection

Symptom (all-or-nothing tracer load failure):

time="..." level=error msg="failed to load perf_unwind_python: ..."
BPF program is too large. Processed 1000001 insn (limit 1000000)
max_states_per_insn 194 total_states 23351 peak_states 1181

Because pyroscope's eBPF tracer loads all unwind programs as a unit, this single program tripping the verifier's compile-time complexity budget aborts the entire tracer. Result: no process on the host is profiled, not just Python.

Affected: grafana/alloy on Linux kernels 7.0.0-31 … 7.0.0-38 (x86_64).

Root cause

This is not a program-size bug. perf_unwind_python is a state-space explosion that exceeds BPF_COMPLEXITY_LIMIT_INSNS (hard-coded 1000000, not tunable at runtime):

Verifier counter Observed
insns processed 1000001 (limit 1000000)
max_states_per_insn 194
total_states 23351
peak_states 1181

The kernel explores an exponential number of verifier states across the Python unwinder's branches before it runs out of instruction budget. The 1-instruction overage is cosmetic — the program is nowhere near fitting.

Upstream fixed this in grafana/opentelemetry-ebpf-profiler PR #1626 (fork: grafana fork PR #69, "python: avoid verifier blowup on 7.0"), which adds a continue_with_next_unwinder path so the Python unwinder bails out to the next unwinder instead of building a giant verifier graph. No Alloy release embeds that fix yet (latest checked: v1.21.3, Oct‑28 build sha256:8ab87120).

Confirmed dead ends (do not waste time on these)

  1. Newer kernel does not help — identical rejection on 7.0.0-31 and 7.0.0-38.
  2. Newer Alloy image does not help — identical rejection from the Sep‑28 build through v1.21.3.
  3. No sysctl exists to raise the verifier budget. The only BPF sysctls are kernel.bpf_stats_enabled, kernel.unprivileged_bpf_disabled, net.core.bpf_jit_enable; none change BPF_COMPLEXITY_LIMIT_INSNS.

Exact fix (working mitigation, restore profiling now)

Disable the Python HLL unwinder in the pyroscope.ebpf component. Python high-level (HLL) frames are lost, but profiling for every other runtime is immediately restored because the failing program is never loaded.

1. Edit the Alloy config

pyroscope.ebpf "default" {
  // ... existing targets/forward_to/etc ...

  // WORKAROUND: avoid verifier state-space explosion in perf_unwind_python
  // on Linux 7.0 kernels until an Alloy release embeds profiler PR #1626.
  python_enabled = false

  // Other per-HLL toggles left at defaults (true):
  // go_enabled       = true
  // hotspot_enabled  = true
  // ruby_enabled     = true
  // php_enabled      = true
  // perl_enabled     = true
  // dotnet_enabled   = true
  // v8_enabled       = true
}

python_enabled is a documented argument of pyroscope.ebpf. The same per-HLL toggles (go_enabled, hotspot_enabled, ruby_enabled, php_enabled, perl_enabled, dotnet_enabled, v8_enabled) exist if you need to isolate other unwinders.

2. Recreate the Alloy container

A bind-mounted config change is not picked up by docker compose up -d. The container has to be recreated so Alloy re-reads the file:

docker compose up -d --force-recreate alloy
# or, equivalently:
docker compose stop alloy && docker compose rm -f alloy && docker compose up -d alloy

A plain docker restart alloy may work if Alloy re-reads its config on SIGHUP reload, but --force-recreate is the reliable path.

3. What this does and does not do

  • ✅ Restores zero-code profiling for Go, JVM/Hotspot, Ruby, PHP, Perl, .NET, V8.
  • ❌ Does not produce Python high-level frames.
  • ❌ Does not fix the underlying verifier blowup — that requires the profiler fix in Alloy.

4. Re-enable Python later

Only after an Alloy release embeds a profiler containing PR #1626:

python_enabled = true

Watch grafana/opentelemetry-ebpf-profiler issue #68 and the Alloy release notes for the bumped profiler dependency.

Verification

Run these after recreating the container. Start from a fresh log stream — old error lines persist across restarts otherwise.

1. No verifier rejection on a fresh log stream

# Count must be 0.
docker logs --since 5m alloy 2>&1 | grep -c 'failed to load perf_unwind_python'

Expected: 0

docker logs --since 5m alloy 2>&1 | grep -iE 'pyroscope|ebpf|loaded' | tail -20

2. Profiles are being received

curl -s http://localhost:4040/metrics \
  | grep 'pyroscope_distributor_profiles_received_total{scope_name="com.grafana.alloy/pyroscope.ebpf"}'

Two-sample check (pure awk, no bc dependency):

get() {
  curl -s http://localhost:4040/metrics | awk -F' ' \
    '/pyroscope_distributor_profiles_received_total/ && /com.grafana.alloy\/pyroscope.ebpf/ {print $NF; exit}'
}
A=$(get); sleep 15; B=$(get)
echo "before=$A after=$B"
awk -v a="$A" -v b="$B" 'BEGIN { exit !(b > a) }' && echo PASS || echo FAIL

3. Expected/non-fatal log noise

These lines are per-process symbolization skips, not tracer failures:

Failed to load <binary>: unsupported Go version
Failed to load <binary>: not a Go executable
Failed to load <binary>: eh_frame FDE parse ...

Only a failed to load perf_unwind_python / BPF program is too large line indicates the tracer-wide failure.
