GAP-096 — MCP server answers an empty graph before the first reconcile

Component: hilo-mcp (JSON-RPC over stdio) vs hilo-cli graph commands Version: master 488609b (hilo 0.3.1-dev) Symptom: vfs_graph_stats → {"total_edges":0,"total_files":0} on a corpus whose .vfs/graph/graph.db cache is absent but whose sibling .vfs/graph/edges.jsonl holds the full edge set; hilo graph stats on the same corpus reports the real counts.

Root cause

GraphDB::open already does a read-through reconcile: if the DuckDB cache is absent/behind and a sibling edges.jsonl exists, it replays the JSONL in (budgeted + resumable, GAP-094). The bug is the gate deciding whether open is ever reached.

The CLI and MCP used different predicates for "does graph data exist?":

  • CLI hilo-cli/src/commands/graph.rs::resolve_graph_db_path returns the DB path if graph.db or edges.jsonl exists, then calls GraphDB::open → reconcile runs → real counts.
  • MCP all six graph tools short-circuited on !Path::new(GRAPH_DB_PATH).exists(). With the cache absent it returned zeros immediately and never called GraphDB::open, so the reconcile never fired — a silent-wrong-answer class bug.

Fix shape: make the short-circuit key identical to the CLI's — "cache exists OR sibling edges.jsonl exists" — so open (and its reconcile) runs before the tool answers. Neither present ⇒ zeros/empty is still correct.

Exact fix

In hilo-mcp/src/tools/mod.rs, add a helper and replace the predicate in all six handlers:

const GRAPH_DB_PATH: &str = ".vfs/graph/graph.db";

/// True when the DuckDB cache exists OR a sibling edges.jsonl does.
/// When the cache is absent but edges.jsonl exists, GraphDB::open
/// reconciles it into a fresh cache (GAP-096).
fn graph_data_present() -> bool {
    const EDGES_JSONL_PATH: &str = ".vfs/graph/edges.jsonl";
    Path::new(GRAPH_DB_PATH).exists() || Path::new(EDGES_JSONL_PATH).exists()
}

-    if !Path::new(GRAPH_DB_PATH).exists() {
+    if !graph_data_present() {
         return Ok(serde_json::json!({ /* zeros / empty */ }));
     }
     ...
     let db = hilo_graph::GraphDB::open(GRAPH_DB_PATH)?;   // now reached; reconciles

Call sites (all six so the bug can't move to a sibling tool): graph_stats (vfs_graph_stats), graph_untested, graph_module, graph_understand, graph_search, rule_check.

Verification (all run at 488609b)

  2. Bug reproduced on the parent (git checkout e56ef28 -- hilo-mcp/src/tools/mod.rs, keep the new test): assertion failed: ... {"total_edges":0,"total_files":0} left: 0 right: 2 test ... FAILED

  3. Full crate suite: cargo test -p hilo_mcp → 32 passed; 0 failed.

  4. Live E2E, both directions (cargo build -p hilo-cli --bin hilo):

  5. edges.jsonl-only scratch, fresh (no graph.db): CLI Total edges: 2 distinct / 2 raw; MCP serve --mcp returns "total_edges":2,"total_files":2 and materializes graph.db. Pre-fix the same request returned {"total_edges":0,"total_files":0}.
  6. Genuinely empty scratch: MCP returns {"total_edges":0,"total_files":0} and creates no cache.

Why it's correct: the fix doesn't reimplement reconcile in MCP; it removes the gate that blocked the existing budgeted/resumable GraphDB::open reconcile, keeping one source of truth identical to the CLI. The request-path budget (reconcile_budget_ms) still bounds the first call and the checkpoint lets the next one resume.
