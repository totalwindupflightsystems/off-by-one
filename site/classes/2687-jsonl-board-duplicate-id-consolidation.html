Answer

Verified end-to-end. The solution is written to ~/duplicate-id-consolidation.md.

What I did

Since the environment contained only the boardctl binary (no board repo), I reverse-engineered the board format by initializing test boards, then reproduced and fixed each failure case with the real binary.

Root cause

Task identity is the JSONL id field, not the line. When a lane appends a close/refile row instead of mutating the filing row, boardctl validate emits [error] tasks.jsonl line N: duplicate task id "X" (also line M) and exits 1.

The three shapes and their repairs

  • A – same-workload refile → drop the appended stub
  • B – different finding reusing a taken id → renumber the later row to the next free id, record provenance
  • C – appended close beside a pending filing → merge close fields into the filing row, flip it complete, drop the appended line

Key discovery from the binary

A raw top-level renumbered_from key validates as RESULT: OK but triggers key-uniformity drift and fails --strict-keys (which the installed pre-commit hook uses). The canonical carrier is dup_note, e.g. dup_note="renumbered_from=BT-102" — it passes plain, --strict-keys, and --fail-on dangling-dep with 0 drift.

Verified results

  • Pre-fix: RESULT: FAIL (3 error(s)).
  • Post-fix: RESULT: OK (0 warning(s)) and hook-equivalent RESULT: OK, with key uniformity: 5/5 rows carry only canon keys (0 drift).
  • Untouched lines confirmed byte-identical against the backup (line-surgical).
  • Trap (a) reproduced: a close-out writing only events/header prints OK while the task row stays pending.
  • Trap (b) reproduced: no --dedupe yields duplicate task_completed events; deduping by (tick_number, task_id) yields exactly one on a same-tick retry.
  • Extracted the exact script embedded in the markdown and re-ran it on a fresh board — same passing result.

The markdown contains the full consolidate.py, the idempotent close-out pattern, exact commands, a verification transcript, and a commit checklist.
