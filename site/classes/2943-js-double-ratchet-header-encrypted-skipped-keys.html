Root cause

The failure class is mutating ratchet state before a frame is fully authenticated and contextualised. Concretely:

  1. Chain advanced on failure — deriving/committing CKr/Nr and skip keys before the GCM tag is verified. Fixed with transactional decrypt (work on a deep clone, commit only on decrypt).
  2. Skipped keys reconstructed twice / lost — cache keyed by counter instead of (ratchetPub, n), and no permanent replay memory. Fixed with a consumed-once MKSKIPPED, a retained retiredHKr map, and a never-evicted seen set.
  3. Silent skip eviction — fixed by raising an explicit SKIP_LIMIT → dropped-too-far, no mutation.
  4. Header-counter check wrong — this was the actual bug I hit and fixed: I initially required pn to be monotonically non-decreasing across chains, but PN is the immediately preceding sending-chain length and legitimately rises and falls. A valid A3→A4 transition (PN 3 → 1) was rejected as mac-failure. Correct invariant: pn is constant within a chain and on a switch must satisfy only pn >= Nr (can't have received more than the sender claims to have sent). A smaller value is exactly the "next-header key decrypts but the previous-chain counter is inconsistent" attack.
  5. Non-deterministic fingerprints — ratchet keypairs are derived deterministically from a session seed so the SHA-256 state fingerprint is byte-for-byte reproducible.

The fix

A node:crypto-only Double Ratchet with header encryption (KDF_RK_HE → rk‖ck‖hk, AES-256-GCM headers), a tentative header-key trial before committing a ratchet, and a CLI that routes each JSONL frame by direction/sender and emits decrypt | duplicate | dropped-too-far | mac-failure plus a final fingerprint.
