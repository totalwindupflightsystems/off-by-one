Solution written to /home/kara/FIX-slide-float-overshoot.md. Summary of the diagnosis and verification:

Root cause

slideT = 0.5 is not an exact float multiple of FIXED_DT = 1/60. 30 × (1/60) = 0.49999999999999994, leaving a positive residual of 5.551115123125783e-17 that triggers a 31st step, which subtracts a full 1/60 and undershoots zero to −0.016666666666666562 (−0.02 in the failing run's accumulator phase). Since the decay is guarded by if (slideT > 0), the negative value is trapped forever — there's no code path back to 0. The old variable-dt loop only passed because rAF deltas vary per run and the crossing occasionally landed exactly on 0 (plus the slow-motion sim gave the 15 s timeout ample margin); the fixed timestep made the failure deterministic.

Fix (one line)

if (PLAYER.slideT > 0 && PLAYER.grounded) PLAYER.slideT = Math.max(0, PLAYER.slideT - dt);

Math.max(0, …) makes 0 a fixed point (max(0, 0 − dt) = 0, stays 0 forever), so reaching exactly 0 becomes a theorem, not luck. The same commit also hardened the QA test: replaced the 250 ms fixed sleep with an in-page 200 ms persistence sample (slideT > 0 throughout) — no time-scale dependence, no cross-context read-after-wait race.

Verification (all run and confirmed)

  • Pure case: buggy guard-decay → 31 steps, final −0.016666666666666562 (stuck negative); clamped → 31 steps, final exactly 0.
  • 20,000 random accumulator phases: old code ends negative 20000/20000; fixed code ends exactly 0 20000/20000 — exhaustive, not flaky.
  • Reproduce anywhere with the tiny slide_verify.js snippet embedded in the doc; final gate is npx playwright test tests/qa.spec.js -g keyboard on the SwiftShader host.

The document also covers rejected alternatives (epsilon compares, if (slideT < dt)), and a regression note to audit other if (x > 0) x -= dt patterns in the game for the same latent bug.
