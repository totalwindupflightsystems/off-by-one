Answer

Fix: memoize bushy join enumeration on physical property, not just relation set

Problem

The enumerator optimises bushy join trees for up to 12 relations with predicate pushdown, interesting orders and physical-property enforcement. The intended behaviour is that a substituted join order which already delivers the query's ORDER BY key is chosen, so no final sort is emitted. The observed defects are:

  1. Interesting orders silently collapse. The memo is keyed only on the relation set S. When two plans for S differ only in the order they deliver, one overwrites the other (usually the unordered/hash-join plan, because it is cheapest). The optimizer then cannot see that a slightly different join order already produces the required order, so it appends a redundant sort.
  2. The top-level plan is chosen before the order is known. Because the delivered order is not part of the memo key, the final selection cannot ask for "the best plan for the full set that satisfies ORDER BY".
  3. An unpruned Cartesian product explodes the memo. Every partition of every subset is generated, including cross products inside a connected join graph, producing shells of states and rA*rB blow-ups.

Root cause

The memo key is the state that must make plans distinguishable. For join enumeration with interesting orders the state is

(relation set, delivered physical order)

not the relation set alone. The delivered order is the property that the consumer (a parent join, or the final ORDER BY) cares about, so it must be part of the key. Storing only the cheapest plan per subset is exactly the "interesting orders collapse" bug: an ordered plan and an unordered plan for the same subset are not the same state and must not be merged.

A secondary root cause of the memo explosion is that the partition generator does not require connected subplans. For a connected query graph, a bushy plan can always be built from connected subgraphs only (the classic CSG-cmp rule); generating disconnected partitions turns into cross products.

The fix

The fix is implemented in bushy_join.py and has four parts.

1. Memo keyed on (subset, delivered order)

memo[S] is a dict[order] -> Plan; a plan is only merged with another when its delivered order is identical, and only if it is cheaper:

def add_plan(p: Plan):
    old = cur.get(p.order)              # key includes the physical property
    if old is None or p.cost < old.cost - 1e-12:
        cur[p.order] = p

2. Physical-property enforcement (the "skip the final sort" step)

After generating joins for S, every interesting order is materialised. If an existing plan already satisfies the target order (the target is a prefix of the delivered order) it is reused; otherwise an explicit sort is costed in:

def _enforce_properties(q, S, cur, orders):
    base = list(cur.items())
    for target in orders:
        if any(q.col2rel[c] not in S for c in target):
            continue                       # order not expressible on this subset
        best_c = best_p = None
        for o, p in base:
            if satisfies(o, target):       # o[:len(target)] == target
                c, cand = p.cost, p
            else:
                c = p.cost + sort_cost(p.rows, target)
                cand = Plan(S, target, c, p.rows, "sort", p, None, (), target)
            if best_c is None or c < best_c:
                best_c, best_p = c, cand
        if best_c is not None and (cur.get(target) is None
                                   or best_c < cur[target].cost - 1e-12):
            cur[target] = best_p

The final plan is then the cheapest full-set plan whose delivered order satisfies ORDER BY — no post-hoc sort is bolted on.

3. Merge join propagates the leading sort key

A merge join on a_col = b_col whose inputs are already ordered on those keys publishes a_col as its delivered order, so the sort key survives the join:

if pa.order[0] == ca and pb.order[0] == cb:
    add_plan(Plan(S, (ca,), pa.cost + pb.cost + rA + rB,
                  rowS, "merge", pa, pb, tuple(sorted(new))))

4. Cross-product pruning: connected subgraphs only (CSG-cmp)

valid_partitions only yields partitions whose two children are themselves connected and are joined by an applicable conjunctive predicate. A subset that is disconnected is never materialised for a connected component:

if len(q.components(A)) != 1 or len(q.components(B)) != 1:
    continue
if connecting_preds(q, S, A, B):
    yield A, B

For a disconnected query graph the connected components are optimised independently and then cross-producted (that is the only place a cross product is legal). A large CROSS_PENALTY makes the cost model agree with the rule "no cross product unless the graph/disjunction forces one".

Verification

Run:

cd ~/bushy
python3 test_bushy.py 40 12      # 40 random graphs, up to 12 relations
python3 demo.py                  # focused interesting-order demos

The harness checks, for every graph:

  • DP cost <= 1.01 x exhaustive-search cost,
  • zero cross products whenever the conjunctive graph is connected,
  • the retained plan is executed and its sorted result equals a reference join over the Cartesian product filtered by all predicates,
  • the order-aware memo is cheaper than a subset-only (buggy) memo.

Key takeaway: the delivered physical order is part of the memoized state. Keying the memo on (relation-set, order) is what lets the enumerator retain an ordered plan, substitute a join order that already produces the sort key, and avoid the redundant final sort—while CSG-cmp pruning plus a cross-product penalty keeps the state space free of unnecessary Cartesian products.
