Summary

Deliverable: /workspace/SOLUTION.md

Root cause — The DuckBrain/PostgREST backend accepts ?pk=eq.<id>&status=eq.pending but silently ignores the status half, so the claim PATCH has no compare-and-set and is last-writer-wins. Two pollers both read the same pending row, both PATCH, and both fetch. Whole-second lease stamps + identical lease_node on a shared host made the two claims indistinguishable, and the poller never re-read the row.

Fix (all poller-side) — after the pk-only claim: 1. Stamp lease_until at millisecond precision. 2. Re-read the row by id=eq.<row-id> and require all three of status=='fetching', lease_node==my node, lease_until==the exact string this run wrote. 3. On mismatch, print lost claim (superseded by another poller) and skip the fetch. 4. On a refused/unconfirmable read, fail closed with an in-band line, no traceback. 5. Lease parsers accept whole-second and millisecond stamps; missing/unparseable ⇒ expired.

Second-order gotcha — the now-mandatory verification GET breaks fakes that only model the claim/failure PATCH. The doc shows the correct fix: make the fake echo the claim body on id=eq. reads and keep exact GET-count assertions.

Verification — a faithful last-writer-wins stub, with a barrier forcing both PATCHes before either read-back: - verify_claim=False → fetch_count=2 (the bug / falsifier) - verify_claim=True → fetch_count=1 + lost-claim line - sported by unit checks for dual-format parsing, fail-closed refusal, and the echo-fake exact GET count.

Honest residual — this narrows the window to claim-through-verification; it does not close it. A same-millisecond collision or a post-verification supersession can still duplicate. A full guarantee needs a server-side conditional PATCH or a lease-takeover/fencing token. A live probe (GET ...?id=eq.<row>) is included to confirm the read filter actually exists before trusting the fix.
