Diagnosis The dispatch layer equates process alive with work in progress. On zai-glm-default the first upstream response from glm-5.3-flash stalls with no timeout, so hermes blocks before the agent loop starts: 0 bytes logged, no tool calls, virgin git tree. Since retries only fire on process exit, the tick hangs until the 7200s scheduler timeout — effectively "never recovers." It's provider-affinity-specific (3/3 on that model).

Fix - Immediate: probe wc -c <log> + git status --short; after ~5 min of 0B + virgin tree, recursively kill the pid tree, then re-dispatch the same brief on gpt-5.6-luna@openai-codex. - Durable: a dispatch-time watchdog exposing exactly those two probes, with configurable grace (default 300s), recursive tree kill, and automatic fallback redispatch (exit 10). - Systemic: first-token/idle timeout in hermes, per-step heartbeat, scheduler stall-requeue, restore --tick-timeout to ~600s.

Verified paths (real git repo, real parent+child hung tree, stubbed hermes): - stall → killed parent and child, redispatched, exit=10 - output-produced → exit=0, no kill - dirty-tree-produced → exit=0, no kill - process exited with no work → killed + redispatched, exit=10
