Answer

Go 1.26 GC pacer assist death spiral in bimodal allocation storms

TL;DR

The failure is not “GOGC too small” and cannot be fixed by raising GOGC. In a bimodal workload, the large-object phase drives heapLive to or past the heap goal. The Go 1.26 pacer then enters its hard-goal branch:

// runtime/mgcpacer.go, revise()
scanWorkExpected = maxScanWork
heapGoal = int64(float64(heapGoal) * 1.1)
...
heapRemaining := heapGoal - int64(live)
if heapRemaining <= 0 { heapRemaining = 1 }     // <-- denominator collapses
assistWorkPerByte = scanWorkRemaining / heapRemaining

A pointer-rich large-slice reallocation therefore charges the allocating goroutine an enormous amount of mark work. When the memory-limit branch wins, sweepDistMinTrigger is ignored as well, so the next mark starts with almost no runway and the loop repeats.

The fix is allocation shaping, not GC tuning: bound every allocation to a small chunk, make bulk data pointer-free where possible, and reuse buffers from a bounded application pool so the large phase stops allocating giant pointer-rich objects during mark. In the verified reproducer this reduces mutator-assist time from 66.1% of wall time to 4.3%, and worst observed per-cycle assist CPU from 82 ms to 2.5 ms.

Environment

$ go version
go version go1.26.8 linux/amd64

The reproducer is run with GOMAXPROCS=4, a 256 MiB soft memory limit, and GODEBUG=gctrace=1 so per-cycle mark-assist CPU is visible. A 4-P runtime makes the assist feedback loop easy to observe; the same mechanism applies at larger GOMAXPROCS, but the background marker can hide it longer.

Reproducer and exact fix

The full self-contained program is below. -mode=baseline is the bad service shape: a steady small-object regime and a periodic large phase that grows pointer-rich []*Cell slices by allocate-and-copy. -mode=shaped keeps the same logical workload but uses pointer-free records in fixed 256 KiB chunks taken from a bounded reusable pool.

Save it as main.go next to this go.mod:

module gcassistdemo

go 1.26

// Command gcassistdemo reproduces a bimodal allocation storm and compares a
// pointer-rich, grow-by-copy large-slice path with an allocation-shaped path.
package main

import (
    "flag"
    "fmt"
    "runtime"
    "runtime/debug"
    "runtime/metrics"
    "sync"
    "sync/atomic"
    "time"
)

type Cell struct { // 40 B, contains pointers: every live Cell is scan work.
    A, B uint64
    P    *Cell
    S    string
}

type Flat struct { // 32 B, pointer-free: no scan work.
    A, B uint64
    X, Y uint64
}

var (
    mode     = flag.String("mode", "baseline", "baseline|shaped")
    duration = flag.Duration("duration", 6*time.Second, "run duration")
    largeMB  = flag.Int("largeMB", 192, "logical large-slice payload target, MiB")
    workers  = flag.Int("workers", 4, "number of steady-state allocators")
    limitMB  = flag.Int("limitMB", 256, "soft memory limit, MiB; 0 = off")
    gogc     = flag.Int("gogc", 100, "GOGC")
    phaseMs  = flag.Int("phaseMs", 200, "steady phase length, ms")
    burstMs  = flag.Int("burstMs", 300, "large phase length, ms")
)

var (
    stop    atomic.Bool
    wg      sync.WaitGroup
    smallMu sync.Mutex
    small   []*Cell
    sink    any
)

func smallWorker(id int) {
    defer wg.Done()
    r := uint64(id)*0x9e3779b97f4a7c15 + 1
    local := make([]*Cell, 0, 4096)
    for !stop.Load() {
        for i := 0; i < 4096; i++ {
            r ^= r << 13
            r ^= r >> 7
            r ^= r << 17
            c := &Cell{A: r, B: r * 3}
            if i&7 == 0 {
                c.P = &Cell{A: r + 1, B: r + 2} // pointer-rich steady state
            }
            if i&15 == 0 {
                c.S = "steady-state-payload"
            }
            local = append(local, c)
        }
        smallMu.Lock()
        small = append(small, local...)
        if len(small) > 200_000 { // bounded rotating live window
            small = append([]*Cell(nil), small[len(small)-100_000:]...)
        }
        smallMu.Unlock()
        local = local[:0]
    }
}

// baselineBurst is the bad path: pointer-rich large slices, reallocated and
// copied on every growth step. Each Mallocgc call can create a huge assist debt.
func baselineBurst(target int) {
    n := 1 << 16
    var old []*Cell
    for n <= target {
        next := make([]*Cell, n)
        copy(next, old)
        for i := len(old); i < n; i++ {
            next[i] = &Cell{A: uint64(i), B: uint64(i) * 5, S: "large-phase"}
        }
        old = next
        sink = old
        n = n * 5 / 4
    }
    sink = nil
    old = nil
}

// fixed path: pointer-free records in fixed-size chunks, reused from a bounded
// application pool. Every allocation is <= 256 KiB and steady-state bursts do
// not allocate at all.
const chunkRecords = (256 << 10) / 32

type chunkPool struct {
    mu   sync.Mutex
    free [][]Flat
    max  int
}

func (p *chunkPool) get() []Flat {
    p.mu.Lock()
    if n := len(p.free); n > 0 {
        b := p.free[n-1]
        p.free = p.free[:n-1]
        p.mu.Unlock()
        return b[:chunkRecords]
    }
    p.mu.Unlock()
    return make([]Flat, chunkRecords)
}

func (p *chunkPool) put(b []Flat) {
    p.mu.Lock()
    if len(p.free) < p.max {
        p.free = append(p.free, b[:0])
    }
    p.mu.Unlock()
}

var flatPool = &chunkPool{max: 1024} // overridden to fit the requested target

func shapedBurst(target int) {
    need := (target + chunkRecords - 1) / chunkRecords
    if need < 1 {
        need = 1
    }
    chunks := make([][]Flat, 0, need)
    for i := 0; i < need; i++ {
        b := flatPool.get()
        for j := range b {
            b[j] = Flat{A: uint64(j), B: uint64(j) * 5, X: uint64(j) ^ 0xdeadbeef, Y: uint64(j) + 9}
        }
        chunks = append(chunks, b)
    }
    sink = chunks
    for _, b := range chunks {
        flatPool.put(b)
    }
    sink = nil
}

func largeLoop(target int) {
    defer wg.Done()
    for !stop.Load() {
        time.Sleep(time.Duration(*phaseMs) * time.Millisecond)
        deadline := time.Now().Add(time.Duration(*burstMs) * time.Millisecond)
        for time.Now().Before(deadline) && !stop.Load() {
            if *mode == "shaped" {
                shapedBurst(target)
            } else {
                baselineBurst(target)
            }
            runtime.Gosched()
        }
    }
}

func readMetric(name string) float64 {
    s := []metrics.Sample{{Name: name}}
    metrics.Read(s)
    switch s[0].Value.Kind() {
    case metrics.KindUint64:
        return float64(s[0].Value.Uint64())
    case metrics.KindFloat64:
        return s[0].Value.Float64()
    default:
        panic("unexpected metric kind")
    }
}

func main() {
    flag.Parse()
    if *limitMB > 0 {
        debug.SetMemoryLimit(int64(*limitMB) << 20)
    }
    debug.SetGCPercent(*gogc)
    target := (*largeMB << 20) / 40
    if target < 1<<16 {
        target = 1 << 16
    }
    flatPool.max = (target+chunkRecords-1)/chunkRecords + 16

    startAssist := readMetric("/cpu/classes/gc/mark/assist:cpu-seconds")
    startGC := readMetric("/gc/cycles/total:gc-cycles")
    start := time.Now()
    for i := 0; i < *workers; i++ {
        wg.Add(1)
        go smallWorker(i)
    }
    wg.Add(1)
    go largeLoop(target)
    time.Sleep(*duration)
    stop.Store(true)
    wg.Wait()

    elapsed := time.Since(start)
    assist := readMetric("/cpu/classes/gc/mark/assist:cpu-seconds") - startAssist
    gcs := readMetric("/gc/cycles/total:gc-cycles") - startGC
    var ms runtime.MemStats
    runtime.ReadMemStats(&ms)
    fmt.Printf("mode=%s gogc=%d limitMB=%d elapsed=%s cycles=%.0f assistCPU=%.3fs assist/cycle=%.2fms assist/wall=%.1f%% heapSys=%dMB heapInuse=%dMB nextGC=%dMB\n",
        *mode, *gogc, *limitMB, elapsed.Round(time.Millisecond), gcs, assist,
        assist*1000/gcs, assist/elapsed.Seconds()*100, ms.Sys>>20, ms.HeapInuse>>20, ms.NextGC>>20)
}

Root cause

1. Assist debt is charged per allocation and converted through the pacer ratio

mallocgc calls deductAssistCredit(size) before the allocation. The whole size is charged to the allocating goroutine (runtime/malloc.go):

assistG.gcAssistBytes -= int64(size)
if assistG.gcAssistBytes < 0 {
    gcAssistAlloc(assistG)
}

gcAssistAlloc converts debt to scan work (runtime/mgcmark.go):

debtBytes := -gp.gcAssistBytes
scanWork := int64(assistWorkPerByte * float64(debtBytes))
if scanWork < gcOverAssistWork {
    scanWork = gcOverAssistWork // only 64 KiB of pre-payment
}

A single 100+ MiB make([]*Cell, n) therefore turns into a very large assist job on one goroutine. The 64 KiB over-assist credit is far too small to amortize a large-object reallocation burst.

2. The hard-goal branch makes the denominator collapse

gcControllerState.revise computes the assist ratio from the remaining heap distance (runtime/mgcpacer.go). In the hard regime (live > heapGoal):

  • scanWorkExpected is replaced by maxScanWork, i.e. assume every scannable byte and all stacks/globals must be scanned;
  • the goal is extended only to 1.1 * heapGoal;
  • heapRemaining = heapGoal - live is clamped to 1 if it is zero or negative;
  • therefore assistWorkPerByte = scanWorkRemaining / heapRemaining explodes.

Observed directly with GODEBUG=gcpacertrace=1:

pacer: assist ratio=2.33733298e+08 (scan 222 MB in 260->225 MB) workers=1+0
pacer: assist ratio=9.99773416050771 (scan 237 MB in 238->238 MB) workers=1+0

The first line is the death-spiral state: the heap goal (225 MB) is already below live (260 MB), so heapRemaining is clamped to one byte while the pacer still expects to scan 222 MB. Any allocation is now almost pure assist work.

3. Bimodal reallocation supplies exactly the wrong shape

The large phase does allocate-and-copy growth of []*Cell:

  • old and new slices are both live during each copy, so the live set temporarily spikes;
  • every Cell contains pointers, so the scan work (maxScanWork) is large;
  • each growth step allocates a larger object than the previous one;
  • the old backing arrays become garbage but may not be swept before the next trigger, so the next mark starts with less runway.

The steady small-object phase and the large-reallocation phase need completely different pacing behavior. The pacer only has one goal and one assist ratio, so tuning for one regime breaks the other.

4. Sweep termination does not provide rescue runway in this state

At the end of a cycle, commit tries to reserve sweep distance:

// runtime/mgcpacer.go, commit()
if isSweepDone {
    c.sweepDistMinTrigger.Store(0)
} else {
    c.sweepDistMinTrigger.Store(c.heapLive.Load() + sweepMinHeapDistance)
}

sweepMinHeapDistance is only 1 MiB. More importantly, heapGoalInternal applies sweepDistMinTrigger only in the non-memory-limit branch. When memoryLimitHeapGoal() < gcPercentHeapGoal, the memory-limit goal wins and the sweep-distance adjustment (and the 64 KiB minimum-runway adjustment) is skipped.

Meanwhile gcStart executes finishsweep_m() in the sweep-termination STW before startCycle. So a large burst can:

  1. allocate past the trigger before the background sweeper catches up;
  2. force remaining sweeping into the next STW sweep-termination phase;
  3. start mark with heapGoal <= heapLive because the memory-limit goal won;
  4. enter the hard-goal assist branch above.

That is the pacer/sweep feedback loop. The CPU is spent in mutator assists during the concurrent mark that precedes mark termination; assists are already disabled during the final STW mark-termination phase, so the latency is visible as a long mark/assist phase followed by the STW completion, not as useful work inside mark termination itself.

5. Why raising GOGC is not a fix

Raising GOGC only raises gcPercentHeapGoal. As soon as the large phase pushes mapped memory toward GOMEMLIMIT, memoryLimitHeapGoal() becomes the smaller goal and the pacer enters the same hard branch. At that point GOGC is irrelevant. If the limit is loose, raising GOGC simply delays collection and increases the transient live set/RSS; the large-object assist cliff remains.

The verified run below shows this directly: GOGC=400 cuts the number of cycles (494 -> 279) but leaves assist wall time at 64.3% and worst per-cycle assist at 82 ms, while peak Sys rises from 364 MiB to 376 MiB. It is not a fix; it changes which resource fails first.

Exact allocation-shaping policy

Apply all four rules to the large-object phase:

  1. Bound every allocation. Split bulk payloads into fixed-size chunks (256 KiB in the reproducer). No single mallocgc can create an unbounded assist debt.
  2. Remove pointers from bulk data where possible. Use numeric records, byte blobs, or indices into a stable side table instead of []*T. This lowers maxScanWork, which is the numerator of the assist ratio. In the reproducer []Flat is 32 B with no pointers, so its scan work is zero.
  3. Reuse from an application-level bounded pool. sync.Pool alone is not enough because the runtime clears it at GC start. The reproducer uses a mutex-protected free list with a hard max bound. Once warm, a burst allocates no new large backing arrays.
  4. Never grow-by-copy in the steady state. Pre-size to the known maximum, or use fixed chunks. If a contiguous growable slice is unavoidable, call slices.Grow/preallocate the final capacity before the burst rather than repeatedly copying during mark.

Keep the memory limit as a guard, but do not use a high GOGC as the fix:

debug.SetGCPercent(100)                 // keep the normal GOGC regime
debug.SetMemoryLimit(containerBudget - headroom)

For pointerful large objects that cannot be made pointer-free, chunk them to a small bound, preallocate all chunks, and insert runtime.Gosched() between chunks so background mark credit can accumulate. That bounds a single goroutine's worst-case assist; the pointer-free/chunk-reuse change is stronger because it removes the scan work instead of merely splitting it.

Production checklist

  • Instrument /cpu/classes/gc/mark/assist:cpu-seconds and /gc/heap/live:bytes versus /gc/heap/goal:bytes.
  • Alert when assist CPU exceeds a few percent of wall time, or when live/goal approaches or exceeds 1.0. In that state the pacer is in the hard branch and every large allocation is dangerous.
  • Cap individual allocation sizes in the large phase. A 256 KiB to 1 MiB chunk bound is usually enough to stop a single mallocgc from becoming a multi-millisecond assist.
  • Prefer pointer-free bulk representations; if pointers are required, store indices into a stable arena instead of []*T.
  • Keep a bounded reusable buffer pool sized to the expected maximum working set. Drop/shrink it explicitly after the large phase.
  • Treat GOGC as a throughput/memory tradeoff, not as a cure for assist storms. Use GOMEMLIMIT for the memory ceiling and allocation shaping for worst-case assist latency.
