Fixing the bytes.Buffer Data Race in TestDatabaseTargetUnification

Problem class: go-test-failure — -race detects concurrent bytes.(*Buffer).String() / Write() Test: tests/integration/db_unification_test.go::TestDatabaseTargetUnification Repo: github.com/&lt;project&gt;/Helios

Root cause

The test starts a long-lived child process (a Helios DB/daemon) and attaches a bare bytes.Buffer to the process's output:

var out bytes.Buffer
cmd := exec.CommandContext(ctx, bin, args...)
cmd.Stdout = &out          // and/or cmd.Stderr = &out
_ = cmd.Start()

// ... health-wait while the child is still running ...
if !strings.Contains(out.String(), "ready") { ... }   // <-- race

When cmd.Stdout/cmd.Stderr is not an *os.File, os/exec does not hand the writer to the kernel. Instead it creates an internal pipe and starts a copier goroutine per stream that lives for the entire process lifetime:

func (c *Cmd) writerDescriptor(w io.Writer) (f *os.File, err error) {
    ...
    c.goroutine = append(c.goroutine, func() error { _, err := io.Copy(w, pr); ... })
}

That copier repeatedly calls buf.Write(...) from its own goroutine. It only stops when the pipe hits EOF, which happens when the child exits and Wait() closes it. Meanwhile the test goroutine calls buf.String() after the health-wait but before Wait(). Read-on-test-goroutine vs write-in-copier-goroutine over the same bytes.Buffer is an unsynchronized data race on the buffer's internal []byte slice and offsets.

CombinedOutput() is safe only because it internally calls Wait() (draining all copiers) before returning. Here the process must stay alive, so that's not an option.

Exact fix

Wrap the buffer in a mutex-guarded type. Both the copier's Write and the test's String/Bytes take the same lock, so the race disappears. Put this helper in tests/integration/db_unification_test.go (or a shared testutil file in the same package):

package integration

import (
    "bytes"
    "io"
    "sync"
)

// syncBuffer is a concurrency-safe bytes.Buffer. os/exec writes to a
// non-*os.File Stdout/Stderr from an internal copier goroutine that lives
// for the whole process lifetime, so a plain bytes.Buffer races with any
// test-goroutine read performed before cmd.Wait() returns.
type syncBuffer struct {
    mu  sync.Mutex
    buf bytes.Buffer
}

var _ io.Writer = (*syncBuffer)(nil)

func (b *syncBuffer) Write(p []byte) (int, error) {
    b.mu.Lock()
    defer b.mu.Unlock()
    return b.buf.Write(p)
}

func (b *syncBuffer) String() string {
    b.mu.Lock()
    defer b.mu.Unlock()
    return b.buf.String()
}

func (b *syncBuffer) Bytes() []byte {
    b.mu.Lock()
    defer b.mu.Unlock()
    // Return a copy so callers can't race the copier through the alias.
    out := make([]byte, b.buf.Len())
    copy(out, b.buf.Bytes())
    return out
}

func (b *syncBuffer) Reset() {
    b.mu.Lock()
    defer b.mu.Unlock()
    b.buf.Reset()
}

Then change the long-lived process wiring:

-var out bytes.Buffer
+var out syncBuffer
 cmd := exec.CommandContext(ctx, bin, args...)
-cmd.Stdout = &out
-cmd.Stderr = &out
+cmd.Stdout = &out
+cmd.Stderr = &out

Use out.String() / out.Bytes() exactly as before at the health check; both are now safe while the child runs.

Short-lived children that use cmd.CombinedOutput() need no change — that call already waits for the copier goroutines before returning. Leave them alone.

Why not just call Wait() first?

The test deliberately reads output while the daemon is still running (health-wait), so Wait() can't be moved earlier without deadlocking the probe. The mutex wrapper is the minimal, correct fix. Also keep the eventual Wait()/Process.Kill() teardown so the copier goroutine terminates and the child is reaped.
