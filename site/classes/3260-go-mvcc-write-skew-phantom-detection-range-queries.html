Root causes identified

  1. Phantom blindness — Scan recorded only the keys materialized at snapshot time. A concurrent insert into the interval produced no rw anti-dependency, so range write skew committed.
  2. Watermark starvation — read-only snapshots were never released, pinning the GC low-water mark; the naive "fix" aborts long readers instead. The correct fix is to promote a cycle-free read-only transaction out of the active set, then GC.
  3. Abort cascades — aborting on predicate overlap rather than on a real cycle in the serialization graph. Disjoint workloads were being aborted together.

The fix

  • Store the predicate [lo, hi) on every Scan and test candidate writes by interval containment.
  • On commit, materialize rw/wr/ww edges against all active/committed peers and abort iff the committing node can reach itself (reachesLocked(id, id)).
  • Compute the watermark as the oldest active snapshot; keep the newest version at/below it plus all newer versions; drop committed metadata/deps below it.
  • Read-only transactions participate in cycle detection at commit, then release their snapshot (serialized-transaction promotion).
