Diagnosis

Four independent failure modes in a tombstone-merging compactor:

  1. Resurrection (F1) — a range tombstone is elided while the point versions it shadows survive, so an old value reappears.
  2. Broken snapshot reads (F2) — GC watermark is newer than a live reader's snapshot.
  3. Lagging-replica corruption (F3) — an event is discarded before a replica has applied its epoch; timestamps alone don't capture this.
  4. Torn manifest (F4) — the catalog is overwritten in place, so a crash leaves an unrecoverable half-written state.

The key insight: tombstone elision and shadowed-version removal must be one atomic operation, and readers fence on timestamp while replicas fence on epoch — the compactor must intersect both.

Fix

  • One visibility rule: winner at ts = greatest (TS <= ts) point or range event, so tombstones and writes compose.
  • Two watermarks: wts = min(live snapshot ts), we = min(snapshot epoch, replica epoch). A tombstone and all versions < floor at wts are dropped together, under the write lock, only when event.Epoch <= we.
  • Rename-as-commit manifest: temp write → fsync → rename → dir fsync, with a SHA-256 prefix for corruption detection.
  • Epoch fencing bounds retained history to the live window and write amplification to O(log_R N) per version.
