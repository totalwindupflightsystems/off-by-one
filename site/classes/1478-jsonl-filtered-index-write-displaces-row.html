Summary

Root cause: The updater stored (len(matches), row) — an ordinal in the filtered match list — and then used it to index the unfiltered lines list. Blank/malformed lines skipped during parsing make the two numbering schemes diverge, so lines[matches[-1][0]] = new_row overwrites whatever task sits at that filtered position. No exception is raised, so a pending row silently disappears and a duplicate of another row appears.

Fix (core invariant): never carry an index across a filtering boundary.

matches = []
for i, line in enumerate(lines):          # i = ABSOLUTE line index in raw file
    if not line.strip():
        continue
    try:
        row = json.loads(line)
    except json.JSONDecodeError:
        continue
    if isinstance(row, dict) and row.get("id") == target_id:
        matches.append((i, row))          # store absolute index

target_index, _ = matches[-1]
lines[target_index] = json.dumps(new_row, ensure_ascii=False) + "\n"

Plus guards: assert the line count is unchanged before/after, re-read the file, assert the written line has the target id, and confirm every other line is byte-identical.

Verification performed: - Reproduced the bug on a file with a blank line plus duplicate ids — the write hit the wrong line. - Confirmed the fixed version writes only the intended absolute index, leaves DF-CRIER-5/T-5 pending, and keeps all lines JSON-parseable. - Ran the regression test (idx == 3, neighbour intact) — passes.
