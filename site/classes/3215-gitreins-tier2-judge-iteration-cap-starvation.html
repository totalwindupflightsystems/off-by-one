Answer

Fixing Tier-2 judge iteration starvation on code-factory

Symptom

Every Tier-2 judge run on the CF-292 close at ee13de4 ended before grading, even though the behavioural change was correct:

Cap exceeded: Iteration cap (100) reached (100.5 used).
Partial verdict — 1 of 3 criteria graded, 2 ungraded.

Four runs on one commit isolate the cause:

Run Criteria shape Result Cost
da60afc3 one compound criterion with five clauses 0/1 graded, cap 100.2 3.55M input
5b9d30d9 same criterion graded, but FAILed on “full unittest suite is green” repo-wide baseline is red
a0a670a5 3 criteria, one behavioural + two suite-running behavioural PASS at iteration 10.2, then cap 100.5, 1/3 graded 2.96M input
a0d1db3d one compact behavioural criterion (5 fixture verdicts + 14-arm test file) tier2 COMPLETE, 3/3 PASS converged

The discriminator is the proof procedure, not the number of criteria and not the cap value.

Root cause

1. Tier-2 cost is charged in iterations, and the cap is global

engine/eval_cap.py charges 1.0 per LLM reasoning turn and 0.1 per tool call. engine/evaluator.py enforces one global budget across all criteria. Splitting a criterion into three does not give each one a third of the budget: the first cheap criterion used ~10 iterations, then the suite-running criteria consumed the remaining ~90 and the cap fired with the later criteria ungraded. Raising GITREINS_MAX_ITERATIONS moves the wall, it does not remove the cost.

2. A suite-wide criterion is a full-suite replay, repeatedly

.gitreins/config.yaml sets guards.test_command: bash tests/selftest.sh. The judge system prompt in engine/evaluator.py has a hard rule: any criterion mentioning tests/build/lint/“the code runs” must run the configured test command fresh and quote its output. bash tests/selftest.sh is a multi-minute, large-output suite on this repo. Each replay inflates context, triggers exploration/compaction, and costs many turns. A criterion such as “the full unittest suite is green” therefore has an unbounded-looking iteration cost, while a targeted fixture/test-file proof converges in ~10 iterations.

3. The repo’s bare discovery suite is intentionally red

python3 -m unittest discover -s tests -p 'test_*.py' exits 1 at ee13de4 with Ran 177 tests ... FAILED (failures=5). The five failures are pre-fix control arms that only make sense when tests/selftest.sh injects CF_BUS_WORKER_SOURCE and the CF_*_PREFIX_CONTROL variables (CF-396). A criterion demanding a green bare discovery suite is therefore unrelated to the change and legitimately fails a correct patch.

4. A compound criterion has no intermediate “done” mark

The judge records progress per criterion index (verified_0, verified_1, …). A single five-clause criterion cannot write a completed item until every clause is settled, so a cap hit reports 0/1 even after extensive actionable review. One obligation per criterion makes partial progress visible and prevents one expensive clause from starving unrelated work.

The fix

Rule: every Tier-2 criterion is one cheap behavioural obligation

  • One obligation, one proof, one criterion.
  • The proof is a targeted fixture or test file: e.g. python3 -m unittest tests.test_node_gateway_auth, not bash tests/selftest.sh and not bare unittest discover.
  • Include the two required labelled sections (FAILIF: and PROOF:); use a command or a file:line/test::case locator.
  • Budget ~10–15 iterations per behavioural criterion. With N behavioural criteria, set the effective cap to max(25, 10 + 15*N).
  • Never put a repo-wide suite claim in the same judge run as behavioural criteria.

Example replacement for the CF-292 close:

The 14-arm test file proves the producer/consumer contract on the current tree:
`python3 -m unittest tests.test_node_gateway_auth` prints `Ran 14 tests` and `OK`;
the five fixture configs yield sibling-key rc=2, child-key rc=2,
comment-before-sibling rc=2, deep direct child rc=0, four-space direct child rc=0.
Against `git show 868e2fc:scripts/node_gateway_auth.py`, the same suite fails the
child-key arm. FAILIF: any fixture verdict differs, or the pre-fix control passes.
PROOF: python3 -m unittest tests.test_node_gateway_auth

Rule: measure a suite-wide claim foreman-side as a base-vs-head differential

A suite claim is “no new failures relative to the base”, not “the entire suite is green” (this repo cannot honestly claim the latter under bare discovery). Run the suite once on the base and once on the head, normalize run-specific paths/timestamps, and compare the FAIL sets:

cd ~/code-factory
head=$(git rev-parse HEAD)
base=$(git rev-parse HEAD^)          # or the row's actual base commit
GITREINS_SUITE_CMD='bash tests/selftest.sh' \
  scripts/tier2_suite_delta.sh "$base" "$head" \
  .gitreins/evidence/tier2-delta.txt

The resulting artifact contains NEW_FAIL_ROWS 0, both commit ids and a SHA-256. Give the judge a criterion that only checks the artifact, not the suite:

The saved differential artifact `.gitreins/evidence/tier2-delta.txt` records
`BASE <sha>`, `HEAD <sha>` and `NEW_FAIL_ROWS 0`, with SHA-256 <digest>.
FAILIF: the file is absent, its HEAD is not the judged commit, or
NEW_FAIL_ROWS is not 0. PROOF: grep -F 'NEW_FAIL_ROWS 0' .gitreins/evidence/tier2-delta.txt

This converts an expensive test execution into a cheap file check. The suite is run once by the foreman; the judge verifies the recorded measurement.

Rule: an unavoidable suite task is its own judge run

If a suite criterion must be graded by the judge, create a separate task such as <id>-SUITE containing only that criterion, give it an explicit cap (GITREINS_MAX_ITERATIONS=100 or higher), and run it after the behavioural <id>-BEH task. Never mix the two: the global cap lets the suite criterion starve the behavioural ones.

Tooling: criterion linter

Save the following as scripts/tier2_criteria.py. It rejects suite criteria mixed with behavioural criteria, flags compounds, and prints the recommended cap before a close starts.

#!/usr/bin/env python3
"""Lint Tier-2 criteria for judge iteration cost.

Usage:
  python3 scripts/tier2_criteria.py check --task-id CF-292
  python3 scripts/tier2_criteria.py check --criterion-file criteria.json
  python3 scripts/tier2_criteria.py check --criterion "..." [--allow-suite]
"""
from __future__ import annotations
import argparse, json, re, sys
from pathlib import Path

SUITE_PATTERNS = (
    r"\btests?/selftest\.sh\b",
    r"\bunittest\s+discover\b",
    r"\bpytest\s+(?:-q\s+)?(?:tests?/?)?\s*$",
    r"\b(?:npm|pnpm|yarn)\s+(?:run\s+)?test\b",
    r"\bgo\s+test\s+\./\.\.\.",
    r"\b(?:cargo|make|tox|nox)\s+test\b",
    r"\b(?:full|entire|whole|repo[- ]wide|repository[- ]wide)\b"
    r"[^.\n]{0,40}\b(?:test|tests|suite)\b",
)
_SUITE_RE = re.compile("|".join(SUITE_PATTERNS), re.IGNORECASE)
_ITEM_RE = re.compile(r"(?m)^\s*(?:\d+[.)]|[A-Z]\d+[:.)])\s+")

def split_criteria(text: str) -> list[str]:
    parts = [p.strip() for p in _ITEM_RE.split(text) if p.strip()]
    return parts or ([text.strip()] if text.strip() else [])

def is_suite(c: str) -> bool:
    return _SUITE_RE.search(c) is not None

def is_compound(c: str) -> bool:
    return c.count(";") >= 3

def report(criteria: list[str], allow_suite: bool) -> dict:
    rows, suite, compound = [], 0, 0
    for i, c in enumerate(criteria):
        s, k = is_suite(c), is_compound(c)
        suite += int(s); compound += int(k)
        rows.append({"index": i, "suite": s, "compound": k,
                     "chars": len(c), "criterion": c})
    behavioural = len(criteria) - suite
    recommended = max(25, 10 + 15 * behavioural)
    if suite:
        recommended = max(100, recommended)
    errors = []
    if suite and behavioural:
        errors.append("suite-running and behavioural criteria are mixed; split "
                      "into <task>-BEH and <task>-SUITE.")
    if suite and not allow_suite:
        errors.append("suite-running criterion present; isolate it in its own task "
                      "and pass --allow-suite, or use a foreman-side differential.")
    return {"criteria": len(criteria), "behavioural": behavioural, "suite": suite,
            "compound": compound, "recommended_max_iterations": recommended,
            "errors": errors, "rows": rows}

def load_criteria(a: argparse.Namespace) -> list[str]:
    if a.criterion:
        return [c.strip() for c in a.criterion if c.strip()]
    if a.criterion_file:
        raw = Path(a.criterion_file).read_text(encoding="utf-8")
        try:
            data = json.loads(raw)
        except json.JSONDecodeError:
            return split_criteria(raw)
        if isinstance(data, list):
            return [str(c).strip() for c in data if str(c).strip()]
        if isinstance(data, dict) and isinstance(data.get("criteria"), list):
            return [str(c).strip() for c in data["criteria"] if str(c).strip()]
        raise ValueError("criterion file must be a JSON list")
    if a.task_id:
        for line in Path(a.board).read_text(encoding="utf-8").splitlines():
            if line.strip() and json.loads(line).get("id") == a.task_id:
                text = json.loads(line).get("acceptance_criteria") or ""
                if not text.strip():
                    raise ValueError(f"{a.task_id} has no acceptance_criteria")
                return split_criteria(text)
        raise ValueError(f"{a.task_id} not found in {a.board}")
    raise ValueError("supply --task-id, --criterion-file, or --criterion")

def main(argv=None) -> int:
    p = argparse.ArgumentParser()
    sub = p.add_subparsers(dest="command", required=True)
    c = sub.add_parser("check")
    c.add_argument("--task-id")
    c.add_argument("--board", default=".coding-hermes/board/tasks.jsonl")
    c.add_argument("--criterion", action="append", default=[])
    c.add_argument("--criterion-file")
    c.add_argument("--allow-suite", action="store_true")
    c.add_argument("--json", action="store_true")
    a = p.parse_args(argv)
    try:
        criteria = load_criteria(a)
    except (OSError, ValueError, json.JSONDecodeError) as exc:
        print(f"tier2-criteria: {exc}", file=sys.stderr)
        return 2
    r = report(criteria, a.allow_suite)
    if a.json:
        print(json.dumps(r, indent=2))
    else:
        print(f"Tier-2 criteria: {r['criteria']} ({r['behavioural']} behavioural, "
              f"{r['suite']} suite, {r['compound']} compound)")
        for row in r["rows"]:
            kind = "SUITE" if row["suite"] else ("COMPOUND" if row["compound"] else "behavioural")
            print(f"  [{row['index']+1}] {kind:11s} {row['chars']:4d} chars  "
                  f"{row['criterion'][:90]}")
        print(f"Recommended evaluator.max_iterations: {r['recommended_max_iterations']}")
        for e in r["errors"]:
            print(f"ERROR: {e}", file=sys.stderr)
    return 1 if r["errors"] else 0

if __name__ == "__main__":
    raise SystemExit(main())

Tooling: base-vs-head suite differential

Save the following as scripts/tier2_suite_delta.sh (make both scripts executable with chmod +x scripts/tier2_criteria.py scripts/tier2_suite_delta.sh). It uses temporary git worktrees, so neither the base nor the head checkout is modified.

#!/usr/bin/env bash
# Foreman-side suite differential: base vs head.
# Usage: GITREINS_SUITE_CMD='bash tests/selftest.sh' \
#          scripts/tier2_suite_delta.sh <base-rev> [head-rev] [out-file]
set -euo pipefail
base_arg=${1:?usage: tier2_suite_delta.sh <base-rev> [head-rev] [out-file]}
head_arg=${2:-HEAD}
repo=$(git rev-parse --show-toplevel)
base=$(git -C "$repo" rev-parse --verify "${base_arg}^{commit}")
head=$(git -C "$repo" rev-parse --verify "${head_arg}^{commit}")
short_base=$(git -C "$repo" rev-parse --short "$base")
short_head=$(git -C "$repo" rev-parse --short "$head")
out=${3:-"$repo/.gitreins/suite-delta-${short_base}-${short_head}.txt"}
cmd=${GITREINS_SUITE_CMD:-bash tests/selftest.sh}
tmp=$(mktemp -d "${TMPDIR:-/tmp}/cf-suite-delta.XXXXXX")
cleanup() {
  git -C "$repo" worktree remove --force "$tmp/base" >/dev/null 2>&1 || true
  git -C "$repo" worktree remove --force "$tmp/head" >/dev/null 2>&1 || true
  rm -rf "$tmp"
}
trap cleanup EXIT
git -C "$repo" worktree add --detach --quiet "$tmp/base" "$base"
git -C "$repo" worktree add --detach --quiet "$tmp/head" "$head"
run_suite() {
  local tree=$1 log=$2
  set +e
  ( cd "$tree" && bash -c "$cmd" ) >"$log" 2>&1
  local rc=$?
  set -e
  printf '%s\n' "$rc" >"$log.rc"
}
normalise_failures() {
  sed -E \
    -e 's#/(tmp|private/tmp|var/folders)/[A-Za-z0-9._/+@-]+#<TMP>#g' \
    -e 's#[0-9]{4}-[0-9]{2}-[0-9]{2}[T ][0-9:.+Z-]+#<TIME>#g' \
    -e 's/\b(pid|port)[ =:]+[0-9]+/\1=<N>/Ig' \
    -e 's/\b[0-9a-f]{7,64}\b/<HEX>/g' \
    -e 's/\b[0-9]+([.][0-9]+)?s\b/<DUR>/g' \
    "$1" | grep -E '(^|[[:space:]])(FAIL|ERROR)([[:space:]:]|$)' | sort -u || true
}
run_suite "$tmp/base" "$tmp/base.log"
run_suite "$tmp/head" "$tmp/head.log"
base_rc=$(cat "$tmp/base.log.rc"); head_rc=$(cat "$tmp/head.log.rc")
normalise_failures "$tmp/base.log" >"$tmp/base.fail"
normalise_failures "$tmp/head.log" >"$tmp/head.fail"
comm -13 "$tmp/base.fail" "$tmp/head.fail" >"$tmp/new.fail"
comm -23 "$tmp/base.fail" "$tmp/head.fail" >"$tmp/fixed.fail"
new_count=$(grep -c . "$tmp/new.fail" || true)
fixed_count=$(grep -c . "$tmp/fixed.fail" || true)
base_fail_count=$(grep -c . "$tmp/base.fail" || true)
head_fail_count=$(grep -c . "$tmp/head.fail" || true)
mkdir -p "$(dirname "$out")"
{
  echo "SUITE_DELTA"
  echo "BASE $base"; echo "HEAD $head"; echo "COMMAND $cmd"
  echo "BASE_EXIT $base_rc"; echo "HEAD_EXIT $head_rc"
  echo "BASE_FAIL_ROWS $base_fail_count"; echo "HEAD_FAIL_ROWS $head_fail_count"
  echo "NEW_FAIL_ROWS $new_count"; echo "FIXED_FAIL_ROWS $fixed_count"
  echo "--- NEW FAIL ROWS (head only) ---"; cat "$tmp/new.fail"
  echo "--- FIXED FAIL ROWS (base only) ---"; cat "$tmp/fixed.fail"
} >"$out"
cat "$out"
echo "artifact=$out"
echo "sha256=$(sha256sum "$out" | awk '{print $1}')"
[ "$new_count" -eq 0 ]

Do not “fix” the symptom by setting evaluator.max_iterations to 1000. That buys more tokens but leaves the per-criterion suite replay in place, so the run still starves whenever the suite is slow or the context grows.

Verification

Measured on the actual repository at ee13de4 in a clean clone:

$ python3 -m unittest tests.test_node_gateway_auth
Ran 14 tests in 0.003s
OK                                     # rc 0: cheap targeted proof

$ python3 -m unittest discover -s tests -p 'test_*.py'
Ran 177 tests in 18.910s
FAILED (failures=5)                    # rc 1: repository-wide baseline is red

The second result is why run 5b9d30d9 failed on “a green full unittest suite”; it is a pre-existing five-arm control baseline (CF-396), not a defect introduced by the graded change.

The criterion linter rejects the two starved shapes and accepts the passing shape:

...

$ python3 scripts/tier2_criteria.py check --criterion-file compact-criteria.json

Recommended evaluator.max_iterations: 25
rc=0

The differential script was verified in both directions on a throwaway repository:

# head introduces one new FAIL row
NEW_FAIL_ROWS 1
FIXED_FAIL_ROWS 0
rc=1

# both base and head carry the same pre-existing FAIL row
BASE_FAIL_ROWS 1
HEAD_FAIL_ROWS 1
NEW_FAIL_ROWS 0
rc=0

That is the required semantics: a pre-existing red baseline is not blamed on the change, while a genuinely new failure still exits nonzero.

End-to-end acceptance for the fix is the same measurement already recorded by the passing run a0d1db3d: one compact behavioural criterion reached tier2 COMPLETE with 3/3 items PASS; the three superseded runs (da60afc3, 5b9d30d9, a0a670a5) stay recorded as evidence, not as closures. After any future close, fail the change if the new verdict is INCOMPLETE with zero criteria graded while the targeted fixture command above exits 0:

verdict=$(find .gitreins/history -name verdict.json -newermt '-30 minutes' | sort | tail -1)
jq -e '.stages.tier2.passed == true and (.items | length > 0) and
       all(.items[]; .status == "PASS")' "$verdict"

If that check fails while python3 -m unittest tests.test_node_gateway_auth is green, the criterion was written as a suite replay or a compound, and the remedy is the same: split the criterion, move the suite claim to the foreman-side differential, and re-run the behavioural task with the arithmetic budget above.
