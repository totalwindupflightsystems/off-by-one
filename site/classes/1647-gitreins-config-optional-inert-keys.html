Answer

I diagnosed and independently re-verified the issue against a clean gitreins==0.12.1 install, then wrote the solution to /home/kara/SOLUTION.md.

What I verified (not inferred)

  • Downloaded the real 0.12.1 wheel and grep'd the installed source, rather than trusting the audit.
  • The "judge not configured" string does not exist in engine/ or gitreins/. The only similar strings are MCP-only: "LLM not configured" in gitreins_mcp/server.py:431,546.
  • defaults.provider and defaults.api_key_env have 0 readers. Provider is auto-detected from the base URL (engine/llm.py:114), credentials come from env (engine/llm.py:89).
  • The judge needs no config: load_pipeline_config returns a full default tier1 + tier2 pipeline when the file is absent (engine/pipeline.py:915).
  • Live no-config lifecycle run: on a fresh repo with config.yaml ABSENT, task create → start → complete executed Tier 2 and persisted passed: True, stages.tier2...verdict: COMPLETE (verdict commit a3922bc4). On an empty repo the same path produced a real INCOMPLETE evaluator verdict (e91ca334).
  • eval_cap_from_config on the authored file resolves exactly: max_iterations=100.0, max_seconds=1800.0, max_input_tokens=1e7, max_output_tokens=1e6, tool_call_weight=0.1, source='.gitreins/config.yaml'.

Additional finding beyond the filed report

I found that defaults.model is also effectively inert: it has a reader (GitReinsDefaults.overlay, surfaced by load_defaults(workdir).model), but no 0.12.1 caller feeds it into LLMClient — every CLI path builds LLMClient() with no args, and _default_model() uses the raw built-in default. The effective knob is GITREINS_LLM_MODEL. The solution labels all three keys accordingly rather than shipping any silently.
