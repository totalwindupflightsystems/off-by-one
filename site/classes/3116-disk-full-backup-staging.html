Diagnosis

The nightly ~/.hermes/scripts/backup-tiered.sh decompresses sqlite scratch into /var/tmp/hermes-backup-staging on the root fs. tmp_<pid>.db (~48.5 G) and replay_/verify_<pid>.db (~48.5 G) coexist at peak (~119 G), pushing 1.8 T root free space below the 5 % DiskFull line. Phase-by-phase cleanup produces the observed +45 G mid-run frees and the 60–210 G nightly oscillation. /mnt/bulk (3.6 T, 95 % empty) is unused. The disk-guard SCRATCH_GLOBS points only at the retired /tmp/kara-backup-stage, so SOFT reclaim reports 0B and never clears stranded scratch.

Fix

  1. Relocate staging: STAGING_DIR=/mnt/bulk/hermes-backup-staging, enforced by /usr/local/lib/hermes/hermes-staging.sh — refuses to run if staging shares st_dev with /, pins one run PID, and cleans up on EXIT/INT/TERM/HUP.
  2. Idempotent patcher /usr/local/sbin/patch-backup-tiered.sh rewrites hard-coded paths, sources the library after set -euo pipefail, and installs the trap.
  3. Replace disk-guard SCRATCH_GLOBS with the orphan-aware, age-gated /usr/local/lib/hermes/scratch-reclaim.sh (deletes only when the embedded PID is dead and older than STALE_MINUTES; never touches a live run). Defer HARD escalation while a backup is live (MON-GAP-032).
  4. /mnt/bulk persistence + RequiresMountsFor=/mnt/bulk so the guard can't recreate the incident on an unmounted mountpoint.

Verification performed

  • bash -n + shellcheck -S warning clean on all three scripts, both as standalone artifacts and as extracted from the embedded heredocs in the doc.
  • Functional self-tests: guard refuses a same-st_dev staging dir, accepts bulk staging and remaining=0 after trap cleanup, and the reclaimer keeps live-PID and young orphans while reclaiming stale orphans.
  • Host-side reproduction/acceptance queries (Prometheus ALERTS, min_over_time free ratio, /proc/*/io) are included in §3 and §5.

Note: this sandbox only contained problem.json (no live host files), so the scripts were validated here by functional self-tests rather than run against real backup data; §5 gives the exact commands to confirm on karahermes-mde-7840hs, including the min_over_time root-ratio check that must stay > 0.05 across a full backup window.
