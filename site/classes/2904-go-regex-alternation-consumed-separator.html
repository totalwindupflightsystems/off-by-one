Fix: consumed-separator overlap in the v_http_status context-anchored RE2 regex

Problem class: go-regex-alternation-consumed-separator Repo: &lt;project&gt;/logsey — internal/logsey/duckidx/duckidx.go Target test: go test ./internal/logsey/duckidx/ -run TestHTTPStatusViewContextAnchored -count=1 Error signature: silent undercount / zero match — no error is raised.

1. Symptom

The context anchor matched "status 503" but silently failed on the most common real-world shape:

gateway shed worker requests HTTP 503      # expected 503, got no match
HTTP 503                                   # no match
HTTP/503                                   # no match

Broken pattern:

(?i)(?:HTTP [/: ]|status[= ]|code[= ]|returned[ ])[ ]*503

2. Root cause

The HTTP branch is HTTP [/: ]. Read the tokens literally:

token meaning
HTTP the literal protocol word
␠ a literal space (separator #1)
[/: ] one more separator char — /, :, or space (#2)
[ ]* zero or more additional spaces
503 the digits

The branch requires two separators before the digits, and the second is consumed by [/: ]. Trace "HTTP 503":

H T T P ␠ 5 0 3
└────┬──┘ │
   HTTP   literal space  ✔  (separator #1)
          └─ [/: ] must match '5'  ✘  → branch fails

status[= ] puts the separator only once in the class, so "status 503" works. This is the classic consumed-separator overlap: an alternation branch eats a character the following required token still needs. Secondary defect: hard-coded 503 with no trailing boundary gave false positives on status 5034.

3. The fix

3.1 Corrected regex

(?i)(?:https?(?:/1\.[0-9]|2)?[/: ]|https?[^a-z0-9]|status[=: ]|code[=:]|returned[ ])[ ]*[1-5][0-9][0-9](?:\b|[^0-9])
  1. HTTP [/: ] → https?[/: ] — separator lives inside the class, consumed exactly once.
  2. https?(?:/1\.[0-9]|2)? — accepts HTTP/1.1, HTTP/1.0, bare HTTP2.
  3. status[=: ], code[=:] — tolerate status: 503 / code:503.
  4. |https?[^a-z0-9] — other real separators (HTTP-503, HTTP.503); does not match HTTP503.
  5. 503 → [1-5][0-9][0-9](?:\b|[^0-9]) — general codes with a trailing boundary so 5034/2000/600 cannot match.

3.2 Go patch — internal/logsey/duckidx/duckidx.go

// httpStatusContextRe matches an HTTP status code only when it is
// context-anchored: a protocol token (HTTP/HTTPS, optionally versioned),
// "status" / "code", or the word "returned".
//
// IMPORTANT: the separator is INSIDE the character class, i.e.
// `https?[/: ]`, never `https? [/: ]`. A trailing literal space duplicates
// the separator and makes the following digits unattachable.
const httpStatusContextRe = `(?i)(?:https?(?:/1\.[0-9]|2)?[/: ]|https?[^a-z0-9]|status[=: ]|code[=:]|returned[ ])[ ]*[1-5][0-9][0-9](?:\b|[^0-9])`

Build the view DDL from this single constant:

viewDDL := fmt.Sprintf(`
CREATE OR REPLACE VIEW v_http_status AS
SELECT ...
FROM %s
WHERE regexp_matches(message, '%s')
`, sourceTable, httpStatusContextRe)

DuckDB's regexp_matches uses RE2, so the pattern is valid verbatim and behaves exactly as Go's regexp.

package duckidx

import (
    "regexp"
    "testing"

func TestHTTPStatusViewContextAnchored(t *testing.T) {
    re := regexp.MustCompile(httpStatusContextRe)

    cases := []struct {
        line string
        want bool
    }{
        // true cases
        {"gateway shed worker requests HTTP 503", true},
        {"HTTP 503", true},
        {"http 503", true},
        {"HTTP/503", true},
        {"http:503", true},
        {"HTTP/1.1 503", true},
        {"HTTP/1.0 500", true},
        {"HTTP2 503", true},
        {"status 503", true},
        {"status=503", true},
        {"status:503", true},
        {"status: 503", true},
        {"code=503", true},
        {"code:503", true},
        {"returned 503", true},
        {"server returned 503 Service Unavailable", true},
        {"upstream returned  503", true},
        {"HTTP 503 Service Unavailable", true},
        {"HTTP 404 not found", true},
        {"code=200", true},
        // false cases
        {"no status token here", false},
        {"HTTP503", false},
        {"status503", false},
        {"HTTP 5034", false},
        {"status 5034", false},
        {"returned 50", false},
        {"HTTP 600", false},
        {"status 099", false},
        {"http server started", false},
        {"HTTP 2000", false},
    }

    for _, tc := range cases {
        if got := re.MatchString(tc.line); got != tc.want {
            t.Errorf("context match for %q = %v, want %v", tc.line, got, tc.want)
        }
    }
}

5. Optional hardening for HTTP/2 / HTTP/2.0

The canonical fix covers HTTP/1.1, HTTP/1.0, and bare HTTP2, but not HTTP/2 503 or HTTP/2.0 503. If those appear, use this verified superset (still rejects HTTP/2 5034):

(?i)(?:https?(?:/[0-9]+(?:\.[0-9]+)?|2(?:\.[0-9]+)?)?[/: ]|https?[^a-z0-9]|status[=: ]|code[=:]|returned[ ])[ ]*[1-5][0-9][0-9](?:\b|[^0-9])

6. Regression discipline (the lesson)

  • Always probe with both true and false cases. A true-only suite passes when the true case matches via a different branch — the consumed-separator failure was invisible because status 503 matched.
  • Include the most common real-world sentence (gateway shed worker requests HTTP 503), not just canonical tokens.
  • Include boundary negatives: HTTP503, status503, HTTP 5034, HTTP 600, status 099.
  • Never duplicate a separator: if a class already contains the space ([/: ]), do not put a literal space before it. Put the separator in exactly one place and let [ ]* absorb only extra spaces.
