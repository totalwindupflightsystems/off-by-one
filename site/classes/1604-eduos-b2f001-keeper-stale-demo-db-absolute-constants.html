Note: this environment contains no eduos/b2f001 checkout and no running Docker daemon, so the runbook is written as a self-contained, directly usable operator document with parameterized paths ($REPO, $BATTERY, $TICK) rather than patching a live file.

Diagnosis

  • Not a product regression. The per-tick pin-precheck keeper compares live pointer vs prior-tick pointer baseline. Both match (MATCH), proving the product pointer is unchanged. The keeper is blind to the battery's hardcoded constants.
  • Actual cause: the demo DB is seeded cumulatively each tick with no reseed, so quizzes/users row counts ratchet upward. b2f001-teacher-battery.py asserts hardcoded absolutes + a floor pinned to an older snapshot, so P3 quizzes, P3 users, and P7 absolutes fail → 3/42.
  • Rootless Docker quirk: the demo DB lives under the user-1002 daemon; DOCKER_HOST must be unix:///run/user/1002/docker.sock.

Fix (in the doc)

  1. Confirm keeper MATCH vs t617 baseline.
  2. Quantify live-vs-pinned drift via docker exec SQL.
  3. Prove live stability 4× over ~2 min with the seeder frozen.
  4. Discover before re-pin, at the pre-battery lifecycle point (avoids the off-by-one cycle).
  5. Re-pin the constants with lineage comments — canonical t618: 31722 / 52 / floor 1104.
  6. Ratchet the next tick's floor from the post-final UI count (max).
  7. Re-run battery → 42/42, plus stale-literal and lineage guard checks.

Doctrine captured in §5: keeper MATCH + failing absolutes ⇒ stale test constants; floor is the pre-battery RATCHET-FROM under battery-before-hop ordering; never weaken absolutes to >=.
