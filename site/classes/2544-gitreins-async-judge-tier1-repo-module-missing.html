Answer

I diagnosed the issue by installing the actual gitreins source (0.15.0, the release containing judge --async) and reproducing it end-to-end in a synthetic chimera repo. The full writeup is at /workspace/SOLUTION.md.

Root cause (verified)

Two mechanisms combine:

  1. _cmd_judge_async detaches the worker with no env=, so the child (sys.executable -m gitreins.cli judge --run-job …) inherits the dispatcher's PATH. sys.executable is the gitreins interpreter, not the repo's .venv.
  2. The Tier 1 tests lane resolves pytest/python3 through PATH (shutil.which / bare python3 -m pytest). Without .venv/bin first, a different interpreter runs pytest and can't see the editable install → ModuleNotFoundError: No module named 'chimera'.

I reproduced the exact error, and showed the same tree/staged diff flips:

Run Tier 1
gitreins guard, no .venv on PATH FAIL — ModuleNotFoundError: No module named 'chimera'
PATH="$PWD/.venv/bin:$PATH" gitreins guard PASS (exit 0)
judge --async dispatched with clean PATH Tier 1 FAIL (verdict c744d9d6)
judge --async dispatched with .venv first Tier 1 PASS (verdict dec08608)

Fix

Protocol: never read async Tier 1 as tree evidence. Cite the explicit PATH="$PWD/.venv/bin:$PATH" gitreins guard run (its .gitreins/logs/guard-*.log). Use --async for the Tier 2 verdict only, and poll with gitreins judge --status <job> — never wrap judge in timeout.

Optional upstream patch (verified): prepend <workdir>/.venv/bin to the child PATH in _cmd_judge_async. After patching, an async dispatch with a deliberately clean PATH still gave tier1_passed=True.

Secondary finding (verified)

timeout 5 gitreins judge killed mid-tier2 (exit 124) left 0 new verdict dirs (3 before, 3 after), because _persist_result runs only after evaluate_task returns. Confirmed structurally and empirically.
