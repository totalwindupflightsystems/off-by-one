Fix: missing projectId in the full-stack fixture causes a misleading whitespace assertion

Class: missing-semantics · Repo: &lt;project&gt; · Version: 0.1.0 · Fix commit: bb775ce17

TL;DR

generatePortraitSchema started requiring projectId on 2026-11-12. The one test that walks the express route + zod validation still sent a fixture body without projectId, so zod failed and the route returned HTTP 400 before the handler ran. The test then asserted on the response body, measuring the error branch, not the success path. The whitespace mismatch (expected "fierce" to be " fierce ") is a red herring — there was never a trimming/sanitisation bug.

Fix: add projectId: 'proj-approve1' to the fixture body in packages/backend/tests/unit/api/routes/portfolio-approved-prompt-route.test.ts. No src change.

Diagnostic rule: assert the HTTP status is 2xx in the same test before asserting the body, so a schema regression fails at the status line instead of masquerading as a trimming bug.

Root-cause analysis

  1. Schema contract changed. packages/backend/src/api/routes/generation.ts defines generatePortraitSchema, and projectId was made required on 2026-11-12:

ts export const generatePortraitSchema = z.object({ projectId: z.string().min(1), // required since 2026-11-12 approvedPrompt: z.string().trim().min(1), });

  1. The full-stack fixture omitted the now-required field. The route test's request body predates the schema change.

  2. Zod fails → 400 before the handler. Around generation.ts:148:

ts const parsed = generatePortraitSchema.safeParse(req.body); if (!parsed.success) { return res.status(400).json({ error: 'invalid_request', issues: parsed.error.issues }); } res.json(generatePortrait(parsed.data)); // only runs on success

  1. The body assertion measures the error branch. A pretest/setup mutation writes the raw padded value (" fierce "); the test asserts the body without checking status. The compared values never came from the success path, so the diff is not evidence of a trimming bug.

Why the service unit test passes: it calls the generation function directly and never validates a request, so projectId is irrelevant and it can return the field verbatim. Only the test crossing the zod boundary diverges.

Exact fix

File: packages/backend/tests/unit/api/routes/portfolio-approved-prompt-route.test.ts

 const requestBody = {
+  projectId: 'proj-approve1',   // required by generatePortraitSchema since 2026-11-12
   approvedPrompt: '  fierce  ',
   // ...existing fields...
 };

 const res = await request(app)
   .post('/api/generation/portrait')
   .send(requestBody);

If your checkout names the file portrait-approved-prompt-route.test.ts (as in the stack trace), apply the same change there. Do not change src.

Hardened test (diagnostic rule)

 const res = await request(app)
   .post('/api/generation/portrait')
   .send(requestBody);

+ expect(res.status).toBe(200);
+ expect(res.status).toBeLessThan(300);
 expect(res.body.portraitPrompt).toBe('fierce');

[status-first on fixed fixture] PASS status= 200 body= {"portraitPrompt":"fierce"}

Vitest's message template is expected <received> to be <expected> (confirmed from @vitest/expect source), so the reported literal shows the normalised vs. raw pretest values — but on a 400 that comparison was never on the success path.

Environment note: vitest run couldn't boot here (hard 12 GB RLIMIT_AS; vite 5 WASM instantiation → Out of memory), so the route/schema behaviour was verified directly with Node + zod + express + supertest.

Prevention

  • Required-field changes are breaking changes for every fixture — grep the test tree when a zod field becomes required.
  • In full-stack tests always assert status first, then body.
  • A service-unit/route-test pass-fail split usually means the two tests measure different branches, not that a layer is buggy.

Files touched: the route test fixture (+ status-first assertion); generation.ts unchanged.
