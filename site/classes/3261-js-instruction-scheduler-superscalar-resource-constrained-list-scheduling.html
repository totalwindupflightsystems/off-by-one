Diagnosis

The task hides two independent failure modes:

  1. False dependencies. Reading deps from architectural register names (RAW+WAR+WAW) creates ordering edges with no data flow (e.g. a WAW on r0). Fix: register renaming — version every write, keep only RAW. Renaming is legal exactly while live versions stay ≤ K.

  2. Co-issue is a matroid intersection, not a greedy scan. Each instruction needs an FU from its mask (transversal matroid) and at most width may begin (uniform matroid). A maximal legal pack is a maximum independent set of the intersection — implemented with Kuhn augmenting-path matching. Multi-cycle issue ports (occ) make the transversal matroid dynamic per cycle.

While verifying I also caught a real correctness trap: a cycle-based list scheduler that readies an instruction from readyTime alone can co-issue a dependent with its producer. The ready set must also require all predecessors to be scheduled.

The fix (highlights)

  • buildRenamedGraph / buildNaiveGraph — isolate the false-dep effect.
  • maxMatching — matroid intersection (FU transversal ∩ width uniform).
  • listSchedule — critical-path (bottom level) tie-break, dynamic FU-port availability, pressure-bounded.
  • exactSchedule — exhaustive B&B over (start, FU) with admissible lower bounds; returns a provably minimal makespan for blocks ≤ 12, marked proven only when the step budget isn't exhausted.
  • computePressure — exact sweep-line live-version count.

Verification (runs in ~1s, node verify.js)

  • False deps: naive optimum 5 cycles → renamed optimum 3 cycles, both fully validated.
  • Optimality: 30 random blocks × n=4..12; B&B proved optimal for 270 blocks; list heuristic strictly worse in 6.
  • Independent cross-check: exact B&B == separate brute force on 200/200 tiny blocks.
  • Pressure: unbounded pressure 7 → K=4,5,6 schedules all validated within budget; K=3 correctly reported infeasible (proven=false) instead of returning an illegal schedule.
