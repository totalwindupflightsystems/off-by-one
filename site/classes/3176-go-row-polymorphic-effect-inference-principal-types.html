Principal Hindley–Milner Inference with Row-Polymorphic Algebraic Effects

Root-cause analysis

There is no failing build to patch: this is a from-scratch engine in which four mechanisms must agree, and a naive implementation fails characteristically on each.

Failure mode Symptom Root cause
Type vars vs. row vars conflated bogus t1 occurs in (t3 -> t4 ! {r1}) a single id counter / comparing TyVar.ID to RowVar.ID in the occurs check
Closed row vs. open row handled wrongly effect mismatch: {io} vs {r1} when calling an effectful function row unification must let the open side absorb the labels the closed side has; a closed row may not absorb anything
Residual double-counted in handle handling io still leaves io escaping main the deep continuation's latent effect already is the residual; residual ∪ handlerEff counts it twice
lacks constraints omitted handler accepts an operation never performed / residual mis-discharged {io|r} needs io ∉ r, and the constraint must propagate when r is later bound

The program reads the expression language as JSON on stdin, infers the least type and least effect row for each top-level binding, generalising free row variables like type variables (this is what yields {io | r} and subeffecting). It emits inferred schemes, residual lacks constraints, and the first type error with its span.

The exact fix

Row unification (asymmetric — the key rule). Rows are a sorted label set plus an optional tail (nil = closed). The open side absorbs the closed side's extra labels; a closed row absorbs nothing.

if ra.Tail == nil && rb.Tail == nil {              // both closed: exact match
    if len(aOnly) > 0 || len(bOnly) > 0 { return mismatch() }
    return nil
}
if ra.Tail != nil && rb.Tail != nil {              // both open: share a fresh tail
    if ra.Tail.ID == rb.Tail.ID {
        if !sameStrings(aOnly, bOnly) { return mismatch() }
        return nil
    }
    t := in.freshRV("t")
    in.bindRow(ra.Tail, &Row{Labels: bOnly, Tail: t})
    return in.bindRow(rb.Tail, &Row{Labels: aOnly, Tail: t})
}
if ra.Tail != nil {                                // b closed, a absorbs
    if len(aOnly) > 0 { return mismatch() }        // a carries labels b lacks
    return in.bindRow(ra.Tail, &Row{Labels: bOnly})
}
if len(bOnly) > 0 { return mismatch() }            // a closed, b absorbs
return in.bindRow(rb.Tail, &Row{Labels: aOnly})

Kind-correct occurs check. Type vars can never occur in an effect row, so a function's effect must not be traversed:

case *TyFun:
    return in.occursTy(v, x.Arg) || in.occursTy(v, x.Ret)   // no occursRow

lacks constraints are checked in bindRow and propagated to the tail the variable is bound to:

for _, l := range rr.Labels {
    if in.lacks[v.ID][l] { return fmt.Errorf("lacks constraint violated: %q", l) }
}
if rr.Tail != nil {
    for l := range in.lacks[v.ID] { in.addLacks(rr.Tail.ID, l) }
}

Deep handlers in two phases. Phase 1 peels every handled label off the body effect to get the residual; Phase 2 types handler bodies with a continuation whose effect is that residual. The overall effect is just the handler-body effect — the residual is already accounted for by resuming.

remainder := be
for _, h := range e.Handlers {                 // be \ {op1, op2, ...}
    rem := &Row{Tail: in.freshRV("r")}
    in.unifyRow(remainder, &Row{Labels: []string{h.Op}, Tail: rem.Tail})
    remainder = rem
}
res := in.resRow(remainder)
for _, h := range e.Handlers {                 // record io ∉ residual
    if res.Tail != nil { in.addLacks(res.Tail.ID, h.Op) }
}
for _, h := range e.Handlers {                 // resume : opRes -> bodyTy ! residual
    resumeTy := &TyFun{Arg: resTy, Ret: bt, Eff: remainder}

}
return resultTy, handlerEff, nil               // NOT union(remainder, handlerEff)

Entry-point check. After inference, main must have an empty effect row; otherwise the first escaping label is reported.

Modelling choices. unionRows approximates the join of two open rows by sharing tails (exact for all closed/concrete and standard row-polymorphic cases; a fully general join is what systems with effect subsumption implement). A handle requires its operation to occur in the body's effect row, so handling a provably absent operation is an effect mismatch.
