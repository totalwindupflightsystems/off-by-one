What I found

The foreman lane is blocked by an all-or-nothing ownership barrier firing on a convention-less bulk copy of judge bundles — not by work in progress. The five diagnostic facts hold: one dominant new top-level class, N byte-identical physical copies (same sha256sum, links=1, different inodes), zero live producer (no ticks, no CLI rescue code, no logs, no git writer cwd), and zero tracking convention (git ls-files .gitreins/rescued-* = 0, no commits). The stale git add .gitreins/history … recipe neither covers nor should cover it.

Verified fix

Quarantine the class out of the worktree (reversible, no commit), keep one canonical copy for the owner, record a class-scoped ruling, and re-prove with sorted-path digests + diff -q. Measured on the repro:

  • before: BLOCKED: 1440 untracked .gitreins paths
  • after: CLEAR: 0 untracked .gitreins paths, nothing staged
  • diff -q expected==end passed; two end censuses had identical SHA-256
  • anti-pattern quantified: git add would have staged 1440 files / 15,937,920 bytes

Two real traps surfaced and are documented: 1. A census/ledger written inside .gitreins/ re-trips the barrier (BLOCKED: 1) — keep scratch and rulings outside the worktree. 2. The /proc writer census must exclude its own process tree and match /proc/<pid>/exe, not argv substrings, or a wrapper shell containing "git add" false-positives.
