HLC Ordering + HLC-Domain Lease Fencing Under Clock Drift

Problem class: go-hybrid-logical-clock-lease-fencing-stale-read Environment: Go 1.26

1. Root-cause analysis

The bug class is mixing clock domains inside one safety decision. A lease fencing layer must answer a single question — "may leader A still serve this read?" — and if that question is evaluated partly with wall-clock time and partly with HLC time, clock drift can make both sides of the comparison "correct" while the system as a whole is wrong.

Three concrete failure modes:

  1. Lease boundaries expressed as wall-clock deadlines. The lease [t0, t0+TTL) is in the authority's clock but checked with the holder's clock. The holder's clock can lag by up to maxOffset; it keeps serving after the true lease end, while a new leader whose clock leads by up to maxOffset starts early. The windows overlap.

  2. Handoff gap too small. Even with all boundaries in HLC, the gap must cover the old holder's possible lag plus the new holder's possible lead. A one-sided gap of maxOffset is safe only at zero drift.

  3. Treating the token fence as the primary safety mechanism. Fence propagation to storage is asynchronous. Between "new leader's lease starts" and "replica learns the new token", a deposed leader's read is still accepted. Correctness must be: the old holder has stopped issuing reads by the time the new leader's lease starts, independent of fence propagation. The token fence is defense-in-depth.

The fix: every lease boundary and every read check lives in one monotone HLC domain, and the handoff gap is 2*maxOffset.

HLC stays within the same ±maxOffset band as the physical clocks

HLC only ever advances its physical component l to the local physical time or an observed remote physical time; it never invents time ahead of the physical clocks. If all physical clocks are within ±M (M = maxOffset) of true time, then under normal operation true_time - M <= L <= true_time + M. The logical counter c only breaks ties at equal l. Operationally, refuse to grant/serve when L - physical > 2*M (a node at true-M receiving from a node at true+M can legitimately see L-pt up to 2M).

2. Exact HLC send/receive update rules

With pt = physicalNow():

// Local event / send.
Send(pt):
    l' = max(l, pt)
    if l' == l: c = c + 1
    else:       c = 0
    l = l'
    return (l, c)

// Receive remote timestamp (lm, cm).
Receive(pt, (lm, cm)):
    l' = max(l, lm, pt)
    if   l' == l && l' == lm: c = max(c, cm) + 1
    elif l' == l:             c = c + 1
    elif l' == lm:            c = cm + 1
    else:                     c = 0          // l' == pt, physical strictly advanced
    l = l'
    return (l, c)

Ordering is lexicographic. Receive returns a timestamp strictly greater than the received one, so send_ts < receive_ts.

3. The fix: HLC-domain lease with a 2*maxOffset handoff gap

Lease boundaries are Timestamps, never wall-clock deadlines:

type Lease struct {
    Holder int
    Token  uint64
    Start  Timestamp
    End    Timestamp
}

func (a *Authority) Grant(holder int, trueTimeMs int64, handoffGap uint64) *Lease {
    now := a.HLC.Send(trueTimeMs)          // authoritative HLC instant
    a.lastToken++
    start := now
    if a.lastEnd != nil {
        floor := a.lastEnd.AddMS(handoffGap)
        if start.Before(floor) {
            start = floor
        }
    }
    l := &Lease{Holder: holder, Token: a.lastToken,
                Start: start, End: start.AddMS(a.LeaseTTL)}
    a.lastEnd = &l.End
    return l
}

func (ls *LeaderSession) MayRead(ts Timestamp) bool {
    return !ts.Before(ls.Lease.Start) && ts.Before(ls.Lease.End)
}

Set handoffGap = 2 * maxOffset.

Why 2*maxOffset is correct

  • A serves only while L_A < E_A. Since L_A >= true - M, the last true time A can serve satisfies true < E_A + M; A is quiescent by E_A + M.
  • B starts when L_B >= S_B. Since L_B <= true + M, the first true time B can start satisfies true >= S_B - M.
  • No overlap requires S_B - M >= E_A + M, i.e. S_B >= E_A + 2*M.

Hence the gap is 2*maxOffset, not maxOffset. The verifier confirms the exact boundary: drift = M is safe, drift = M+1 breaches.

Storage fencing is defense-in-depth:

func (r *Replica) Read(holder int, token uint64, ts Timestamp, trueTime int64, key string) (Commit, bool) {
    if r.fence != nil && token < r.fence.Token {
        return Commit{}, false            // deposed leader, fenced out
    }
    ...
}

  2. RunLeaseScenario(drift, maxOffset, ttl, handoffGap) — leader A lags true time by drift, B leads by drift; grants HLC leases, serves A reads while its HLC lease is alive, starts B when its HLC reaches its lease Start, and propagates B's fence asynchronously. Reports R_A_Last, R_B_Start, and StaleCommits.

Invariant asserted:

No fenced-out leader read commits after the new leader's lease start.

main.go checks the expectation: safe for drift <= maxOffset, breach detected for drift > maxOffset (so the verifier itself is proven to work).

6. Summary

Concern Wrong Right
Lease boundary clock wall clock / mixed HLC (l,c) only
Handoff gap maxOffset (one-sided) 2*maxOffset
Read validity compare wall deadline Start <= ts < End in HLC
Deposed leader token fence only HLC lease + token fence
Safety under slow fence propagation depends on propagation old holder quiesces first
Drift violation visibility silent stale read verifier reports trace + invariant

Reusable rule: keep every lease computation and read decision in the HLC domain, and set lease.HandoffGap = 2 * maxOffset. If measured drift exceeds maxOffset, the gap is insufficient and the verifier surfaces the exact trace where a deposed leader's read commits after the new leader's lease start.
