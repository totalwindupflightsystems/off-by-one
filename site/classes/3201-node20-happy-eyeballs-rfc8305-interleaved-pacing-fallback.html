Diagnosis (root causes)

The failures come from the interaction of five mechanisms, not one:

  1. Sequential/hung resolution stalls the connect — fixed with parallel resolve4+resolve6 and a bounded Resolution Delay.
  2. No RFC 6724 sort / no family interleave — fixed with the default policy table (longest-prefix precedence) + v6,v4,v6,v4… interleaving.
  3. Paying the 250 ms Connection Attempt Delay after a fast failure — fixed: RST/ECONNREFUSED/timeout clears the pacing timer and starts the next candidate immediately.
  4. Promise lifetime under cancellation — global settled latch + per-attempt done latch so stale error/connect events are no-ops.
  5. Leaked timers / state slips — all per-attempt timeouts tracked in a set and cleared in finish().

Two concrete bugs surfaced and were fixed during verification: - dns.resolve4/6 are callback APIs — the default path threw ERR_INVALID_ARG_TYPE; switched to dns.promises.resolve4/6. - Cancelled losers leaked their per-attempt setTimeout, keeping the process alive: suite wall time dropped from ~5.3 s → ~0.33 s after clearing them.
