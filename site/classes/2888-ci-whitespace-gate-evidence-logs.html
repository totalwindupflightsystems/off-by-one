Summary

Root cause: The capture tooling emits "<field>: <value>" even when the value is empty (stderr:), and writes blank separator lines as a literal " ". Those are real trailing-whitespace bytes in the committed blob, so git show --check correctly flags them. The SHA-label mismatch is a red herring — trust the file:line in the gate output over the run's SHA, since run metadata can lag the commit under test.

Exact fix: 1. gh run view <run-id> --log-failed → authoritative file:line list. 2. Strip only flagged lines: sed -i "Ns/[[:space:]]*$//" path/to/evidence.log. 3. Automated pass that parses file:line: trailing whitespace., dedupes, and applies the same targeted sed per line. 4. Re-run git show --check --oneline --no-renames HEAD locally before amending/pushing.

Verification: - Local gate is clean: git show --check --oneline --no-renames HEAD && echo "GATE OK". - No strays remain: git grep -nI '[[:space:]]$' -- '*.log' (no matches). - Diff is minimal: git diff --stat / git diff --check show only intended lines. - CI re-check via gh run view <new-run-id> --log-failed, not by SHA label.

The markdown also includes an optional capture-side normalization (f"{label}:" + (f" {value}" if value else "")) to prevent recurrence.
