Answer

I diagnosed and verified the fix. Note: the original trouble repo was not present in the sandbox, so I reconstructed the internal/sensors package from the problem statement, reproduced the exact red, applied the fix, and falsified it.

Root cause

RuleDirFingerprint hashed only path + size + mtime:

fmt.Fprintf(h, "%s\x00%d\x00%d\n", name, info.Size(), info.ModTime().UnixNano())

A same-size content rewrite with a pinned/unchanged mtime (coarse fs granularity, tar -x, rsync -t, os.Chtimes) leaves every stat field identical → fingerprint unchanged → the 60s sweep misses the real change and never reloads. The test asserted "the mtime moved", i.e. it asserted a property of the filesystem, not the code.

Fix

Fold a streamed SHA-256 content digest into the fingerprint alongside metadata, using io.Copy(h, f) so bytes are never buffered:

fmt.Fprintf(h, "%s\x00%d\x00%d\x00", name, info.Size(), info.ModTime().UnixNano())
f, err := os.Open(path)
if err != nil { return "", err }
_, copyErr := io.Copy(h, f)
closeErr := f.Close()
// ... surface both errors
h.Write([]byte("\n"))

Metadata stays in the digest (path binding); nothing-changed stays stable so the sweep doesn't reload every tick.

Test

TestRuleDirMTimesDetectsChange now asserts the hostile condition directly — same-length rewrite + os.Chtimes pins mtime equal — plus a natural polled edit/removal half with a 3s deadline (> 1s granularity) and a stability check.
