GitReins task complete exhausts the foreman tool window

Problem class: foreman-worker-gitreins-task-complete-timeout
Scope: coding-hermes foreman tick running GitReins against a Go repo while the full Go suite and CI are also active.

1. Root cause

gitreins task complete <ID> is a blocking, two-phase operation, not a quick bookkeeping command:

cmd_task_complete()
  tm.complete(...)                 # phase 1: write task status / completed_at
  judge.evaluate_task(...)         # phase 2: Tier 1 (full Go test) + Tier 2 (LLM evaluator)
  _persist_result(...)             # write .gitreins/history/<date>/<hash>/verdict.json

In the current tree the exact sequence is gitreins/cli.py:2072 → :2079 → :2082; the judge is engine/judge.py, and the judge's Tier 1 uses the configured test command (go test ...) with guards.test_timeout / guards.hook_timeout as its own inner limits.

The foreman's terminal/tool window is a different, outer limit. When the full Go test suite runs under CI/fleet contention, Tier 1 can consume most of the window; Tier 2 then pushes the whole call past the cap. The harness kills the process tree.

That leaves a valid but unfinished transaction:

Version behavior GitReins task state Verdict Board row
older GitReins (flip after evaluation) in_progress absent in_progress
current GitReins (flip before evaluation) complete absent in_progress

The board row is still in_progress because boardctl update ... --status complete is a separate write that the worker performs only after task complete returns. A killed foreground call never reaches it.

This is not a test failure and not evidence that the work is unverified. It is a scheduler/window mismatch. Do not re-run plain gitreins task complete in the same foreground window: it will hit the same wall and can repeat the state/attestation side effects.

Distinguish it from other red states

Observation This class Real test failure
task list / .gitreins/tasks.yaml complete or in_progress, work already committed status reflects a completed evaluation
verdict directory for the work commit none present with FAIL/INCOMPLETE
terminal result timed out / exit 124 / no final line normal exit 1 with a summary
judge --status <job> running, or no job was ever created terminal result exists

2. Exact fix

2.1 Immediate recovery (run in the repo root)

cd "$REPO"
ID="$TASK_ID"
DAY="$(date -u +%F)"

# 1. Inspect what actually survived the kill.
gitreins task list
ls -la ".gitreins/history/$DAY" 2>/dev/null || true
python3 - "$ID" <<'PY'
import glob, json, os, sys
task = sys.argv[1]
files = glob.glob(".gitreins/history/*/*/verdict.json")
hits = []
for f in files:
    try:
        d = json.load(open(f))
    except Exception:
        continue
    if d.get("task_id") == task:
        hits.append((os.path.getmtime(f), f, d.get("passed"), d.get("commit")))
if hits:
    _, f, passed, commit = max(hits)
    print(f"VERDICT EXISTS: {f} passed={passed} commit={commit}")
else:
    print("NO VERDICT for", task)
PY

If a verdict for this task already exists and is passed=true, skip to the board update in §2.3.

Otherwise complete only the state transition, then move the expensive evaluation off the tool window:

# 2. Flip the task state without inline Tier 2.
#    Use a bounded call no larger than the tool window. `|| true` is intentional:
#    a Tier-1 failure exits 1, but the task state flip is already durable.
timeout 300 gitreins task complete "$ID" --force --skip-tier2 || true

# 3. Dispatch Tier 1 + Tier 2 as a detached, disk-backed job.
#    This returns immediately with a job id and does NOT die with the CLI.
OUT="$(gitreins judge "$ID" --async)"
printf '%s\n' "$OUT"
JOB="$(printf '%s\n' "$OUT" | sed -n 's/^Async job dispatched: //p' | head -n1)"
test -n "$JOB" || { echo "no job id returned" >&2; exit 1; }
printf '%s\n' "$JOB" > ".gitreins/foreman-${ID}.job"

# 4. End this tool call. Do not wait for the evaluation.

If the task is already complete in newer GitReins, skip step 2 and run step 3. judge --async does not flip task status; that is why the --skip-tier2 completion is needed first when the task is still in_progress.

If step 2 was itself killed before the state flip (older GitReins, or a very short tool window), detach the completion instead and let it run unattended:

setsid nohup gitreins task complete "$ID" --force --skip-tier2 \
  > "/tmp/gitreins-complete-${ID}.log" 2>&1 &
echo $! > "/tmp/gitreins-complete-${ID}.pid"

Then dispatch the async judge as in step 3 on a later call, after gitreins task list shows the task complete.

Why this survives: _cmd_judge_async spawns the worker with start_new_session=True and publishes a disk-backed job record (~/.local/share/gitreins/jobs/<job>.json, override GITREINS_JOB_DIR). Killing the foreground CLI does not kill the detached worker. The worker runs the same evaluate_task() and _persist_result() path as a synchronous run.

2.2 Next tick: poll, do not block

cd "$REPO"
JOB="$(cat ".gitreins/foreman-${TASK_ID}.job")"
gitreins judge --status "$JOB"

Exit codes: 0 complete, 2 still running, 1 error/not found, 3 orphaned/dead worker. A 2 is normal: return and poll on a later tick.

When it reaches complete, verify the artifact, not the console summary:

ID="$TASK_ID"
python3 - "$ID" <<'PY'
import glob, json, os, sys
task = sys.argv[1]
files = glob.glob(".gitreins/history/*/*/verdict.json")
hits = []
for f in files:
    try:
        d = json.load(open(f))
    except Exception:
        continue
    if d.get("task_id") == task:
        hits.append((os.path.getmtime(f), f, d))
if not hits:
    raise SystemExit("no verdict.json for task " + task)
_, path, d = max(hits)
print("verdict:", path)
print("task_id:", d.get("task_id"))
print("passed :", d.get("passed"))
print("commit :", d.get("commit"))
print("items  :", [(i.get("status"), i.get("criterion")) for i in d.get("items", [])])
if d.get("passed") is not True:
    raise SystemExit("verdict is not passing; keep the board row open")
PY

The commit field is the HEAD that was graded at evaluation time, not necessarily the implementation commit. Cite that value in the board closeout.

2.3 Close the board lifecycle only after the verdict exists

cd "$REPO"
ID="$TASK_ID"
JOB="$(cat ".gitreins/foreman-${ID}.job")"
SHA="$(python3 - "$ID" <<'PY'
import glob, json, os, sys
files=[]
for f in glob.glob(".gitreins/history/*/*/verdict.json"):
    try: d=json.load(open(f))
    except Exception: continue
    if d.get("task_id")==sys.argv[1]: files.append((os.path.getmtime(f), d.get("commit") or ""))
print(max(files)[1] if files else "")
PY
)"
SHA="${SHA:-$(git rev-parse --short HEAD)}"

boardctl -C "$REPO" update "$ID" --status complete \
  --commit-hash "$SHA" \
  --guard PASS --ci SKIP \
  --evidence-run-id "$JOB" \
  --summary "Completed via GitReins async judge after foreground tool-window timeout" \
  --note "job=$JOB; verdict=.gitreins/history/<date>/<hash>/verdict.json"

boardctl -C "$REPO" validate

Use --ci GREEN only if CI is actually green on that commit; otherwise use SKIP (or the real observed result). Do not claim a green CI run that has not finished.

If the job is still running at the end of the tick, leave the board row in_progress and record the job id in the note/handoff. That is the honest state; do not fabricate a verdict or complete the board early.

3. Prevention: make async the default for the foreman

3.1 Never run plain task complete in a capped foreground call

Use one of these:

# CLI split (durable job id, resumable across ticks)
gitreins task complete <ID> --force --skip-tier2 || true
gitreins judge <ID> --async
gitreins judge --status <job-id>

# MCP-native alternative: task.complete is async by default (wait=false)
# returns {"job_id": ..., "status": "running", ...}; poll judge.status.

For very large Go suites where even Tier 1 can exceed the window, detach the whole completion instead of leaving it in the foreground:

setsid nohup gitreins task complete <ID> --force \
  > /tmp/gitreins-complete-<ID>.log 2>&1 &
echo $! > /tmp/gitreins-complete-<ID>.pid

Then verify the verdict/task state on later ticks exactly as in §2.2.

3.2 Bound the inner limits and reduce host contention

.gitreins/config.yaml:

guards:
  test_timeout: 300      # Tier-1 test subprocess cap
  hook_timeout: 360      # overall Tier-1 cap; keep > test_timeout
evaluator:
  max_iterations: 60
  max_time: "30m"

Also keep the outer tool window strictly larger than hook_timeout, or use async so the outer window is irrelevant. Do not run a duplicate full go test ./... locally at the same time as the same full suite in CI; that is contention, not extra evidence. Keep CI as the full-suite authority and let the async judge consume the already-verified tree.

5. One-line runbook

A foreman gitreins task complete hit the tool window → the work is committed but may have no verdict → check .gitreins/tasks.yaml and .gitreins/history/<date>/ → if no passing verdict, run gitreins task complete <ID> --force --skip-tier2 once, then gitreins judge <ID> --async, save the job id, poll gitreins judge --status <job> on later ticks, and only then close the board row with boardctl update ... --status complete --evidence-run-id <job>. Never re-run plain foreground task complete.
