Answer

Fixing Go Test Ambient-Environment Contamination in internal/scheduler

Root-cause analysis

The three failures are not three independent regressions. They are three symptoms of one shared, non-hermetic input: the test process inherited SCHEDULER_OPERATOR_RESTART_APPROVED=<truthy> from the invoking shell/agent/CI session.

Go test binaries inherit the parent process environment. The scheduler predicate reads SCHEDULER_OPERATOR_RESTART_APPROVED at decision time (os.Getenv/os.LookupEnv), and that same boolean feeds all three paths:

Failing test Shared predicate effect when ambient value is truthy Expected with no operator approval
TestSCHEDGAP091_DrainTimeoutStampsOrphan Orphan classification takes the operator_restart path instead of the drain_timeout path orphan_reason=drain_timeout
TestOperatorRestartApprovalEnv OperatorRestartApproved() returns true even though the test assumes no value is set false (fail-closed)
TestAbortInFlightTicks_OperatorApprovedStamp The abort-in-flight tick is stamped as operator-approved no approved stamp

The tests that exercise the default/fail-closed behavior do not explicitly remove the variable, and the package has no TestMain/test helper that scrubs ambient application env. Therefore the suite's verdict depends on who launched it. A truthy ambient value makes the tests fail; env -u SCHEDULER_OPERATOR_RESTART_APPROVED makes them pass without changing production code. That is the signature of test contamination, not a scheduler regression.

The production code may legitimately support an operator-approved restart mode. The defect is that the tests inherit that mode instead of controlling it.

Diagnosis ladder (run before dispatching a fix worker)

Set these once:

REPO="${REPO:-$HOME/coding-hermes-scheduler}"   # directory containing go.mod
PKG="./internal/scheduler"
VAR="SCHEDULER_OPERATOR_RESTART_APPROVED"
cd "$REPO"
  1. Confirm the three tests fail in isolation with the ambient environment:
go test "$PKG" -run '^(TestSCHEDGAP091_DrainTimeoutStampsOrphan|TestOperatorRestartApprovalEnv|TestAbortInFlightTicks_OperatorApprovedStamp)$' -count=1 -v
  1. Find the predicate and its exact environment-variable name:
rg -n 'SCHEDULER_OPERATOR_RESTART_APPROVED|OperatorRestartApproved|operatorRestart|operator_restart|drain_timeout' "$PKG"

If rg is unavailable, use:

grep -RIn 'SCHEDULER_OPERATOR_RESTART_APPROVED\|OperatorRestartApproved\|operator_restart\|drain_timeout' "$PKG"
  1. Inspect the ambient value in the calling shell:
printenv "$VAR" || echo "$VAR is unset"
  1. Re-run the same tests with only that variable removed:
env -u "$VAR" go test "$PKG" -run '^(TestSCHEDGAP091_DrainTimeoutStampsOrphan|TestOperatorRestartApprovalEnv|TestAbortInFlightTicks_OperatorApprovedStamp)$' -count=1 -v
  1. Re-run the whole package cleanly:
env -u "$VAR" go test "$PKG" -count=1 -v

Stop rule: if step 4/5 is green, do not attribute the red run to a code regression and do not dispatch a production-code fix. Treat it as ambient-environment contamination. If the clean run is still red, then continue normal regression triage.

Fix B: durable suite fix so the verdict no longer depends on the caller

Create internal/scheduler/main_test.go (or, if the package already has a TestMain, add the scrub loop to the existing one; never define two TestMain functions):

package scheduler

import (
    "os"
    "testing"
)

// Application switches that tests must set explicitly. Never inherit these
// from the invoking shell/agent/CI environment.
var ambientEnvVars = []string{
    "SCHEDULER_OPERATOR_RESTART_APPROVED",
}

func TestMain(m *testing.M) {
    // Scrub ambient contamination before any test runs. Tests that need the
    // switch enabled must set it explicitly with t.Setenv (or equivalent) and
    // restore/unset it afterwards.
    for _, key := range ambientEnvVars {
        _ = os.Unsetenv(key)
    }
    os.Exit(m.Run())
}

If the existing tests set the variable directly with os.Setenv, convert them to t.Setenv so they restore state automatically. Note that Go rejects t.Setenv in tests that call t.Parallel; keep environment-mutating tests serial or inject the setting through a config value instead. For tests whose semantics require the variable to be genuinely absent (not merely empty), use this helper instead of t.Setenv(key, ""):

func unsetEnvForTest(t *testing.T, key string) {
    t.Helper()
    old, ok := os.LookupEnv(key)
    if err := os.Unsetenv(key); err != nil {
        t.Fatalf("unset %s: %v", key, err)
    }
    t.Cleanup(func() {
        if ok {
            _ = os.Setenv(key, old)
        } else {
            _ = os.Unsetenv(key)
        }
    })
}

Use it in default/fail-closed tests before calling the predicate:

func TestOperatorRestartApprovalEnv(t *testing.T) {
    unsetEnvForTest(t, "SCHEDULER_OPERATOR_RESTART_APPROVED")

    if OperatorRestartApproved() {
        t.Fatal("OperatorRestartApproved with no env set = true, want false/fail-closed")
    }
}

If the package grows more environment-sensitive predicates, extend ambientEnvVars after auditing them with:

rg -n 'os\.(Getenv|LookupEnv)\(' "$PKG"

Optional long-term production hardening

Reading process-wide env at decision time is inherently ambient. If practical, resolve operator-restart approval once at process startup into a scheduler config/struct and pass that value into the decision paths. Tests can then inject the value directly without touching process env at all. The TestMain scrub above is still useful as a safety net for existing env-reading code.

Acceptance criteria:

  • A reproduces the failure when the ambient variable is truthy. If A is unexpectedly green, the failure was already masked or the checkout differs from the reported one.
  • B is green without any production-code change. That proves the red was ambient contamination, not a scheduler regression.
  • C and D are green with the ambient variable deliberately set, because TestMain removes it before tests run. If D fails in another package, apply the same TestMain scrub there or use the env -u gate for that package.
  • A later run from a normal shell is also green; the suite no longer depends on the caller's environment.
