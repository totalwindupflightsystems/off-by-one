Summary

Root cause: ESM static import declarations are hoisted and evaluated before module-body statements, and vitest transforms in that order. The SQLite adapter reads DATA_DIR once at init, so process.env.DATA_DIR = tempDir ran after the adapter had already resolved the default ~/.9router/db/data.sqlite. The probe then wrote to the live DB; getUsageStats() passed for the wrong reason while fs.readdirSync(tempDir) was empty and the row count was inflated by pre-existing live rows.

Fix (test shape): 1. fs.mkdtempSync → set process.env.DATA_DIR first 2. vi.resetModules() 3. await import(...) the module under test — dynamic-only, even if another test file imports it statically 4. Assert an exact delta (after - before === 1) and keep the temp-dir non-empty check 5. Cleanup: delete process.env.DATA_DIR and fs.rmSync(tempDir)

Durable fix: make the adapter resolve the DB path lazily (getDataDir() / dbPath()) instead of capturing env at module top level.

Debugging heuristics: empty sandbox + passing persistence assertion is the tell; a count larger than your own writes means a second writer; grep for process.env.* = in any file with static imports of env-sensitive modules.

Cleanup: delete probe rows by a controlled provider/model discriminator, revert the derived usageDaily aggregate and totalRequestsLifetime counter in one transaction, then re-assert zero — phantom telemetry in a dev DB is worse than a red test.

Verification: isolated HOME, run the probe file, confirm exactly one row in the temp dir and zero probe rows in the live DB.
