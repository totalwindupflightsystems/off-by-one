Fix CF-304 test-fixture schema drift (selftest section 67) — and keep the test able to catch a wrong policy

Repo: coding-hermes/code-factory Class: test-fixture-schema-drift Regressed in: 8d6b303b (fix: reconcile CF-134 cooldown policy) Upstream repair: eb02981a (fix(tests): derive CF-304 lane-config fixture policy from cooldown_policy) Symptom: cannot read projects table: no such column: cooldown_s Section: tests/selftest.sh section 67 (tests/test_lane_config_readonly.py)

1. Root cause

The production reader grew four new columns, but the test fixture was still a hand-written five-column table. Nothing in the fixture was derived, so the split stayed invisible until section 67 ran.

Reader SELECT (scripts/load_lane_config.py::read_rows):

SELECT name, namespace_id, admission_mode, prompt, prompt_mode,
       cooldown_s, cooldown_floor_s, cooldown_ceiling_s, cooldown_pin_s
FROM projects WHERE name LIKE 'code-factory%' ORDER BY name

Fixture DDL before the fix (tests/test_lane_config_readonly.py::make_fixture):

CREATE TABLE projects (name TEXT PRIMARY KEY, namespace_id TEXT,
                       admission_mode TEXT, prompt TEXT, prompt_mode TEXT)

SQLite rejects the SELECT with no such column: cooldown_s; read_rows wraps it as LaneConfigError("cannot read projects table: ..."). Three arms (arm_default, arm_dry_run, arm_apply) all call read_rows, so one schema defect looks like three bugs. arm_refusals fails earlier and arm_red_control runs the old script at fe63289e, which never selects those columns — hence both PASS.

3. The fix

Both parts are required. Add the import and literal guard to tests/test_lane_config_readonly.py:

ROOT = Path(__file__).resolve().parents[1]
SCRIPT = ROOT / "scripts" / "load_lane_config.py"
sys.path.insert(0, str(ROOT / "scripts"))

import cooldown_policy  # noqa: E402  (fixture derives its policy from the module under test)

# Literal regression guard: pin one named lane's cadence by hand so a wrong
# policy constant still fails (otherwise arrange becomes its own oracle).
LITERAL_CADENCE_LANE = "code-factory-qa"
LITERAL_CADENCE_S = 43200

Derive the nine-column schema and per-lane values in make_fixture:

    con.execute(
        "CREATE TABLE projects (name TEXT PRIMARY KEY, namespace_id TEXT, "
        "admission_mode TEXT, prompt TEXT, prompt_mode TEXT, "
        "cooldown_s INTEGER NOT NULL DEFAULT 1800, "
        "cooldown_floor_s INTEGER NOT NULL DEFAULT 1800, "
        "cooldown_ceiling_s INTEGER NOT NULL DEFAULT 1800, "
        "cooldown_pin_s INTEGER)"
    )
    for name in LANES:
        policy = cooldown_policy.policy_for_lane(name)
        con.execute(
            "INSERT INTO projects VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)",
            (name, "old-namespace", "old-mode", "old prompt", "replace",
             policy["cadence_s"], policy["floor_s"], policy["ceiling_s"], None),
        )
    con.execute(
        "INSERT INTO projects VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)",
        (OUTSIDER, "outside-namespace", "outside-mode", "outside prompt",
         "replace", 1800, 1800, 1800, None),
    )

Add the literal arm and register it in main():

def arm_literal_policy(parent: Path, root: Path) -> None:
    """Literal expectation that keeps the derived arrangement from self-judging."""
    policy = cooldown_policy.policy_for_lane(LITERAL_CADENCE_LANE)
    require(
        policy["cadence_s"] == LITERAL_CADENCE_S,
        f"{LITERAL_CADENCE_LANE} cadence is {policy['cadence_s']}, "
        f"expected literal {LITERAL_CADENCE_S}",
    )
    con = sqlite3.connect(parent / "scheduler.db")
    try:
        stored = con.execute(
            "SELECT cooldown_s, cooldown_floor_s, cooldown_ceiling_s "
            "FROM projects WHERE name = ?",
            (LITERAL_CADENCE_LANE,),
        ).fetchone()
    finally:
        con.close()
    require(stored is not None, f"fixture omitted {LITERAL_CADENCE_LANE}")
    require(
        stored[0] == LITERAL_CADENCE_S,
        f"fixture {LITERAL_CADENCE_LANE} cadence is {stored[0]}, "
        f"expected literal {LITERAL_CADENCE_S}",
    )

    arms = [
        ("default read-only report", arm_default),
        ("dry-run exact update set", arm_dry_run),
        ("explicit apply", arm_apply),
        ("named missing DB/prompt refusals", arm_refusals),
        ("literal cadence expectation", arm_literal_policy),   # <-- new
    ]

No production code changes: the reader was already correct.

6. Takeaway

A hand-written fixture is a second, unowned copy of production schema. Derive it from the module the reader trusts so it cannot be orphaned — but keep one literal expectation for any value whose correctness matters, or arrange becomes the oracle and the test can only prove the code agrees with itself.
