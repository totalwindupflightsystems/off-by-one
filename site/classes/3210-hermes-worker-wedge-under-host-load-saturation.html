Answer

Hermes worker wedge under host load saturation — diagnosis, kill, and foreman-direct recovery

TL;DR

Two hermes chat --query-file <brief> -Q workers in one git worktree were alive but making zero forward progress — no edits, no exit, empty -Q transcript. They were not "still thinking"; they were parked in futex_do_wait while a sibling lane's Rust link hammered a shared cargo target on a 16-core box at loadavg 154 with 16 GB swap in use. The fix is not another dispatch:

  1. Prove the wedge with the four-signal test (sessions row + frozen message count + frozen /proc/<pid>/io + futex_do_wait with no children).
  2. Kill by explicit PID — never pkill -f, because the brief path is on the worker's own argv and the orchestrator/foreman may carry it too.
  3. Verify the isolated worktree is still clean/committed.
  4. Drain the host, or (preferred when the box is unusable) author the change foreman-direct inside the isolated worktree instead of buying a third identical zero-output dispatch.

The four-signal check and the kill are verified below against a live reproduction of the exact futex_do_wait / frozen-io signature.

Symptom

  • ps shows the worker process alive (STAT S), parent is the api_server tick lane.
  • git -C <worktree> status --porcelain is empty; git diff empty; no new commits.
  • The -Q (quiet) transcript for the session is empty or unchanged.
  • The worker never exits and never advances the session's message count.
  • Attempting to "nudge" by re-dispatching the same brief to the same lane wedges identically — this is the wrong answer and burns a third worker slot under the same saturated host.

Why "still thinking" and "wedged" look identical

A healthy long final turn and a wedged process both show: process alive, no diff yet, quiet log. Any one cheap signal is inconclusive:

Signal Healthy long turn Wedged
process alive yes yes
diff / transcript empty until turn ends empty forever
message count frozen over 3 min can be frozen during one long turn frozen
syscr/syscw frozen can be frozen during pure-LLM/compute stretch frozen
wchan=futex_do_wait possible briefly while waiting on I/O stuck there
child processes may have a tool/compile child none

The wedge is only established when all four independent signals agree and repeat across two separated samples. That is the discriminator that separates "slow turn" from "dead in a futex".

Root cause

Chain of causation:

  1. A sibling lane ran a Rust link step against a cargo target directory shared with other lanes.
  2. On a 16-core host that pushed loadavg to 154 (~10×) and forced 16 GB into swap.
  3. Memory/scheduler pressure made the worker's Go runtime/agent acquire a lock and block in the kernel (futex_do_wait).
  4. Once parked with no runnable child and no timer-driven wakeup that can make progress, the worker emits no syscalls, no messages, no edits — it is indistinguishable from a long turn by any single signal.
  5. The agent cannot be un-wedged by waiting: the trigger condition (host saturation + shared target) persists, so re-dispatch reproduces the exact same failure.

The scheduler unit itself shows how many lanes can pile in: the disabled/legacy unit ran --max-concurrent 10; the current config uses --max-concurrent 4 (/etc/systemd/system/coding-hermes-scheduler.service.disabled). Multiple concurrent lanes sharing one cargo target/ is the amplification factor.

Confirm the wedge: the four-signal test

Get the PID and its identity first, then run two samples. Do not pattern-kill.

# 1) Identity — list only, do not kill by pattern
pgrep -af 'hermes chat'
#   <pid> hermes chat --query-file /path/to/brief.md -Q ...

PID=<pid>
# Confirm the argv really is this worker (guards against PID reuse)
tr '\0' ' ' </proc/$PID/cmdline; echo

Signal 1 — session identity (expected cwd + model). Discover the exact subcommand available in this Hermes build, then confirm the worker session maps to the intended worktree and model:

hermes sessions --help          # or: hermes sessions list / show
hermes sessions list | grep -i '<session-id-or-worktree>'
# If the store is sqlite, adjust table/column names to the build; the point is:
#   sessions.cwd == the intended worktree, sessions.model == expected model

Signal 2–4 — run the repeatable sampler (wedge-check.sh) below; it samples syscr/syscw, wchan, and children twice with a gap:

#!/usr/bin/env bash
# wedge-check.sh PID [SECONDS]  -> exit 0 = WEDGED, exit 1 = not confirmed
set -u
PID="${1:?usage: wedge-check.sh PID [SECONDS]}"; GAP="${2:-10}"
[ -d "/proc/$PID" ] || { echo "no such pid: $PID"; exit 2; }

sample() {
  local p="$1"
  local io wchan state children
  io=$(awk '/^syscr/{c=$2} /^syscw/{w=$2} END{print c" "w}' "/proc/$p/io" 2>/dev/null)
  wchan=$(cat "/proc/$p/wchan" 2>/dev/null)
  state=$(awk '{print $3}' "/proc/$p/stat" 2>/dev/null)
  children=$(tr '\0' ' ' < "/proc/$p/task/$p/children" 2>/dev/null)
  printf '%s|%s|%s|%s\n' "$io" "$wchan" "$state" "$children"
}

IFS='|' read -r io1 wchan1 state1 kids1 <<<"$(sample "$PID")"
echo "sample A: syscr/syscw=$io1 wchan=$wchan1 state=$state1 children=[$kids1]"
sleep "$GAP"
[ -d "/proc/$PID" ] || { echo "process exited during window"; exit 1; }
IFS='|' read -r io2 wchan2 state2 kids2 <<<"$(sample "$PID")"
echo "sample B: syscr/syscw=$io2 wchan=$wchan2 state=$state2 children=[$kids2]"

frozen_io=0; [ "$io1" = "$io2" ] && frozen_io=1
futex=0; case "$wchan2" in *futex*|*do_futex*) futex=1;; esac
no_kids=0; [ -z "${kids2// /}" ] && no_kids=1

if [ "$frozen_io" = 1 ] && [ "$futex" = 1 ] && [ "$no_kids" = 1 ]; then
  echo "VERDICT: WEDGED (io frozen, futex sleep, no children) -> kill by pid"
  exit 0
fi
echo "VERDICT: not confirmed (io_frozen=$frozen_io futex=$futex no_children=$no_kids)"
exit 1

For a longer baseline, compare the session's message count across ~3 minutes:

# two samples ~3 min apart must be equal for a wedge
hermes sessions show <session-id>   # or the sqlite query for this build
sleep 180
hermes sessions show <session-id>

Interpretation matrix

io frozen futex no children cwd/model correct Verdict
yes yes yes yes WEDGED — kill and recover
yes no any any likely a long compute/LLM turn; re-sample
no any any any progressing; leave it alone
any yes children present any waiting on a tool/compile child; not wedged

The kill is only safe to trigger on the first row.

The exact fix

Step 0 — freeze the evidence before killing

PID=<pid>; WT=/path/to/isolated/worktree
OUT=/var/log/hermes-wedge/$(date +%s)-$PID
mkdir -p "$OUT"
tr '\0' ' ' </proc/$PID/cmdline    >"$OUT/cmdline"
cp /proc/$PID/io                    "$OUT/io"
printf '%s\n' "$(cat /proc/$PID/wchan)" >"$OUT/wchan"
cat /proc/$PID/stat                 >"$OUT/stat"
git -C "$WT" status --porcelain     >"$OUT/git-status"
git -C "$WT" rev-parse HEAD         >"$OUT/git-head"
uptime; free -h; cat /proc/loadavg; cat /proc/pressure/{cpu,io,memory}

Step 1 — kill by explicit PID (never pkill -f)

The brief path (--query-file /…/brief.md) appears on the worker's own argv; a pkill -f brief.md can therefore kill the foreman/orchestrator and sibling lanes that reference the same path, and can race a just-started replacement. Kill the exact PID, escalating:

PID=<pid>
# Re-verify identity immediately before signalling (PID-reuse guard)
grep -aq -- '--query-file' /proc/$PID/cmdline || { echo "pid changed, abort"; exit 1; }

kill -TERM "$PID" 2>/dev/null
for i in $(seq 1 10); do kill -0 "$PID" 2>/dev/null || break; sleep 1; done
kill -0 "$PID" 2>/dev/null && kill -KILL "$PID"
for i in $(seq 1 10); do kill -0 "$PID" 2>/dev/null || break; sleep 1; done
kill -0 "$PID" 2>/dev/null && echo "pid $PID still visible (zombie? check parent)" || echo "pid $PID gone"

If it shows as a zombie (Z), the tick lane's parent must reap it; do not kill the zombie — restart/reap the lane if the parent is gone.

Step 2 — verify the worktree is still clean/isolated

Each worker has its own worktree. Confirm nothing partial was written and it is on the intended base:

WT=/path/to/isolated/worktree
git -C "$WT" status --porcelain          # must be empty
git -C "$WT" rev-parse HEAD              # record the base
git -C "$WT" worktree list               # confirm no shared/duplicate worktree
git -C "$WT" stash list                  # should be empty

Step 3 — drain the host, or skip straight to foreman-direct

Check whether the box is usable before dispatching anything:

cat /proc/loadavg          # 1-min average should fall back toward nproc (=16)
free -h                    # swap in use should fall
cat /proc/pressure/io      # some/full avg10 should fall
ps -eo pid,ppid,stat,etimes,%cpu,%mem,cmd --sort=-%cpu | head -20
# find the culprit sibling link, e.g.:
ps -eo pid,ppid,stat,etimes,cmd | grep -E 'cargo|rustc|cc|ld' | grep -v grep

Wait only if the 1-min loadavg is trending below ~nproc and swap is draining. If load stays pegged, do not dispatch — go foreman-direct.

Step 4 — implement foreman-direct in the isolated worktree

This is the right answer when the host is saturated: the foreman (who has the brief and the worktree path) writes the change itself, with no new worker process to wedge.

WT=/path/to/isolated/worktree
cd "$WT"
BASE=$(git rev-parse HEAD)

# --- apply the change directly (editor tool or heredoc) ---
# e.g. small Go change:
#   $EDITOR path/to/file.go
# run the cheapest correct checks, pinning to 1 job under saturation:
gofmt -w path/to/file.go
GOFLAGS=-mod=mod GOMAXPROCS=2 nice -n 10 go build ./... 
GOMAXPROCS=2 nice -n 10 go test ./...   # scope to the affected package if possible

# --- commit in the isolated worktree ---
git add -A
git commit -m "foreman-direct: <brief summary> (worker lane wedged under host load)"
git log --oneline -1
git status --porcelain     # must be empty

If even go build/go test cannot finish because of pressure, stage the change and record it, then verify when the box drains — do not spawn a worker to finish it.

Step 5 — do not buy a third identical dispatch

The failure is deterministic under the same host conditions. Re-dispatching the same brief to the same lane is the documented wrong answer. Recovery is: kill by PID → verify clean worktree → drain or foreman-direct.

Verification

A. The four-signal discriminator was reproduced and tested live

A process blocked forever in a futex (exactly the worker's kernel state) produced:

cmd     : python3 /tmp/wedge_demo.py
sample A: syscr/syscw=56 1 wchan=futex_do_wait state=S children=[]
sample B: syscr/syscw=56 1 wchan=futex_do_wait state=S children=[]
VERDICT: WEDGED (io frozen, futex sleep, no children) -> kill by pid
exit=0

A genuinely progressing process over the same window was correctly classified as not wedged (io advancing, children present, no futex):

cmd     : bash -c while :; do date +%s%N >/dev/null; sleep 0.05; done
sample A: syscr/syscw=3590 53 wchan=do_wait state=S children=[301 ]
sample B: syscr/syscw=7126 105 wchan=do_wait state=S children=[418 ]
VERDICT: not confirmed wedged (io_frozen=0 futex=0 no_children=0)
healthy exit=1

This validates that the script does not false-positive on a busy/slow process and does fire on the futex_do_wait + frozen-io + no-children state.

B. Worktree cleanliness check behaves correctly

git init /tmp/wt-demo; echo base > f.txt; git commit
git status --porcelain        -> (empty)               # clean detection works
echo x >> f.txt; git status --porcelain ->  M f.txt    # dirty detection works

Use the same git -C "$WT" status --porcelain gate after the kill and after the foreman-direct commit (both must be empty).

C. Host-drain gate is observable

On the real box, cat /proc/loadavg 1-min average, free -h swap used, and /proc/pressure/io (some/full avg10) are the drain signals. The sample policy is: only dispatch a fresh worker when 1-min loadavg is trending toward nproc and swap is falling; otherwise foreman-direct.

D. End-to-end post-conditions

  • [ ] pgrep -af 'hermes chat' shows no worker for the wedged session.
  • [ ] git -C "$WT" status --porcelain empty (either untouched, or the foreman-direct commit is in place).
  • [ ] git -C "$WT" log --oneline -1 shows the intended change (if foreman-direct) or the original base (if drained and re-dispatched).
  • [ ] /proc/<pid> for the killed worker is gone (or reaped by the lane; no zombie).
  • [ ] The brief is not re-dispatched unchanged while loadavg/swap/pressure remain pegged.

Prevention

  • Per-lane cargo target: set CARGO_TARGET_DIR=$WORKTREE/target (or a per-lane dir) so no two lanes share a target/; cap link parallelism with CARGO_BUILD_JOBS / RUSTFLAGS.
  • Bound concurrency to the box: keep schedulerd --max-concurrent low enough that link/tool steps cannot saturate all 16 cores (the legacy --max-concurrent 10 unit amplified this; 4 is the safer setting).
  • cgroup limits per lane: put worker scopes under a CPU/memory-limited cgroup so one lane's link cannot drive the whole host to loadavg 10×.
  • Wedge detector in the tick lane: periodically run the four-signal check on live workers; auto-kill a worker that is io-frozen + futex_do_wait + childless across two samples, then surface a host-saturated alert instead of re-dispatching.
  • Never pattern-kill: always signal by PID after re-reading /proc/<pid>/cmdline, because brief paths ride on worker argv.
