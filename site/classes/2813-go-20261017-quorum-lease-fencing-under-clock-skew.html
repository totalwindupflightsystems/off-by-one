Fenced Quorum Leases: Safe Lease Coordination under Delayed Messages, Process Pauses, and Bounded-but-Unknown Clock Skew

Problem class: go-20261017-quorum-lease-fencing-under-clock-skew

TL;DR. Time-based leases cannot be made safe when the clock-skew bound is unknown: no lease duration can be proven longer than the worst pause/skew. The fix is to stop using time for safety. A majority-backed coordinator mints a strictly monotonic fencing token for every grant, and the storage service accepts a write only if its token is at least the largest token it has already accepted. A stale holder can then be paused arbitrarily and its clock can be arbitrarily wrong — its old token is rejected by the storage, so it can never overwrite a newer holder's committed write. Clocks and timeouts are still used, but only for liveness (retrying acquisition), never for correctness.

Verified implementation lives in ~/quorum-lease-fencing/ (fencing.go, coordinator.go, lease_test.go, clock_test.go, cmd/demo/main.go, SOLUTION.md). All tests pass under -race.

1. System and failure model

Roles:

  • Replicas R = {r_1 … r_N}, N = 2f+1. They hold the durable coordination state (the largest promise each has made). quorum = f+1 = floor(N/2)+1.
  • Coordinators. Active client-facing lease coordinator. On failover, another coordinator takes over with no shared in-memory state.
  • Storage (the "partitioned storage service"). The protected resource. It is reachable by holders even when they are partitioned from the coordinator, which is exactly the dangerous case.

Assumptions (crash-stop, partially synchronous, non-Byzantine):

  1. Crash-stop + stable storage. A replica or coordinator may crash, pause, or be partitioned at any time. If a replica has durably recorded a promise, that promise survives the crash/pause. Replicas never lose durable state or lie.
  2. Asynchronous network. Messages may be delayed arbitrarily and reordered. They are not corrupted. During stabilized periods a majority can exchange messages within some finite, unknown time Δ.
  3. Clocks. Physical clocks may be skewed/drifted by an amount that is bounded but unknown. Consequently no timeout derived from clocks can be trusted for safety. Process pauses (GC, VM suspend, SIGSTOP) can exceed any fixed lease duration.
  4. No Byzantine faults. Replicas and storage follow the protocol.

Goal:

  • Safety: a stale holder can never commit a write that overwrites a newer holder's committed write, under any delay/pause/skew allowed above.
  • Availability: after stabilization (a majority reachable and responsive, no contention), a coordinator acquires a lease within O(N · Δ).

2. Root-cause analysis

2.1 Why the obvious design fails

A textbook lease coordinator does this:

grant(holder, D):
    if now < expiry: reject        # lease still believed active
    holder, expiry = holder, now + D

holder may act while local_now < expiry

This makes safety depend on timing. Two things break it:

  • Unknown skew. For the check to be safe you must pick D > 2·max_skew + max_RTT. If the skew bound is unknown, there is no D you can justify. An adversary/reality with a larger skew grants B while A's slow clock still says A holds the lease.
  • Pauses. A GC pause, VM freeze, or SIGSTOP can exceed any fixed D. The holder wakes up and continues as if it still held the lease.

Even if the coordinator uses only its own clock, the holder decides it may act using its own clock, so skew on the holder reintroduces the bug. Coordinator grants A at T0 for D, grants B at T0+D+ε; A's clock is behind by 2ε, so A still believes it is valid and writes concurrently with B. Two writers enter, corruption comes out. (Verified by TestClockSkewBreaksNaiveLeaseButNotFencing.)

2.2 The real invariant that was missing

Mutual exclusion of holders is not the property the storage actually needs, and under unknown skew it is impossible to guarantee without also giving up availability. The property the storage needs is:

Fencing safety: if the storage has accepted a write with token t, then it will never again accept a write with token < t.

If every newer grant carries a larger token, then a stale holder is automatically fenced once the newer holder writes. This decouples correctness from clocks entirely.

3. The fix

Two ideas, both required:

3.1 Mint tokens through a majority (Paxos-style promise)

Each replica keeps one durable value promised. A coordinator runs ballots until a majority promises a token t strictly greater than everything promised before:

  • Prepare(t) succeeds at a replica iff t > promised; it durably sets promised = t.
  • A grant with token t requires OK from a majority.

Because any two majorities intersect, and because promised never decreases:

  • Two different grants can never receive the same token.
  • If grant G2 starts after grant G1 has its majority, then token(G2) > token(G1).

No clock is consulted. Delays and reordering only affect how many ballots are needed, never the monotonicity.

3.2 Enforce the token at the storage

The storage keeps max_token and accepts a write iff token >= max_token, updating max_token. This is the linearization point. A stale writer holding t_old < max_token is rejected even though it is partitioned from the coordinator, paused, or its clock is wrong.

3.3 Recovery

A replacement coordinator starts with hint = 0. Its first ballot loses at exactly the replicas that still carry the previous grant's promise; those replicas report their promised value, the coordinator jumps past it, and the next ballot wins a strictly larger token. No clock-based "wait for the old lease to expire" is needed or used. Hence failover is fast and safe.

3.4 What time is still used for

Timeouts/backoff are used only to decide when to retry Acquire. If a majority is unreachable, Acquire returns ErrNoQuorum. That is a liveness failure and can never expose a stale writer.

4. Safety argument

Lemmas.

  • L1 (replica monotonicity). For every replica r, r.promised is non-decreasing, and once r.promised = p, r.Prepare(t) returns OK only if t > p. Immediate from the code (promised is only assigned when t > promised).
  • L2 (majority intersection). Any two majority sets of N = 2f+1 replicas intersect. Standard pigeonhole: |M1| + |M2| >= 2(f+1) = N+1 > N.
  • L3 (grant order). If grant G1 with token t1 has completed (majority M1 promised t1), any later successful grant G2 with token t2 satisfies t2 > t1. Let M2 be G2's majority. Pick r ∈ M1 ∩ M2. When G2's ballot reached r, r.promised >= t1 (L1); for r to answer OK, t2 > r.promised >= t1. If G2's ballot was concurrent with G1's, then M1 ∩ M2 promised one of the two first; whichever is later in token order is the one whose promise reached the intersection first, so completed grants remain totally ordered by token.

Theorem (stale-write exclusion). Consider a failover: holder S was granted t_S, then holder F was granted t_F in a grant that completed after S's grant. By L3, t_F > t_S.

  • If F writes before S's post-pause write, the storage's max_token >= t_F > t_S, so S's write is rejected.
  • If S writes before F, then S's write is ordered before F's; when F writes, t_F >= max_token so it is accepted and supersedes S.

In both cases S can never overwrite F's committed value. The argument holds even though S may be paused arbitrarily long, S's write may be delayed arbitrarily, and S's clock may be arbitrarily wrong, because neither the coordinator nor the storage consults a clock. ∎

Corollary (linearizable resource). All writes accepted by the storage form a non-decreasing token sequence. Any observer that reads the stored token gets the largest granted token that has committed so far, so the resource is linearizable with respect to the token order (and hence with respect to the grant order).

Remark on mutual exclusion. We deliberately do not promise that two holders are never simultaneously past Acquire. Under unknown skew that promise is unprovable without sacrificing availability. Fencing is the safety mechanism; the lease is an efficiency/liveness optimization. If a workload needs true mutual exclusion for non-idempotent side effects, make those side effects idempotent or fence them too.

5. Availability bound after stabilization

After stabilization assume a majority answers within Δ and no new grants occur by other coordinators. Let P be the largest promise held by any replica.

  • Each failed ballot strictly increases the coordinator's next proposal number (it sets hint to the largest rejected promise and then proposes hint+1).
  • Every rejection reports a promised value drawn from the at most N replicas' durable values, and it is strictly larger than the current proposal.
  • Therefore at most N ballots can fail before the proposal exceeds P; one more ballot succeeds.

Bound: O(N) ballots, i.e. O(N·Δ) wall-clock once the network stabilizes. With N = 5 this is at most a handful of round trips; the tests show a fresh coordinator recovering in one or two ballots in the uncontended case. If a majority is down, Acquire returns ErrNoQuorum (safety is preserved by refusing to mint). This is the standard CAP trade-off: the coordinator is CP; fencing guarantees the storage is never corrupted regardless.

fencing.go

package quorumlease

import (
    "errors"
    "fmt"
    "sync"
)

var ErrStaleToken = errors.New("stale fencing token")

type Token uint64

type Storage struct {
    mu       sync.Mutex
    maxToken Token
    value    []byte
    accepted []AcceptedWrite
}

type AcceptedWrite struct {
    Token Token
    Value []byte
}

func NewStorage() *Storage { return &Storage{} }

// Write commits value iff token is not older than the highest token seen.
func (s *Storage) Write(token Token, value []byte) error {
    s.mu.Lock()
    defer s.mu.Unlock()

    if token < s.maxToken {
        return fmt.Errorf("%w: presented %d, highest accepted %d", ErrStaleToken, token, s.maxToken)
    }
    s.maxToken = token
    s.value = append(s.value[:0], value...)
    s.accepted = append(s.accepted, AcceptedWrite{Token: token, Value: append([]byte(nil), value...)})
    return nil
}

func (s *Storage) Read() (Token, []byte) {
    s.mu.Lock()
    defer s.mu.Unlock()
    return s.maxToken, append([]byte(nil), s.value...)
}

func (s *Storage) AcceptedTokens() []Token {
    s.mu.Lock()
    defer s.mu.Unlock()
    out := make([]Token, len(s.accepted))
    for i, w := range s.accepted {
        out[i] = w.Token
    }
    return out
}

func (s *Storage) Accepted() []AcceptedWrite {
    s.mu.Lock()
    defer s.mu.Unlock()
    out := make([]AcceptedWrite, len(s.accepted))
    copy(out, s.accepted)
    return out
}

coordinator.go

package quorumlease

import (
    "errors"
    "sync"
)

var ErrNoQuorum = errors.New("no quorum reachable")

type Replica struct {
    id int

    mu        sync.Mutex
    promised  Token
    available bool
}

func NewReplica(id int) *Replica {
    return &Replica{id: id, available: true}
}

type PrepareResp struct {
    Responded bool
    OK        bool
    Promised  Token
}

// Prepare: durable promise step. Promises never decrease.
func (r *Replica) Prepare(t Token) PrepareResp {
    r.mu.Lock()
    defer r.mu.Unlock()

    if !r.available {
        return PrepareResp{Responded: false}
    }
    if t > r.promised {
        r.promised = t
        return PrepareResp{Responded: true, OK: true, Promised: t}
    }
    return PrepareResp{Responded: true, OK: false, Promised: r.promised}
}

func (r *Replica) Close()  { r.mu.Lock(); r.available = false; r.mu.Unlock() }
func (r *Replica) Pause()  { r.mu.Lock(); r.available = false; r.mu.Unlock() }
func (r *Replica) Resume() { r.mu.Lock(); r.available = true; r.mu.Unlock() }

func (r *Replica) Promised() Token {
    r.mu.Lock()
    defer r.mu.Unlock()
    return r.promised
}

type Cluster struct {
    mu       sync.Mutex
    replicas []*Replica
}

func NewCluster(n int) *Cluster {
    c := &Cluster{}
    for i := 0; i < n; i++ {
        c.replicas = append(c.replicas, NewReplica(i))
    }
    return c
}

func (c *Cluster) Size() int              { return len(c.replicas) }
func (c *Cluster) Quorum() int            { return len(c.replicas)/2 + 1 }
func (c *Cluster) Replica(i int) *Replica { return c.replicas[i] }
func (c *Cluster) Replicas() []*Replica   { return c.replicas }

func (c *Cluster) BroadcastPrepare(t Token) []PrepareResp {
    c.mu.Lock()
    reps := append([]*Replica(nil), c.replicas...)
    c.mu.Unlock()

    resps := make([]PrepareResp, len(reps))
    for i, r := range reps {
        resps[i] = r.Prepare(t)
    }
    return resps
}

type Coordinator struct {
    name    string
    cluster *Cluster

    mu          sync.Mutex
    hint        Token
    maxAttempts int
}

type Lease struct {
    Token  Token
    Holder string
}

func NewCoordinator(name string, cluster *Cluster) *Coordinator {
    return &Coordinator{name: name, cluster: cluster, maxAttempts: 1_000_000}
}

func (c *Coordinator) SetMaxAttempts(n int) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.maxAttempts = n
}

// Acquire: majority-promised, strictly increasing token. No wall clock.
func (c *Coordinator) Acquire() (Lease, error) {
    quorum := c.cluster.Quorum()

    c.mu.Lock()
    budget := c.maxAttempts
    c.mu.Unlock()

    for attempts := 0; attempts < budget; attempts++ {
        c.mu.Lock()
        c.hint++
        t := c.hint
        c.mu.Unlock()

        acks := 0
        var highestRejected Token
        for _, resp := range c.cluster.BroadcastPrepare(t) {
            if !resp.Responded {
                continue
            }
            if resp.OK {
                acks++
            } else if resp.Promised > highestRejected {
                highestRejected = resp.Promised
            }
        }

        if acks >= quorum {
            return Lease{Token: t, Holder: c.name}, nil
        }

        c.mu.Lock()
        if highestRejected > c.hint {
            c.hint = highestRejected
        }
        c.mu.Unlock()
    }
    return Lease{}, ErrNoQuorum
}

In a production coordinator (Raft/etcd/ZooKeeper-style) the token should be the committed log index/epoch of a Grant entry, and the Grant entry must be committed by a majority before its token is returned. The promise register above is the minimal safety core; replacing it with a real replicated log preserves the same argument.

8. Assumptions, caveats, and extensions

  • Stable storage is mandatory. If a replica can forget a promise (disk wiped, Byzantine, or "recover by reinstalling"), majority intersection no longer holds and two grants could share a token. Persist promised with fsync/write-ahead logging before replying OK. In Raft terms, only commit the Grant entry after it is on a majority's durable log.
  • Byzantine faults are out of scope. A lying replica can violate promised monotonicity. Fencing tokens still protect against stale honest holders, but token minting needs BFT consensus (PBFT/HotStuff) under Byzantine assumptions.
  • Equal tokens are accepted by Storage for idempotent retries. This is safe because L3 guarantees two distinct grants never carry the same token. If you prefer strict >, add a per-request idempotency key.
  • This does not provide mutual exclusion of holders. Under unknown skew that is impossible without sacrificing availability; fencing is the safety boundary. Keep critical-section side effects idempotent and fence every side effect with the token (not just the final write).
  • Availability requires eventual synchrony. Acquire needs a reachable, responsive majority. It correctly returns ErrNoQuorum otherwise rather than guessing.
  • Real deployment. Return the token as X-Fencing-Token (or a generation number) on every write; make the resource enforce it with a compare-and-set on (max_token, value). This pattern matches Google Chubby, ZooKeeper zxid, etcd revision, and object-store conditional writes via generation match.

9. One-paragraph summary

The root cause is that the naive design makes safety depend on time, which is unsound when skew is unknown and pauses are unbounded. The fix makes safety a pure function of a durable, majority-minted, strictly monotonic fencing token checked at the resource, and relegates time to liveness only. Majority intersection after a Paxos-style durable promise guarantees later grants get larger tokens, so recovery needs no clock-based wait, and the storage's token check guarantees a paused or skewed stale holder can never commit after a newer holder. The included tests verify stale-write fencing, crash recovery, delayed messages, replica pauses, concurrent uniqueness, no-quorum safety, and the availability bound after stabilization.
