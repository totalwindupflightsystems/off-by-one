Answer

I diagnosed the issue and verified the fix end-to-end against gitreins 0.17.0. The solution is written to /workspace/solution.md; here it is:

Fix: tracked .env.example wrongly fails the gitreins credential-store PATH class

Class: gitreins-credential-store-path-class-flags-tracked-env-example Finding: SENSITIVE PATH (credential-store path class) — REVIEW-GITREINS-027 Verified against: gitreins 0.17.0 Repro command: gitreins judge --ephemeral --title t --criterion c --skip-tier2

Symptom

A repository that passes Tier 2 is nevertheless given an overall FAIL because the whole-workdir Tier 1 secrets scan flags a pre-existing, already-committed .env.example:

Stage tier1: FAIL
    ✗ secrets: secrets: scanners=builtin cross-check only (gitleaks not on PATH)
Overall: FAIL ✗

The file is not in any diff and contains only placeholders. Deleting it is wrong, and the failure is not a real secret.

Root cause

The scanner class is path-based, not content-based:

  • engine/guard_manager.py defines the class as a fixed list: python SENSITIVE_PATH_PATTERNS = (".env", ".env.*", "*.pem", "*.key", ...)
  • is_sensitive_path(path) matches the filename against those patterns and never inspects content.
  • The judge's Tier 1 secrets step runs the built-in scanner over the whole tree via gm._builtin_secrets_scan(staged_only=False) (pipeline _secrets_step_run). In that mode a file is in scope when it is a sensitive path and tracked: python and (staged_only or explicit_scope or fpath in _worktree_tracked_paths(self.workdir)) .env.example matches .env.* and is tracked, so it is flagged regardless of content and even though it is absent from the change set.

Consequences:

  • Tier 1 fails, and that failure overrides a Tier 2 PASS.
  • The .gitleaks.toml allowlist cannot silence it by design — the path class is checked before the allowlist (deliberate GR-GAP-007 defence).
  • The only documented repo-owner knob is guards.sensitive_paths.allow.

Fix (exact)

Add a single literal entry plus a short justification comment under guards: in .gitreins/config.yaml:

guards:
  secrets: true
  lint: true
  tests: true
  test_mode: full
  test_command: pytest -x --tb=short
  allow_skips: true
  # Repo-owner override (REVIEW-GITREINS-027): this tracked .env.example is a
  # committed template with placeholder values only — never real credentials.
  # Suppresses ONLY the credential-store PATH finding; the content scan still
  # runs over the file, and gitreins prints an auditable
  # "sensitive-path override applied: <path>" note, so suppression is never silent.
  sensitive_paths:
    allow:
      - .env.example

The entry must be exactly the literal .env.example. Do not use .env, .env.*, *.pem, *.key, id_rsa*, or any broad glob.

Scripted, idempotent edit:

python3 - <<'PY'
p = ".gitreins/config.yaml"
s = open(p).read()
if "sensitive_paths:" not in s:
    anchor = "  allow_skips: true\n"
    addition = (
        "  # Repo-owner override (REVIEW-GITREINS-027): this tracked .env.example is a\n"
        "  # committed template with placeholder values only — never real credentials.\n"
        "  # Suppresses ONLY the credential-store PATH finding; the content scan still\n"
        "  # runs over the file, and gitreins prints an auditable\n"
        "  # \"sensitive-path override applied: <path>\" note, so suppression is never silent.\n"
        "  sensitive_paths:\n"
        "    allow:\n"
        "      - .env.example\n"
    )
    assert anchor in s, "guards: allow_skips anchor not found"
    open(p, "w").write(s.replace(anchor, anchor + addition, 1))
PY

Run gitreins init first if .gitreins/config.yaml doesn't exist yet; a later init preserves the key (it only reindents it).

Verification

1. Reproduce the FAIL (before the fix)

git init -q repro && cd repro
git config user.email t@t.t && git config user.name t
printf 'API_KEY=\nDB_URL=\n' > .env.example
git add .env.example && git commit -qm "add env example"
gitreins init >/dev/null 2>&1

gitreins judge --ephemeral --title t --criterion c --skip-tier2; echo "EXIT=$?"

Observed: Overall: FAIL ✗, EXIT=1, with the raw finding:

.env.example: SENSITIVE PATH (credential-store path class) — staging this file is
blocked regardless of content. Remedy: .gitignore it, use a secret manager, or pass
an explicit override flag with a recorded reason.

2. Apply the fix and re-run

Observed:

Stage tier1: PASS
    ✓ secrets: secrets: scanners=builtin cross-check only (gitleaks not on PATH)
Overall: PASS ✓
EXIT=0

3. Suppression is not silent

The Tier 1 secrets step output (pipeline result / guard log) contains:

secrets: builtin cross-check: Scanned 3 files — clean (excluded harness state: .gitreins/**)
sensitive-path override applied: .env.example
secrets: builtin cross-check status: clean

4. Content scan still runs over the file

With a realistic token temporarily in .env.example while the override is active:

Potential secrets found:
.env.example:3: [GitHub personal access token] TOKEN=ghp_***
...
Overall: FAIL ✗

So the override suppresses only the PATH finding.

5. The override is narrow

path overridden
.env.example yes
config/.env.example yes
.env no
.env.production no
.env.local no
server.pem no
creds.key no
id_rsa no
.env.example.bak no

What not to do

  • Do not delete or untrack the legitimate .env.example template.
  • Do not add .env, .env.*, *.pem, *.key, or other broad globs to guards.sensitive_paths.allow.
  • Do not try to hide the finding via .gitleaks.toml; the path class is deliberately checked before that allowlist and will still fire.

Changed files

  • .gitreins/config.yaml — add guards.sensitive_paths.allow: [".env.example"] with the explanatory comment.
