Summary

Root cause: The board tracks intent (status: pending) while git tracks state (HEAD already contains the change). They drift, so the scheduler re-dispatches already-done work. A second, subtler bug is closing the row with the board-closeout commit SHA instead of the code commit SHA, which invalidates commit_hash as proof.

Fix (decision rule, all three must pass): 1. Static presence — git show HEAD:<file> | grep -Ec '<pattern>' >= 1 2. Behavioral proof — go test ./... -run '<TestRegex>' = PASS 3. Contract — error code + message literals present at HEAD

Then:

SHA=$(git rev-parse HEAD)          # capture BEFORE the board commit
boardctl update DF-101 --status complete --commit-hash "$SHA" \
  --guard PASS --ci GREEN --worker-status verified \
  --completed-at "$(date -u +%Y-%m-%dT%H:%M:%SZ)" --summary "Verification-only: ..."
git add .coding-hermes && git commit -m "board: close DF-101 as verification-only ($SHA)" && git push

No task_dispatched event, no worker_status=dispatched.

Verified end-to-end (go1.26.8, git 2.53.0, boardctl dev), including: - pattern count 2 at HEAD, handler test PASS - row → status=complete, worker_status=verified, guard=PASS, ci=GREEN, commit_hash=<code sha> - board commit pushed to a bare origin; parity row_sha == code_sha and board_head == origin - boardctl validate → RESULT: OK - grep -c task_dispatched events.jsonl → 0 - negative gate: missing pattern → refuses closeout, row stays pending - the reusable script was re-run on a second row (DF-102) → PARITY OK

The doc includes the copy-paste tools/verification-only-closeout.sh, the individual command steps, captured outputs, and gotchas (show has no --json; grep -c exits 1 on zero; re-running update --status complete appends a duplicate event; commit board bookkeeping separately).
