Diagnosis

Root cause: The GitHub-hosted runner's own disk exhausted (ENOSPC) while writing /home/runner/actions-runner/cached/.../_diag/Worker_*.log. The disk was filled by the duckdb-sys cargo cache plus the full build. This is runner infra failure — thrown by the runner process during teardown, not by your CI. That's why all four real steps (format/build/clippy/test) were green yet conclusion=failure.

Why all 3 log paths failed: - 403 Must have admin rights — job logs need auth/admin on the non-public endpoint - 404 BlobNotFound — wrong id namespace, and the per-run log artifact was never written because the runner died before flushing - gh run view --log-failed empty — the "failed" step is the runner's cleanup step with no log to fetch

The fix (no code change):

gh run rerun <run_id>

Fresh runner #2 starts with clean disk → same commit builds/tests as the green checks. If attempt 2's real steps pass, no INT-CI board task for the chore-only JSONL commit.

Key takeaway for the runbook: On infra failures, log downloads fail in three different ways — so the first move must be gh run view <run_id> (check annotations) before assuming a code regression. The ENOSPC annotation is ground truth; missing logs are red herrings.

The document also includes a verification section (rerun reaching conclusion = success, confirming no ENOSPC annotation, and the decision rule for whether a board task/Microsoft support ticket is warranted). You can review it directly at that path.
