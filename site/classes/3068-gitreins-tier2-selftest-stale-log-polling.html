Fixing gitreins-tier2-selftest-stale-log-polling

Repo: <organization>/gitreins · Base commit: 55168c4be616af2913db38c2c3111106265d6bd5 (main) Patch: owned-handles.patch (sha256 1e9e82ca…645), also written to /workspace/owned-handles.patch Verdict on the product: none — this is an evaluator-infrastructure defect, so the board row stays open and the caps stay unchanged.

TL;DR

Tier 2's only command primitive (run_command) is synchronous and bounded. When a repo selftest (the CF‑022 full selftest / inference restart‑revocation test) outran that bound, the judge agent backgrounded it and sleep‑polled a fixed /tmp/st4.log. A fixed log path is the previous run's bytes, and a producer started with &/nohup/setsid is not owned by the judge, so the poll can never observe the real exit. The agent retries the same poll until the 15/60 caps fire; ps/pgrep finds no live selftest/inference-contract process; no merit verdict is produced. Raising the caps only lengthens a guaranteed timeout, so the fix is to require an owned process exit handle (waitpid) instead of polling a file — and to make the stale‑log idiom unrepresentable.

Root-cause analysis

  1. No owned handle for a long job. engine/evaluator.py::_tool_run_command delegates to engine/command_hygiene.run_bounded, which spawns with a short command_timeout, waits for the child, then reaps the process group. There is deliberately no way to say "start this and give me a liveness/exit handle", so the LLM invented nohup <suite> & ; sleep 29; wc -l /tmp/st4.log.
  2. The producer is detached from the judge. &/nohup/setsid moves the suite out of the group run_bounded owns. The judge can no longer reap it or learn its exit. The log tail is the only thing left, and it is stale.
  3. Stale log + no process ⇒ undecidable wait. A fixed /tmp/st4.log survives across runs. When the current producer is already dead (or was never started by this run), the bytes never change, so wc -l/tail can never signal completion. pgrep -f "<suite>" is not a fix — the poll's own shell argv contains the pattern, so pgrep -f self‑matches (gitreins-tier2-judge-poll-loop-suite-iterations, DAGGER‑0927). The "process census finds no selftest process" observation is exactly this.
  4. The caps are a symptom, not the bug. 15→60 (or any rung) just moves the cliff: the loop cannot succeed by construction. So the correct action is to preserve the caps, stop escalating, and leave the row open until the code fix lands.
  5. A second, subtle trap. Even with a pipe, a Python Popen.communicate() waits for EOF on the pipe, and a backgrounded child inherits the pipe. So a "fix" that keeps stdout=PIPE would hang on a live grandchild even after the owned child exited. The owned handle must be Popen.wait() (waitpid), with output written to a private temp file.

Exact fix

Three layers: an owned-handle API + stale-poll guard in command_hygiene, evaluator wiring + prompt guidance, and regression tests. The stale-poll guard is what makes the requirement enforceable: run_command(cmd="sleep…; …/tmp/*.log") is refused with a message naming background=true/wait_command.

+def wait_owned(
+    handle: str, *, timeout: float | None = None, max_output: int = MAX_EVIDENCE_CHARS
+) -> dict[str, Any]:
+    """Block on an owned handle's exit (the authoritative completion signal).
+

+    proc, out = entry

+    except subprocess.TimeoutExpired:

Operational handling for the currently stuck row (caps preserved)

Do not raise 15/60, do not re-dispatch a worker, and keep the board row open. Triage read-only:

# Is the judge merely waiting, or actually working?

ps -o pid,etime,time,stat,args --ppid "$JUDGE"                # current child step
awk '{print "io_rchar=" $1, "io_wchar=" $2}' /proc/$JUDGE/io  # frozen => waiting
ls -l --time-style=full-iso /tmp/st4.log                      # stale mtime?
pgrep -af 'inference-contract|selftest' || echo 'NO PRODUCER ALIVE'

If the same sleep … /tmp/st4.log step repeats while the artifact mtime is frozen and no producer exists, it is this defect. On a fixed build the judge owns the handle, so the run reaches wait_command and returns a real exit_code; re-judge at the same task + same commit once the patch is deployed. The product merits its verdict only after that re-judge — until then the row stays open.
