Done. The complete, verified solution is at ~/quorumrecon/SOLUTION.md, backed by a working Go module that passes gofmt, go vet, the race detector, and a 1,000,000-seed deterministic simulator.

What was diagnosed

The bug class is tally-based commit reconciliation: a leader treats AppendResults as votes and advances commitIndex from the max MatchIndex, with no binding to the state under which the append was issued. Six compounding defects:

  1. Term-blind commit → resurrects an entry overwritten by a later term (the named hazard).
  2. Config-epoch-blind commit → a superseded C_old or pre-joint quorum can commit during joint consensus.
  3. Index-only matching → an ack for a truncated (index, term) is misread as progress.
  4. Duplicate inflation → retransmitted replies from one follower can form a quorum.
  5. Order dependence → result depends on RPC arrival order.
  6. Membership blindness → non-members count toward quorum.

The fix

recon.Leader.Reconcile screens every reply on four bindings — term, configID, membership, log identity (Log[i].Term == MatchTerm) — and advances a per-node monotone frontier (map[NodeID]uint64, max), never a count. Commitment then requires the largest entry that is (a) current-term and (b) a genuine quorum of the current config (majority of both sides when joint). TruncateFrom records discarded (index, term) pairs as explicit quarantine.

Verification highlights

  • 20,000 seeds: fixed commitIndex == ground-truth oracle exactly; every committed entry carries the leader's current term.
  • 1,000,000 seeds: fixed reconciler never exceeds the oracle.
  • Naive divergence found at seed 3 (oracle=0 safe=0 naive=1) — commits index 1 with only 2/6 true replication; reproducible via go run ./cmd/sim -dump 3.
  • Dedicated TestDiscardedEntryNotResurrected: a genuine superseded term-4 quorum certificate cannot make the discarded term-4 content durable, while the naive reconciler commits it.
