Deliverables

/home/kara/SOLUTION.md (main deliverable, 361 lines) — title, root-cause analysis, exact fix, verification:

  • Root cause: npx next dev ran 18 days → the dev bundler's in-memory React Client Manifest desynced from the module graph. SSR still emitted HTTP 200 + HTML, but the flight payload referenced client module IDs absent from the manifest → hydration could never mount the login form → blank white shell, while next dev kept serving degraded 200s forever (no crash, so restart:-only policies never fire). Chunk probes pass because chunk files are intact; the broken artifact is the in-memory mapping to them — hence the probe blind spot.
  • Fix (3 layers):
  • Operational: docker compose restart web (regenerates the manifest from current files — verified live: form rendered, student login → hydrated dashboard, manifest error ceased).
  • Durable: a fix/docker-compose.healthcheck.yml overlay (zero edits to the base file) with a Node fetch probe that greps SSR HTML for id="email"/id="password" (fails on blank shell), restart: unless-stopped, and an autoheal sidecar — with the key subtlety documented: compose restart policies only react to container exit, not health, so the healthcheck must be glued to a restart mechanism. A no-Docker-socket watchdog alternative (watchdog.mjs as PID 1) is included.
  • Regression: fix/tests/e2e/login.spec.ts asserting toBeVisible() on email/password/submit plus a fill()/toBeEnabled() hydration proof (guards the subtler "SSR renders but hydration dead" variant).
  • Verification: recorded live outcome from the incident + repeatable commands: positive/negative healthcheck probes, full unhealthy→autoheal-restart loop, kill/restart-policy test, and the one-liner that would have caught the outage.

Fix package (/home/kara/fix/): compose overlay, healthcheck.mjs, playwright.config.ts, login.spec.ts — all validated (node --check on all JS, YAML parsed clean).

The doc ends with a long-term recommendation: stop running next dev in production (next build + next start/standalone) — dev-mode HMR/manifest rewriting is the root enabler of this failure class, and content-aware checks are kept regardless.
