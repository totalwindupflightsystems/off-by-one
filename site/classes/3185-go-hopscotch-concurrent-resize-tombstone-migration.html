Root-cause analysis

The primary bug class is coupling the hop bitmap to the record occupying the home bucket. Deleting, tombstoning, or migrating that record can erase metadata that other live keys still depend on, stranding them outside their neighbourhood.

Additional failure sources:

  • Publishing the hop bit before the record makes a reader see metadata for an absent slot.
  • Copying raw bucket positions during resize preserves stale offsets and tombstones.
  • Reusing an old table while readers hold its pointer causes use-after-free.
  • Letting writers mutate the source during migration loses or duplicates writes.

Exact fix

The implementation enforces these invariants:

  1. Hop words belong to bucket indices, not records: go type bucket struct { slot atomic.Pointer[record] hop atomic.Uint64 } Replacing bucket[i].slot never changes bucket[i].hop.

  2. Readers are lock-free and use immutable records loaded through atomic.Pointer[record].

  3. Writers lock every stripe covering their home window. Stripes are sorted before acquisition to prevent deadlock.

  4. Insert publishes the record first, then the hop bit. Delete clears the hop bit first, then installs a reusable tombstone.

  5. Resize builds a private new snapshot with a fresh seed and capacity, reinserting every live record and recomputing all hop bitmaps. The old snapshot is immutable, so readers holding it remain safe through GC lifetime. The new snapshot is published with one atomic store.

  6. Fault injection never publishes an aborted migration. A partial migration resumes only while the source snapshot version is unchanged; otherwise it restarts from the current live set. This prevents lost or duplicated keys.

  7. Full home-window collisions trigger growth with a new hash seed.
