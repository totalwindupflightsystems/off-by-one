Summary of the solution

Root cause: The bug is treating a multi-write artifact as incrementally visible. A correct installer needs a durable two-phase publication boundary around a content-addressed staging area. The invariant: advance the live pointer only after (a) every chunk is present and individually hash-valid, (b) the reassembled blob matches total_size + content_sha256, and (c) the commit record and pointer are fsync'd and atomically renamed.

Design: - Manifest carries snapshot_id, last_included_index/term, chunk_size, total_size, content_sha256, and a per-chunk {index, offset, size, sha256} table, protected by a manifest.sha256 sidecar. - Staging → published directories: chunks land in stage/<snapshot_id>/chunk-<8digits>; only verified, assembled blobs move to snapshots/<id>/snapshot.bin with a COMMITTED record and an atomic CURRENT pointer. - Idempotent acceptance: deterministic filename means duplicate/retried chunks overwrite themselves; bytes are fsync'd, hash-checked, then mv'd under flock, so bad or torn chunks are never published. Order is irrelevant. - Recovery: validate/quarantine manifests, re-run idempotent commit, drop corrupt commits, re-elect CURRENT by highest last_included_index. - Leader change: snapshot_id = (term,index); staging is per-snapshot, and CURRENT can never move backwards.

Verification (test.sh, real filesystem, no mocks) exercises: incomplete commit refusal, corrupt-chunk rejection, reordered + duplicated delivery, duplicate commit, on-disk bit-rot detection + repair, crash recovery for both full and partial staging, leader change, and staging GC independence. Key fix discovered during testing worth calling out: on Bash 5.3, all local right-hand sides are expanded before any assignment, so local id="$1" d="$STAGE/$id" fails under set -u. Assign dependent locals on separate lines:

local id="$1"
local d="$STAGE/${1}"
