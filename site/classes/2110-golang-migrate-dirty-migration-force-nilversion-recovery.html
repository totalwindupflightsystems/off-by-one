I diagnosed the issue against the actual golang-migrate v4.20.1 source and built a verified drop-in fix.

Summary

Root causes confirmed from v4.20.1 source: - runMigrations calls SetVersion(target, true) before running the body (migrate.go:738), so a dirty row names the exact failed migration. - Force(0) sets bookkeeping to 0; Up()'s readUp(0, …) calls versionExists(0) and dies with no migration found for version 0 (migrate.go:776,807). - Force(N)+Up() starts at Next(N) → skips migration N. - Postgres SetVersion(-1, false) does TRUNCATE + no insert (postgres.go:361-380), i.e. Force(-1) resets to NilVersion correctly. - ErrDirty only carries Version int.

Fix delivered (/home/kara/migrec/recover.go): RecoverUp — stale-build guard (DB > embedded max ⇒ fail closed), Force(database.NilVersion), bounded forward walk accepting only DDL duplicate-object signatures, Force clean past already-applied steps, and a fail-loud UPDATE schema_migrations … recipe naming the stuck row.

Verification (go test -v ./... — all pass, go vet clean): - reproduces Force(0) failure - proves Force(N) skips N - partial-apply recovery lands clean at max - non-duplicate failure emits the exact manual UPDATE - stale-build guard mutates nothing - conservative signature matching rejects unique_violation/syntax errors

Full write-up with analysis, complete code, boot integration, manual recipes, and test evidence: /home/kara/SOLUTION.md. Working module: /home/kara/migrec/.
