Fixing the Go test timeout hang: recursive sync.RWMutex.RLock deadlock in HealthMonitor.GetMetrics

Problem class: go-test-timeout-hang Source: helios INT-CI-2, run 41453480374, fix commit 27e63979f698a1303abc236a7ce9bc84f1616526 Symptom: TestHealthMonitorMetrics sleeps 150 ms but ran 9m53s and tripped the suite budget with panic: test timed out after 10m0s. Intermittent: the same tree passed CI 90 minutes earlier.

1. Root cause

HealthMonitor.GetMetrics() held the read lock and then called GetStaleAgents(), which took the same read lock again:

// BUG
func (m *HealthMonitor) GetMetrics() Metrics {
    m.mu.RLock()
    defer m.mu.RUnlock()

    stale := m.GetStaleAgents() // <-- calls m.mu.RLock() a SECOND time
    total := len(m.agents)
    return Metrics{TotalAgents: total, StaleAgents: len(stale), HealthyAgents: total - len(stale)}
}

func (m *HealthMonitor) GetStaleAgents() []string {
    m.mu.RLock()
    defer m.mu.RUnlock()
    return m.staleAgentsLocked(time.Now())
}

Go's sync.RWMutex read locks are not reentrant. Taking RLock twice in one goroutine is not "sharing" the read lock — it increments readerCount twice and needs two RUnlocks. More importantly, Go's RWMutex is writer-preferring: once a writer is blocked in Lock(), every subsequent RLock() blocks until that writer is done.

That yields a two-goroutine deadlock:

reader goroutine                              writer goroutine (monitor loop / Stop)
----------------                              --------------------------------------
RLock()              readerCount = 1
                                              Lock()  -> blocks, sets writer-pending
                                                       (readerCount goes negative)
GetStaleAgents()
  RLock()            writer pending -> BLOCKS
                                              waiting for readerCount == 0
        ^                         v
        +------- both wait forever --------+
  • The reader waits for the pending writer to finish.
  • The writer waits for the reader to release the outer read lock.
  • Neither can proceed. Classic writer-starvation deadlock.

Why it is intermittent

The deadlock needs a writer to arrive in the tiny window between the outer RLock and the nested RLock. Under low host load the two read locks are taken back-to-back and the window is missed, so the test passes. Under CI load (scheduling jitter, the monitor ticker, GC, other packages) the interleaving is hit, the test hangs, and the 10-minute suite budget is consumed.

Why Stop() also hangs

TestHealthMonitorMetrics (and any caller) uses defer monitor.Stop(). Stop() takes the write lock, so it is another writer that queues behind the wedged reader. The deferred cleanup hangs too, which is why the failure surfaces as a suite-wide panic: test timed out rather than a normal test failure. This exact second symptom was reproduced locally (see §4).

Diagnostic tells (generalizable)

Tell Meaning
Test body is trivially short but runtime is minutes blocking, not slow work
Hang point is inside a helper called under an already-held RLock recursive read lock
Flaky / host-load dependent scheduling window, not logic
Deferred Stop()/Close() also hangs writer queued behind the wedged reader

2. The exact fix

Compute everything under the single outer RLock; remove the nested locking call. Use the lock-free inner helper (or an inline loop).

 func (m *HealthMonitor) GetMetrics() Metrics {
     m.mu.RLock()
     defer m.mu.RUnlock()

-    stale := m.GetStaleAgents() // nested RLock -> deadlock
+    now := time.Now()
     total := len(m.agents)
+    stale := len(m.staleAgentsLocked(now))

     return Metrics{
         TotalAgents:   total,
-        StaleAgents:   len(stale),
-        HealthyAgents: total - len(stale),
+        StaleAgents:   stale,
+        HealthyAgents: total - stale,
     }
 }

Equivalent pure-inline form, if you prefer not to keep the helper:

func (m *HealthMonitor) GetMetrics() Metrics {
    m.mu.RLock()
    defer m.mu.RUnlock()

    now := time.Now()
    total := len(m.agents)
    stale := 0
    for _, seen := range m.agents {
        if now.Sub(seen) > m.staleTTL {
            stale++
        }
    }
    return Metrics{
        TotalAgents:   total,
        StaleAgents:   stale,
        HealthyAgents: total - stale,
    }
}

The lock-free helper used by the fix (caller must already hold m.mu, read or write):

func (m *HealthMonitor) staleAgentsLocked(now time.Time) []string {
    var stale []string
    for id, seen := range m.agents {
        if now.Sub(seen) > m.staleTTL {
            stale = append(stale, id)
        }
    }
    return stale
}

Rule to prevent recurrence

A method that takes m.mu.RLock() must only call unexported *Locked helpers that assume the lock is already held. It must never call an exported method that acquires m.mu itself.

Apply the same rule to every RLock-holding method (metrics, snapshots, health summaries), and audit for any other RLock→exported-method chains. Add a package comment documenting the invariant next to the mu field.

3. Bounded regression test (watchdog)

The test below runs 20 000 GetMetrics() calls against a goroutine continuously taking the write lock, with a 15-second select/time.After watchdog. A future reintroduction of the deadlock fails in seconds instead of eating the suite budget.

package monitor

import (
    "fmt"
    "sync"
    "testing"
    "time"
)

func TestGetMetricsNoHang(t *testing.T) {
    m := NewHealthMonitor(30 * time.Second)

    now := time.Now()
    for i := 0; i < 100; i++ {
        m.Register(fmt.Sprintf("agent-%03d", i), now)
    }
    // Make half the fleet stale so the stale-counting path is exercised.
    for i := 0; i < 100; i++ {
        m.Register(fmt.Sprintf("stale-%03d", i), now.Add(-time.Hour))
    }

    // Writer contention: keep the write lock churning.
    stop := make(chan struct{})
    var wg sync.WaitGroup
    wg.Add(1)
    go func() {
        defer wg.Done()
        for {
            select {
            case <-stop:
                return
            default:
            }
            m.mu.Lock()
            m.mu.Unlock()
        }
    }()

    done := make(chan struct{})
    go func() {
        defer close(done)
        for i := 0; i < 20000; i++ {
            got := m.GetMetrics()
            if got.TotalAgents != 200 || got.StaleAgents != 100 || got.HealthyAgents != 100 {
                t.Errorf("unexpected metrics: %+v", got)
                return
            }
        }
    }()

    select {
    case <-done:
    case <-time.After(15 * time.Second):
        close(stop)
        // Deliberately do NOT call m.Stop() here: if the monitor is wedged,
        // Stop() takes the write lock and blocks forever too, which would
        // defeat the watchdog and let the suite run to its 10m timeout.
        // Returning from the test is enough; leaked goroutines do not block
        // process teardown.
        t.Fatal("GetMetrics hung for 15s: recursive sync.RWMutex.RLock deadlock")
    }

    close(stop)
    wg.Wait()
    m.Stop()
}

Design notes

  • Writer preference is what makes it deterministic. A spinning m.mu.Lock() goroutine guarantees a pending writer; once it queues, the next nested RLock blocks, so the bug reproduces on every run rather than flaking.
  • Do not defer m.Stop() on the failure path. If the monitor is deadlocked, Stop() is another writer and hangs, masking the watchdog. Return immediately on timeout.
  • 15 s watchdog. Generous enough to avoid false positives on a loaded CI box, small enough that a regression fails in seconds.

5. Summary
Root cause GetMetrics held m.mu.RLock and called GetStaleAgents, which re-acquired m.mu.RLock. Go read locks are non-reentrant and writer-preferring, so a writer arriving between the two locks deadlocks reader and writer (and any deferred Stop()).
Fix Compute the stale count under the single outer RLock via the lock-free staleAgentsLocked helper; remove the nested RLock call.
Prevention RLock-holding methods may only call *Locked helpers; never call exported lock-acquiring methods.
Regression guard 20 000 GetMetrics calls under writer contention + 15 s time.After watchdog; do not call Stop() on the timeout path.
Verified go test -race green on the fixed code; watchdog fails the buggy code in 15 s with the exact two-goroutine deadlock.
