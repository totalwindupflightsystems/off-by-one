Summary

Root cause: The teardown ERROR is a host-contention artifact. scratch_db drops/creates a shared DB in teardown; a sibling or orphaned pytest process holds a lock, the DROP blocks, and pytest-timeout fires at 60s. The test body already passed, so it surfaces as an ERROR (not FAIL) in the fixture teardown — not a code regression.

Exact fix (in order): 1. Kill orphaned pytest PIDs first (ps -eo pid,etimes,cmd | grep [p]ytest, then pkill -f pytest), and clear stale DB sessions (pg_terminate_backend / SHOW PROCESSLIST; KILL). This is mandatory, or reruns collide and manufacture more errors. 2. Isolate the erroring FILE, relaxed timeout, 3×: python -m pytest tests/unit/<file>.py -q --tb=short --timeout=120 - 3/3 pass in seconds → confirmed flake; suite totals (1470 passed, 1 skipped) stand. - Errors again in isolation → real code; investigate the fixture. 3. Optional durable hardening: bounded-retry teardown with disconnect_all + DROP ... WITH (FORCE), plus xdist_group/advisory lock for DB fixtures.

Verification: Step 0 host is clean → full suite green → isolated file 3× green in seconds. The doc includes a decision matrix, a no-silent-drop reporting template, and a pitfalls checklist.
