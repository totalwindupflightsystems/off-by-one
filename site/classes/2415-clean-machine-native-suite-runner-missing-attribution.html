Answer 1

I diagnosed the incident and wrote the complete, self-contained solution to ~/QA-BUNKER-26-solution.md.

What it is

Root cause: In ~/.hermes/scripts/bunker-qa.sh the detection ladder and the venv+pytest provisioning bootstrap are two independent "is this a Python repo?" conditions. QA-BUNKER-24 extended detection to pytest.ini/conftest.py, but the bootstrap still armed only under pyproject.toml. A pytest.ini-only repo is therefore selected for python3 -m pytest but never gets a runner — on a fresh JIT agent (stdlib-only python3, venv bin not on PATH) every suite leg dies No module named pytest. Harness row QA-BUNKER-26; not a product row.

Exact fix (generated-remote bootstrap guard):

-# python venv + pytest bootstrap (arms only for pyproject.toml repos)
-if [ -f pyproject.toml ]; then
+# QA-BUNKER-26: arm for every shape the detection ladder selects.
+if [ -f pyproject.toml ] || [ -f pytest.ini ] || [ -f conftest.py ] || [ -f tests/conftest.py ]; then

with the existing fresh-creation + best-effort top-up (|| true) body unchanged, plus a recommended shared python_repo_shape() predicate so the two halves can never drift again.

Verification I actually ran (in the markdown, with real output): - Local control: auger py_compile OK, ruff clean, 218 tests collected. - A self-contained fresh-agent repro that builds a real stdlib-only venv: pre-fix rc=1 → UNVERIFIED (No module named pytest), post-fix rc=0 → OK (1 passed). - Classifier battery and generated-bytes regression test, plus the fresh-agent acceptance run.

Grade rule is preserved throughout: runner-missing native legs are UNVERIFIED ("suite NEVER RAN, no repo signal"), never FAIL, never OK.
