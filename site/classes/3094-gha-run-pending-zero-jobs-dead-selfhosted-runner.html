GitHub Actions Run Pending with Zero Jobs: Dead Self-Hosted Runner

Problem class: gha-run-pending-zero-jobs-dead-selfhosted-runner
Applies to: jobs pinned to [self-hosted, <label>], runner installed as actions.runner.*.service, gh CLI available.

Summary

A workflow run stays queued/pending for hours with zero jobs started, while other workflows at the same SHA complete green on GitHub-hosted runners. This is not a spending block and not a code failure. GitHub cannot schedule the job because the only runner matching the workflow’s labels is offline. The runner unit is disabled, and the unit’s ExecStart target is missing. The outage is amplified by job-level concurrency: queued runs stack behind a stuck run, while push supersession cancels older runs. The result is a long window with zero successful conclusions.

The fix is an owner-approved choice:

  1. Restore or provision the matching self-hosted runner, or
  2. Retire the self-hosted legs from the workflow.

In either case, add workflow-level supersede-on-push concurrency so one stuck run cannot hold the verdict channel hostage.

1. Symptoms

Use this runbook when all of the following are true:

  • The run is queued, pending, or requested for hours; no job has started.
  • gh run view <run-id> --json jobs shows queued job objects with no assigned runner and zero executed steps.
  • Other workflows on GitHub-hosted runners pass at the same SHA.
  • The workflow uses runs-on: [self-hosted, <label>].
  • gh api repos/<owner>/<repo>/actions/runners shows the matching runner as offline.
  • Recent run history contains many cancelled runs from push supersession and one or more stuck queued runs, but no success.
  • The runner systemd unit is inactive and disabled.

“Zero jobs” here means zero jobs started/assigned. GitHub may still list queued job definitions for the run. The important distinction is that no runner has been assigned and no steps have run.

2. Root-cause analysis

2.1 Scheduling starvation: no online runner matches the labels

GitHub Actions assigns a job only when an online and idle runner matches all requested labels. For:

runs-on: [self-hosted, kara-main]

the runner must be registered with both self-hosted and kara-main, must be online, and must be idle. If the only matching runner is offline, GitHub leaves the job queued. It does not fail fast. The run waits until:

  • the runner comes back online,
  • the run is cancelled manually,
  • or the run is superseded/cancelled by the channel.

That is why the run shows pending/queued with zero jobs started.

2.2 The runner unit is disarmed, and the installation is missing

The observed unit:

actions.runner.&lt;project&gt;-dev-&lt;project&gt;.kara-main.service

is disabled. A disabled unit is not the same as a crashed unit; systemctl is-enabled returning disabled is a deliberate disarm marker. Do not silently re-enable shared infrastructure. Record the state and ask the owner whether to restore or retire.

On this host, systemd-analyze verify also shows:

Command ~/actions-runner/runsvc.sh is not executable: No such file or directory

So even if someone enabled the unit, it would still fail to start. The runner installation at the path expected by the unit is missing. The restore path must therefore repair or reinstall the runner, not just run systemctl enable.

2.3 Channel hostage: job-level concurrency plus push supersession

Two workflow behaviors turn a dead runner into a prolonged verdict outage:

  • Job-level concurrency groups with cancel-in-progress: false serialize queued runs. New runs stack behind the stuck run or behind each other.
  • Push supersession cancels older runs when a new commit arrives. The older runs show cancelled; the newest run remains queued behind the dead runner. Across many pushes, the history shows many cancellations and zero successes.

The dead runner is the trigger. The job-level concurrency and missing workflow-level supersession are the amplifiers that keep the verdict channel blocked for hours.

2.4 Differential diagnosis

Scenario Runner API evidence Run/job evidence Fix
Spending block Runner status irrelevant Job fails almost immediately; zero executed steps; annotation about failed payments or spending limit Fix billing/spending limit
Plain queue backlog Matching runner is online, busy: true; possibly multiple online runners Jobs are assigned or waiting for capacity; queue eventually drains Add capacity, reduce concurrency, cancel stale runs
Dead/offline self-hosted runner Matching runner is offline, busy: false; unit may be disabled/inactive; last diag activity old Run queued for hours; no runner assigned; zero steps; same SHA green on hosted runners Restore/provision runner or retire self-hosted legs

If the runner is offline, this is not a capacity backlog. Waiting will not schedule the job.

4. Fix

4.0 Decision gate: record first, then ask the owner

A disabled unit is a deliberate disarm marker. Do not silently re-enable shared infrastructure. Record the evidence, then ask the owner:

  • Restore/provision the runner, or
  • Retire the self-hosted legs.

Record the incident state before making changes:

{
  echo "=== $(date -u) ==="
  systemctl list-unit-files 'actions.runner.*.service' 2>&1 || true
  systemctl is-enabled "$RUNNER_UNIT" 2>&1 || true
  systemctl is-active  "$RUNNER_UNIT" 2>&1 || true
  systemd-analyze verify "/etc/systemd/system/$RUNNER_UNIT" 2>&1 || true
  gh api "repos/$OWNER/$REPO/actions/runners?per_page=100" \
    --jq '.runners[] | {id,name,status,busy,labels:[.labels[].name]}' 2>&1 || true
  gh run list -R "$OWNER/$REPO" --workflow "$WF" --limit 100 \
    --json databaseId,status,conclusion,createdAt,headSha \
    --jq '.[] | [.databaseId,.status,(.conclusion//"-"),.createdAt,.headSha[0:8]] | @tsv' 2>&1 || true
} | tee "runner-incident-$(date -u +%Y%m%dT%H%M%SZ).log"

4.1 Path A: restore or provision the runner (owner approved)

Use this path only when the owner confirms restore. If the owner confirms retirement, use Path B.

A1. Repair the existing installation

If the host is reachable but runsvc.sh or the runner directory is missing, reinstall the runner package in place. Preserve .runner and .credentials if present.

RUNNER_DIR="~/actions-runner"
sudo -u kara mkdir -p "$RUNNER_DIR"
cd "$RUNNER_DIR"

# Back up the registration if it exists.
if [ -f .runner ]; then
  sudo -u kara cp -a .runner ".runner.bak.$(date -u +%Y%m%dT%H%M%SZ)"
fi

RUNNER_VERSION=$(gh api repos/actions/runner/releases/latest --jq '.tag_name' | sed 's/^v//')
curl -fL -o actions-runner.tar.gz \
  "https://github.com/actions/runner/releases/download/v${RUNNER_VERSION}/actions-runner-linux-x64-${RUNNER_VERSION}.tar.gz"
tar xzf actions-runner.tar.gz

If .runner is absent or invalid, register the runner:

RUNNER_TOKEN=$(gh api -X POST \
  "repos/$OWNER/$REPO/actions/runners/registration-token" --jq .token)

./config.sh \
  --url "https://github.com/$OWNER/$REPO" \
  --token "$RUNNER_TOKEN" \
  --name "$RUNNER_NAME" \
  --labels "$LABEL" \
  --unattended \
  --replace

For an organization-level runner, use the org URL and org registration token:

RUNNER_TOKEN=$(gh api -X POST \
  "orgs/$OWNER/actions/runners/registration-token" --jq .token)

A2. Enable and start the unit

If the existing unit is correct and now points to an installed runsvc.sh:

sudo systemctl daemon-reload
sudo systemctl enable --now "$RUNNER_UNIT"
sudo systemctl status "$RUNNER_UNIT" --no-pager -l

If the unit does not exist on a replacement host, use the runner’s service installer:

cd "$RUNNER_DIR"
sudo ./svc.sh install kara
sudo ./svc.sh start

Then list the generated unit and use its exact name for verification:

systemctl list-unit-files 'actions.runner.*.service'

A3. Provision a replacement on a new host

If the old host is unreachable or lost:

  1. Provision a new Linux host.
  2. Install the runner package as in A1.
  3. Register with the same runner name and labels, using --replace.
  4. Start the service as in A2.
  5. Remove a stale duplicate offline runner record only after the replacement is online and confirmed:
gh api -X DELETE "repos/$OWNER/$REPO/actions/runners/$OLD_RUNNER_ID"

Do not delete the replacement by mistake. Confirm the ID and name first.

A4. Clear stale queued runs

After the runner is online, old queued runs may represent obsolete commits. Cancel queued runs older than two hours so the channel clears and the newest commit owns the verdict:

gh run list -R "$OWNER/$REPO" --workflow "$WF" --status queued --limit 200 \
  --json databaseId,createdAt \
  --jq '.[] | select((.createdAt | fromdateiso8601) < (now - 7200)) | .databaseId' \
  | while read -r id; do
      echo "cancelling stale queued run $id"
      gh run cancel "$id" -R "$OWNER/$REPO" || true
    done

4.2 Path B: retire the self-hosted legs (owner approved)

Use this path when the self-hosted runner should no longer serve this workflow. If the job genuinely needs self-hosted hardware, provision a replacement and update the label instead of silently switching to hosted.

B1. Change the workflow’s runs-on

Before:

jobs:
  e2e:
    runs-on: [self-hosted, kara-main]

After, for a GitHub-hosted replacement:

jobs:
  e2e:
    runs-on: ubuntu-latest

Or point at a replacement self-hosted label:

runs-on: [self-hosted, replacement-label]

B2. Remove job-level serialization from the verdict job

Remove any job-level concurrency: block from the CI verdict job. If a deploy job needs a mutex, keep it only on that job and pair it with a timeout.

Before:

jobs:
  e2e:
    concurrency:
      group: bunker-e2e
      cancel-in-progress: false

After: delete that block. Use workflow-level concurrency instead, as shown in Path C.

B3. Disable and optionally deregister the runner

After no workflow targets the dead label:

sudo systemctl disable --now "$RUNNER_UNIT"

If the runner is dedicated to this workflow and should be removed from GitHub:

gh api -X DELETE "repos/$OWNER/$REPO/actions/runners/$RUNNER_ID"

If the runner is shared with other workflows, disable it only with owner approval and do not delete the registration until all consumers are migrated.

B4. Cancel queued runs that target the retired label

Queued runs from the old workflow version will never be scheduled. Cancel them:

gh run list -R "$OWNER/$REPO" --workflow "$WF" --status queued --limit 200 \
  --json databaseId,createdAt \
  --jq '.[].databaseId' \
  | while read -r id; do
      echo "cancelling orphaned queued run $id"
      gh run cancel "$id" -R "$OWNER/$REPO" || true
    done

4.3 Path C: bound the verdict channel with supersede-on-push concurrency

Add this at the workflow top level, not under a job:

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

Effect:

  • A new push to the same ref cancels the older run in the same group.
  • The newest commit owns the verdict channel.
  • One stuck run cannot hold the channel for hours while newer commits wait.

Do not use cancel-in-progress: true on production deployment workflows unless supersession is intentional. For deployment workflows, use a separate concurrency group with cancel-in-progress: false and a job timeout. For CI verdict workflows such as bunker-e2e, supersede-on-push is the desired behavior.

Example workflow header:

name: bunker-e2e

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

# Supersede older runs on the same ref. The newest push owns the verdict.
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  e2e:
    # If restoring: keep [self-hosted, kara-main].
    # If retiring: use ubuntu-latest or a replacement label.
    runs-on: [self-hosted, kara-main]
    timeout-minutes: 60
    steps:
      - uses: actions/checkout@v4
      # ...

Important: GitHub’s job timeout-minutes starts when the job is assigned and running. It does not reliably bound time spent waiting in the queue. Queue time must be bounded by workflow-level concurrency plus a stale-run reaper.

4.4 Optional stale-queue watchdog

Run this on a schedule when the matching runner is offline. It cancels queued runs older than two hours.

#!/usr/bin/env bash
set -euo pipefail

OWNER="${OWNER:?}"
REPO="${REPO:?}"
WF="${WF:?}"
RUNNER_NAME="${RUNNER_NAME:?}"
MAX_AGE_SECONDS="${MAX_AGE_SECONDS:-7200}"

OFFLINE_COUNT=$(gh api "repos/$OWNER/$REPO/actions/runners?per_page=100" \
  --jq "[.runners[] | select(.name==\"$RUNNER_NAME\" and .status==\"offline\")] | length")

if [ "$OFFLINE_COUNT" -eq 0 ]; then
  exit 0
fi

gh run list -R "$OWNER/$REPO" --workflow "$WF" --status queued --limit 200 \
  --json databaseId,createdAt \
  --jq ".[] | select((.createdAt | fromdateiso8601) < (now - $MAX_AGE_SECONDS)) | .databaseId" \
  | while read -r id; do
      echo "cancelling stale queued run $id for offline runner $RUNNER_NAME"
      gh run cancel "$id" -R "$OWNER/$REPO" || true
    done

5.5 Verify supersede-on-push concurrency

Use a scratch branch or two back-to-back workflow_dispatch runs on the same ref. Do not push empty commits to production branches without approval.

# Safe proxy for supersede-on-push: two runs on the same ref.
gh workflow run "$WF" -R "$OWNER/$REPO" --ref main
gh workflow run "$WF" -R "$OWNER/$REPO" --ref main
sleep 15

gh run list -R "$OWNER/$REPO" --workflow "$WF" --limit 4 \
  --json databaseId,headSha,status,conclusion,createdAt \
  --jq '.[] | [.databaseId,(.headSha[0:8]),.status,(.conclusion//"-"),.createdAt] | @tsv'

Expected:

  • The older run ends cancelled.
  • The newest run owns the verdict and completes success.
  • No queued run is left holding the channel.

If the workflow only supports push, use a scratch branch that the workflow triggers on:

git switch -c ci/concurrency-check
git commit --allow-empty -m "ci: concurrency check 1"

  --jq '.[] | [.databaseId,(.headSha[0:8]),.status,(.conclusion//"-"),.createdAt] | @tsv'

Expected: first push’s run cancelled, second push’s run success.

5.6 Acceptance checklist

  • [ ] Owner decision recorded: restore/provision vs retire.
  • [ ] If restored: unit enabled and active; runner API shows online, busy: false, correct labels.
  • [ ] If retired: workflow no longer targets the dead label; unit disabled; runner deregistered or explicitly drained.
  • [ ] At least one run on the current SHA completes success with stepCount > 0.
  • [ ] No queued run older than two hours for this workflow.
  • [ ] Workflow-level concurrency uses cancel-in-progress: true.
  • [ ] No job-level concurrency block serializes the verdict job.
  • [ ] Supersede behavior verified: older run cancelled, newest run succeeds.
  • [ ] An alert exists for “runner used by a workflow is offline.”

6. Rollback and operational notes

  • If restoring the runner causes unexpected load or a security concern, disable it again only with owner approval:

bash sudo systemctl disable --now "$RUNNER_UNIT"

  • If workflow-level cancel-in-progress: true cancels a run that must not be superseded, move that workflow to a separate concurrency group with cancel-in-progress: false and a bounded timeout.
  • Do not delete a shared runner registration just because one workflow retired its label. Verify all consumers first.
  • Do not treat “run is no longer queued” as success. Require a success conclusion with executed steps.
  • A disabled unit is a deliberate disarm marker. Record it, ask the owner, and avoid silently re-enabling shared infrastructure.
