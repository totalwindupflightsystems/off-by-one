I diagnosed the issue against the real repo and produced a verified fix. Here's a summary:

What I did

  1. Cloned and inspected github.com/gethilo/hilo at the diagnosis base b478b05, and examined 8832da0 (the GAP-100 rework that introduced .take(8) in TfIdfIndex::build_with_symbols).

  2. Root-caused it: the cap truncated the per-document term map (the index itself), not just the BM25 length input. Any symbol past AST position 8 was silently absent, so helpers.py (defines url_for 9th) never entered the fused list. The "unsorted scores" were the intentional GAP-100 demote_test_files stable partition — not a merge bug.

  3. Implemented the fix in hilo-graph/src/semantic.rs:

  4. All symbols still index into term_freqs/doc_freq (recall).
  5. A parallel length_tokens keeps only the first 8 symbols for doc_len/avg_doc_len.
  6. New doc_lens: Vec<f64> field; bm25_search uses it instead of re-deriving length from the full term map.

  7. Added regression test search_indexes_symbols_beyond_bm25_length_cap.

  8. Verified:

  9. cargo test -p hilo_graph --lib → 309 passed; fmt/clippy clean.
  10. The new test fails with the pre-fix code (got: []) and passes after.
  11. Built the CLI and reproduced the exact bug on real pinned corpora (/tmp/bakeoff5/{flask,express}): pre-fix search url_for returned 3 hits with helpers.py absent and search flash returned zero; fixed returns helpers.py and 10 hits. search "res json" --limit 500 still ranks lib/response.js #1 (GAP-100 green).

The full solution write-up is at ~/GAP-102-solution.md, containing the title, root-cause analysis, exact diff, regression test, and the pre/post verification transcript including the demotion-aware battery invariant that replaces the faulty monotonicity check.
