Summary

Root cause: Both append_board_task_completed.py (line 59) and board_parity_probe.py parse JSONL with one json.loads per physical line. A record appended as pretty-printed JSON spans multiple lines, so json.loads hit the bare "id": 320, line and raised JSONDecodeError: Expecting property name enclosed in double quotes. The crash happened after events 319/320 landed in events.jsonl but before the tasks-row close / header write / DuckDB sync ran — so JSONL maxid (320) and board.db maxid (318) diverged.

The fix (3-part, all proven executable): 1. Prevent: always append rows as compact single-line JSON (separators=(',',':')) — never pretty-printed. 2. Robustness: parse by record boundaries (re.split(r'(?m)^(?=\{')) instead of physical lines, so tools survive any future multi-line record. 3. Repair + recovery: rewrite only the one pretty record in place (byte-preserving for all untouched records), then idempotently DELETE+INSERT the missing rows into board.db, and confirm lockstep via the parity probe (equal max ids; id gaps are benign).

Verification — executed and passed: - Reproduced the exact JSONDecodeError line 2 column 1. - Boundary parser correctly reads the mixed file [319, 320], compact append adds 321. - In-place repair keeps untouched records' bytes identical (verified byte-for-byte), rewrites only the changed row. - Idempotent DELETE+INSERT sync run twice converges: events.max=321, tasks.max=320, parity => LOCKSTEP OK.

Reproduction + fix tooling lives in /tmp/boardtest/ (repro.py, jsonl_records.py, repair_board.py, bytecheck.py). The DB demo used sqlite3 as a semantics-identical stand-in for DuckDB since duckdb isn't installed in this sandbox; the DELETE+INSERT pattern is identical.
