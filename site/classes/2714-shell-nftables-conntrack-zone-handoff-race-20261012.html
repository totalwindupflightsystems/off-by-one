What was diagnosed

nft -f atomicity covers the ruleset, not conntrack state. Conntrack entries are keyed by zone and live until timeout/-D/netns destruction. Because ct zone set is evaluated in raw before the conntrack lookup, an atomic swap that changes an interface's zone reclassifies in-flight flows, orphaning the old entry and creating a duplicate in the new zone. Two outcomes:

  • ZONE_SPLIT — same 5-tuple live in two zones (leak/split-brain).
  • STALE_ACCEPT — a prior-generation ESTABLISHED entry lets a now-unauthorized flow bypass ct state new policy.

The interleaving is deterministic (tracked before swap, packet after swap); load only makes it common.

The fix

  1. Stable owner-derived zones — never recompute a live interface's zone on unrelated swaps.
  2. Provision-before-up — commit the zone rule in the same atomic transaction that authorizes the interface; ip link set ... up only after commit.
  3. Selective retirement — conntrack -D -z ZONE -s ADDR/-l LABEL, never conntrack -F and never whole-zone drain when an authorized owner shares it.
  4. Idempotent trap-based cleanup safe after partial failure.

Verification (actually run)

bash zone_handoff_race.sh selftest → SELFTEST PASS:

  • Buggy scenario emits ZONE_SPLIT (tuple in zones 100 and 0) + STALE_ACCEPT.
  • It simultaneously classifies the zone-stable, still-authorized flow as LEGIT_INFLIGHT, proving the detector distinguishes the two.
  • Fixed scenario: no split/stale, LEGIT_INFLIGHT preserved, retired flow correctly becomes POLICY_DROP.
