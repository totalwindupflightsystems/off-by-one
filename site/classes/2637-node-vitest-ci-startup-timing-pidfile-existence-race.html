Fix: daemon pidfile-existence race in the Vitest CI startup test

Problem class: node-vitest-ci-startup-timing-pidfile-existence-race

Symptom

Flaky CI failure at:

await waitForHealth(baseUrl);
expect(fs.existsSync(pidFile)).toBe(true); // flaky

The test samples pidfile existence in the same tick /health first answers.

Root cause

The daemon reaches two observable states non-atomically: 1. /health starts answering via server.listen, and 2. the pidfile is written asynchronously later.

waitForHealth only waits for (1). The single-shot fs.existsSync is a point-in-time snapshot; under CI scheduling the pidfile write lands a few ms after health is ready, so the assertion fails even though the daemon is healthy. This is the same startup-timing family as INT-CI-021/023/025/026. The defect is in the test — it conflates "health ready" with "startup side effects durable".

The fix

Poll for the pidfile with a bounded timeout before asserting.

import fs from 'node:fs';

export async function waitForFile(
  file: string,
  { timeoutMs = 10_000, intervalMs = 50 }: { timeoutMs?: number; intervalMs?: number } = {},
): Promise<void> {
  const deadline = Date.now() + timeoutMs;
  while (Date.now() < deadline) {
    if (fs.existsSync(file)) return;
    await new Promise((resolve) => setTimeout(resolve, intervalMs));
  }
  if (fs.existsSync(file)) return; // final check
  throw new Error(`Timed out after ${timeoutMs}ms waiting for file: ${file}`);
}

// before (racy)
await waitForHealth(baseUrl);
expect(fs.existsSync(pidFile)).toBe(true);

// after (deterministic)
await waitForHealth(baseUrl);
await waitForFile(pidFile, { timeoutMs: 10_000, intervalMs: 50 });
expect(fs.existsSync(pidFile)).toBe(true);

Notes: don't just raise the health timeout (health is already ready); don't use a bare sleep(500) (reintroduces flakiness). A stronger daemon-side fix would write the pidfile before advertising readiness, but the polling helper is the correct minimal test-side fix.

Verification

Self-contained reproducer (/tmp/pidrace/race.mjs) simulated the daemon and ran 300 rounds with a 5ms pidfile write delay:

single-shot existsSync failures: 299/300  (missed-by ms samples: 0.017, 0.01, 0.014, 0.01, 0.01)
polling existsSync failures:     0/300

Negative path verified — helper still fails clearly on a genuinely missing file:

threw after 302 ms: Timed out after 300ms waiting for file: /tmp/definitely-missing.pid

Suggested CI confirmation: run the test file 20× in a loop and 10× under nproc-saturating yes load, expecting all green.
