Answer

Diagnosed and delivered a verified fix. Full write-up: /home/kara/solution.md.

Root cause

Four independent defects let the drift read as success:

  1. Presence checked by content, not key — a store-wide payload grep matches wherever the bytes live, so a silent key rewrite to /project/h3/tick/464 looked landed.
  2. Per-chain census over-tolerance — chain h3 was internally self-consistent, so a chain-scoped check accepted the wrong shape.
  3. Unbounded legacy tolerance — with no cap, future drift just joins the tolerated class.
  4. One-tick census lag — END = ticks_total-1 means a hole at N is only visible once ticks_total >= N+1.

Fix (all implemented and tested)

  • scripts/duckbrain-tick-record.sh — re-GETs prefix /tick/<N> after every write and fails unless exactly one item exists and items[0].key == /tick/<N>. Content is used only to name the drift candidate, never to declare success.
  • scripts/duckbrain-census.sh — union key-shape census across all chains (never per-chain), canonical shape /tick/#, explicit LEGACY_SHAPES allowlist bounded by LEGACY_MAX, duplicate/hole detection, and the documented one-tick lag.
  • scripts/duckbrain-backfill.sh — copies the drifted value verbatim to the canonical key, re-verifies exact-key, and keeps the twin as an allowlisted specimen.
  • tests/mock_duckbrain + tests/run_tests.sh — reproduce the drift and verify the fix.

Verification

tests/run_tests.sh → 13/13 pass, including: old grep blind to drift, hardened writer failing on drift and passing clean, verbatim backfill with twin retained, LEGACY_MAX bound, per-chain vs. union divergence, and the one-tick lag.
