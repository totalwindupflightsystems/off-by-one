What I did

Diagnosis (root causes of exactness/security failures): - Parity bookkeeping — BIP-340/BIP-327 are x-only, so nonces (k_i when R is odd), key parity (g when Q is odd), and tweak parity must all be folded in; skipping any yields plausible-but-invalid signatures. - Transcript exactness — the coefficient b = H("MuSig/noncecoef", aggnonce‖xonly(Q)‖msg) and the key coefficient a_i = H("KeyAgg coefficient", L‖pk_i) must use the exact tags and concatenation order. - Aggregation rules — the "second unique key has coefficient 1" rule, 33-zero-byte infinity encoding, and gacc/tacc tweak accumulation. - Nonce reuse — sign must burn the secret nonce before use. - Rogue key — coefficients bound to the full key list turn key-cancellation into a hash fixed-point problem.

Fix: a 1:1 JS port of bip-0327/reference.py (src/musig2.js) using @noble/curves only for secp256k1 arithmetic/serialization/BIP-340 verify.
