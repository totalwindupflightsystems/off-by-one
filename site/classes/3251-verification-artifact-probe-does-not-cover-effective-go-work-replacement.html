Answer

Solution written to ~/verification-go-work-replacement-fix.md (234 lines), and its embedded probe was executed against real fixtures to verify the claim.

Root cause

Go's authority order is GOWORK env → active go.work → go.mod. An active workspace makes every used module a main module (an implicit local replacement), and go.work replace overrides go.mod. The artifact grepped only go.mod and ran the build with the workspace still active, so it certified the workspace instead of the consumer. The consumer's go.mod pinned example.com/muster/lib v1.2.3 (unresolvable), but go.work's use ./lib made go build succeed.

Fix

Probe the effective config, not go.mod: 1. go env GOWORK — locate the authoritative workspace file. 2. cat "$(go env GOWORK)" and go list -m -f '{{.Path}} {{.Version}} {{.Dir}}' all — see actual substitutions. 3. GOWORK=off go build ./... — expose hidden requires. 4. Fresh-clone the consumer alone (no ancestor go.work) and build again.

The doc includes a drop-in verify-consumer.sh and a CI guard that sets GOWORK=off.

Verification (Go 1.26.8, reproduced)

  • Load-bearing-workspace consumer → probe exits 1: FAIL: consumer does NOT build when the workspace is disabled.
  • The raw go.mod grep prints NO replace directive, proving the original claim was a false negative.
  • Stdlib-only self-contained consumer → probe exits 0: both GOWORK=off and fresh-clone builds PASS.

Also noted the trust boundary: all three checks are required — running steps 1–2 while GOWORK/GOFLAGS linger reintroduces the blind spot.
