Root cause

The tier-2 iteration ceiling is enforced at two layers, and the binding value is:

effective_cap = MIN(stage.max_iterations, evaluator.max_iterations)

So raising only one knob (the usual "obvious" stage edit) leaves MIN(...) unchanged and the next gitreins task complete re-caps with the same INCOMPLETE — Cap exceeded message. The neighboring input-token knob must also be re-sized from measured burn:

tpi = Σ input_tokens / Σ iterations   (from .gitreins/usage.jsonl)
new_token_budget = ceil(tpi × new_cap × 1.15)

Fix

Raise max_iterations one rung (400 -> 600) in both blocks, scale the token neighbor, commit as chore, re-run gitreins task complete. The wrapper does all of it and hard-fails if MIN(stage,evaluator) did not strictly increase; the config fixer is a comment/format-preserving regex editor (works with max_iterations/iterations/iteration_cap and auto-detects the token key).

Verification

I reproduced the exact proven transition against a stub judge on a synthetic repo:

INCOMPLETE Cap exceeded: Iteration cap (400) reached  verdict=788c0b69
        ↓  effective cap 400 -> 600, token neighbor 120000 -> 206000, chore commit
verdict=3bd6a682 result=PASS evidence=complete tier1=PASS tier2=PASS

Also verified edge cases: per-iteration usage.jsonl records (tpi=300), missing usage.jsonl (cap still raised, token knob untouched), off-ladder caps (falls back to +200), and comments preserved in the YAML.

The markdown includes both the automated fast path and an equivalent no-script manual path, plus acceptance criteria and a rollback/troubleshooting section.

Diagnosis summary

The tier‑2 INCOMPLETE / Cap exceeded: Iteration cap (N) reached is a judge-loop ceiling, not a task failure. It comes from .gitreins/config.yaml:evaluator.max_iterations, with precedence:

GITREINS_MAX_ITERATIONS (env) > .gitreins/config.yaml:evaluator.max_iterations > default 100

Two traps: -1 means defer to default (100), not unlimited; and env overrides silently win over YAML edits.

Fix (gitreins 0.15.0)

cd /path/to/repo
export GITREINS_MAX_ITERATIONS=300   # env override, wins over YAML
gitreins task start <task-id>
gitreins judge --async <task-id>
gitreins judge --status <job-id>

Resume via task start + judge — not task complete, since complete on an already-complete task never resets state. Use judge --async + judge --status because foreground/background complete re-runs are SIGTERM-prone at ~96 minutes.

Verification: gitreins config get evaluator.max_iterations reports 300; a re-run converges to VERIFIED/PASS (or, if it still fails, reports the new 300 cap, proving the override applied).

Note: on this host the gitreins symlink is broken (~/.local/share/pipx/venvs/gitreins missing) and no .gitreins/ tree exists, so the commands could not be executed here — the document is based on the verified 0.15.0 behavior given in the task context.

Fixing GitReins Tier-2 “iteration cap exceeded” on the CF-019 recovery criterion

Problem class: gitreins-tier2-iteration-cap-exceeded Repository: coding-hermes/code-factory Subject commit: 3daa92c1fbf6a19eb83078733876c27ac5f49967 (unchanged, published) Observed artifact: docs/audits/code-factory-CF-019-131459-judges.json → all_passed=false Verdict: The product work is correct. The “cap” numbers are evaluator budget exhaustion, not test failures. The fix is to (1) stop pinning the judge to the one-package heuristic and (2) split the single overloaded recovery criterion into bounded per-predicate judges. Do not re-run the same monolithic judge.

1. Root cause analysis

1.1 What the numbers actually mean

GITREINS’ Tier-2 judge is an agentic evaluator with a fractional iteration budget, not a 0–15 or 0–30 score:

  • each LLM reasoning turn costs 1.0;
  • each tool call costs tool_call_weight, default 0.1;
  • the cap is checked before a call (iteration_credit >= max_iterations), so the final usage may drift slightly above the cap.

That is exactly why the logs read 15.8/15, 30.2/30, 30.5/30, 30.6/30, 30.8/30. The value after the slash is the cap; the value before it is credit consumed. Hitting it produces Verdict(verdict="INCOMPLETE", summary="Cap exceeded: … Increase max_iterations or split criteria.") — an evaluator residual, not a product failure. In the recorded CF-019 run, Tier 1 was PASS and only the Tier-2 runtime-recovery predicate remained INCOMPLETE.

Reproduce the accounting deterministically (no LLM/network):

cd /path/to/gitreins
PYTHONPATH=. python3 - <<'PY'
from engine.eval_cap import EvalCap
def spend(cap, llm, tools):
    for _ in range(llm):
        if (e := cap.record_llm_call()): return e
    for _ in range(tools):
        if (e := cap.record_tool_call()): return e
for cap in (EvalCap(max_iterations=15), EvalCap(max_iterations=30), EvalCap(max_iterations=100)):
    err = spend(cap, 16, 150)          # 16.0 + 15.0 = 31.0 credit
    print(cap.max_iterations, "->", cap.summary(), "|", err)
PY

1.2 The cap was pinned too low and the criterion was too broad

.gitreins/config.yaml in this repo pins the evaluator cap that gitreins init’s size heuristic chose for a one-package project:

evaluator:
  max_iterations: 15      # _detect_project_size: packages <= 1 -> 15

GitReins’ own product default is now 100, and its test suite records the reason: “Default max_iterations is 100 (was 15 — too low for complex criteria)”. The repo outgrew the heuristic: tests/recovery-contract.py alone is 352 lines of real-Git fixtures with an independent 13-test suite, three semantic mutants, and failure-propagation checks.

Splitting the monolithic lifecycle judge into per-criterion ephemeral judges fixed AC 1, 2 and 4 (small evidence surfaces). Criterion 3 — “Define recovery after node/host loss and prove the chosen recovery with a falsifiable test” — was still one judge that had to run the whole recovery suite, read two large Python files plus two specs, and inspect three mutants. It needed ≈30.6 credit, so GITREINS_MAX_ITERATIONS=30 still capped it. Doubling 15→30 moved the wall; it did not reduce the work.

1.3 Why identical retries are the wrong move

The deterministic cap error is a function of (criterion breadth, evidence surface, cap). Re-running the same criterion with the same scope and cap reproduces the same exhaustion (the CF-002 record shows unchanged retries capping at 30.5 and 30.8). A single criterion must be narrowed, or the cap raised — a blind retry is neither.

2. Exact fix

2.1 Raise the repo cap to the product default (one-line patch)

.gitreins/config.yaml:

 evaluator:
-  max_iterations: 15
+  # code-factory carries a real-Git loss/reclone contract + semantic mutants.
+  # 15 is gitreins init's one-package heuristic; the product default is 100.
+  max_iterations: 100
   static_analysis_diagnostics: false

GITREINS_MAX_ITERATIONS remains a valid per-process override, but it must no longer be required to make a judge finish. Do not use -1 (unlimited) for unattended runs; keep a finite cap so a runaway judge still terminates.

2.2 Split CF-019 criterion 3 into bounded predicates

Run each predicate as its own ephemeral judge (--scope working-tree, --json). Each command is independently re-runnable and each evidence surface is small. Freeze the checkout first and record HEAD/tree/tracked fingerprint before and after the batch (the ephemeral schema omits the commit).

export GITREINS_LLM_BASE_URL=https://openrouter.ai/api/v1
export GITREINS_LLM_API_KEY="$OPENROUTER_API_KEY"       # or your provider key
export GITREINS_LLM_MODEL=deepseek/deepseek-v4-flash
export GITREINS_MAX_ITERATIONS=100
REPO="$(git rev-parse --show-toplevel)"; cd "$REPO"

# AC3a — positive recovery path (pinned commit, pre-loss artifact pin, repeat/fresh)
gitreins judge --ephemeral --scope working-tree \
  --title CF019-AC3a-positive-recovery --json \
  --criterion 'CF-019 AC3a (positive recovery only): run `python3 -B tests/recovery-contract.py RecoveryContract.test_recover_after_loss_and_repeat` and require exit 0/OK. Inspect tests/recovery-fixture.py::recover to confirm the fresh checkout is the pinned full commit (not origin/main), artifact bytes are hashed against the pre-loss control pin, and JSON reports pending=unknown, unpublished_work=unrecoverable. Hermetic local Git fixture only.'

# AC3b — artifact integrity + expectation pin
gitreins judge --ephemeral --scope working-tree \
  --title CF019-AC3b-artifact-and-pin --json \
  --criterion 'CF-019 AC3b: run `python3 -B tests/recovery-contract.py RecoveryContract.test_changed_artifact RecoveryContract.test_missing_artifact RecoveryContract.test_metadata_and_artifact_cannot_redefine_expectation RecoveryContract.test_artifact_rechecked_on_repeat` and require exit 0. Confirm changed same-length bytes, missing bytes, and record+artifact tampering are rejected against a control pin kept outside the lost worker.'

# AC3c — metadata / trust-pin / workspace refusals
gitreins judge --ephemeral --scope working-tree \
  --title CF019-AC3c-metadata-trust-workspace --json \
  --criterion 'CF-019 AC3c: run `python3 -B tests/recovery-contract.py RecoveryContract.test_corrupt_metadata RecoveryContract.test_missing_metadata RecoveryContract.test_pinned_but_invalid_metadata RecoveryContract.test_invalid_trust_pin RecoveryContract.test_dirty_or_wrong_workspace_not_overwritten` and require exit 0. Confirm schema/duplicate-key/type violations, bad trust pins, and occupied or dirty destinations are refused without overwrite.'

# AC3d — missing commit
gitreins judge --ephemeral --scope working-tree \
  --title CF019-AC3d-missing-commit --json \
  --criterion 'CF-019 AC3d: run `python3 -B tests/recovery-contract.py RecoveryContract.test_missing_commit` and require exit 0. A syntactically valid full commit absent from real Git must yield exit 1 with exactly `FAIL recovery:commit_missing`.'

# AC3e — falsifiability (mutants + caller propagation)
gitreins judge --ephemeral --scope working-tree \
  --title CF019-AC3e-falsifiability --json \
  --criterion 'CF-019 AC3e: run `python3 -B tests/recovery-contract.py MutationControls` and require exit 0. Confirm the three semantic mutants (trust-pin bypass, artifact-digest bypass, origin/main substitution) each cause an assertion failure after compilation, and that a failing recovery child propagates through tests/selftest.sh as SELFTEST: FAIL.'

# AC3f — documentation authority and stated limits
gitreins judge --ephemeral --scope working-tree \
  --title CF019-AC3f-doc-authority --json \
  --criterion 'CF-019 AC3f: inspect docs/STORAGE-RECOVERY.md and specs/STORAGE.md#recovery-protocol against tests/recovery-fixture.py. Require that every executable claim (pinned full commit, control-side artifact rehash, pending=unknown, unpublished=unrecoverable, local/one-filesystem limits, no production certification) matches the fixture and that no live-storage claim is made.'

The already-passing AC 1, 2 and 4 judges stay as they are; only AC3 is decomposed. Preferred granularity: one observable predicate per judge, never two independent rejection families in one criterion.

2.3 Aggregate honestly — preserve partial evidence

Record every judge’s raw JSON plus its exit code, and set all_passed to the conjunction, never to “any criterion verified”. This mirrors the existing code-factory-CF-002-split-judges-0937.json (all_passed:false, outcome:"partial-not-accepted-as-complete"). A capped judge must appear as a residual, not be silently promoted.

mkdir -p docs/audits
OUT=docs/audits/code-factory-CF-019-131459-judges.json
python3 - "$OUT" <<'PY'
import json, subprocess, sys, pathlib
out = pathlib.Path(sys.argv[1])
repo = subprocess.run(["git","rev-parse","--show-toplevel"],capture_output=True,text=True,check=True).stdout.strip()
head = subprocess.run(["git","-C",repo,"rev-parse","HEAD"],capture_output=True,text=True,check=True).stdout.strip()
tree = subprocess.run(["git","-C",repo,"rev-parse","HEAD^{tree}"],capture_output=True,text=True,check=True).stdout.strip()
# ... run each judge command, collect {"name","exit_code","passed","evidence"} ...
# results = [...]
record = {
  "run_id": "CF019-SPLIT-131459",
  "evaluated_commit_external": head,
  "frozen": {"commit": head, "tree": tree},
  "all_passed": all(r["passed"] for r in results),      # conjunction, not "any"
  "passing_criteria_count": sum(r["passed"] for r in results),
  "capped_lifecycle_runs": [r for r in results if not r["passed"] and "Cap exceeded" in json.dumps(r)],
  "results": results,
  "disposition": ("complete" if all(r["passed"] for r in results)
                  else "partial-not-accepted-as-complete"),
}
out.write_text(json.dumps(record, indent=2))
print("all_passed =", record["all_passed"], "| outcome =", record["disposition"])
PY

2.4 Guardrails

  • Keep --scope working-tree and a frozen SHA; ephemeral evidence omits the commit, so capture HEAD/tree/fingerprint around the batch.
  • Never stage a criterion with two unrelated predicate families.
  • If a judge caps, narrow it or raise the cap; do not re-issue the identical command.
  • Do not change product source/tests to make a judge fit. The recovery contract was already green and guarded.

Appendix — quick reference

Symptom Meaning Action
Cap exceeded: Iteration cap (30) reached (30.6 used) Evaluator budget exhausted; product may be fine Split the criterion or raise evaluator.max_iterations
15.8/15, 30.2/30 Expected pre-call lenient check drift Not a bug
One criterion never finishes Criterion too broad One observable predicate per judge
Same command caps again Deterministic budgeting Never retry identically; narrow scope
Aggregated all_passed=false with passing sub-judges A capped residual exists Keep it; disposition partial-not-accepted-as-complete

Bottom line: don’t chase the /15 or /30 as scores and don’t retry the monolith. Set evaluator.max_iterations: 100 for this repo, decompose CF-019 AC3 into the six bounded predicates above, and aggregate with all_passed as a conjunction — preserving the partial evidence exactly as the CF-002 record already models.
