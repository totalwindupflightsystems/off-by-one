Fixing go-vuln-hpack-race: GO-2026-6617 (HTTP/2 HPACK Encoder Race) and Related Go 1.26.9 Stdlib Vulns

Summary

govulncheck flags a Go service that builds with go1.26.6 and golang.org/x/net v0.59.0. The headline finding is GO-2026-6617 — an HTTP/2 server crash caused by an HPACK encoder race in net/http. It is one of several vulnerabilities fixed in the go1.26.9 standard library and in golang.org/x/net v0.60.0.

The fix is a two-part dependency bump:

  1. Raise the module's Go version (the go directive) to 1.26.9 so the fixed stdlib (net/http, crypto/tls, net/http/internal/http2) is linked.
  2. Upgrade golang.org/x/net to v0.60.0 (the out-of-tree http2 package carries the same HPACK/flow-control bugs).

After the bump: go build, go vet, go test, and govulncheck all pass, and govulncheck reports No vulnerabilities found. (exit code 0).

Root-Cause Analysis

What GO-2026-6617 is

HTTP/2 servers could end up crashing due to inadvertently modifying their HPACK encoder concurrently. The server modifies the HPACK encoder from two goroutines without synchronization: one uses the encoder to encode a HEADERS frame while sending a response, and another resizes the encoder's table when handling a SETTINGS_HEADER_TABLE_SIZE frame. A client can repeatedly send a request while changing the header table size to crash the server. — GO-2026-6617 (CVE-2026-97032)

Why the version bump is the whole fix

A Go binary contains the standard library of the toolchain that built it, not a library resolved per-package like a normal module. govulncheck reads the Go version recorded for the build — derived from the module's go directive (and/or toolchain line) — and reports the effective versions as net/http@go1.26.8, crypto/tls@go1.26.8, etc.

The vulnerable code is fixed only in go1.26.9:

net/http    introduced: 0          fixed: 1.26.9   (branch 1.26)
net/http    introduced: 1.27.0-0   fixed: 1.27.2

golang.org/x/net is a separate module that vendors/duplicates the HTTP/2 server (golang.org/x/net/http2). It has the same HPACK, flow-control, window, and Trailer bugs and is fixed in v0.60.0:

golang.org/x/net/http2   introduced: 0   fixed: 0.60.0

So there is no source change to make inside the application. You must:

  • move the Go directive forward so the compiler/stdlib is >= 1.26.9, and
  • move golang.org/x/net forward so the in-app HTTP/2 implementation is >= 0.60.0.

Only bumping one of the two leaves findings (the stdlib copy and the x/net copy are both reported for GO-2026-6617, -6612, -6611, and -6603).

The Exact Fix

Run from the repository root:

# 1. Bump the out-of-tree HTTP/2 implementation (and anything x/net pulls in).
go get golang.org/x/net@v0.60.0

# 2. Raise the Go language/toolchain minimum so the fixed stdlib is used.
#    With GOTOOLCHAIN=auto (the default), this fetches and builds with go1.26.9.
go mod edit -go=1.26.9

# 3. Reconcile go.mod/go.sum.
go mod tidy

Resulting go.mod:

module example.com/hpackdemo

go 1.26.9

require golang.org/x/net v0.60.0

require golang.org/x/text v0.42.0 // indirect

Notes / variations

  • If go.mod has a toolchain line (e.g. toolchain go1.26.6), move it too, or delete it and let the go directive drive selection: bash go mod edit -toolchain=go1.26.9 # or: go mod edit -toolchain=none
  • Pin to the exact floor (v0.60.0), don't use @latest, so the result is reproducible. Any >= v0.60.0 is fine.
  • GOTOOLCHAIN: if the runner is offline or sets GOTOOLCHAIN=local, it cannot download go1.26.9. In that case install go1.26.9+ on the image and ensure go.mod's directive matches. GOTOOLCHAIN=auto is the default and was used successfully here.
  • Clean the module cache if a stale x/net is pinned by replace/exclude; go mod graph | grep golang.org/x/net verifies only v0.60.0 remains.
  • Commit both go.mod and go.sum.

Add a CI gate so this stays fixed

govulncheck exits non-zero when a called vulnerability is found, so it can be used directly as a gate:

# .github/workflows/vulncheck.yml
name: govulncheck
on:
  schedule: [{ cron: "0 6 * * 1" }]   # weekly sweep for new stdlib vulns
  push: { branches: [main] }
  pull_request:
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod      # honors the go 1.26.9 directive
      - run: go install golang.org/x/vuln/cmd/govulncheck@latest
      - run: govulncheck ./...

Because a future advisory may fix the stdlib in a newer 1.26.x patch, keep the "bump go directive + affected modules" step in the periodic sweep. The decision rule is simple:

  1. New stdlib finding with Fixed in: <goX.Y.Z> → go mod edit -go=<goX.Y.Z>.
  2. New module finding with Fixed in: <module>@vN → go get <module>@vN.
  3. go mod tidy && go build ./... && go test ./... && govulncheck ./....
