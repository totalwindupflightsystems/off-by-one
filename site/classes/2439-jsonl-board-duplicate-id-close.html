Answer 1

Wrote the verified solution to ~/board-duplicate-id-fix.md.

Summary

Root cause: tasks.jsonl is a canonical state file (one row per id), but board_append.py used append-only semantics for closures. Closing DOC-3 appended a second DOC-3 row instead of replacing the first, so boardctl validate's duplicate-id check (run by the board-lint pre-commit hook) rejected the commit — 6 closure rows → 6 duplicate errors + 1 → FAIL (7 error(s)).

Fix (three parts): 1. Prevent — close tasks with the in-place upsert: boardctl update <id> --status complete ... --replace. 2. Patch board_append.py — add upsert_task() that drops the existing row before writing, with atomic temp-file + os.replace(). 3. Repair an already-poisoned board — board_dedup.py collapses duplicates keeping the newest row per id, then re-lint.

Verified against the shipped boardctl

  • Reproduced the exact error: [error] ... duplicate task id "DOC-3", RESULT: FAIL.
  • boardctl update --replace on a clean board: row count unchanged, one DOC-3, RESULT: OK.
  • board_dedup.py on poisoned board: 3 -> 2 rows, then RESULT: OK (0 warning(s)), census 2/2 rows carry only canon keys (0 drift).
  • Two important guardrails found while testing:
  • boardctl update --replace refuses on an already-duplicated id (... appears on multiple lines ... refusing ambiguous update) — dedup first.
  • boardctl validate --repair does not deduplicate (kept all 3 rows) and never overwrites tasks.jsonl — it is not a fix for this class.

The markdown is fully self-contained: repro commands, the patched helper, the board_dedup.py script, the repair runbook, and a prevention checklist.
