Fix: consensus-shim-response-timeout-vs-planning-wall

Repo: <organization>/consensus (pinned 52bc6608), consumed by &lt;project&gt;/&lt;project&gt;-core Verdict: The planning loop legitimately outlives the shim's hard-coded 90s response budget. Make the budget configurable and set it above the deployment's planning wall. Shrinking the planning wall below 90s is not a fix — it abandons the session instead of delivering the answer.

1. Root cause

POST /session/{id}/message runs the turn synchronously: the shim wraps the request context with its own deadline and calls svc.SendMessage, which drives the harness planning loop to completion before returning the assistant turn.

  • Budget (upstream, identical at 52bc6608 and main): internal/shim/opencode/server.go:150 go const defaultMessageResponseTimeout = 90 * time.Second assigned in NewServer and used by all three synchronous turn paths (sessionMessage, sessionCommand, sessionInit).
  • Planning wall (HarnessConfig.PlanningTimeoutSec, internal/config/config.go:73, default 180), observed as timeout=3m0s, with max_turns=10.
  • Observed LLM latency: elapsed_ms=7000..16000, one 62996. Ten planning turns plus the final response cannot finish inside 90s.

Deterministic sequence:

planning: starting interactive session session_id=<uuid> max_turns=10 timeout=3m0s
llm:      response received ... elapsed_ms=7000..16000
planning: commands staged (turn=1..9)
opencode-shim: error method=POST path=/session/<uuid>/message status=504 code=RESPONSE_TIMEOUT
(later) planning: responding to user turn=10

The answer is produced; the shim already returned 504 RESPONSE_TIMEOUT at 90s. The sidecar constructs the shim with no timeout argument and the only override (CONSENSUS_TEST_RESPONSE_TIMEOUT) is read by a test helper, so the deployment had no supported surface to raise the budget:

// consensus-sidecar/cmd/sidecar/main.go:269
opencode.NewServer(database, cfg.Adapters.OpenCode.AdminKey, shimEvents, shimService)

Why "shrink the planning wall" does not work

On context expiry the harness calls handlePlanningTimeout (internal/harness/planning.go:984), which marks the session failed, rolls the transaction back, and returns an error. It never reaches responding to user. Lowering planning_timeout_seconds below the shim budget trades a 504 for a failed/abandoned session with no answer — the exact failure the class prohibits.

2. The fix

2a. Upstream: expose the budget (env + functional option)

internal/shim/opencode/server.go — keep the 90s default, add a production env override and a programmatic option. Existing callers keep compiling because NewServer gains a variadic option slice.

const defaultMessageResponseTimeout = 90 * time.Second

// MessageResponseTimeoutEnv overrides the shim's synchronous message-response
// budget in production. Accepts Go duration strings ("5m", "300s").
const MessageResponseTimeoutEnv = "CONSENSUS_MESSAGE_RESPONSE_TIMEOUT"

// ServerOption configures the opencode shim at construction.
type ServerOption func(*Server)

// WithMessageResponseTimeout overrides the maximum time a synchronous
// POST /session/{id}/message waits for the agent response. Values <= 0 are
// ignored so an accidental zero cannot disable the bound.
func WithMessageResponseTimeout(d time.Duration) ServerOption {
    return func(s *Server) {
        if d > 0 {
            s.messageResponseTimeout = d
        }
    }
}

func messageResponseTimeoutFromEnv() time.Duration {
    v := strings.TrimSpace(os.Getenv(MessageResponseTimeoutEnv))
    if v == "" {
        return 0
    }
    d, err := time.ParseDuration(v)
    if err != nil || d <= 0 {
        return 0
    }
    return d
}

func NewServer(dbase db.DB, adminKey string, eventBus EventBus, svc Service, opts ...ServerOption) *Server {
    s := &Server{
        // ...
        messageResponseTimeout: defaultMessageResponseTimeout,
        // ...
    }
    if d := messageResponseTimeoutFromEnv(); d > 0 {
        s.messageResponseTimeout = d
    }
    for _, opt := range opts {
        opt(s)
    }
    slog.Info("opencode-shim: message response budget", "timeout", s.messageResponseTimeout)
    // ...
}

Precedence: default (90s) < CONSENSUS_MESSAGE_RESPONSE_TIMEOUT < WithMessageResponseTimeout. Full patch in the appendix and at /workspace/shim-message-response-timeout.patch.

2b. Deploy: land the patch and set the budget

The sidecar image is built from the pinned upstream SHA, so bump the pin to a revision carrying the patch or apply the patch during the image build; then set the env var.

# after the upstream checkout at UPSTREAM_SHA
COPY patches/shim-message-response-timeout.patch /tmp/
RUN cd /src/consensus && git apply /tmp/shim-message-response-timeout.patch

# docker-compose.yml, consensus service
services:
  consensus:
    environment:
      # planning wall is 180s; leave room for the final response generation.
      - CONSENSUS_MESSAGE_RESPONSE_TIMEOUT=5m

docker compose up -d --build consensus

Do not change the test. Do not lower planning_timeout_seconds below the budget.

4. Why not the alternatives

  • Rebuild the sidecar image — deployed image already carried the pinned revision; only StartedAt/image id change. False positive.
  • Treat it as an LLM auth error (401 / gpt-4o) — stale blocked_reason; current logs show no 401 and provider is api.deepseek.com/deepseek-v4-pro.
  • Lower the planning wall below 90s — handlePlanningTimeout fails the session without delivering a turn, so the responding to user clause fails.
  • Edit the test — out of bounds; does nothing to the production budget.
